# 云同步 v3（2026-09-13）

本目录是当前后端同步协议的权威实现与说明。服务统一使用 `sync_v3.app:app`，`main:app` 是同一服务的兼容别名。旧 Studio、会员、Key 配发和 v1/v2 服务代码已删除；现有旧表不自动清空或迁移。

## 边界

FastAPI、SQLAlchemy、账号认证继续复用。云端保存带版本的业务文档和附件，不执行客户端 AI 对话，不接管生成中的任务。客户端仍以本地 raw message 构建上下文；UI 投影不能替代 raw 数据上传。

API 已覆盖文档、附件、冲突、首次同步、增量同步、通知及一致快照。Flutter 已接入账号与 v3 同步，使用主业务数据库的完整 raw 行，旧独立同步库不参与。公网服务已部署，消息整体同步与媒体单份存储已部署；近期读取服务 read-v1 与独立媒体队列客户端已部署安装，手机显示同步完成；Mac 已处理旧队列并核对全部业务摘要一致，云端已有2,458文件全部落盘校验，159无文件历史引用保留占位；实机完成状态见 ADR0028／0029 与需求日志，不以测试通过代称多端同步完成。

## 文档契约

业务实体使用 `{kind, entity_id, payload_version: 1, payload, blob_ids, media_ids}`。`kind` 为有限白名单，定义在 `contracts.py`：会话、原始消息、消息块、投影映射、模型配置、结构化记忆、归档记录、记忆墓碑、日记、话题摘要、设置、插件预设、Markdown 记忆与媒体身份信息。

`payload` 是客户端业务数据的完整 JSON 文档，不是服务器的 SQL 行，也不是拼接好的模型请求。服务器保留全部字段，包括原始消息、工具调用和原始创建时间；`payload_version` 不匹配则拒绝，不能静默剔除未知字段。实体内部语义及跨实体引用由客户端契约适配器负责校验；云端校验封装、大小、版本、账号所有权和附件归属。

新客户端将原消息 `row`、`message_blocks` 和 `message_projection_mappings` 组成 `message_snapshot_version: 1` 的单个 `messages` 文档。子记录修改只标记所属消息，接收时验证归属并在同一事务内恢复整组记录。旧独立子文档只用于兼容历史队列；父消息升级后，服务端拒绝旧客户端以无快照消息或独立子记录覆盖它，返回 `client_upgrade_required`。`status.message_snapshot_version=1` 声明此能力。

每个对象独立递增 `version`；每个账号拥有 `epoch` 与递增 `seq`。`epoch` 防止客户端把另一代服务器的数据误当作原来的数据。`seq` 与实际提交顺序一致，绝不使用设备时间或数据库独立自增序列推断提交顺序。

## 接口

除健康检查与登录外均须 `Authorization: Bearer ...`，前缀 `/api/v1/sync/v3`：

| 接口 | 行为 |
|---|---|
| `GET /status` | 读取协议能力、epoch 与当前 cursor |
| `GET /bootstrap?epoch=...&after=0&limit=100` | 首次读取指定水位时每个对象的最新版本；后续页固定使用首包 through |
| `GET /read?epoch=...&stage=head&after=0&through=...&limit=512` | 固定水位的近期窗口、历史补齐或当前增量；返回 documents/dependencies，按 next_cursor 翻页 |
| `POST /missing-blobs` | `{digests:[sha256,...]}`，最多 512 项，仅返回本账号缺失的文件摘要 |
| `POST /push` | 原子提交最多 100 个操作，返回逐操作持久化结果 |
| `GET /pull?epoch=...&after=0&limit=100` | 按序补齐变化；后续页携带 through，按 next_cursor 继续 |
| `GET /wait?epoch=...&after=...&timeout=25` | 最长 25 秒长轮询通知；断线后仍依靠 pull 补齐 |
| `PUT /blobs/batch` | 合批上传 ZIP，最多 64 个文件，全部验证后发布 |
| `PUT /blobs/{sha256}` | 二进制流上传，最多 128 MiB，校验成功后发布 |
| `GET /blobs/{sha256}` | 下载当前账号已提交的附件 |
| `GET /conflicts` | 查看未解决冲突，包含本地提交与云端原版本 |
| `POST /conflicts/{id}/resolve?use_incoming=false` | 选择保留云端或采用冲突提交；校验预览 cursor |
| `POST /snapshots` | `{name}` 创建当前账号的一致快照 |
| `GET /snapshots`、`GET /snapshots/{id}?after=0&limit=100` | 快照列表与分页内容，按 next_cursor 继续直到 has_more=false |
| `POST /snapshots/{id}/restore` | 将快照恢复作为新一轮变更发布，不回退同步序号 |

提交示例（字段名、状态不能沿用旧协议）：

```json
{
  "protocol_version": 3,
  "epoch": "从 status 获取",
  "device_id": "持久设备编号",
  "mutations": [{
    "op_id": "每次逻辑修改唯一，重试不变",
    "kind": "messages",
    "entity_id": "原始消息编号",
    "base_version": 0,
    "action": "put",
    "payload_version": 1,
    "payload": {"client_schema": 16, "row": {"id": "原始消息编号", "created_at": 123, "content": "示例"}, "message_snapshot_version": 1, "message_blocks": [], "message_projection_mappings": []},
    "blob_ids": []
  }]
}
```

成功为 `status: applied`，包含提交后的 `document`；冲突为 `status: conflict`，包含 `conflict_id` 与 `current`。重试返回第一次完全相同的结果。相同 op_id 改内容、未知类型、缺失附件、超前版本会拒绝并回滚整批；**冲突是已持久化的结果**，原对象不改，双方版本进入独立冲突记录，同步到所有设备。

客户端业务修改和 dirty 修订标记同事务；编码附件后，冻结修订和 outbox 内容再上传，确认时只清理同一修订，保留上传期间的新编辑。收到结果后才能确认队列；拉取数据与 next_cursor 同事务提交。待上传修改不能被拉取覆盖。旧 bootstrap 先收齐再写库；支持 indexed_read_version=1 的客户端使用下述分阶段读取。随后从 through 接着读取增量。通知只是唤醒，不推进游标。实体删除使用 `action: delete` 墓碑；恢复使用当前版本的 `put`。消息编辑、重生成均允许，无“消息不可编辑”限制。

首次合流时，两端已存在的同 ID 数据会按版本产生冲突，不会假定相同 ID 即相同内容。跨平台路径必须由客户端转换成附件标识；服务器不会读取 payload 内的 URL/本机路径。实际已提交的文件列入 blob_ids，必须先上传；消息引用的长期媒体身份列入 media_ids，先提交 media_assets 元数据即可，不要求旧原图已上传。

冲突解决和快照恢复请求为 `{op_id, device_id, epoch, expected_cursor}`。恢复前应先创建当前状态快照；恢复不会删除旧快照。快照固定已提交水位，内容由不可变变更记录重建，创建时不复制全库；分页 blob_ids 是该页引用的附件集合。独立备份文件保存加密分页清单与附件，分页内容通过摘要绑定到加密索引。v3 初版保留所有变更、操作回执和附件，不执行旧 v2 的 7 天物理清理，长期离线设备仍可补齐。将来压缩日志须另加过期游标及全量重建协议，并保全被快照引用的版本。

## 近期优先与历史补齐

`status.indexed_read_version=1` 与 `blob_probe_version=1` 声明新能力。`read.stage=head` 包含全部设置、插件预设、渠道、会话、Markdown 记忆及每个会话按原始时间最近 50 条可见消息；`history` 补其余对象，`delta` 读取 after 之后每实体最新状态。软删除/墓碑仍在完整历史与增量内。已由完整父消息覆盖的旧独立消息块和映射不重复传输；不可变日志仍保留供旧 API 与备份使用。

每页固定 `through`，最多 512 个主文档，目标约 1 MiB 未压缩 JSON；单个较大文档允许越过目标。消息对应的会话、媒体身份以及旧子文档的父消息按同水位补为 dependencies；依赖总量上限 16 MiB，超过显式拒绝。服务器新增轻量可重建读索引，新写入同事务保存，旧记录启动时每 500 条回填，重复初始化不重复插入。关联 ID、时间、快照标记位于读索引，正文继续加密。

客户端将页、依赖、首轮阶段及游标同事务保存；业务记录最多 64 项一组恢复，完整消息内部保持原子性。`head` 先应用当前页，历史按页后台补齐，不等待整个账号与所有文件。最后一页尚未应用时重启，inbox 仍保留以供恢复。旧接收队列不自动删除，脏数据和冲突继续保护。已有 initialized 接收端按独立读取阶段补跑近期窗口；完整当前 payload 与较新或同版 incoming 完全相同且无冲突/冻结操作时，可在事务内修复旧比较基线并清除对应 dirty revision。

已收到提交结果的序号单独持久化；只消费连续确认前缀，避免把刚上传的正文再下载回来。序号中间缺一项就停止跳过，继续拉取其他设备的修改；不能用最大确认序号直接推进游标。

## 压缩与批量传输

支持能力由 status 的 `json_gzip` 与 `blob_batch_version=1` 声明。JSON 请求使用 gzip，响应协商 gzip；扩展后的 JSON 仍受原 16 MiB 限制，格式损坏/压缩炸弹直接拒绝。二进制图片/音频下载不再重复 gzip。

`PUT /blobs/batch` 接收 ZIP，文件名严格等于 SHA256，最多 64 个文件，展开合计最多 16 MiB；所有文件验证完成后才发布。本账号重复提交幂等，不能使用目录、路径穿越或加密条目。客户端按 12 MiB/64 文件打包，最多并发 3 批；图片与语音用 ZIP STORE 合并请求，原文件字节不变，不浪费 CPU 重压已压缩图片。超过打包阈值的单个文件继续流式上传。

业务文档和媒体元数据每批最多 100 条，业务批次按实际 UTF-8 体积进一步限制为 8 MiB。先登记媒体身份，再提交已冻结 outbox，文件独立传输后更新可用摘要；丢响应仍使用相同业务操作编号重试。上传前用 missing-blobs 查询服务端已提交摘要，文件上传成功但确认丢失时也不重复传文件。outbox 只按批次读入发送内容，原始本地副本在确认时逐条读取，避免把大批 Base64 历史复制到内存。近期原图也按批收集上传；不先制作覆盖全库的巨大 ZIP。接收端先注册身份并预留稳定路径，再按依赖排序写业务数据；网络文件不在业务应用事务中等待。持久媒体队列每批 32 项，下载最多 3 路；失败退避 30 秒，进程中断保留最长 5 分钟领取租约，下轮继续，完成时按队列修订条件清除。已显示的 CloudImage 在文件到达后自动刷新。

## 图片分层与客户端范围

`status.media_version=1`、`media_usage_version=1`，`recent_original_days=30`。`media_assets` 保存独立稳定 ID、MIME、字节数、原始日期、宽高、缩略图 blob、原图 SHA256/可选 blob 和源设备位置。ID 通常初始化为内容摘要，但协议不要求身份 ID 等于文件摘要。位置只是可用性线索，服务器不读取设备路径。

- 所有历史消息与图片身份照常同步；所有可读取图片生成最长边 320 的 JPEG 缩略图。优先由 Flutter 引擎直接缩小解码，避免 Dart 解码整个原图；不支持的格式回退旧解码器。不同解码器产生不同缩略图时，按服务器已确定的摘要重新取得缓存，保证摘要与文件相符。
- 只有已知超过 30 天、且仅用于聊天的图片可推迟原图。聊天按 `last_chat_at_ms` 最近引用日期判断；未知日期保守传原图。非聊天用途（头像、背景、插件、预设及其他文件）设置 `original_required=true`，完整传输原件，不以缩略图替代。旧图近期再次引用或转作非聊天用途时提升为原图传输；原始创建日期仍保留。已有原图和已上传原图不因超过期限删除。
- 语音、音色样本、文件等不受图片年龄限制，文件存在时完整传输；源文件已经缺失时保留身份和原引用信息。
- `media_assets` 只引用实际上传的 blob；无原图不触发 `missing_blob`。普通消息必须引用本账号存在的媒体身份，不能跨账号引用。
- 元数据更新合并已有原图/缩略图及源位置，`original_required` 取逻辑或、`last_chat_at_ms` 取最大值；较弱用途不能覆盖原图要求，过时客户端不能把已上传原图改回空。
- 模型视觉输入和图片导出先解析实际原图；缺失时明确失败，不用缩略图代替，也不悄悄丢图。普通纯文本输入沿原有模型能力/插件过滤规则执行。

客户端保留 10 张业务表的完整行语义，其中消息块和投影映射聚合到所属消息，不再各自生成传输对象。另包含 `aicove.ui_models.v1`、全部 `aicove.plugins.*` 正式配置、提示词自定义节点、主动回复触发器、直连模型配置，以及酒馆预设/变量文件和联系人 MEMORY.md。插件预设、角色绑定和 API 配置随业务行/设置传输。设备 ID、诊断凭据、账号令牌、缓存、权限和运行中的生成任务不作为可迁移设置。

首次源设备在空账号上初始化；接收设备要求无历史消息。两边已有历史时暂停，不能自动覆盖。本次用户确认 Mac 的少量记录只是测试数据，已清理后作为接收端。账号保留数字 ID、唯一标识和用户名；退出保留本地绑定，目前禁止另一账号接管同一数据库，完整的本地账号数据集切换尚未实现。

同步使用持久 outbox/inbox、事务触发器和设置写入门。业务表提交后合并 300 毫秒唤醒上传；每 3 秒检查云端进度，无变更时只读 status，每五次空闲检查完整检查一次设置、文件和增量数据，应用恢复时补同步。SQLite 首次保护副本由 `VACUUM INTO` 生成，避免把全部 raw 行读进 Dart 内存；媒体文件不因首次同步被搬走或删除。云同步有删除传播，不能替代独立离线备份；历史快照、数据库/附件卷及加密密钥应分别保留。

## 客户端本地存储与迁移

已知媒体字段中的内嵌音频/图片写入按内容摘要去重的持久文件；同一文件多处引用只保留一份媒体字节。正文、工具调用参数、生成参数与原始回复保留。图片块可用稳定媒体 URI，音频保留播放器可读取的实际文件引用；同步时统一编码为媒体 ID。复用已有媒体索引和内嵌文件，不再次复制先前已提取的音频。

媒体身份和来源索引集中在独立 SQLite 数据库，首次导入旧 JSON 小文件；旧文件保留用于回退，后续不再按条目创建 JSON。同步比较基线只保存 SHA256 摘要，冻结 outbox 保存实际待提交内容和原操作编号。无冲突的完整消息在 cloud_versions 中只保留版本封装和快照标记，不再保留第二份正文；冲突与旧子记录归属信息仍保留。旧本机尚未消化的基线不会批量清理。

迁移先完成既有冻结 outbox，再转换比较基线与子记录 dirty 标记。源设备重新发布完整消息和非聊天引用，接收设备不能把尚未完整接收的历史重新播种。内嵌媒体整理逐条读取、先落盘校验、再按原值比较更新；复用已有一致数据库保护副本，可中断重试。完成后一次 VACUUM 回收数据库空页；保护副本、旧索引和原图不自动删除，磁盘总占用须计入这些保留物。

界面分别显示消息确认数量、本轮真正上传的唯一文件数与字节数。媒体身份可能包含缺失源引用，不能把身份数或消息子记录数称为附件文件数。

## 加密与运行

正文、设置、凭证、冲突、操作回执和快照清单使用固定 `SYNC_V3_ENCRYPTION_KEY` 加密落盘；这是服务器持有密钥的加密，不是端到端加密。附件按账号分目录保存原始二进制，应使用受保护的持久卷与 HTTPS。密钥与数据库、附件必须分别备份，丢失密钥将无法解密。

公网账号管理使用新版 `/api/v1/admin/users` 分页统计及 `/api/v1/admin/users/{id}/active` 停用/恢复接口，必须是管理员。普通账号无法操作，当前管理员不能禁用自己。这里不挂载旧账号物理删除接口；SQLite 开启外键检查，带同步数据的账号不能被旧维护代码直接删除，避免编号复用造成归属错误。

启动命令：`uvicorn sync_v3.app:app --env-file .env --host 127.0.0.1 --port 8000`（工作目录 cloud_backend）。环境变量参考 `../sync-v3.env.example`。新增表由启动初始化创建，安装标记校验 schema 与固定加密密钥；不改原业务表。没有有效加密密钥、密钥与历史数据不匹配、数据库初始化失败或 JWT 签名密钥不足时启动失败。认证继续使用已有 bcrypt 密码哈希，移除与当前 bcrypt 不兼容的 passlib 包装层，直接锁定 bcrypt 5.0.0；JWT 新签发 sub 使用字符串，兼容既有合法数字用户编号。

首次客户端接入以本机当前完整数据为初始化来源；旧云端表不是当前 Flutter 完整数据的备份，不能补出旧协议未保存的 raw、附件和插件绑定。原表保留，旧维护入口已删除，不自动迁移不完整的历史为“完整数据”。
