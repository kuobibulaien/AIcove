# 0123 跨端模型请求账本、负责设备统一与上下文／记忆同步

- 状态：accepted（2026-11-13 用户确认分两步连做）
- 日期：2026-11-13
- 关联：ADR0038（上下文摘要与长期记忆）、ADR0051（局域网直连）、ADR0058（云同步 v3）、ADR0065（诊断导出分级）、ADR0069（在途发送状态不出设备）、ADR0084（主动回复负责设备）、ADR0104（后台补处理与局域网优先增量）、ADR0116（多 Key 统一选号与失败归属）

## 背景

多端（手机与桌面端）目前仅同步 5 类数据：`conversations`、`providers`、`messages`（`status='sending'` 暂缓外发）、`settings`、`plugin_presets`。由此带来两类实质性问题：

1. **跨端模型请求不可观测**：`AppLogger`、`ApiLogger`、`TraceStore` 仅写单机文件，会话报错与故障切换弹窗仅在单机内存。一端发生请求超时、重试、多 Key 耗尽切换或后台自动调用时，另一端日志中心与诊断导出完全看不到对端的模型请求记录；单机故障切换弹窗复制本轮报错日志时也缺失 `roundStartedAt` 与对端并发请求对照。
2. **后端状态独立导致重复调用模型与数据分叉**：
   - **上下文摘要（`context_summaries`）未同步**：一端手动翻篇（同步了 `conversations.context_start_message_id`）或自动压缩后，另一端缺摘要，发消息时命中 `ContextManager._recover` 或重跑 `compactAuto`，在发送链路内阻塞重调模型（既重复扣费、丢失用户手改摘要，又拖长本轮耗时导致超时）；语音通话前上下文简报 `VoiceCallContextBrief` 仅存进程内存，重启或换端拨打也会重复请求摘要模型。
   - **长期记忆与进度（`memory_items`、`memory_progress`）未同步**：聊天记录同步后，两端各自发消息（`MemoryPlugin.buildMemory -> resumeOnce`）或压缩后（`onCompacted -> schedule`）都会把同一批历史消息重复喂给记忆 Agent，双倍调模型且两端记忆分叉。
   - **后台负责设备未统一、在途请求互不可见**：仅主动回复接入了 `ProactiveOwnership`，且未认领旧会话允许所有设备放行；长期记忆自动整理未接负责设备门禁；一端正在执行长耗时模型请求时，另一端无感知。

## 决定

全套架构分两步连续落地：第一步建立跨端模型请求账本与统一的会话负责设备／避让门禁；第二步把上下文摘要、通话前简报与长期记忆（含整理进度）接入局域网与云端同步。

### 一、跨端模型请求账本（`ModelRequestLedger`）

1. **单设备专属键、零写冲突同步**：
   - 每台设备只写自己名下的同步偏好键 `aicove.plugins.observability.model_runs.<deviceId>.v1`（命中既有 `aicove.plugins.*` 同步白名单，天然兼容旧客户端与未重部署的 `sync_v3` 服务端，无需把高频请求行塞进云端永久实体修订表）。
   - 值顶层固定为单一字段 `{"snapshot": {"version": 1, "device_id": "...", "device_name": "...", "updated_at_ms": ..., "runs": [...]}}`，保证 `cloud_setting_policy` 的字段时钟永远只有 `snapshot` 一项，绝不触碰 `sync_v3` 单设置 1000 字段上限。
   - 每设备滚动保留最近 **80 条已结束记录 ＋ 当前有效 `running` 记录**（超过 7 天的已结束记录自动淘汰），单键体积恒定在数十 KB 以内。
2. **记录时机与单调状态机**：
   - 统一收口于四个模型执行入口（`executeWithProviderKeyFailureRecording` 及其调用上下文 Zone：前台聊天、后台 Agent［含主动回复规划／生成、上下文压缩、记忆整理、通话简报／总结］、TaskAgent、WebApp AI）。
   - 仅在 **开始（`running`）**、**长请求低频续租（间隔 ≥ 60s）** 与 **结束（`succeeded` / `failed` / `cancelled`）** 时写入，流式分块期间不写。
   - 每条记录含确定性白名单字段：`runId`、`deviceId`、`deviceName`、`conversationId`（可空）、`turnId`（可空）、`purpose`、`providerId`、`model`、`attempt`、`status`、`stageSeq`（`running=1`，续租递增，终态 `1000`）、`startedAtMs`、`updatedAtMs`、`endedAtMs`、`durationMs`、`leaseUntilMs`（默认 `now + 180s`）、`errorBrief`（脱敏且截断至 240 字符，严禁包含 prompt／回复正文、API Key、Authorization 或原始长响应体）。
   - 同机前后台多 isolate 在 `cloudLocalWrite` 锁内 `reload()` 后按 `runId` 合并：同 `runId` 取更大 `stageSeq`（同 `stageSeq` 取更大 `updatedAtMs`），防止迟到的 `running` 覆盖终态。
3. **跨端可观测与报错日志补齐**：
   - 提供只读聚合端口读取本机与所有已同步对端的 `ModelRunRecord`（按时间倒序／按会话筛选，过期 `running` 即 `now >= leaseUntilMs` 在展示与门禁侧视为 `timed_out_stale`，不冒充仍在运行）。
   - 接入日志中心（`LogViewer` 统一列表／API 视图显示设备来源标签）、受控诊断包（`DiagnosticBundle` 白名单汇总）及 `ModelRequestErrorReport.buildFullLog`（补齐 `chat_actions_failover` 的 `roundStartedAt`／`errorDetail`，并附同会话近期跨端模型请求记录）。

### 二、统一的会话负责设备与在途避让策略

1. **共享会话负责权（`ConversationOwnership`）**：
   - 将原 `ProactiveOwnership` 提炼为跨业务共享能力（保留同步键 `aicove.plugins.trigger.owner_devices.v1` 不丢历史认领）。
   - 用户在本机主动发消息、手动压缩、手动启动／恢复长期记忆重建或手动立即触发主动回复时，调用 `claim(conversationId)` 将本机登记为该会话负责设备。
   - **未认领旧会话收敛**：当会话尚无显式 `owner` 时，若已知同步设备名录／已批准局域网对端中存在其他设备 ID，仅由设备 ID 字典序最小者兜底负责（单机未配对时本机天然负责），消除旧会话多端同时放行的缺口。
2. **对端运行态避让与手动发送轻提示**：
   - **后台自动任务严格避让**：主动回复（分析、预生成、派发）与长期记忆自动整理（`MemoryKeeperService.resumeOnce` 及自动压缩触发，不含用户在本机手动点击「重建／继续」）执行前均检查：① 本机须为会话负责设备；② 跨端账本中不存在**其他设备**对该会话未过期的 `running` 请求（`now < leaseUntilMs`）。不满足时跳过或延后重试。
   - **用户手动发送不硬锁死**：异步同步无法提供分布式原子锁，硬拦截会因对端断网／杀进程造成死锁。用户在本机手动发消息时，若检测到对端存在该会话未过期的 `running` 请求，以简短轻提示告知「另一台设备正在生成回复，已继续在本机发送」，正常执行本机发送并 `claim` 接管负责权。

### 三、上下文摘要、通话简报与长期记忆跨端同步（第二步）

1. **新增三类表级同步实体**：
   - `context_summaries`（主键 `id`）：同步手动翻篇摘要、自动压缩摘要，以及新增持久化的语音通话前简报（`kind = 'voice_brief'`，`listHistory` 管理界面仍只展示 `manual` / `auto`）。另一端已有有效摘要时直接命中，不再触发 `ContextManager._recover`、重复 `compactAuto` 或重复生成通话简报。
   - `memory_items`（主键 `id`）：同步角色长期记忆条目；本地派生二进制列 `embedding` 在外发编码时剥离置空，避免跨网传输大块冗余向量。`CloudLocalStore.apply` 写入或删除 `memory_items` 时同步维护本地 `memory_items_fts` 全文分词索引。
   - `memory_progress`（主键 `owner_id`）：同步长期记忆整理书签与暂停状态。并发版本合并遵循单调进度规则：`generation` 更大者优先；同 `generation` 下 `until_at` 更晚者优先（保留对应 `until_id`），防止旧进度倒退引发已整理批次重跑。
2. **依赖顺序、本地触发通知与协议兼容**：
   - **外键依赖顺序**：`PRAGMA foreign_keys = ON` 下，`context_summaries`、`memory_items`、`memory_progress` 均外键依赖 `conversations(id)`。注意 `'context_summaries'` 字典序早于 `'conversations'`，因此在 `CloudSyncEngine`、驱动表排序、`LanRepository` 捕获／应用与 `recentChanges` 父实体携带中，统一按「新增／更新先 `conversations` 后子表，删除先子表后 `conversations`」排序；若极端乱序收到孤儿行且本地尚无对应 `conversations`，跳过落库或延后，不抛外键异常中断整轮同步。
   - **变更通知**：三张 raw SQL 表同时安装 `cloud_dirty` / `lan_dirty` SQLite 触发器，并在各自 Store 写事务提交后调用 `notifyExternalSyncChange()` 立即唤醒局域网增量推送；远端 `apply` 后通知内存缓存／`MemoryKeeperService.changes` 刷新。
   - **双通道向后兼容协商**：
     - 局域网直连：在 `/lan/v1/status` 声明能力位 `context_memory_sync: 1`；仅向同样声明该能力位的对端列举和发送上述三类新 `kind`，对旧版本对端自动过滤，避免旧端 `LanRevision.fromJson` 报未知类型失败。
     - 云同步 v3：`cloud_backend/sync_v3/contracts.py` 的 `KINDS` 加入 `'context_summaries'`、`'memory_items'`、`'memory_progress'`；客户端 `CloudSyncEngine` 读取 `/status` 返回的 `kinds` 集合，仅向已支持对应 `kind` 的服务端冻结上传，连接旧服务端时保留在 `cloud_dirty` 待升级后补传，不阻塞现有消息与设置同步。客户端 `CloudLocalStore.apply` 对未知未来 `kind` 安全忽略或明确提示更新，不再落入文件分支触发类型异常。

## 代价

- 局域网与云同步均为异步最终一致，两端离线或毫秒级同时点发送仍无法提供强一致互斥锁；本方案通过「单点负责设备 ＋ 产物与进度同步 ＋ 在途租约避让」消除常态重复触发，而不引入中心化锁服务。
- 模型请求账本只同步结构化元数据与脱敏摘要，要查看某台设备单轮完整数 MB 请求载荷仍需在该设备本机导出完整版 Trace（符合 ADR0065 隐私分级）。

## 验收门

1. **第一步离线回归**：
   - 四类模型入口均在开始／结束写入本机 `model_runs.<deviceId>` 账本，终态不被迟到 `running` 覆盖，超出 80 条自动裁剪且 `setting_times` 字段数恒为 1，不含 API Key 与对话正文；
   - 跨端同步后，日志聚合与故障切换报错日志可读到对端模型请求事件与本轮开始时间；
   - 统一负责设备门禁覆盖主动回复与长期记忆自动整理，未认领会话在多设备名录下只由单一确定性设备兜底；对端存在有效 `running` 租约时后台自动任务避让，手动发送弹轻提示并正常接管。
2. **第二步离线回归 ＋ 云端契约测试**：
   - 设备 A 手动翻篇／自动压缩／生成通话前简报同步到设备 B 后，B 发消息或拨号直接复用摘要，不触发 `_recover` 或重复调压缩模型；
   - 设备 A 整理长期记忆后同步到设备 B，B 的 `memory_items_fts` 可检索到新记忆，且 `MemoryKeeperService` 不对已整理范围重复调模型；进度并发合并满足高 `generation`／更晚 `until_at` 单调性；
   - 外键顺序（`context_summaries` 与 `conversations` 同批到达）、LAN 旧端能力过滤、云端 `sync_v3` pytest 契约测试与旧服务端 `kinds` 兼容均通过。
