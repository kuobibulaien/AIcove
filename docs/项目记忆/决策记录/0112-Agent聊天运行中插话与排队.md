# 0112：Agent 聊天运行中插话与排队

关联：ADR0101（杂活任务的 steer_task）、0108（单一执行内核）、0111（Agent 模式能力）。

## 背景

对照 Pi 1.2.0 找差距时发现：Agent 模式的聊天在运行中没法插话，也没法排队追问，只能先停止再重发。内核早有 `AgentLoop.steer()`，但只接到了后台杂活任务；聊天里一次运行的全部轮次最终落成一条助手消息，把插话塞进同一次运行，会让落库顺序和气泡顺序对不上。

Pi 的语义（`docs/rpc-commands.md`）：插话在当前这一轮的工具调用全部执行完、下一次模型请求之前送达；排队只在 Agent 停下后送达；两者都不打断正在执行的工具，要打断用 Esc；中止时把排队的消息退回编辑器。

## 决定

1. **插话＝让出再发**：插话时不把消息塞进正在运行的循环，而是让本次运行在当前这批工具结算后、下一次模型请求前结束（内核 `AgentLoop.yieldAtBoundary()`，停止原因 `KernelStopReason.steered`），已完成的步骤照常落库成助手消息，再把插话作为新的用户消息走普通发送。模型看到的顺序与 Pi 一致（工具结果 → 插话 → 继续），聊天记录自然分成前后两段，现有落库、投影、换模型重试链路不变。模型已经不再调工具、正在写最后答复时，答复照常写完，随后接着处理插话。
2. **排队＝整轮结束再发**：排队的输入等本次运行彻底结束后，作为新的用户消息发出。
3. **一次一条，插话优先**：队列按加入顺序保存，每次运行结束只发一条，有插话先发插话；新运行开始时（含重新生成）队里还有插话，这次运行也会在第一批工具后让出。下一条在上一轮收尾时同步登记成新任务（排队发送先登记任务再记 trace，普通发送顺序不变），中间没有空闲空档，停止与撤回直接作用于它。排队输入按阶段处理：还没落库被停止就退回、不再落库；落库失败且查不到这条才退回；落库后出错则标失败并收尾。内核在轮首和发请求前各检查一次让出，准备上下文（如压缩）期间的插话也不会多发一次请求。撤回插话（放回输入框）会撤销让出，本次运行照常做完。
4. **不打断工具**：插话和排队都不取消正在执行的工具；想立刻停仍用停止按钮。
5. **没发出去的留着等用户放回**：停止、运行失败或下一条用户消息落库失败时，队列里的输入转为「未发出」，显示在输入框上方，不自动发出，也不自动写进输入框（避免切会话、编辑旧消息时被覆盖）；用户点放回或按 Option/Alt+↑ 时合并到输入框（排在已有草稿前面）。Pi 是直接退回编辑器，这里多一步，换来不丢字。队列只在内存里，应用被杀时丢失（与 Pi 相同）。
6. **只对 Agent 模式会话生效**（`effectiveAgentMode == tool`）；聊天模式的输入框与发送行为不变。
7. **输入框交互**：
   - 桌面（仅 Agent 会话）：Enter 空闲时发送、运行中插话；Option（Windows/Linux 为 Alt）+Enter 运行中排队；Shift+Enter 换行；Option/Alt+↑ 把排队的话放回输入框；输入法组字中不拦截。注意这改变了 Agent 会话里 Enter 原来换行的行为。
   - 手机：运行中输入框有字时点发送＝插话、长按＝做完再发；没字时仍是停止。
   - 排队的输入显示在输入框上方（「插话」「做完再发」「未发出」标签），右侧按钮放回输入框；运行中输入框占位文字提示用法。
   - 运行中只能插入文字；带附件或处于编辑草稿时提示等这轮做完。

## 代价

- 每次插话多一次上下文装配（系统提示、记忆检索等重新计算），比 Pi 在同一循环内注入多一点开销；换来不改落库结构。
- 排队只在内存，重启丢失；不跨设备。
- 落库报错后若连查询都失败，这条仍会出现在「未发出」里，可能是已发过的文字；它不会自动重发，由用户判断。
- 普通发送在主 try 之前出错会卡住发送状态、落库中被停止的消息终态，是本次之前就有的问题，未处理。
