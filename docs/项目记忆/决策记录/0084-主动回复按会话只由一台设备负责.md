# 0084 主动回复按会话只由一台设备负责

- 状态：accepted（2026-10-15 用户确认按推荐方案修）
- 日期：2026-10-15
- 关联：ADR0079（主动回复判断与执行拆分）、ADR0051（局域网直连）、ADR0058（云同步 v3）

## 背景

触发器列表 `aicove.auto_triggers.v1` 整份随设置同步（局域网与云端），但「已有待发触发器」的会话状态（`aicove.proactive_states.v1`）和执行认领（本地 SQLite）都只在本机。多台设备同时在线时：

- 每台设备都可能自己发起分析（切后台、静默唤醒），看不到别的设备已排好的触发器，于是各建一条；
- 同步过来的触发器，每台设备的前台轮询都会去发；
- 触发器控制器的内存列表同步后不刷新，再写入时用旧列表覆盖，整份「后写赢」。

结果是同一会话可能收到两条主动消息、模型被调用两次。

## 决定

1. **负责设备＝用户最后发消息的设备**。新增随同步的映射 `aicove.plugins.trigger.owner_devices.v1`：会话 ID → `{device_id, at_ms}`（设备 ID 与同步引擎同源 `aicove.cloud.device_id`）。每个会话是一个字段，按字段合并，取最新一次认领；值里带认领时间，同一台设备再次发消息也会刷新字段时间，不会输给另一台设备更早、尚未传到的认领。放在 `aicove.plugins.` 前缀下，旧版本客户端的同步白名单已接受。
2. **认领**：本机用户发消息时（`AnalyzerScheduler.handleUserMessageActivity`），以及用户在本机手动点「立即触发」时，写入本机为负责设备。读映射、改本会话、保存都在同步写锁 `cloudLocalWrite` 里完成，不覆盖同步刚写入的其他会话。
3. **门禁**（`ProactiveOwnership.owns`）：
   - 分析：开始时、模型给出计划后（删旧触发器之前）、预生成后各查一次，不是负责设备就取消本机计时器并跳过；
   - 前台轮询跳过该会话的触发器（不认领、不发送、不作废）；WorkManager 后台任务入口直接跳过；
   - 送达前（前台／后台、消息／来电，`beginDelivery` 之前）再查一次，已交给另一台设备就释放本机执行认领，并按「被接管」放弃。
4. **未认领的会话**（升级后还没发过消息）对所有设备放行，与原来一致；第一条消息之后即收敛到一台。
5. **触发器列表只按存储改**：控制器的每次写入都在 `cloudLocalWrite` 里重读存储 → 修改 → 保存 → 更新内存。作废、失败重试是否生效，以存储里的最新状态判断，不会把同步或用户刚写入的暂停／送达改回去。同步应用了设置后，控制器也在同一把锁里重读列表。

## 代价

- 设备间同步是异步的，只能最终收敛：认领还没传到另一台设备时，两台设备在这段时间里仍可能都放行。要在任何时序下都严格只有一台执行，需要跨设备协调，本次不做。
- 混用没有这道门禁的旧版本客户端时，旧版本那端照旧会分析和发送。
- 触发器列表在设备之间仍是整份后写赢：两台设备几乎同时写列表时仍可能丢一方的写入，但非负责设备基本不再写，概率很低。
- 用户在 A 设备说完话后只开着 B 设备，主动回复仍由 A 负责；A 不在线就不会有主动回复，直到用户在 B 上说话。
- 在别的设备上建的手动触发器，由负责设备的前台轮询发送，负责设备上没有登记 WorkManager 后台任务。

## 验收门

两台设备局域网同步同一账号：在 A 上聊天后，只有 A 产生并发送主动消息；B 的日志出现 `analysis_skipped_other_device`；换到 B 上发消息后改由 B 负责。离线测试见 `test/features/auto_reply/proactive_owner_device_test.dart`（9 项）；生成途中切换归属、释放认领失败两种时序没有确定性测试；真实双端未验。Codex 审查四轮，第四轮「可以合并」。
