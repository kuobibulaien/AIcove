# 酒馆兼容组合预设与上下文接入

## 背景

用户确认“酒馆兼容插件（测试）”与绘图、音色同级，最低必须让预设、正则和世界书真正影响上下文，导入后有逐条开关；非核心能力后推。不是仅把原入口搬进空壳页面。

## 决定

1. 沿用稳定 `Conversation.recipeId` 作为酒馆插件组合绑定，不新增并行角色字段或数据库迁移。原酒馆预设加可选 `compatibilityData`，承载附加正则、世界书和逐条覆盖开关；原始预设JSON保留，不靠改动源文件重新计算身份。
2. `TavernCompatibilityPort` 定义插件配置、资源修改和有效预设读取，应用层控制器供UI使用；总开关/默认预设由本地JSON保存。请求按owner绑定一次性解析，明确绑定优先、缺失失败关闭、未绑定用默认；总开关关闭恢复原上下文，不把此插件伪装成AITool权限。
3. 世界书扫描经过 `TavernWorldScannerPort`，以raw派生请求历史为输入，通过marker和深度注入现有装配器。消息regex、世界书触发、WORLD_INFO regex、预设装配依次执行；不另起第二套聊天发送通路。
4. UI与请求共享同一解析结果；开关持久化、连续写串行、文件原子替换；请求执行中更改角色/默认项/开关不污染已固定的预设和正则快照。

## 备选与代价

不选“新增一张组合表并迁移所有角色绑定”：核心目标可用既有recipeId完成，新增映射只会扩大本批风险。代价是世界书/独立正则暂按组合内导入，没有统一共享资源库、组合复制/删除/导出；基础组合是现成模板，不代表整个资源管理最终形态。

不把静默降级称为兼容：世界书高级条件/位置不支持则明确提示并跳过；保留原始内容以待后续支持。预算是项目估算器与安全上限，不保证与上游tokenizer逐字一致。后台专业Agent权限不在本批扩展。

## 验收门

真实最终请求证明三类资源开关改变messages且不改raw；角色A/B隔离、默认引用优先级、请求快照稳定、重新打开文件后开关保留；导入与列表在窄宽屏可操作；异常正则不能卡住UI，坏配置可停用恢复。
