# 0087 Agent 工作区插件：Agent 可随意涂改的笔记本

- 状态：accepted（2026-10-16 用户逐条确认方向；Codex 三轮审查意见已并入；实施方案见 [实施方案](../../../apps/aicove_flutter/docs/02_前后端分离与架构规范/Agent工作区与杂活Agent实施方案.md)；W1 已实现）；第 2 条的文件工具部分与第 4 条（QuickJS 脚本、不提供 Shell）已由 [ADR0098](0098-工作区按Pi对齐为完整harness工具层.md) 取代（2026-10-21），存储与提交协议不变
- 日期：2026-10-16
- 关联：ADR0064（Dart 微内核与全插件化、QuickJS 脚本插件）、ADR0008（插件预设与角色绑定）、ADR0017（插件上下文过滤）、ADR0051／0058（局域网直连、云端保底）、ADR0084（按会话只由一台设备负责）、ADR0088（聊天模型委派杂活 Agent）

## 背景

AIcove 也被当作 harness 使用，用户希望 Agent 有一块能自己创建、写入、修改文件的地方，能放可运行的脚本、能建定时任务，并能在多台设备间按需同步。

讨论中排除了更大的方案：

- **全能设备 Agent**（操作手机界面、系统 API、终端、Root，参照 Eta）：各家系统迟早会有自己的 AI 助手，AIcove 不在这里投入；这些能力（L1～L4）以后做成可选装插件，自研或转交原生 Agent 均可。
- **挂载用户任意文件夹**：需要安卓「所有文件访问」、iOS／macOS 安全书签与平台差异处理；Agent 只管 AIcove 自己的一亩三分地就够了。
- **工作区作为 Agent 的上级属性**（Agent 归属某个项目）：电脑上的 harness 在不同项目里只是拿到不同的提示词和文件，工作区更像 skill 一样的能力。
- **git 快照**：手机端需要 libgit2 等原生依赖；撤销需求用修改历史即可满足。

## 决定

### 1. 定位与授权

- 新增内置插件 `workspace`。每个工作区是这个插件管理的一个条目，可以新建、导入、删除，概念上相当于一个预设。与 ADR0008「一个插件绑一个配置包」不同，角色拿到的是**可访问工作区的授权列表**。
- 工作区的元数据（ID、名称、描述）存在 `.aicove/workspace.json`；成员设备列表按第 7 条的成员协议维护。本机有哪些工作区记在本机登记表里，不随设置同步。工作区的提示词是根目录下可选的 `AGENTS.md`。
- **授权按单个 Agent 给出**：角色在工作区插件里勾选可访问的工作区（默认一个都没有），由该角色派出的杂活 Agent（ADR0088）使用；以后的内置 Agent（如教程 Agent）各自声明自己的列表。
- **内置授权（2026-10-21 补充）**：AIcove酱（`aicove_assistant`）固定拥有 `aicove` 默认工作区，写在代码里（`WorkspaceGrants.builtInFor`），不写进角色的插件列表，所以出厂和老用户的「全部插件」状态不用改写、也不用迁移；角色编辑页把这一项显示为常开、不可关。其他角色仍默认一个都没有。
- **有效授权的唯一解析规则**：（角色显式授权＋内置授权） ∩ 杂活 Agent 预设允许 ∩ 插件全局启用 ∩ 本机存在。预设（包括默认预设和共享预设）只能收窄权限，不能授予权限。办事类插件（联网搜索、MCP）也按同一条规则解析，并沿用 ADR0072「MCP 必须由角色显式开启」。
- 角色里的授权列表随角色同步。某台设备上没有对应的工作区时，该项显示为「本机没有」，执行时跳过；编辑角色时**保留原 ID**，不因本机没有而清掉。
- 按需加载：系统提示词里只列出有效授权的工作区名称和描述；Agent 调用 `workspace_open` 后才拿到 `AGENTS.md` 和顶层目录，与现有技能包 `read_skill_*` 同一套路。Agent 可以用 `workspace_create` 新建工作区，新工作区自动加入创建它的角色的授权列表。

### 2. 存储、文件工具与条件提交

- 普通工作区放在 `appDataDirectory()/workspaces/<工作区 UUID>/`，不访问 App 以外的目录。
- 文件工具：`read`、`write`、`edit`、`list`、`glob`、`grep`、`move`、`delete`，参数都带工作区 ID，路径只接受相对路径。
- **`.aicove/` 由宿主维护**：通用文件工具对它只读，元数据和成员信息只能通过导入、退出接口改，定时任务只能通过定时工具改。
- 路径规则（写入时就拦，不留到同步时）：拒绝绝对路径、`..`、指向工作区外的符号链接；文件名统一为 NFC，拒绝 Windows 保留名（`CON`、`NUL` 等）、字符 `<>:"|?*`、结尾的空格或点；同一目录内忽略大小写后重名的拒绝。单段文件名与整条相对路径设一个**四端共同的预算**，同时按 UTF-16 码元（Windows）和 UTF-8 字节（安卓等文件系统单段 255 字节）两种口径限制：路径长度按 Windows 传统上限 260 减去应用数据根目录的长度来定，文件名还要给冲突后缀留出余量。本机根目录太长、预算不够时，直接阻止新建和导入，并说明原因。这样任一平台写出的文件，在其他三个平台都能落地。具体数值见实施方案。
- **写前校验**：读取时返回 `revision`（内容 SHA-256）。覆盖或编辑已有文件必须带 `expected_revision`；`edit` 的旧文本必须唯一匹配，除非显式指定 `replace_all`。
- **条件提交**：校验 revision、预留配额、保存修改前的内容、替换文件、更新索引，必须作为一次不可交错的提交完成。所有写入方（文件工具、脚本、同步写入、撤销，包括安卓后台 isolate）都经过同一个提交协调器，靠本机工作区索引库（独立于主数据库的 SQLite 文件）的写事务做跨 isolate 串行化。两个任务拿着同一个 revision 同时提交时，只有一个成功。不提供 Agent 可见的文件锁。
- **崩溃恢复靠意图记录**：SQLite 事务管不到磁盘上的文件，所以每次修改分三步：
  1. 先提交一条意图记录：操作 ID、路径、修改前后的哈希、所属 run、阶段。同一个事务里**占用**这次涉及的路径（move 同时占用源路径和目标路径）。路径被占用期间，其他写入方不能为它创建新的意图，直接返回「正在写入，请稍后重试」；
  2. 再动文件；
  3. 最后完成索引提交，并标记意图记录已完成。

  启动时逐条处理未完成的意图：磁盘内容等于修改后的哈希，就补完提交；等于修改前的，就作废这条意图；两者都不是，就把这个路径标为冲突。恢复完成之前，这个工作区拒绝写入。路径的占用到第 3 步完成或恢复处理完才释放。
- **修改代次**：索引里每个路径除了内容哈希，还记录「最后一次修改它的操作 ID」，给撤销判断因果用。内容相同的两次修改，操作 ID 也不同。

### 3. 随意改，靠撤销兜底

- 每次写入、移动、删除文件之前，先把修改前的内容按哈希存进 `workspaces/.history/`（不同步），再在同一次提交里更新索引。修改记录按 run 分组。
- **撤销只针对本机 Agent 产生的修改**，按逆序逐项进行。每一项撤销前，检查这个路径「最后一次修改的操作 ID」：它要么是这一项本身，要么是同一次撤销刚刚撤掉这一项后面那一项时产生的撤销操作（撤销操作会记下自己撤掉的是哪一项）。都不是，就说明之后被别的轮次或其他设备改过，这一项不撤销，并且同一路径上本轮更早的记录也全部跳过，一并报告为冲突。只看内容哈希不够，因为内容可能被改回同样的值。撤销进度持久记录，崩溃后可以继续。撤销本身也是一次普通修改，会正常产生新的同步修订。
- 因为可以撤销，**已授权工作区内的文件写入在工具闸门里直接放行**，不逐次询问；删除整个工作区、清空修改历史属于危险操作，需要询问。
- 修改历史另设保留策略（按时间和总大小）。**撤销历史和同步内容分开保留**：同步当前修订、冲突副本、正在传输中引用的内容永远固定，不受撤销历史的清理影响；清理按引用是否还可达来做，正在进行的撤销所引用的内容同样固定。固定内容超出预算时，阻止新的写入，而不是删掉同步内容。

### 4. 运行环境：QuickJS 脚本

- Agent 只需要一个能跑代码的地方，不提供 IDE 或命令行。
- `run_script(工作区, 路径, 参数)`：在 QuickJS 沙箱中运行工作区里的 `.js` 文件，返回输出、返回值与报错。宿主只开放：读写本工作区文件（经过同一个提交协调器）、HTTP 请求、发系统通知、写日志。
- 现有 `aicove_quickjs` 是同步求值，每次求值的期限写死为 1 秒，遇到未完成的 Promise 会直接失败，不能等待宿主的异步调用。因此需要**新增一套异步运行机制**：Promise 调度、宿主请求／回复协议、整次运行的期限（包含等待宿主的时间）、取消，以及会话关闭后晚到回调的丢弃。它的限额与酒馆预设运行时分开配置，不能改变现有预设的行为。这一机制作为 ADR0064 第三批脚本插件的宿主桥基础。
- 不提供 Python、Node 或系统 Shell；需要时由以后的桌面端 L2 插件提供。

### 5. 定时任务

- **定义与运行记录分开**：每个任务的定义单独存成一个文件 `.aicove/schedules/<任务 ID>.json`（随工作区同步，只能用定时工具改），包括 ID、版本、间隔或 cron、创建者时区（IANA 名称）、触发内容、执行设备、目标会话、是否启用。这样两台设备改不同的任务不会互相冲突。同一个任务出现并发修改时，**暂停这个任务**，等用户在界面上选定一份再恢复。运行记录存在本机索引库，不同步。
- **第一版不允许更换执行设备**：想换设备，就停用原任务、在新设备上重建。这样就不会出现离线的旧执行设备和新执行设备同时执行的情况。
- 触发内容二选一：跑某个脚本，或者唤醒某个角色的杂活 Agent 执行一句提示词（ADR0088）。后者必须指定目标会话，结果要告诉用户时，回执发到这个会话。
- **只由一台设备执行**：执行设备默认是创建它的设备，其他成员只显示、不执行。同一台设备上，前台计时器和后台任务按「任务 ID＋版本＋计划触发时刻」原子认领，抢不到的一方跳过。执行前重新读取：任务是否启用、本机是否仍是成员和执行设备。任务被修改、关闭，或本机退出成员后，旧的认领全部失效。
- 安卓用现有的系统后台任务和前台服务尽量准时；桌面端只在 App 运行时执行；iOS 不保证后台执行。每个任务按补跑游标处理：错过的触发在下次启动时最多补跑一次。执行到一半时崩溃，记为「结果不确定」，不自动重跑。

### 6. AIcove 默认工作区：数据库的文件视图

- 内置一个 ID 固定为 `aicove` 的默认工作区，给以后的教程 Agent 等使用。它**不存真实文件**：读取 `roles/…`、`presets/…`、`settings/…`、`chats/…` 时，按固定目录布局从数据库现场生成内容。数据库仍是唯一真相源。
- **字段白名单投影**：每类内容只输出白名单里的字段。API Key、MCP 令牌等凭据只显示「已配置」或「未配置」。列目录、搜索、按路径读取都走同一套过滤。隐私空间里的角色和会话完全不出现。
- 聊天记录在这里只读。只有用户把 `aicove` 显式授权给某个角色时，该角色的杂活 Agent 才能读到聊天记录（AIcove酱的内置授权不算：实现这层投影时，她读 `chats/…` 仍须按 ADR0093 逐个角色经用户同意）；ADR0088 说的「看不到聊天记录」，指的是不会自动装配进上下文。
- 默认工作区不参与工作区同步，它对应的数据本来就随现有数据同步。
- 第一版只读；写回（角色、预设、设置）放在后续批次，经现有领域服务与修改日志实现。

### 7. 同步：默认仅本机，导入后成员间同步

- 新建的工作区只属于本机。在另一台设备上可以选择「从已连接设备导入」某个工作区。之后只在成员之间同步，未导入的设备收不到这个工作区。
- **成员协议**：
  - 每台设备的成员记录是**独立的一个同步实体**（工作区 ID＋设备 ID），只有这台设备自己能写，内容是加入或退出、以及这台设备自己的递增版本号。因为没有两台设备写同一个实体，所以不会出现并发冲突，也不依赖时钟：重新加入用更大的版本号覆盖之前的退出。
  - **导入**：源设备核实请求方是已配对设备后，给它发一次性的导入授权。这个授权同时覆盖首次完整复制和提交它自己的加入记录，可以重复提交（幂等）。加入记录被源设备接受后，请求方才成为正式成员。导入中断后，凭同一个授权可以续传。
  - **退出**：退出的设备仍然可以把自己的退出记录发给其他成员，这是成员鉴权唯一的例外入口，只接受这台设备自己的成员实体。其他成员之间也会继续转发这条记录。
  - 工作区列表里，名称前显示成员设备。退出同步后，本地副本保留，不删除。
- **鉴权覆盖所有入口**：摘要、游标、修订、附件分块、入站写入，每一处都检查对方是否为成员；只过滤摘要是不够的。一台设备**得知**某设备已退出之后，就拒绝那台设备的数据请求。同步是异步的，还没收到退出记录的设备做不到立即拒绝。
- **能力在每次同步会话时刷新**：不只在配对时声明一次。每次建立同步会话时交换各自支持的能力，缺少这个字段就当作不支持；一端关闭工作区同步后，立即失效。
- **实体**：工作区文件的实体 ID 采用有长度上限的稳定形式（工作区 ID 加路径哈希），原路径放在载荷里，接收端仍要过一遍路径规则。只把工作区实体发给声明支持的设备，旧客户端照常同步原有数据。工作区实体**不进入云端上传或代传**；云端保底以后另行决定。
- **安全落地**：发布修订之前，先把内容固定保存为不可变快照（按第 3 条的同步内容规则固定）。接收端先把内容下载到暂存区并校验哈希，再经提交协调器落地（路径规则、配额、条件写入）。待落地状态持久保存，重启后继续。删除留墓碑。修改历史不同步。
- **冲突副本命名**：并发修改时保留两份，另一份改名为冲突副本。命名算法要稳定：设备名先过一遍文件名规则做合法化；原名按预算截短；末尾加短哈希避免撞名。改名之后的路径仍要在共同路径预算之内。
- 远程操作另一台设备上的工作区（不复制、直接使用）本期不做，留到需要借用其他设备能力的 L2 插件时再设计。

### 8. 界面

- 主页底部的「角色」标签改为「工作区」：工作区列表（带成员设备前缀）、新建与导入、只读文件浏览、按 run 撤销、定时任务列表与开关。
- 角色页现有的搜索（角色＋全部聊天记录）迁到「聊天」标签。「新建聊天」和角色编辑的入口保留在聊天这边，不再单独保留角色列表页。
- 术语：界面上的「工作区」从此专指 Agent 工作区。宽屏布局外壳的代码类名 `MoeWorkspace` 不改，在术语表里注明它不是这个概念。

## 代价

- 写入不逐次询问：Agent 可以在已授权的工作区里大量改写文件，只能事后撤销。撤销管不到脚本通过 HTTP 对外产生的影响，也不能撤销其他设备同步过来的修改。
- 多了一个本机工作区索引库，还有一套异步 QuickJS 运行机制，都需要长期维护。
- 只支持 JS 脚本；QuickJS 没有 JIT，重计算会慢；iOS 上下载并执行脚本的审核口径未核实（同 ADR0064）。
- 定时任务在 iOS 上、以及桌面 App 关闭时，不能准时执行。
- 默认工作区的投影和白名单与数据库结构耦合，数据库字段变化时要一起维护。
- 同步冲突只按整个文件保留两份，不做三方合并。
- 去掉独立的角色列表页后，习惯从「角色」标签进入聊天的用户，需要改走聊天列表和搜索。

## 验收门

1. **路径规则**：四个平台的保留名、非法字符、大小写重名、NFC／NFD、越界路径，以及上限前、等于上限、超过上限三种情况，都有离线测试。
2. **条件提交**：两个任务拿同一个 revision 同时提交，只有一个成功（包括跨 isolate 的情况）；在「意图已提交、文件已改名、索引还没提交」等每个阶段杀进程后重启，都能按意图记录恢复正确。
3. **撤销**：没有后续修改时，撤销后与这一轮之前逐字节一致；有后续修改（其他轮次或同步入站）时，后续内容不丢，冲突项被报告出来；A 轮写 0→1→2、B 轮再写 2→1 后撤销 A，B 的修改不丢；删除后重建出同样的内容，也不会被误撤；撤销中途崩溃后可以继续。
4. **授权**：未授权、预设不允许、本机没有的工作区，都不会出现在 Agent 的工具和提示词里，调用直接失败；共享预设无法扩大角色的权限；在没有该工作区的设备上编辑角色后，授权 ID 仍然保留。
5. **脚本**：`await http.fetch` 之后再写文件能成功；超时、取消、JS 异常之后都不会再有晚到的写入；越权路径会失败；现有酒馆预设回归测试全部通过。
6. **同步**：
   - 两台设备导入同一工作区后，增删改双向到达；并发修改时两份都保留，最长文件名产生冲突副本时名字仍然合法；
   - 非成员设备，无论走摘要、修订还是附件哈希，都拿不到数据；设备获知某设备已退出后，拒绝它的请求；
   - 导入中断后可以续传；退出时第三台设备离线，上线后能收到退出记录；
   - 新旧客户端混用时，原有数据的同步不受影响；单端升级、双端升级、关闭能力三种情况，能力都能正确刷新；
   - 在元数据和附件之间断网后可以续传；修改历史清理之后，离线成员上线仍然能续传；接收端配额不足时明确失败。
   - 定时任务：两台设备并发编辑不同任务互不冲突；同一任务的并发修改会让该任务暂停。
7. **默认工作区**：读到的内容与 App 当前数据一致；凭据不出现在任何读取、列目录、搜索结果里；隐私空间的内容不出现。
