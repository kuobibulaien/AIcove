# 0088 聊天模型只派活：办事交给后台杂活 Agent

- 状态：accepted（2026-10-16 用户确认：聊天模型只挂一个派活工具、一律直接转后台、生图留在聊天模型；Codex 三轮审查意见已并入）；2026-10-17 W2 已实现（离线通过＋DeepSeek Flash 真实模型跑通「派活→回执→人设转告」，未上真机、未做双端），与本文的偏差见[实施方案](../../../apps/aicove_flutter/docs/02_前后端分离与架构规范/Agent工作区与杂活Agent实施方案.md) W2「实施记录」：回执消息改为 outbox 幂等补写；跨设备转告显示与请求副本去重、回执标签注册与导出、执行设备离线显示已于 10-17 补齐（同时间按原始消息 ID 而非设备 ID 排序）
- 日期：2026-10-16
- 关联：ADR0064（微内核，DB 原始消息唯一真相源）、ADR0060（统一装配与调度分离、交付通道）、ADR0017（请求副本过滤）、ADR0044（语义标签注册表）、ADR0072（MCP 连接器）、ADR0074（通话记录块的先例）、ADR0079（主动回复）、ADR0084（按会话只由一台设备负责）、ADR0087（Agent 工作区插件）、ADR0038（记忆两层）

## 背景

聊天模型的上下文应该留给人设、用户记忆和情绪价值。现在联网搜索、MCP 等工具直接挂在聊天模型上，工具调用的参数和大段返回结果都会进入聊天上下文；ADR0087 的工作区、脚本和定时任务如果也照这样挂上去，上下文会被大量杂活占满。

## 决定

### 1. 聊天模型的工具面

- **办事类全部移交给杂活 Agent**：联网搜索（`web_search`／`web_fetch`）、MCP 连接器、工作区文件工具、脚本运行、定时任务，以及以后的 L1～L4 设备插件。
- **聊天模型只多一个工具 `delegate_task`**，有三个动作：`start`（派活，附任务说明）、`reply`（回答杂活 Agent 提出的问题）、`cancel`（取消）。
- **表达类与陪伴类留在聊天模型上**：生图（本来就是标签）、表情包、语音、主动来电，以及提醒（`create_reminder` 等）。它们属于角色「怎么表达」和「自己许下的约定」，返回结果很短，不会污染上下文。
- **模型内置搜索也要关掉**：聊天 run 一律在最终的供应商请求体上执行内置搜索抑制，包括渠道额外参数里的 `enable_search`、`web_search_options`、Gemini 搜索工具等。不再依赖「联网搜索插件是否在请求里」来决定是否抑制。
- **历史也要清干净**：只从工具清单里移除办事类工具还不够。迁移前留在历史里的办事类调用与结果，要在原始消息转成请求副本时成对移除（ADR0017 机制），原始历史本身不动。「角色授权给杂活 Agent 的能力」与「聊天请求允许回放的工具」分开判断：即使角色开启了联网搜索或 MCP，它们的调用也不再回放进聊天请求。

### 2. 一律直接转后台

- `delegate_task(start)` 先把任务记录持久化，**持久化成功后**才返回 `{task_id, status: accepted}`，不等待执行结果。请求键是宿主持久化的复合键：设备 ID＋会话 ID＋这次聊天 run 的 ID＋轮次＋工具调用 ID。供应商给的工具调用 ID 不保证全局唯一（比如 Gemini 会按序号生成），不能单独用作键。同一个键再次提交时，核对角色和会话一致后返回原来的任务，不新建。聊天模型接着用人设的口吻回话，比如「我去弄一下，好了告诉你」。
- 聊天模型的系统提示词明确规定：没有收到回执之前，只能说「在处理」，不能编造结果。
- 每台设备同时运行的任务有数量上限，超出时排队。

### 3. 杂活 Agent

- 没有人设。它是一个插件预设：模型（可以和聊天模型不同）、最大轮数、允许的办事类插件、允许的工作区。角色绑定这个预设，未绑定时用默认预设。有效能力按 ADR0087 第 1 条的规则解析（角色显式授权 ∩ 预设允许 ∩ 全局启用 ∩ 本机可用），预设只能收窄权限，不能授予权限。
- 内核层面只是另一次 run，使用自己的装配配方（ADR0060），不另起一套循环。
- **聊天记录不会自动装配进它的上下文**。它只拿到任务说明、角色 ID，以及有效授权的工具和工作区。只有用户把 `aicove` 默认工作区显式授权给该角色时，它才能通过文件工具读到聊天记录（ADR0087 第 6 条）。
- 任务说明不清楚时，它返回 `needs_input` 和一个问题，由聊天模型用人设口吻转问用户；用户回答后，聊天模型用 `reply` 让任务继续。继续时新开一次 run，上下文从本机保存的过程记录恢复。

### 4. 回执

**结构**：回执是一种新的消息块 `TaskReceiptBlock`，存成一条原始消息，随聊天同步。做法沿用 ADR0074 通话记录块的先例：消息正文是给模型看的简短事件标签，结构化字段存在块里。字段带版本号：

- `v`
- `receipt_id`（稳定 ID，等于任务 ID 加序号）
- `task_id`
- `status`：`done` / `failed` / `needs_input` / `cancelled` / `interrupted`
- `summary`：有硬上限，超出按字符截断并标注已截断
- `question`：仅 `needs_input` 时有
- `artifacts`：工作区 ID 加路径
- `executor_device`
- `side_effect_uncertain`：取消或中断时，外部请求可能已经生效
- `notify`：`always`／`on_failure`／`never`，决定要不要转告用户。聊天派出的任务固定为 `always`；定时任务按定义填写，缺省为 `on_failure`；`needs_input` 不论这个字段怎么填都会转告。待转告队列只按这个字段创建，不需要查任务表。

整条回执（序列化后的块）有字节硬上限；`summary`、`question`、`artifacts` 各有自己的上限，见实施方案。

**派生**：任务卡片和请求副本里的简短系统事件，都只从这个块派生，不依赖本机的任务表。所以在没有任务表的设备上，回执也能正确显示和回放。正文里的标签经 ADR0044 注册表声明。回执不进入记忆整理；导出时转成一行文字；旧客户端会看到这段正文。

**聊天里的呈现（2026-10-21 修订）**：回执消息不在聊天列表里显示，只作为人设转告的输入；派活那一轮只在消息下方留一行淡色等待条（「后台处理中…」），任务结束即消失，结果由人设自己回复。只有派活调用、没有文字的那一轮不画气泡。回执详情在「后台任务」页查看。

**过程记录**：杂活 Agent 的完整过程只存在执行设备本机，不进聊天上下文，也不同步。点开任务卡片时，执行设备上能看到全部过程，其他设备只能看到回执。

### 5. 状态机与崩溃恢复

- **状态**：`queued → running → (needs_input → running)* → done | failed | cancelled | interrupted`。
- **事务**：凡是会产生回执的状态变化（进入终态，以及进入 `needs_input`），都和回执消息、本机「待转告」记录（以 `receipt_id` 为键，仅当 `notify` 要求转告时创建）在主数据库的同一个事务里完成。
- **检查点**：过程记录先持久化到检查点，再推进任务状态。`reply` 之后新开的 run 从最近的检查点恢复上下文。
- **启动恢复**：启动时恢复所有没走完的阶段：
  - 状态为 `queued` 的任务，重新排队；
  - 状态为 `running` 的任务，标为 `interrupted` 并写回执，不重放已执行的操作；
  - 有回执但还没转告的，继续转告；
  - 已经转告过的，不重复转告。

### 6. 执行权与转告权分开

- **执行权**：始终在启动任务的设备上，不迁移。
- **转告权**：属于 ADR0084 里这个会话的负责设备。负责设备从本机或同步收到需要转告的回执后，按 `receipt_id` 认领转告，然后唤醒聊天模型用人设口吻发一条消息。如果聊天模型正在生成，就等这一轮结束；如果用户不在，就走主动回复的发送链路。
- **重复转告的收敛**：ADR0084 只保证最终收敛，认领还没同步过去时，两台设备可能各自生成一条正文不同的转告。每条转告候选有自己的物理消息 ID（`receipt_id`＋生成它的设备 ID），并以 `receipt_id` 作为逻辑去重键。显示和请求副本按一条专门规则只取一条：创建时间最早的胜出，同一时间再按设备 ID 排序。落选的那条照常保留在原始历史里，只是不显示、不进请求副本。不承诺跨设备只生成一次，只承诺最终只显示一次。
- **控制请求**：`reply` 和 `cancel` 的处理函数在返回「已受理」之前，先持久化一条带类型的原始控制事件（`TaskControlBlock`：版本、`control_id`、目标任务、所回答的问题回执 ID、内容），随聊天同步到执行设备。这样不依赖聊天这一轮是否成功落库。执行设备消费控制事件时，「标记已消费」和任务状态变化在同一个事务里完成，按 `control_id` 幂等。只有在线产生的控制事件才可执行：导入、编辑历史产生的消息不会生成可执行的控制事件；回答的问题回执 ID 与任务当前状态不符的，一律忽略。执行设备离线时，任务卡片显示「执行设备离线」，等它上线后再处理。
- 定时任务触发的杂活（ADR0087 第 5 条）直接运行杂活 Agent，不经过聊天模型；只有回执需要告诉用户时，才进入本条流程，发到定时任务指定的目标会话。

### 7. 取消

取消令牌会传到每一个宿主操作（文件提交、HTTP、脚本）。各操作在真正提交之前检查令牌，已取消就不再提交。取消之后，要等正在进行的操作停下或收敛，才确认 `cancelled`。如果外部请求已经发出，回执里标记 `side_effect_uncertain`，不承诺撤销。

### 8. 总开关与回滚

杂活执行有一个持久的总开关，带代次号。关闭时：

- 停止新任务的派发、控制事件的消费和定时触发，并取消已登记的系统后台任务；
- `running` 的任务按第 7 条取消，写入 `cancelled` 回执；
- `queued` 和 `needs_input` 的任务冻结。

重新打开后，冻结的任务不会自动继续，要由用户在任务卡片上手动恢复；关闭期间错过的定时触发不补跑，补跑游标直接移到当前时间。

## 代价

- **联网搜索不再在当轮回复里完成**：用户问一件需要查的事，会先收到「我去查一下」，结果稍后以新消息到达。即时性变差，但聊天上下文保持干净。
- 每件杂活至少多一次模型调用（杂活 Agent 一次，收到回执后聊天模型再说一次），费用和延迟都会增加。
- 任务说明的质量取决于聊天模型；说明写不清楚时，杂活 Agent 会做偏或反复追问。
- 执行设备离线时，任务的追问和取消都会卡住。完整的过程记录只能在执行设备上查看。
- 手机端 App 被系统回收时，正在运行的任务会中断。iOS 的后台基本不能继续执行。
- 现有角色开启的 MCP 连接器与联网搜索，迁移后改由该角色的杂活 Agent 使用，从「当轮可用」变成「派活后可用」。
- 新增 `agent_tasks` 表，主数据库需要做一次 schema 迁移。

## 验收门

1. 聊天模型的**最终请求**里，不再出现办事类工具的定义、调用和原始结果（包括迁移前的历史）；只有 `delegate_task` 和回执事件。
2. `delegate_task(start)` 在任务持久化后立即返回；完成后，聊天模型根据回执主动发出一条消息；回执到达时如果正在生成，不打断当前生成。
3. `needs_input` 能经聊天模型转问用户，`reply` 后任务继续；`cancel` 后，被延迟的写入和 HTTP 结果都不会再落地，并行工具批次同样如此；控制已受理但聊天这一轮随后失败时，命令仍然能到达执行设备。
4. 在每一个事务边界杀进程后重启（包括 `needs_input` 的写入边界），都不会丢回执、不会重放副作用；`queued` 的任务能恢复执行；同一次调用重试 `start` 只会有一个任务；不同会话里出现相同的供应商工具调用 ID 时，会各自创建任务。
5. 执行过程中换到另一台设备说话：回执由新的负责设备转告；两台设备各自生成正文不同的转告时，不论同步顺序如何，最终都只显示一条，两份原文都保留在原始历史里；在另一台设备上回答或取消，能到达执行设备；执行设备离线时，状态显示正确；`notify=never` 的定时任务回执，在任何设备上都不会自动生成人设转告（`needs_input` 除外；回执本身照常存进原始历史）。
6. 在没有任务表的设备上，回执卡片和请求副本都能正确显示和回放。
7. 聊天模型最终的供应商请求体里，不带任何内置搜索参数，渠道额外参数里配置了也不例外。
8. 有排队任务、系统后台任务时关闭总开关，再重新打开，行为符合第 8 条。
