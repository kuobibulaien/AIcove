# 0038 记忆与上下文重构为短期／长期两层

日期：2026-09-23。状态：accepted（用户以 /goal 授权直接开工；开工前经 Codex gpt-6-astra 审查，已按审查意见修订本文）。实施后替代 ADR0004、ADR0007、ADR0024（已 superseded）、ADR0027。

## 背景

现状见[记忆与上下文压缩现状总览](../../../apps/aicove_flutter/docs/04_功能模块规范/记忆系统/记忆与上下文压缩现状总览.md)：旧向量四层库、角色 `MEMORY.md`、手动／自动／运行时三种压缩、记忆待写队列，分散在两个模块里，一共 11 个接口，开关一层套一层。用户要求重构成「像个正常 harness」的机制：有短期记忆和长期记忆，有手动压缩和自动压缩，压缩和记忆相互联动；旧记忆数据不需要兼容，从原始消息重新提取；向量库只作为可选项。

参考了 Claude Code、OpenClaw、Hermes Agent、Letta、mem0、Codex CLI、LangGraph/LangMem 和 SillyTavern 生态。它们的共同做法是：原文不动；常驻的一小块记忆每轮都带；记忆库需要时再检索；压缩时顺带整理记忆；记忆按「新增／更新／删除／不动」四种操作维护；默认用关键词全文检索，向量检索可选。

## 用户已确认（2026-09-23）

1. 长期记忆存 **SQLite 表 + 全文索引**，不再用 MD 文件作为真相源。
2. **删除全部记忆类派生数据**。原始聊天（`messages`／`message_blocks` 等）一条都不删，也不改。
3. **只在自动压缩和手动压缩时**允许维护和修改长期记忆，并且由**专门的记忆 Agent** 负责。聊天模型只管聊天，不获得任何记忆工具或上下文读取工具，避免工具调用污染聊天上下文。
4. 其余按推荐执行：日记功能随旧库一起删除；分批交付。
5. 窗口外检索本期只做关键词；向量检索只留接口，以后再写（2026-09-23 追加）。

## 决定

### 1. 两个服务、两个后台 Agent

```text
原始消息（唯一真相，不动）
├─ 上下文管理器 ContextManager（短期记忆）
│    请求内容 = 角色卡 + 长期记忆注入块 + 当前有效摘要 + 最近原文
│    · 自动压缩：有效窗口 80% 触发，保留约 16% 最近原文，其余交给压缩 Agent 写摘要
│    · 手动压缩：翻篇，新话题只带摘要，不带旧原文（旧格式不延续）；可预览、可编辑、可撤销
│    · 压缩前先在请求副本里截短超长工具结果（只截断，不另存原文，不提供 context_read；ADR0061 起改为保留最近 3 次、旧结果按时间换占位，代码待实施）
├─ 长期记忆库 MemoryStore（每个角色一份）
│    · 常驻层：约 2000 tokens，每轮都带
│    · 档案层：事实和往事，由代码按本轮对话检索，把最相关的几条注入（有 token 上限）
│    · 检索经 MemoryRetriever 接口；本期只实现 FTS5 关键词（BM25＋新近度），向量实现以后再接
└─ 联动
     压缩 Agent（无工具）→ 摘要落库 → 触发记忆 Agent（后台运行，不阻塞聊天）
     记忆 Agent 只有只读的 memory_search；变更以 JSON 输出，代码校验后连同书签一个事务写入
```

- **压缩 Agent**：只负责写摘要，没有工具。自动压缩必须等它写完摘要才能发送；手动压缩先给用户预览摘要。
- **运行时压缩保留**：工具循环每一轮请求模型之前都检查一次预算；超了就先截短过长的工具结果，还不够再以「闭合的工具调用组」为单位做摘要（只改这一次请求，不落库，也不触发记忆 Agent）。服务端明确报「超长」时，强制压缩后只重试这一次模型调用。
- 请求副本会把历史里 `memory_search`、`memory_read`、`context_read` 这几个旧工具的调用和结果成对过滤掉，原始历史不改。
- **记忆 Agent**：输入是一批还没处理过的原文、当前常驻层，以及按这批原文检索到的相关档案；只有一个只读的 `memory_search` 工具。它最后输出一组变更（新增／更新／删除），由代码校验后**和书签推进放在同一个事务里**写入，所以不存在「写了一半」或重复写的情况。
- **任务不会丢**：「需要处理到哪条消息」直接从 `context_summaries` 推算（手动摘要的边界、自动摘要覆盖到的最后一条），重建时另记重建目标。摘要一落库，任务就已经存在，不依赖「提交后再通知」；程序中途退出，下次压缩、发送或启动时会接着处理。
- **并发**：每个角色同时只有一个记忆任务在跑，按时间顺序一批一批处理。重建会让「重建代次」加一，旧任务在写入事务里发现代次变了，就放弃这次写入。写入时会重新检查锁定、删除状态和角色的记忆开关。撤销手动压缩只会缩小待处理的范围，已经写入的记忆不会回滚。
- 用户手动编辑过的条目会被锁定，记忆 Agent 只能读、不能改或删。
- 聊天请求里只注入记忆，不暴露任何记忆工具；插件工具（生图、语音等）不受影响。检索在发送前由代码完成，不调用模型，也不产生工具循环。
- 检索词取「本轮用户输入＋最近两轮对话」；排序用 BM25 相关度加新近度；结果按 token 上限截断。

### 2. 数据（SQLite v18，一次升级建齐）

整个重构只升一次版本到 v18，新表一次建齐，不拆成 B1=v18、B2=v19，避免重演「升了版本却缺表」。新增的表都通过专用 Adapter 的参数化 SQL 访问，建表语句各自独立：

| 表 | 作用 |
|---|---|
| `context_summaries` | 手动和自动摘要：owner、kind（manual/auto）、boundary_id（手动＝新话题边界；自动＝覆盖到的最后一条）、topic_boundary（所属话题的起点）、来源 ID 与指纹、正文、创建时间 |
| `memory_items` | 长期记忆条目：owner、layer（core/archive）、标题、正文、来源消息 ID、是否锁定、时间；不做软删除 |
| `memory_items_fts` | 档案检索用的全文索引（复用现有中文二元分词，由 Dart 写入） |
| `memory_progress` | 每个角色的提取书签（已处理到哪条消息）、重建目标、重建代次、暂停、最近错误 |

**旧数据退役**（`LegacyMemoryRetirement`，每次启动检查，幂等）：

1. 如果旧表或 `contact_memories/` 目录还在，先把 `memories`、`summarization_records`、`memory_tombstones`、`diaries`、`topic_handoffs`、`compaction_memory_jobs`、`runtime_context_records` 全部导出成 JSON，连同 `contact_memories/` 一起复制到 `ApplicationSupport/legacy_memory_backup/<时间>/`，并在写入后回读校验；
2. 把 `topic_handoffs` 里的**手动摘要**迁入 `context_summaries`（kind=manual），保证已有话题边界的衔接不断；自动摘要不迁（发送时按需重新生成）；
3. 以上都成功后，才删除旧表和目录。中途失败或退出，下次启动从第 1 步重做（导出目录按时间另建，不覆盖）。

`onUpgrade` 只负责建新表；旧表不在 v18 的 Drift 注册里，退役前仍留在磁盘上，也不再安装同步触发器。

保留：`messages.summarized` 字段（不再使用，不删列）；`conversations.context_start_message_id` 仍是话题边界。

**边界没有摘要时**（例如其他设备同步来的边界、迁移失败的历史）：发送前按需把边界之前的最近一段原文整理成手动摘要，保存后继续；整理失败就阻止本次发送并提示原因，不会把缺失的背景当成空白。

### 2.1 同步过渡

- 同步表清单去掉 `memories`、`summarization_records`、`memory_tombstones`、`diaries`、`topic_handoffs`，文件同步去掉 `contact_memories/`。
- 这些**已退役的 kind**：启动时清掉本地的 dirty、outbox、inbox 和 version 记录；上传时直接跳过；云端推下来的旧记录只清掉收件箱、推进进度，不写本地，也不回传删除。
- 同步载荷里的 `client_schema` 改用独立常量 `kCloudRowSchema`，表示「会同步的那几张表」的结构版本（当前为 17），不再跟整库版本绑定。这次没有改动任何同步表的列，所以 v17 和 v18 的设备之间能继续同步聊天。以后改动同步表的列时，要同时升这个常量。
- 新表暂不同步（放在 B5，需要改云端协议并部署，单独确认）。

### 3. 重新提取（从原始消息重建）

每个角色都可以发起「从聊天记录重建记忆」。先按字数估算要调用多少次模型、大约多少 token，用户确认后，按批次把原文交给记忆 Agent 执行，每批处理完推进书签，可以暂停、下次续跑。它和压缩后的记忆维护共用同一个 Agent 和同一个书签，不另写一套流程。

### 4. 设置和界面

- 新建「上下文与记忆」设置页：上下文窗口、压缩模型、记忆模型（默认与压缩模型相同）。向量开关和 Embedding 模型等 B4 实施时再加。长期记忆插件页只保留说明。
- 角色是否使用长期记忆，继续由该角色插件列表里的「记忆」决定（ADR0035）。
- 角色记忆页：分常驻和档案两栏浏览、编辑、锁定、删除，另有「从聊天记录重建」按钮。
- 删除日记页、记忆回收站页，以及和 MD 记忆相关的设置入口。

### 5. 云同步

`memories`、`summarization_records`、`memory_tombstones`、`diaries`、`topic_handoffs`、`contact_memory` 这几类数据客户端不再上传。新表先只存在本机，同步放到最后一批：需要改云端协议并部署，部署前单独确认。云端已有的旧记忆数据是否清理，也在那一批单独确认。

## 分批交付（每批可单独验收、单独回滚）

| 批 | 内容 | 验收要点 |
|---|---|---|
| B1 上下文管理器 | 用 ContextManager 替换三条压缩路径；v18 建齐新表；旧压缩表随退役流程备份后删除；去掉 `context_read` 和运行时原文存档；设置页收拢 | 真实 SQLite 验证：阈值等号、手动翻篇不带旧原文、自动压缩保留近期原文、撤销、编辑源消息后摘要失效、重放不倒灌；最终请求装配测试 |
| B2 长期记忆库与记忆 Agent | 新增 `memory_items`、全文索引和书签；记忆 Agent 与工具；每轮自动注入；删除旧四层库、日记、MD 记忆的代码与数据；新角色记忆页 | 角色隔离；锁定条目不可改；聊天请求中没有记忆工具；记忆 Agent 失败不阻塞聊天；注入不超上限；宽窄屏源码预览 |
| B3 重新提取 | 估算、确认、分批、暂停与续跑 | 中断后续跑不重复写；书签正确；处理大体量历史时不卡界面 |
| B4 可选向量（暂缓） | 本期只保留 MemoryRetriever 接口和 `memory_items` 的可空向量列，不实现 Embedding；以后用户决定时再实现混合检索 | 本期验收：关键词实现通过接口接入，替换实现时不需要改聊天链路 |
| B5 云同步 | 新表加入同步协议；旧类型下线；云端部署 | 单独确认后执行 |

B1～B4 作为一次版本发布（同一个 v18 迁移），按批提交；B5 需要部署，单独确认。

不在本期范围：主动关怀的「后台即时生成」自己读取和截取原文，不走发送装配，因此拿不到新摘要和长期记忆（预生成走发送装配，不受影响）。以后需要统一时再改。

## 代价

- 旧记忆数据（四层库、日记、`MEMORY.md`、自动摘要）删除后不能在应用内恢复，只能从 `legacy_memory_backup/` 的 JSON／MD 副本手动找回。
- 聊天模型不能主动翻档案。已经压缩出窗口的旧事，只能通过常驻层、摘要和代码按本轮话题检索出的档案条目进入上下文，检索没命中的这一轮就看不到；以后通过 MemoryRetriever 接入向量检索可以缓解。窗口内的原文不受影响，模型直接可见；这些内容在压缩时进入摘要，并同时交给记忆 Agent，中间没有遗漏的空档。
- 重新提取要把历史全部过一遍模型，费用和时间与聊天记录总量成正比。
- 在 B5 完成之前，新记忆和摘要只保存在本机；现有的导入导出本来就不包含记忆。角色记忆页提供「复制全部记忆」，作为临时的手动备份。

## 回滚

每批单独提交。回滚代码不会降级 schema：旧表删除后不会自动恢复，需要的话从 `legacy_memory_backup/` 里的 JSON 和 MD 副本手动找回。退回旧版本之前，必须先恢复这些备份。原始聊天全程不受影响。
