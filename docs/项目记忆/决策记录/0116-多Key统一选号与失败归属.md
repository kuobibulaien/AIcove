# 0116 多 Key 统一选号与失败归属

## 背景

聊天已有多 Key 策略，后台 Agent、TaskAgent 和网页 AI 却另取首个 Key；预览还会消耗轮询位置。整轮执行的 catch 无法区分模型、工具、预设和嵌套摘要的失败，锁外生成设置补丁也会覆盖并发计数或用户换过的新 Key。

## 决定

1. 模型请求统一经 `ChatRequestConfigBuilder` 解析。实际请求构建默认消费轮换；上下文预览、主动回复前置可用性检查显式使用 `consumeKeyRotation: false`。只读随机策略取首个候选，不改变实际请求的随机策略。沿用健康／启用候选、全错误重试、旧列表和 direct 兜底规则，不新增必须有 Key 的门禁。
2. `BackgroundAgentRequestConfig` 保留旧构造入口，新增 Key item ID、原始索引及策略。后台、TaskAgent、WebApp 完整传入 `ApiConfig.providerId` 与上述身份；旧注入 DTO 未填 providerId 时从完整模型引用推导，避免静默变成 OpenAI。
3. 四个执行入口使用 `executeWithProviderKeyFailureRecording`。每个入口建立独立的 `ModelRequestFailureTracker` Zone，真实模型 HTTP／响应体读取／SSE 上游错误登记原异常对象。仅当前入口拥有且最终抛出的异常可落账；嵌套摘要属于子请求，不误记父请求。保留异常原类型、对象和堆栈，不包装 Timeout／Socket，不更改 retry／诊断合同。
4. 继续只对 `exhaust` 策略记录失败并切换；Kernel 内部重试或流式回退最终成功不落账。计数单位是一次失败的执行入口：摘要业务层修改额度后另发请求属于新的执行，先前真实失败记录保留。取消异常、已取消令牌、本地配置／脚本／工具异常不计 Key 故障。
5. `AppSettingsNotifier.recordProviderMultiKeyFailure` 在设置事务内先 reload 偏好缓存、现读存储，再核对最新策略与身份生成补丁。指定 item ID 时必须仍存在且 Key 相同，不向别的同值 item 降级匹配；无 ID 的旧配置保留索引／Key 兼容。失败计数不清空思考能力探测记忆；记账存储失败不覆盖原模型异常。

## 代价

轮询游标仍是当前 isolate 的进程内状态，不承诺跨 isolate 共用一个持久化游标。新增请求来源追踪仅服务失败归属，不是另一套模型执行器。前端、插件注册和模型循环收拢留给后续步骤。

## 验收门

`tool/flutterw test --no-pub` 的 16 个相关测试文件分批共 172 项通过；其中新增流水线测试覆盖真实上下文预览、四入口身份／失败记账、嵌套压缩同渠道与跨渠道隔离、并发计数、跨 isolate 偏好缓存刷新与换 Key 保护、取消、超时类型和回退恢复。保留 WorkManager 的 `prefs.reload()`。未改 UI，未运行付费模型或装机。
