# 编辑草稿与分支提交分离

## 背景

用户在聊天真相源审计后确认修复编辑取消丢历史。旧 editMessage 在回填输入框前截断 raw 后缀；草稿没有原消息锚点，取消/退出不能恢复。用户确认“编辑只是草稿，确认发送才改变历史；本地提交后AI失败保留新分支重试”。

## 决定

1. 进入编辑不写历史。ChatEditPort 从同一 DB 快照准备 owner、raw 用户消息ID、历史版本与回填原文；UI 不使用投影文本充当编辑后的原文。
2. 草稿沿用按联系人隔离的 SharedPreferences JSON，增加 edit 标识，保留旧格式读取。回填按owner传递，空文本/空附件也替换旧输入。取消只清草稿；损坏标识或缺失编辑附件阻止发送，不能降级成普通发送。
3. 确认发送时验证owner、忙碌状态、raw版本及话题边界，再用同一SQLite事务软删旧后缀、插入新用户消息/blocks、更新预览。版本改变、写入失败或重复提交均拒绝，保留旧历史和草稿。原记录不物理删除。
4. 本地提交与模型完成分开：Composer只在收到本地受理后清草稿；模型随后失败，已提交消息标记失败可重试，不自动回到旧分支。失败响应不能自动再次提交旧编辑。普通发送方法签名和重生成语义不改变。
5. 本批保守拒绝旧话题/压缩边界之前的编辑，避免无效marker令旧上下文回流；跨话题重放与已提交后的撤销需独立设计。

## 代价与限制

- 历史版本目前对当前会话有效raw行、blocks和边界做完整SHA-256校验；优先防止旧草稿覆盖新消息，但长历史读取/哈希成本待优化，不宣称点击性能已解决。
- 草稿字段变更不升级SQLite schema或备份格式。SharedPreferences不是与聊天DB同库事务；提交后若崩溃、清草稿失败，旧草稿可能还在，但原版本校验会阻止重复提交。最新500ms内的输入仍可能因进程强杀而未保存，原历史不会因此丢失。
- DB提交后的时间线刷新独立执行；刷新失败不把已成功提交误报为可安全重试的失败，重新进入可从DB恢复。未实现整组UI缓存与DB跨层原子回滚。
- 不修改插件配置、云同步、重新生成回放，不修复已经丢失的数据。

## 实现与验收

客户端 `lib/src/features/chat/application/chat_edit.dart` 定义契约；`ChatHistoryStoreAdapter` 适配；`ChatHistoryStore.prepareEdit/commitEdit` 提供快照校验与事务；`ChatActions.submitEditedMessage` 复用文字/图片/文件发送内部链路；`Composer` 提供取消、持久草稿与确认受理。

测试：`test/features/chat/chat_edit_commit_test.dart`（事务、过期、重复、话题边界及三种真实发送门面）；`test/features/chat/presentation/widgets/composer_draft_persistence_test.dart`（360/1000px、取消、重建、坏标识、跨owner、受理前后草稿）；既有A03由失败转通过。构建/完整回归与未验项写入本次需求日志，不以契约通过代替真机验收。

回滚：仅撤本批代码，保留DB及草稿文件；旧版本不理解edit标识时不得自动重发这些草稿。回滚不自动恢复已提交旧分支，必要时先把编辑入口禁用，禁止清库或覆盖其它并行改动。
