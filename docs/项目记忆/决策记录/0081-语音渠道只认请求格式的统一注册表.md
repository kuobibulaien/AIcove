# 0081 语音渠道只认请求格式：统一的语音格式注册表

- 状态：accepted（2026-10-14 用户确认：新增「自定义 REST」格式；删除硅基流动语音格式，旧数据迁成 OpenAI TTS）
- 日期：2026-10-14
- 关联：ADR0008／0009（插件预设与音色预设）

## 背景

语音渠道的协议是三套逻辑拼起来的。添加页有一份语音格式列表，详情页只认识对话和绘图格式，合成时又按 requestFormat、渠道 id、网址关键字和模型名四种方式猜厂商。渠道类别则由模型名推断，Fish Audio 的 `s2.1-pro` 推断不出是语音模型，内置 Fish 渠道就被归成了对话渠道。结果是：详情页只能在 OpenAI、Claude、Gemini 三种对话格式里选，还显示对话用的 `/chat/completions` 路径；语音模型选择器里看不到 Fish 的模型；阿里云要靠网址才能认出来。

## 决定

1. **唯一注册表**：`TtsRequestFormat`（`features/plugins/tts/tts_request_format.dart`）列出全部语音格式：OpenAI TTS（`openai_tts`）、MiniMax、阿里云（`aliyun`，合成时按模型名分成 CosyVoice 和 Qwen-TTS）、Fish Audio、自定义 REST（`custom_rest`）。添加页、详情页的格式切换、存储规整和合成路由都从这里读，旧别名也在这里映射。
2. **只认 requestFormat**：`TtsProviderFactory.resolve` 和 `TtsService` 只按渠道的 `customConfig.requestFormat` 路由，不再按网址、渠道 id 或模型名猜。
3. **存储规整（每次读写设置时执行，可重复执行）**：
   - 旧别名改写为规范值，例如 `siliconflow_indextts` 改成 `openai_tts`、`fishaudio` 改成 `fish_audio`。
   - 纯语音渠道没写格式时，按网址补一次厂商格式。
   - 纯语音渠道，以及 Fish、自定义 REST 这两种模型名推断不出类型的格式，渠道里所有没有手动设置类型的模型都写成 `tts`，渠道能力随之变为语音。
   - 同时带对话和语音模型的混合渠道仍按模型名推断。
4. **详情页**：语音渠道可以在全部语音格式之间切换，不显示对话 API 路径和额外请求参数。选自定义 REST 时出现「请求模板」，模板 JSON 存在 `customConfig.tts_template`，包含 path、headers 和 body，支持 `{text}`、`{voice}`、`{model}`、`{speed}`、`{apiKey}` 占位符。
5. **删除硅基流动语音**：专用的合成适配器、音色上传服务和音色管理 Provider 一并删除。硅基流动的 `/audio/speech` 本来就兼容 OpenAI，所以旧渠道迁到 OpenAI TTS 后，系统预置音色和已上传音色的 URI 仍然可用。`VoicePreset` 里 `siliconFlow*` 相关字段保留，只用来读取旧数据。

## 代价

- 硅基流动的参考音频实时克隆（`references`）和上传音色功能没有了。只配了参考音频、没配音色 ID 的旧预设会提示「请填写音色 ID」。
- 自定义 REST 只支持「POST JSON、响应直接是音频」这一种形态。需要轮询任务、走 WebSocket 或返回 JSON 里嵌音频的厂商，还得单独写适配器。
- 语音通话仍然只支持 Fish 的实时接口（ADR0074），这次没有扩展。

## 验收门

- 离线：注册表别名与规整规则、Fish／旧渠道／混合渠道的存储规整、详情页格式列表、自定义 REST 端到端请求，这些都有测试，全量测试通过。
- 待实测：真机上内置 Fish 渠道在语音模型选择器中出现并能合成；自定义 REST 接入一家真实厂商。
