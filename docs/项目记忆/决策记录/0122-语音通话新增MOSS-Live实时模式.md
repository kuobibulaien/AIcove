# 0122 语音通话新增 MOSS-Live 实时模式：端到端引擎与级联流水线并存

- 状态：proposed（2026-11-12 用户试听克隆音色后确认方向「很像，写 ADR」；以下实现细节由 AI 拟定，已经 Codex 只读复审并按意见修订，待用户审阅；未施工）
- 日期：2026-11-12
- 关联：ADR0074（语音通话级联流水线；本文为其「通话与语音条同一音色」硬约束开一个例外，见决定 3）、ADR0090（通话派活）、ADR0088（杂活 Agent 派活）、ADR0084（按会话只由一台设备负责）、ADR0081／0082（语音与识别格式注册表）、ADR0116（多 Key 选号）、ADR0038（记忆唯一真相在本地）

## 背景

ADR0074 没有选端到端语音模型，理由有两条：音色只能用模型自带的，带不走用户的音色预设；还要另起一个「大脑」，人设、预设、世界书、记忆这些链路就都绕开了。级联流水线的代价是延迟：从说完话到听见首块音频，实测 2.5～3.1 秒；而且桌面没有回声消除，只能半双工。

MOSS-Live 1.0（OpenMOSS／模思，2026-11-07 发布，接口 `wss://api.mosi.cn/v1/realtime`，Beta，限时免费）是全双工实时语音模型。它能按语义判断用户是否说完，也能分辨是不是在对它说话，评测里对「在跟别人说话」的误接话率为 2%。它还支持把任务委派给客户端的后台执行。协议以[官方接口文档](https://platform.moss.cn/docs/reference/moss-live)为准。

2026-11-12 用真实 Key 实测（探针脚本不入库，过程见需求日志 #2423）：

| 项目 | 结果 |
|---|---|
| 克隆音色 | 用户 27 秒录音调 `POST /v1/audio/voices` 克隆，再在实时会话里 `change_voice`，服务端回 `voice_changed`，无报错 |
| 音色是否生效 | 回复的基频中位数为 286 Hz，参考录音 281 Hz，默认音色 246 Hz；用户试听确认「很像」 |
| 首包延迟 | 输入语音结束到收到首块音频 0.94～1.29 秒（Mac，单次） |
| 转写 | 服务端同时给出用户和角色两侧的转写，用户这句识别全对 |

第一条理由**部分缓解**：音色可以从同一段参考音频克隆，声音相近，但和语音条的音色不完全一致（见决定 3）。第二条仍然成立，需要在设计里接受或补偿。

## 备选

- **用 MOSS-Live 替换级联流水线**：会丢掉自选模型和预设逐轮装配，也没法打字插话。不采用。
- **只把 MOSS 当成又一家 TTS 接进级联**：MOSS 另有 `moss-tts-1.5-flash` 流式合成，可以以后按 ADR0081 单独接；但这样拿不到全双工和语义判停，解决不了延迟。不在本文范围。
- **新增实时模式，与级联并存，按角色选择**：采用。

## 决定

### 1. 两种通话引擎，按角色选

- 角色的通话设置新增「通话方式」，有两档：「标准」（现有级联，默认）和「实时（MOSS-Live）」。存储位置和同步口径与角色的语音设置一致。
- 三类条件分开判断：
  - **能选实时模式**：已配置 MOSS 渠道（渠道商新增 MOSS，接口地址 `https://api.mosi.cn`）；角色的音色预设已有可用的 MOSS 音色（见决定 3）。不满足时，选项灰掉，并用一句话说明缺什么，不等到接通时才报错。
  - **能发起通话**：与标准模式相同，全局语音开关和角色语音开关都开着（ADR0074 决定 8）。
  - **能派活**：见决定 5。
- 实时模式不用识别来源设置（ADR0082）：MOSS 自己听，自己转写。

### 2. 引擎边界：抽出通话会话接口

- `ActiveVoiceCall` 目前用到会话的这些成员：`start`、`hangUp`、`phases`、`partialTranscripts`、`transcript`、`transcriptChanges`、`muted`、`speakerOn`、`sendText`。施工时先核对其他调用方（悬浮窗、桌面小窗镜像、`connectedAt` 等），再定下最小接口 `VoiceCallEngine`；`ActiveVoiceCall` 改为只依赖它。现有 `VoiceCallSession` 作为级联实现，行为不变。
- 新增 `MossLiveCallEngine`，复用 `CallAudioInputPort`（16 kHz 单声道 PCM16，正好是 MOSS 默认的上行格式）和 `CallAudioOutputPort`。下行用 `media.configure` 设为 PCM16 24 kHz，和 Fish 现在的播放链路同一采样率，省掉重采样。
- 协议细节全部关在这个实现里：建会话、配置、音频二进制帧、播放回执、打断、保活、重连。会话生命周期、悬浮窗、桌面小窗镜像、通话气泡这几层都不认识 MOSS。
- MOSS 的 WebSocket 和克隆请求都要接入 ADR0116 的选号与失败记账：新增 MOSS 的执行入口，不能因为引用了 ADR0116 就当作已覆盖。音色绑定的账号约束见决定 3。

### 3. 音色：从音色预设的参考音频克隆，一次克隆反复用

- **这是 ADR0074「通话与语音条同一音色」的例外，需要用户确认。** 同一段参考音频在 Fish 和 MOSS 各克隆一份，两边声音相近，但不保证完全一致。设置页要用大白话写明这一点。
- 音色预设新增 MOSS 音色绑定，包含三项：`voiceId`；创建时用的渠道 id 和 Key 指纹（Key 的哈希，不存明文）；克隆时参考音频的指纹（文件哈希）。绑定随音色预设同步。
- 来源只有一个：音色预设里已有的参考音频（`localAudioPath` 或 `promptAudioUrl`）。用户在音色预设页点「为实时通话生成 MOSS 音色」，宿主取参考音频，转成单声道 WAV，超过 30 秒就截取前 30 秒（接口限制：30 秒、10 MB），然后调 `POST /v1/audio/voices`，把返回的 ID 存进绑定。按钮旁写明「参考音频会上传到 MOSS」。
- 只有供应商音色 ID、没有参考音频的预设，不能生成 MOSS 音色，实时模式选项灰掉并说明原因。
- 参考音频指纹只在本机能读到这个文件时核对；对不上时提示「参考音频已更换，需要重新生成」，不会悄悄沿用旧音色。别的设备没有这个文件时，直接用已同步的 `voiceId`。
- 克隆音色属于创建它的 MOSS 账号。接通时只用绑定里记下的那把 Key，不参与多 Key 轮换；那把 Key 被删了，就提示重新生成。
- 接通时先发 `change_voice`，收到 `voice_changed` 后再开麦。出错时**不退回默认音色**，因为用错声音比打不通更糟；但要按错误分开提示：错误码表明音色不存在或不可用时，提示重新生成；鉴权、网络、限流等错误照实提示，不要求重新生成。错误码要在实测里收集。

### 4. 人设与上下文：接通时一次性压进去

- 接通时仍然调用 ADR0074 决定 2 的同一个装配入口（`prepareApiConfig`，`persistSideEffects: false`），拿到同一份请求消息列表。装配结果里预设内容、宏展开和占位已经混在一起，**不尝试还原成「角色卡、规则、世界书、记忆」几类**，而是按以下规则拍平：
  - `session.persona`：`name` 填角色名；`prompt` 只填角色卡本身（直接从角色数据取，不从装配结果里拆），上限 8000 字，超出时截尾并记诊断日志。
  - `session.instructions`：先放固定的通话约束（口语短句、不出 Markdown 和插件标签），然后把装配后的消息按原顺序、带角色标签序列化。上限 16000 字，其中预留 2000 字给后台摘要。
  - **超长时的裁剪顺序**：通话约束不动；先从最旧的对话原文开始，按整条删除；原文删光了还超长，再从后往前按整条删预设和系统消息，并记诊断日志说明删掉了几条。字数按 Unicode 字符计。
  - 接通前摘要在后台整理（ADR0074 原逻辑）。整理好以后，用一次 `session.instructions.append` 补进去，只补一次，上限 2000 字，并检查回执确认。
- `client_context.update` 上报设备时区，不上报位置。
- 不开 MOSS 的服务端长期记忆（`memory_scope` 保持默认的 `session`）。记忆的唯一真相仍在本地（ADR0038），不往第三方再存一份。
- 明确接受：实时模式下，回复由 MOSS 自己的模型生成，不用用户选的聊天模型；预设和正则不会逐轮重新装配；世界书只按接通时的上下文命中一次，通话中途提到的新关键词不会触发。设置页的说明文字要用大白话讲清楚这几点。

### 5. 派活：用 MOSS 的客户端委派对接杂活 Agent

**启用条件**：与 ADR0090 第 1 条一致，必须同时满足：角色模式允许派活（ADR0120）、派活开关和杂活总开关都开着、角色授予杂活 Agent 的实际权限不为空。不满足时，`attach_session` 不带委派，通话里只聊天。

**交接映射**：

- 接通时按 ADR0084 认领该会话的负责设备（`claim`），与 ADR0090 第 6 条相同。
- 收到 `session.delegation.created` 时，用 `delegation.id` 当作幂等键，调用 ADR0088 的杂活启动入口（与 `delegate_task start` 同一个持久化入口），并把「MOSS 会话 id、委派 id ↔ 本地任务 id」写进 `callRecord.tasks`。同一个委派 id 重复到达，只启动一次。
- `purpose` 为 `reasoning` 时同样启动杂活，只是 MOSS 会在 `timeout_ms` 内等结果；超时后任务照常在后台跑。
- 进度和结果用 `session.commentary.append` 回传：进度用 `in_progress`，结果用 `completed`／`failed`，带 `delegation_id`；`event_id` 取「任务 id＋回执序号」，重试时复用同一个 id 和同一份内容。超过 2000 字先摘要。收到 `presentation_capacity` 错误时，回执留在本地，稍后重试。
- 收到 `session.delegation.cancelled` 时，按 ADR0088 取消对应任务，并丢弃它之后的回执。

**通话前派出的任务**：这些任务的回执在通话期间由通话接管（ADR0090 第 4 条），用不带 `delegation_id` 的会话级 `commentary.append` 送进去。

**转告完成的判定**：收到 `session.commentary.appended` 回执，就算这条回执已转告。MOSS 会自己选轮次边界说出来，所以实时模式**不实现** ADR0090 第 3、4 条里自管的等待集合和输入队列。代价是：收到回执后、角色还没说出口时就挂断，这条结果会被当成已转告；`callRecord.tasks` 记下回执时间，代码写入的任务状态行照常提示。

**追问（`needs_input`）**：MOSS 没有「回答某个委派」的接口，所以第一版不在电话里续答。收到追问时，用 `commentary.append` 让角色告诉用户「这件事要你补充信息，挂断后在聊天里回我」，任务保持等待输入状态，挂断后按 ADR0088 在文字聊天里转告。

**挂断与断线**：挂断不取消任务。没收到 `appended` 回执的回执，退回 ADR0088 的文字转告。断线时先按 `session.closing.data.reconnect` 用原 `session_id` 重连一次；重连失败按挂断处理。

**摘要**：通话摘要 Agent 的输入带上任务事件，和 ADR0090 第 5 条一致。

**前台工具**：不开放自定义工具（`session.tools`）。生图、提醒这类工具仍不进通话，与 ADR0090 第 1 条一致。

### 6. 播放回执与逐句记录

- 现有 `CallAudioOutputPort.played` 是按推入时长和墙钟**估算**的，不是播放器回报的真实进度。实时模式给每个 `response.audio.context` 建一张台账：`run_id`、`turn_id`、`chunk_id`，以及这块音频在本轮累计时长里的起止位置。估算进度越过某块的终点，就发 `playback.chunk.completed`；`response.audio.done` 之后全部越过，就发 `playback.completed`。收到 `response.audio.stop` 时清空播放队列，先补发已越过的块，再用 `played_audio_ms` 报当前那块已播的毫秒数。
- 关掉扬声器时，进度照常走（与现有 `silenced` 语义一致），按「已播出」上报。也就是说，「播出」不等于「用户听到」，这一点与标准模式口径相同。
- 逐句记录：`input.transcript.done` 和 `output.transcript.done` 记为 `CallTurn`；收到 `input.transcript.revised` 时，按 `turn` 原地更新那一句。被打断的一句，先用 `response.interrupted.data.text`；文档没有保证它等于用户实际听到的部分，所以验收时要对照播放台账核实。对不上时，改用 ADR0074 决定 5 的做法，按已播时长估算前缀。
- 挂断后的存档、通话气泡（`CallRecordBlock`）和同步不变。气泡记下这通电话用的是哪种方式（`callRecord.engine`）；旧客户端不认识这个字段，会直接忽略。

### 7. 全双工与回声

- 实时模式要求一直上传麦克风。新增一个按设备保存的开关「防回声（角色说话时不听你说）」：打开时，角色说话期间只发静音帧，等于半双工，不能插话；关闭时是全双工。
- 默认值：桌面**打开**，因为没有回声消除；手机在系统语音处理实际启用时**关闭**，否则打开。是否启用以 `callVoiceProcessingSupported` 和编译开关 `AICOVE_CALL_NO_VOICE_PROCESSING` 的结果为准。开关旁写「戴耳机时可以关掉，就能随时插话」。行为由用户选，不在背后悄悄改变。
- 「关话筒」发送 `{"action": "mic_state", "enabled": false}`；「关扬声器」只在本地静音。

### 8. 打字

- MOSS 没有直接塞一段文字进对话的接口，所以实时模式下，通话页和悬浮窗不显示「打字」入口（ADR0074 决定 9 只在标准模式下有效）。
- 不拿 `session.commentary.append` 冒充用户发言：那是给后台结果用的通道，语义不对，模型也会把它当成系统消息。

## 代价

- 实时模式下，角色的口吻和知识取决于 MOSS 的模型和拍平后的人设。复杂预设、按轮触发的世界书、正则这些都打折扣，同一个角色在两种模式下会有差别。
- 通话与语音条不再保证同一音色（决定 3 的例外）；没有参考音频的音色预设用不了实时模式。
- 依赖单一供应商的 Beta 接口，「限时免费」以后会收费，协议也可能变。所以把它整个关在一个引擎实现里，出了问题只影响实时模式。
- 克隆音色绑定在一个 MOSS 账号的一把 Key 上，换 Key 就要重新生成；参考音频会上传到 MOSS 的服务器。
- 转告完成以 `appended` 为准，存在「已转告但没说出口就挂断」的窗口；`needs_input` 第一版只能挂断后在文字聊天里续答。
- 桌面默认半双工，要戴耳机并手动关掉「防回声」，才能用上全双工插话。
- 引擎接口抽出来以后，`ActiveVoiceCall` 和两种实现都要补测试，改动面在 ADR0074 和 0090 的代码上。ADR0090 本身还是 proposed，派活部分要等它确认后一起施工。

## 验收门

1. 抽出接口后，标准模式行为不变：现有通话测试全部通过，`ActiveVoiceCall` 不再引用具体实现类。
2. 音色：有参考音频的预设能生成 MOSS 音色并保存绑定；换了参考音频后提示重新生成；只有远端音色 ID 的预设，实时模式选项灰掉并说明原因；在另一台设备上用同步过来的绑定能接通；音色失效与鉴权、网络错误的提示分开，都不退回默认音色。
3. 用真实 Key 实测：接通后角色用克隆音色说开场白；从说完话到听见首块音频不超过 1.5 秒（Mac 戴耳机，取 5 次中位数）；关掉防回声后用户插话，角色在 1.5 秒内停下。
4. 播放回执：台账发出的回执不引起 `error` 事件，服务端也不因等不到回执而报播放超时（`response.interrupted.data.reason`）；打断后逐句记录里的那句，与按台账估算的已播前缀一致，或在不一致时按决定 6 回退。
5. 人设拍平：超长角色卡和预设按决定 4 的顺序裁剪，`session.updated.data.error` 为空，摘要追加不触发 `instructions_full`；角色自称和口吻与角色卡一致，不再自称「小默」。
6. 派活：用户在电话里让角色查东西，委派 id 重复到达只启动一次，结果回来后角色在轮次边界主动说出来；通话前派出的任务，结果在通话中转告；`needs_input` 在电话里只提示，挂断后在文字聊天里转告；挂断时没收到 `appended` 的结果在文字聊天里转告一次。两台设备同时在线时，回执只由通话设备认领。
7. 挂断后通话气泡、逐句记录、摘要（含任务事件）和同步与标准模式一致；旧客户端打开带 `callRecord.engine` 的气泡不报错。
8. 手机外放、Mac 戴耳机、Mac 外放各实测一次：分别记下系统语音处理是否真的生效、关掉防回声后会不会自己打断自己，据此确认决定 7 的默认值。
