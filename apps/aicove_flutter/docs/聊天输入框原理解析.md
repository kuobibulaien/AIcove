# 聊天输入框 (Composer) 架构与机制

> 更新日期：2026-04-01

本文档详细解析了 AIcove 中复杂的多功能聊天输入框 (`Composer`) 的实现原理。
主要代码文件位于 `lib/src/features/chat/presentation/widgets/composer.dart`。

## 1. 核心职责
`Composer` 承担了聊天界面的最底层核心交互功能，包括：
- **面板平滑切换**：键盘和自定义更多面板（More Panel）之间的无缝切换交互。
- **动态高度自适应**：保证输入框随键盘高度变化而弹起，不会被遮挡。
- **多模态输入集成**：支持文本输入、附件（图片/文件）选择并发送、以及回复引用消息。
- **全平台输入焦点兼容**：兼容移动端（软键盘）和桌面端（物理键盘），并对桌面端的“焦点抢夺”问题做了特殊处理。

## 2. 键盘与面板平滑切换原理
聊天对话框常见的痛点是“键盘与应用内的自定义面板相互切换时，会发生高度跳变（闪烁/收起再弹出）”。本项目引用了 `chat_bottom_container` 库作为核心状态管理。

### 状态机管理
输入框下方的空间被称为“面板（Panel）”，存在三种互斥的状态：
- `none`：无面板（只有底部的安全区）。
- `keyboard`：软键盘面板。
- `other`（或内部称为 `more`）：自定义更多功能面板（如附件选择、模型切换）。

### 高度冻结机制 (`_holdPanelHeight`)
在从“键盘”切换到“更多面板”的过程中，原本屏幕上的软键盘会经历一段收起（高度减小到0）的系统动画，而更多面板正准备展开。
如果是依赖于原生的 `viewInsets.bottom`（键盘遮挡高度）监听，输入框会跟着系统键盘一起掉下去（高度清零）然后再弹起来（变成面板高度），导致整个界面跳跃。

**解决方案（锚点锁定）：**
1. 记录此时软键盘处于最高状态下的高度值 `_anchorPanelHeight`。
2. 将布尔值 `_holdPanelHeight` 设为 `true`。
3. 在系统键盘慢慢收起（下降）的过程中，我们在获取面板高度 `_morePanelHeight(context)` 的函数里添加条件判断：不再盲目听从逐渐缩小的系统键盘高度，而是让面板**死死咬住**那个 `_anchorPanelHeight` 锚点高度。
4. 从而保住了这块扩展面板展开时的尺寸不被清零，彻底消除切换缝隙。

```dart
// 核心代码片段示例
double _morePanelHeight(BuildContext context) {
  final liveInset = _liveKeyboardInsetLayout(context);
  // 关键修正：处于冻结状态（切换中）时，不再让减小的 liveInset 覆盖锚点高度
  if (liveInset > 0 && !_holdPanelHeight) {
    _keyboardHeight = liveInset;
    _anchorPanelHeight = liveInset;
  }
  // 强制返回锁定（最大化）的高度...
}
```

## 3. 焦点粘性与桌面端兼容
由于 Flutter 对于 Android / iOS 是通过软键盘事件反馈，而对于 macOS / Windows 更多是基于物理键盘操作，焦点的管理尤为复杂。

### 焦点防抢夺难题 （`_intentionalUnfocus`）
在桌面端或部分特殊输入法（如语音输入弹窗）激活时，Flutter 输入框会经历一次**被动失焦**。由于失去了焦点，`chat_bottom_container` 库内部会认定为用户结束输入，自动将状态切换成 `none` 收起输入框。

**解决方案：**
在 `initState` 中添加一个特殊的监听器 `_onDesktopFocusChange`，进行**防误伤恢复**：
- 如果发现了失去焦点事件，先判断它是不是我们代码里主动调用的 `unfocus()` 操作触发的（由 `_intentionalUnfocus` 标志记录）。
- 如果不是主动调用的（那就是被动失焦拉跨了），延时 100ms 复查一轮。
- 如果焦点没有跑到页面里的其他文本框，代码将主动调用 `.requestFocus()` 把光标抢回来，使得 UI 输入状态保持稳定。

## 4. 后续维护排错指南
如果你在聊天界面遇到了相关 BUG，请首选检查 `composer.dart` 这个“大管家”文件：

1. **点击加号，更多面板弹不出来、半道被系统键盘收回顶掉**
   - 此时问题百分百出在高度计算逻辑。检查 `_holdPanelHeight` 的赋值时机，以及 `_morePanelHeight` 计算逻辑中那个限制条件是否还在工作！
   
2. **点下更多后，输入法莫名其妙失去焦点，需要点两下才能打字**
   - 检查是否有地方意外调用了 `inputFocus.unfocus()`。或者是 `chat_bottom_container` 框架包由于配置问题强行改掉了焦点状态（检查 `ChatBottomHandleFocus.requestFocus` 参数是否正确传递）。
   
3. **桌面端发送后，或者语音输入中断后，光标焦点丢失了需要自己点一下屏幕**
   - 说明桌面端的防御被击穿了，检查 `_intentionalUnfocus` 这个标志位是不是哪里设成 `true` 忘了改回去，导致延时抢夺焦点的计时器没起作用。

## 5. 发送按钮保护（生成中拦截）
从 2026-02-24 开始，发送按钮增加了“生成中保护”：

- 当 AI 正在生成时，发送按钮会从 `↑` 切换为 `暂停` 图标。
- 点击该按钮不会直接发送新消息，而是弹出确认框：
  - `继续生成`：关闭弹窗，不做任何改动。
  - `停止`：中断当前生成任务，并把输入框恢复到可继续发送的状态。
- 输入框依然允许提前输入文字，但发送动作会被拦截，避免“上一条还没生成完就把下一条发出去”。

### 相关文件职责
- `lib/src/features/chat/presentation/widgets/composer.dart`
  - 负责按钮图标切换、点击拦截、确认弹窗交互。
- `lib/src/features/chat/chat_actions.dart`
  - 负责真正的“停止生成”逻辑（将当前生成标记为中断，并丢弃后续结果）。

## 6. 模型列表来源与禁用渠道过滤（2026-02-27 修复）
本次修复针对“已禁用渠道的模型仍出现在聊天输入框模型选择列表”问题。

### 功能和文件对应
- `lib/src/features/chat/presentation/widgets/composer.dart`
  - 职责：聊天输入框“选择模型”弹窗。
  - 读取来源：`settings.modelList`，自己不做渠道过滤。
- `lib/src/features/settings/app_settings.dart`
  - 职责：把存储层数据映射为 `AppSettings`，并汇总 `modelList/defaultModelName/defaultChatModels`。
  - 修复点：在 `_calculateModelMeta` 中跳过 `provider.enabled == false` 的渠道，避免禁用渠道进入可用模型列表。
  - 修复点：清理 `default_chat_models` 中失效模型，防止禁用渠道残留模型继续进入默认轮询链。

### 排查口诀（给小白）
- 模型弹窗里出现了不该出现的模型：先看 `composer.dart` 是否读取 `settings.modelList`。
- `settings.modelList` 内容不对：去看 `app_settings.dart` 的 `_calculateModelMeta` 是否正确过滤 `enabled`。

## 7. 模型选择弹窗的默认队列拖动排序（2026-04-01）
聊天输入框“更多”面板里的模型选择器，现在分成了两段：

- **默认队列**：显示 `default_chat_models` 中仍然可用的模型，首位就是当前默认模型。
- **其他可用模型**：显示 `settings.modelList` 里剩余的可见模型。

### 行为规则
- 长按拖动“默认队列”项，会直接重排 `default_chat_models`。
- 重排后首位模型会同步写回 `default_model`，因此不仅影响当前默认模型，也影响失败后的自动切换顺序。
- 点击“其他可用模型”中的任意项，会把该模型提升为当前默认模型，并插入默认队列队首。

### 相关文件职责
- `lib/src/features/chat/presentation/widgets/composer.dart`
  - 职责：从更多面板打开模型选择器，并在用户点选模型后切换当前默认模型。
- `lib/src/features/chat/presentation/widgets/composer_model_picker_sheet.dart`
  - 职责：渲染“默认队列 + 其他可用模型”两段式弹窗，并在拖动排序后持久化队列。
- `lib/src/features/settings/app_settings.dart`
  - 职责：提供 `setDefaultChatModels` / `setDefaultModelName`，把排序和选中结果写回本地设置。

### 排查口诀（给小白）
- 拖动后顺序没保存：先看 `composer_model_picker_sheet.dart` 是否触发了 `setDefaultChatModels`。
- 点了其他模型却没提到队首：先看 `composer.dart` 是否在弹窗返回后调用了 `setDefaultModelName`。
- 弹窗里队列和设置页顺序不一致：先看 `app_settings.dart` 里的 `default_chat_models` 是否已经被正确规范化。

## 8. 草稿持久化与附件恢复（2026-03-23）
聊天输入框的草稿现在不再只保存纯文本，而是统一保存为“当前会话维度的草稿快照”：

- **作用域改为按会话隔离**：草稿 key 从旧的全局 `composer_draft_text` 升级为 `composer_draft_v2:<conversationId>`，避免不同角色/会话之间串草稿。
- **内容改为文本 + 附件一起存**：除了输入框文字，还会把当前待发送的 `SelectedAttachment` 一并写入 `SharedPreferences`。
- **图片会先转成可恢复的本地路径**：用户从相册/相机选中的图片，会优先复制到应用内的 `composer_drafts` 目录，再把该路径写入草稿，降低退出后临时路径失效的概率。
- **兼容旧草稿**：如果用户本地还残留旧版 `composer_draft_text`，首次进入会话时会自动迁移到当前会话的新版 key。
- **恢复时有兜底**：如果附件路径已经失效，输入框只恢复文字，不显示坏附件，同时把无效附件从草稿快照里清掉，避免反复报错。

### 排查口诀（给小白）
- 文字恢复了但图片没回来：先看 `composer.dart` 里的 `_stabilizeAttachmentForDraft` 和 `_loadDraftSnapshot`。
- 切换会话后草稿串了：先看 `_syncDraftScope()` 有没有拿到正确的 `activeConversationProvider`。
- 旧版本升级后草稿消失：先看 `_readStoredDraftSnapshot()` 里的旧 key 迁移逻辑有没有被跳过。
