# 聊天请求上下文真相源与组装规范

> 更新日期：2026-04-23
>  
> 适用范围：`apps/aicove_flutter/` 内所有面向模型的请求组装链路，包括主聊天发送、重试、重生成、编辑后重发、主动回复、后台 Agent、预生成与调试链路。
>
> 定位：项目级基石规范。后续任何实现细节、局部优化或兼容分支，都不得违背本文定义的边界。

---

## 1. 这份文档解决什么问题

项目已经明确了“聊天时间线的数据库真相源”原则，但当前还缺一份更上层的**请求上下文规范**，用来回答下面这些问题：

- 发给模型的 `messages` 到底应该从哪里来
- 前端分段/投影和模型上下文之间的边界在哪里
- 用户点击“编辑”后，历史上下文应该如何截断
- 用户点击“删除”后，是否会影响后续模型请求
- 主聊天、主动回复、后台 Agent、预生成链路，是否遵守同一套上下文组装规则

本文只做一件事：**把“数据库真相源 -> 请求上下文组装 -> Provider 请求体”这条链路的口径写死。**

---

## 2. 一句话结论

### 2.1 唯一真相源

- **数据库 raw message 是唯一真相源。**
- 这里的 raw message 指数据库中的原始消息记录及其必要语义材料，例如：
  - `messages`
  - `message_blocks`
  - `raw_payload` 中仅用于恢复原始 assistant 语义的字段

### 2.2 前端分段不是上下文

- 前端消息分段、投影、多模态后补、窗口裁切，都是**前端展示层 read model**。
- 它们可以影响“用户看见什么”，**不能直接决定“模型看见什么”**。

### 2.3 请求上下文必须重新组装

- 所有发给模型的 `messages`，都必须从数据库 raw message 重新组装。
- 组装过程允许使用显式的“上下文边界元数据”（例如编辑重发边界），**但不得直接使用前端投影消息列表充当上下文**。

### 2.4 编辑会改变上下文，删除不会

- **编辑用户消息**：等价于“从该用户消息重新发起一条新分支”，该消息之后的旧文本上下文失效，组装请求时必须截断。
- **删除消息**：默认只是前端可见性动作，不改变 canonical request context，不改变数据库真相源语义。

## 3. 分层定义

本文把聊天相关数据严格分成三层。

## 3.1 Raw Message Layer（原始消息层）

职责：

- 作为聊天语义的唯一真相源
- 保存用户/assistant 的原始轮次语义
- 提供后续投影和请求组装所需的最小材料

典型内容：

- 文本消息
- 图片/音频/文件等 blocks
- assistant 原始工具调用语义
- 为了重建 assistant 语义而保留的 `raw_payload`

约束：

- 原始消息层不能被前端展示策略污染
- 原始消息层不为“某次 UI 分段结果”背书
- 原始消息层可以被编辑/重发边界解释，但边界本身不等于前端展示状态

## 3.2 Projection Layer（前端投影层）

职责：

- 从 raw message 派生出更适合 UI 展示的消息列表
- 支持 assistant 分段、多气泡展示、图片/音频补位、列表窗口裁切

典型能力：

- `raw assistant` 一条消息拆成多个 UI 气泡
- 多模态内容按插入点投影到时间线
- 仅展示最近 N 条
- 旧消息上滑分页时再投影

约束：

- Projection Layer 只服务 UI
- Projection Layer 不是第二套真相源
- Projection Layer 的结果**不得直接反向输入模型**

## 3.3 Request Context Layer（请求上下文层）

职责：

- 从 raw message 与显式边界信息，组装出某次“面向模型”的上下文
- 输出 provider 无关的 canonical `messages`
- 在此基础上再进行 system prompt、reminder、工具、标签语义、token 截断与 provider 适配

关键点：

- 它是**派生层**，不是持久真相源
- 但它的输入只能来自：
  1. 数据库 raw message
  2. 显式上下文边界元数据
  3. 本次请求自己的附加输入（例如本轮 userText、system reminder）

## 3.4 Context Boundary Metadata（上下文边界元数据）

上下文边界元数据是少数允许影响请求组装的控制信息，例如：

- 编辑重发的起点
- regenerate / retry 的重放锚点
- 当前激活分支
- 需要丢弃的旧后缀

约束：

- 它必须是**显式的、可追溯的、可持久化或可由真相源推导的**
- 它不是“当前页面正显示哪些气泡”
- 它不是“用户此刻是否点开了某条折叠消息”

## 4. 不可违背的硬规则

以下规则是项目级约束，不允许被局部实现覆盖。

### 4.1 同一数据库状态必须导出同一请求上下文

在同一份 raw 数据库状态、同一份边界元数据下：

- 主聊天发送
- 后台主动回复
- 预生成
- 调试请求

应得到**等价的 canonical request context**。

UI 是否分段、是否滚动到顶部、是否只显示了尾部 20 条，不得改变结果。

### 4.2 UI 投影不能反哺模型

禁止把以下内容直接当成模型上下文：

- 前端投影消息列表
- 前端分段后的 assistant 气泡
- UI 窗口缓存
- 任何“当前页面可见消息集合”

### 4.3 Provider 请求体必须最后一步才生成

正确顺序应是：

1. raw message
2. request context
3. system/reminder/tools/tag semantics/token truncate
4. provider adapter request body

不允许直接从 UI 或某个 provider 特化缓存倒推上下文。

### 4.4 快照不是新的真相源

任何 `contextSnapshot`、调试缓存、后台任务输入快照，都只能是派生工件。

要求：

- 可以丢失
- 可以重建
- 不能成为新的 canonical source
- 不能比数据库 raw message 拥有更高优先级

### 4.5 删除默认不改变 canonical context

除非未来单独立项、明确引入“语义删除 / 上下文压缩”规范，否则：

- 用户删除消息 = 前端动作
- 不改变数据库真相源语义
- 不改变后续模型请求上下文

## 5. canonical request context 的标准组装流程

以下流程适用于所有面向模型的请求。

## 5.1 Step 1：确定本次请求的目的

请求目的包括但不限于：

- 普通发送
- retry
- regenerate
- 编辑后重发
- 主动回复预生成
- 后台主动回复
- 分析型后台 Agent

请求目的不同，允许携带不同的附加输入，但**上下文读取规则必须一致**。

## 5.2 Step 2：从数据库读取 raw message

必须读取：

- 当前会话的 raw message
- 稳定顺序
- 能回溯 raw source 的原始语义材料

禁止：

- 直接读取 projected message 列表作为请求上下文

## 5.3 Step 3：解析有效上下文区间

在 raw message 序列上计算本次请求的有效区间：

- 默认情况下，使用当前会话的有效主分支
- 如果存在编辑重发边界，则按边界截断旧后缀
- 如果存在 retry/regenerate 锚点，则按锚点解释本轮重放区间

此步骤的输出是：

- 本次请求允许进入上下文的 raw message 子序列

## 5.4 Step 4：应用编辑语义

### 规则

用户确认发送编辑内容时，语义上不是“修改已有历史的一小段文本”，而是（仅点击编辑仍是草稿，不改变历史，见第13节）：

> 从该用户消息重新发起一次发送。

因此必须满足：

1. 找到被编辑的原用户消息 `U`
2. 保留 `U` 之前仍然有效的 raw 上下文
3. 用新的用户输入替换/重发 `U`
4. **丢弃 `U` 之后旧分支上的所有文本上下文**

这里的“后续文本需要抛弃”指：

- `U` 之后的旧 assistant 回复失效
- `U` 之后的旧用户消息也不再属于当前主分支
- 后续模型请求必须基于新分支，而不是旧分支

### 结论

- 编辑会改变 canonical request context
- 编辑不是 UI 动作，而是上下文边界动作

## 5.5 Step 5：忽略前端删除可见性

在没有单独“语义删除规范”之前，请求组装器必须忽略前端层的删除可见性状态。

也就是说：

- 某条消息在 UI 上被隐藏
- 某条投影气泡被用户删除
- 某段 assistant 分段不再展示

都**不能自动等价为“从 canonical context 中移除”**。

## 5.6 Step 6：把 raw message 转成 canonical messages

转换原则：

- 一条 raw user message，应按其原始语义转换
- 一条 raw assistant message，应保留为单个语义回合
- 工具调用与工具结果应按原始语义成组
- 多模态 blocks 依据“模型可理解的 canonical 表达”转换

特别说明：

- **UI 上一条 assistant 被分成 3 个气泡，不代表 canonical context 里也要变成 3 条 assistant message**
- Projection Layer 的拆分规则不得泄漏到 Request Context Layer

## 5.7 Step 7：叠加请求级附加信息

只有完成 canonical messages 之后，才允许叠加：

- persona system prompt
- system reminder
- 时间感知
- 标签语义说明
- 工具定义
- 其他与本次请求相关的附加上下文

顺序要求：

- request context 先确定
- 附加 prompt 后置注入

## 5.8 Step 8：做 token 截断

token 截断只能发生在 canonical request context 完成之后。

要求：

- 截断规则对主聊天、后台 Agent、主动回复链路尽量一致
- 截断不能回退去使用 projected messages
- reminder / system / tools 的保留策略必须明确、可测试

## 5.9 Step 9：交给 provider adapter 生成最终请求体

只有到这一步，才允许：

- OpenAI `messages`
- Claude `system + messages`
- Gemini `systemInstruction + contents`

等 provider-specific 转换。

## 6. 关键场景语义

## 6.1 普通聊天发送

规则：

- 从数据库 raw message 读取当前有效分支
- 加入本轮用户输入
- 组装 canonical context
- 再注入 system/reminder/tools

不得：

- 直接从当前聊天页可见气泡拼请求

## 6.2 retry / regenerate

规则：

- retry / regenerate 是 request-layer 的重放行为
- 必须从 raw source 重新计算有效上下文
- 不能因为当前 UI 只缓存了尾部窗口，就只拿尾部窗口当上下文

## 6.3 用户编辑

规则：

- 编辑是新的主分支起点
- 被编辑用户消息之后的旧后缀全部失效
- 后续上下文只能基于新分支重建

这条规则优先级高于：

- 前端当前展示状态
- 当前页面缓存
- 任何旧的 projected snapshot

## 6.4 用户删除

规则：

- 删除默认只影响前端显示
- 不改变 canonical request context
- 不改变“数据库真相源作为模型输入基础”的原则

如果未来要让删除影响模型上下文，必须：

1. 单独定义“语义删除”规范
2. 明确落库方式和边界元数据
3. 补齐兼容、回放和回归测试

在此之前，删除一律视为前端动作。

## 6.5 主动回复 / 预生成 / 后台 Agent

规则：

- 这些链路不是例外
- 它们必须和主聊天链路共用同一套 raw -> request context 规则
- 不能为了方便直接吃 projected history

如果某条后台链路需要冻结上下文快照，快照也必须满足：

- 来自 canonical request context 或 raw source
- 不能来自 projected bubbles
- 快照失效后，仍可从数据库重新组装

## 6.6 调试与日志

允许记录：

- raw context
- canonical request context
- provider request body

但不允许因为日志或调试方便，而把某个中间缓存反过来变成运行时真入口。

## 7. 明确禁止的做法

以下做法在本项目中视为违规：

### 7.1 把 projected message 列表直接喂给模型

例如：

- 直接使用 `loadRecentProjectedMessages()` 作为模型上下文
- 直接把 assistant 分段气泡逐条 `toHistoryJsonList()`

### 7.2 把 UI 快照当成 canonical context

例如：

- 从当前聊天页可见消息直接生成后台请求
- 只因为分页窗口没加载到，就默认历史不存在

### 7.3 把删除展示误认为删除上下文

例如：

- 用户删除一个前端气泡，就从后续请求中移除对应语义
- 隐藏一段 UI 消息，就当成 canonical context 已裁剪

### 7.4 用前端投影回写新的真相源

例如：

- 持久化整份 projected bubble 列表，并把它作为后续请求主入口
- 用 UI 插入位点直接决定模型上下文结构

## 8. 服务职责边界

为避免后续继续混层，推荐按职责理解现有/未来服务：

## 8.1 Raw History Reader

职责：

- 只负责从数据库读取 raw message
- 不做 UI 分段
- 不做页面窗口裁切语义

## 8.2 Request Context Assembler

职责：

- 读取 raw message
- 解析有效分支与编辑边界
- 生成 canonical request context
- 提供给主聊天、后台 Agent、主动回复等所有模型请求方

## 8.3 UI Projection Service

职责：

- 只负责 raw -> UI projection
- 不参与 canonical context 决策

## 8.4 Provider Adapter

职责：

- 只负责 canonical context -> provider request body
- 不负责决定上下文边界

## 9. 验收标准

满足以下条件，才算真正遵守本文规范。

### 9.1 展示策略变化不影响请求体

例如：

- assistant 分段策略调整
- 时间线窗口从 20 条改 30 条
- 某条消息的前端投影结构变化

都不应改变同一数据库状态下的 canonical request context。

### 9.2 编辑会稳定截断后缀

给定：

- 用户编辑中间一条用户消息

必须保证：

- 该点之后旧 assistant / user 后缀不再进入新请求上下文

### 9.3 删除不影响 canonical context

给定：

- 用户删除一个前端气泡

必须保证：

- 后续请求上下文不因此变化

### 9.4 所有模型链路使用同一套上下文规则

以下链路都应通过同一套 request context 规则：

- 主聊天发送
- retry / regenerate
- 主动回复分析
- 主动回复预生成
- 后台主动回复发送
- 其他后台 Agent

### 9.5 快照可废弃、可重建

任何快照丢失后，都应能从：

- 数据库 raw message
- 边界元数据

重新恢复等价的 canonical request context。

## 11. 最终原则（必须记住）

只记一句话也行：

> **唯一真相源是数据库；前台消息分段从数据库拿，发送实际请求的上下文组装也必须从数据库拿。用户编辑通过正式分支边界重发，显式手动压缩通过下节的数据库交接事务改变上下文；删除默认只是前端动作。**

## 12. 手动内容交接（2026-09-05，已实现）

“压缩并开启新话题”是显式的上下文边界操作，不是 UI 投影裁切：

1. TopicCompactionPort 从 DB raw 快照生成纯内容摘要，记录 owner、原始消息 ID 范围及内容版本；不以 UI 最后一个气泡决定截止点。
2. 用户确认后，SQLite v16 的 topic_handoffs 与 conversations.contextStartMessageId 同事务写入。原始消息不删除；摘要是带来源的派生材料，不能覆盖 raw 真相源。
3. 标准聊天请求装配为最新角色卡/预设＋有效记忆＋内容摘要＋新话题 raw 消息。摘要不作为回复格式示例；来源变化或重放其覆盖范围内旧消息时不注入。
4. 角色 MD 归档是另一提交步骤，有 pending/archived/cancelled 状态；文件失败不撤销已经可靠保存的交接。撤销恢复前一上下文边界，但不删除已经写入的 MD。
5. 两个 raw 历史读取器均允许边界之后为空；不因最后一条恰为边界而回流整个旧话题。加入摘要后，预算不能挤掉当前问题仍静默发送。

实施说明：[上下文压缩与记忆联动方案](../04_功能模块规范/记忆系统/上下文压缩与记忆联动方案.md)。第一批不扩展后台分析器/主动关怀的摘要装配权限，自动压缩也尚未接入。

## 13. 编辑的草稿与提交边界（2026-09-06）

1. 点击编辑、取消编辑、退出页面与恢复草稿，都不改变raw历史。编辑草稿按会话持有原始用户消息ID及DB历史版本，回填原文与版本在同一快照读取，不以气泡显示文本代替原文。
2. 用户确认发送时，在应用层固定owner，检查生成状态和目标版本，再将旧后缀软删、新用户消息及内容块写入、会话预览更新放进同一DB事务；任何写入失败全部回滚。UI缓存不是截断依据。
3. 输入框只在本地受理成功后清草稿，不等待整次模型响应。模型随后失败，保留新分支供重试；旧草稿不能再次提交。取消发生在本地提交之前，已提交后的撤销不属于本批能力。
4. 草稿损坏、附件缺失、目标消失、owner不符、话题边界无效或历史版本改变时，明确拒绝而非自动降级成普通发送。当前保守拒绝编辑话题/压缩边界之前的旧消息，不静默重置边界。
5. 草稿保存与DB提交不是一个跨存储事务；崩溃后若残留已提交草稿，版本校验必须阻止重复提交。SharedPreferences防抖只保证已保存的草稿恢复，不能承诺强杀前最后字符一定落盘。

## 14. 插件关闭时的请求派生过滤（2026-09-11）
