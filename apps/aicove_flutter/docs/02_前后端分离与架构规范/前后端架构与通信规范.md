# 前后端架构与通信规范

> 适用范围：AIcove 全端架构说明
> 核心目标：明确前后端职责边界，规范状态流转与 API 调用，严禁“上帝类”与“胖前端”。

## 1. 架构总览与术语定义

本项目采用 **“前端 / 本地后端 / 云端”** 三层分离架构。所有业务开发必须严格遵守以下边界：

| 模块名称 | 部署形态 | 核心职责 | 绝对禁忌 |
| :--- | :--- | :--- | :--- |
| **前端 (Frontend)** | Flutter 客户端 (Mobile/Desktop) | UI 渲染、动画、路由、本地状态管理、本地数据库读写、录音/播放。 | ❌ 禁止在前端拼接发给大模型的系统提示词或复杂上下文。<br>❌ 禁止在前端直接调用大模型原生流式 API (应通过后端/网关代理)。 |
| **本地后端 (Local Backend)** | 随客户端本地运行的网关 / Agent | Agent 运行时、工具调用路由、记忆总结、触发器轮询、提示词组装、多模态分发。 | ❌ 禁止硬编码特定 UI 平台的逻辑。<br>❌ 禁止绕过数据库直接向前端推送幽灵状态。 |
| **云端 (Cloud Backend)** | 远端服务器 (`cloud_backend/`) | 身份认证、数据增量同步、云备份、跨设备触发器同步、额度管理。 | ❌ 禁止处理单次普通的对话生成逻辑 (除非是云触发器强制干预)。 |

## 2. 职责边界划分

### 2.1 状态管理的唯一真相源
- **数据库是唯一真相源 (Single Source of Truth)：** 前端页面上看到的所有气泡、消息状态，都必须是从数据库 `raw message` 投影出来的 `read model`。
- 前端界面的“可见消息”、“多模态卡片”**绝对不允许**直接打包作为上下文反向传给大模型。
- **发送请求规范：** 前端只负责将“用户输入文本/图片”提交给本地后端，本地后端负责从数据库查询历史记录，并按照《聊天请求上下文真相源与组装规范》组装 Canonical Request Context。

### 2.2 大模型请求与工具调用 (Agent 流程)
- **前端发起：** 提交 `{ "text": "你好", "session_id": "xxx" }`。
- **本地后端处理：**
  1. 拦截并组装系统提示词 (Persona + 时间信息)。
  2. 提取历史记忆 (通过 RAG 或摘要)。
  3. 携带可用 Tools (技能、多模态插件) 发送给大模型。
  4. 解析大模型返回的 Tool Calls。
  5. 后端执行 Tool (如：生成图片、总结记忆)，然后将结果返回给模型。
  6. 后端最终将处理好的多模态消息 (分段的文字 + TTS标记 + 图片链接) 流式返回给前端。
- **前端接收：** 前端仅作为无情的“渲染机器”，负责正则匹配 `<tts>`、`<image>`、`<emoji>` 标签并展示或播放。

### 2.3 主动关怀 (Trigger) 与记忆 (Memory)
- **记忆 (Memory)：** 后端按照时间间隔或轮次，定期在后台启动一个静默 Agent，读取最近的对话记录生成短期摘要或长期画像，并入库。前端只负责拉取展示。
- **主动关怀 (Trigger)：** 后端维护一个触发器列表 (如：中午 12 点提醒吃饭)。轮询机制在后端运行，一旦触发，后端生成内容并主动写入数据库。前端通过监听数据库变化 (Drift Watch) 自动在界面弹出新消息，无需前端主动拉取。

## 3. API 通信规范

### 3.1 接口风格
- “本地后端”当前以 Flutter 进程内的 Dart 应用层/服务层形式实现（`chat_actions.dart`、Port / Adapter 等），前端与它之间是方法调用，不走 HTTP。
- 与**云端**及外部模型供应商的通信默认采用 **RESTful API**；流式对话采用 **SSE / 流式 HTTP**。
- 云端请求路径规范：`/api/v1/模块名/动作`。

### 3.2 错误处理
- 统一使用标准的 HTTP 状态码。
- 返回体格式强制统一：
  ```json
  {
    "code": 200,          // 业务状态码
    "message": "success", // 错误信息，前端直接用于 Toast 提示
    "data": {}            // 核心载荷
  }
  ```
- 前端必须在 `api_client.dart` 这一层统一拦截错误码并抛出标准 Exception，禁止各个 UI 页面各自为战写 `try-catch` 解析错误 JSON。

## 4. 前端开发的三大铁律

1. **“UI 不做决定”**：用户点击“重试”、“编辑”等按钮，本质上只是发送一个对应的 Action 给后端，UI 不能自作主张修改本地显示，必须等待数据库变化后被动刷新。**例外：“删除”是仅前端可见的行为**，只影响前端消息列表、不改动数据库 raw message，详见[聊天删除仅前端可见实施说明](聊天删除仅前端可见实施说明_20260423.md)。
2. **“解耦复杂逻辑”**：但凡涉及到“该传几条消息给模型”、“系统提示词怎么写”、“该不该调用绘图插件”，全部移出 Flutter 业务代码，交由后端或独立的 Agent 模块处理。
3. **“复用先行”**：不允许在页面手写颜色和尺寸，必须使用 `tokens.dart`；不允许自己手搓弹窗，必须使用 `MoeToast` 等公共组件。

---
> 💡 *本规范为后续重构与开发的最高指导原则。在进行任何新功能开发时，必须先自我拷问：“这段代码该放在前端还是后端？”*
