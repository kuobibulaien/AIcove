# 03 与记忆系统集成

> 本文档描述记忆机制如何作为第一批接入方，改接后台 Agent 运行时

---

## 为什么记忆机制要先接

记忆机制是最适合第一批改接后台 Agent 的模块，因为它同时具备：

1. 强依赖主聊天上下文
2. 需要严格控制上下文窗口大小
3. 不适合污染主聊天 session
4. 未来还会衍生出不同任务目标（总结、合并、分类、压缩）

如果记忆机制先接通，后面的触发器规划、日反思、风险识别都可以沿着同一模式落地。

---

## 当前链路的主要问题

记忆机制目前虽然已经有自己的插件与服务，但后台运行方式还不够统一：

- 某些逻辑直接在插件内拼上下文
- 某些逻辑直接在服务层决定总结窗口
- 后续如果继续扩展“不同总结目标”，容易重复造轮子

缺的不是“记忆能力”，而是一个统一的后台 Agent 运行入口。

---

## 接入后的推荐形态

推荐把记忆机制改造成如下调用方式：

```text
MemoryPlugin / MemoryService
  -> 构造 BackgroundAgentDefinition
  -> 调用 BackgroundAgentService.run(...)
  -> 消费 BackgroundAgentRunResult
  -> 写入 memory repository
```

---

## 记忆总结 Agent 的建议定义

### `BackgroundAgentDefinition`

建议示意：

- `id = memory_daily_summary`
- `name = 记忆总结`
- `objectivePrompt = 你负责从对话中提取适合进入长期记忆的信息`
- `contextSpec.lastMessages = 12` 或根据次日总结窗口动态计算
- `allowedToolNames = []` 或仅开放记忆辅助类工具

第一阶段建议：

- 记忆总结 Agent 默认不开工具
- 先只返回结构化文本/JSON 结果

这样风险更低，也便于先验证公共运行时是否稳定。

---

## 记忆机制的第一阶段接法

### 阶段 1：只替换“怎么跑”

保留现有：

- MemoryPlugin
- MemoryService
- memory repository
- 现有入库规则

替换为：

- 总结模型的实际调用入口改成 `BackgroundAgentService`

目标：

- 不改业务规则
- 只收敛后台运行时

### 阶段 2：再替换“怎么定义”

等公共运行时稳定后，再把记忆相关的不同任务收敛为多份定义：

- 记忆总结 Agent
- 记忆合并 Agent
- 记忆压缩 Agent

这样以后就不是“MemoryService 里塞越来越多分支”，而是“定义不同 agent，复用同一运行时”。

---

## 推荐边界

### `BackgroundAgentService` 负责

- 读上下文
- 跑模型
- 执行工具
- 回结果

### Memory 侧负责

- 决定什么时候总结
- 决定用哪份 `BackgroundAgentDefinition`
- 校验总结结果
- 写入仓库

这条边界一定要守住，否则后台 Agent 运行时又会被业务侵入，重新变成大杂烩。

---

## 迁移注意事项

1. 不要在第一阶段就把记忆、触发器、反思一起改。
2. 不要让 `BackgroundAgentService` 直接依赖 Memory 专有仓库。
3. 不要把唤醒逻辑塞回公共运行类。
4. 不要新建第二套工具协议。
