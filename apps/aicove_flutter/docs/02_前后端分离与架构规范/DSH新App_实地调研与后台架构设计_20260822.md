## 第一部分：为什么现在退到后台会被掐断（实地诊断）

### 1.1 根因不是一个，是三个叠加

**根因 A：Flutter 引擎跟着 Activity 走**

`MainActivity : FlutterActivity`（[MainActivity.kt](../../android/app/src/main/kotlin/com/example/aicove_flutter/MainActivity.kt)）使用默认引擎，不是 cached engine。用户划掉任务卡片 → `Activity.onDestroy` → FlutterEngine 销毁 → Dart isolate 死亡。

**这是守护服务救不了的**——因为服务不持有引擎。

**根因 B：SSE 流跑在 Dart isolate 内**

[agent_api.dart:938](../../lib/src/core/api/agent_api.dart#L938)：

```dart
final response = await _client.send(request).timeout(timeout);
await for (final chunk in response.stream
    .transform(utf8.decoder)
    .transform(const LineSplitter())) { ... }
```

`package:http` 的 socket 属于 Dart isolate。isolate 死，连接立即断，服务端那半句话再也拿不回来。

**根因 C：流式内容只在内存，从不落盘**

这是最致命的一条。追踪链路：

```
chat_actions_stream_placeholder.dart
  _flushTimer  →  _flushNow()  →  _applyState(finalize: false)
    → conversationTimelineCache.replaceMessagesTransient(...)
      → conversation_short_window_store.dart
```

而 `conversation_short_window_store.dart` **没有任何 `AppDatabase` / `databaseProvider` 引用**——它是纯内存短窗缓存。方法名 `replaceMessagesTransient` 里的 `Transient` 就是字面意思。

只有 `finalize: true`（流正常结束）才会走到 [chat_history_store.dart](../../lib/src/features/chat/services/chat_history_store.dart) 的 `_db.transaction`。

> **结论：掐断 = 整条 AI 回复全部丢失，连已经显示在屏幕上的半句都不剩。**

### 1.2 守护服务是个空壳

[PersistentGuardService.kt](../../android/app/src/main/kotlin/com/example/aicove_flutter/PersistentGuardService.kt) 全部 204 行，做的事只有：建通知渠道、`startForeground` 挂一个常驻通知、`START_STICKY`。

它**不持有任何工作、不持有引擎、不做任何投递**。它唯一的作用是让进程不容易被 LMK 回收（对根因 B/C 有间接帮助，对根因 A 完全无效）。

### 1.3 三个已确认的次生问题

**（1）`dataSync` 类型在 Android 15 会被系统掐**

[AndroidManifest.xml](../../android/app/src/main/AndroidManifest.xml)：

```xml
<service android:name=".PersistentGuardService"
         android:foregroundServiceType="dataSync" />
```

Android 15（API 35）对 `dataSync` 类型前台服务施加 **24 小时内累计 6 小时**上限，超限系统强制停止。守护模式在 Android 15 上撑不过一天。

**（2）`SCHEDULE_EXACT_ALARM` 是白申请的**

manifest 里申请了权限，`MainActivity` 也 import 了 `AlarmManager`——但全项目 Kotlin 侧 **没有任何 `setExact` / `setExactAndAllowWhileIdle` / `setAlarmClock` 调用**（已 grep 确认为空）。`AlarmManager` 只被用来查 `canScheduleExactAlarms()` 显示给 UI 看。

**（3）主动关怀跑了两套并存机制**

- 前台：[analyzer_scheduler.dart](../../lib/src/features/auto_reply/data/analyzer_scheduler.dart) 用 Dart `Timer`（`_analysisTimers` / `_silentTimers` / `_backgroundAnalysisTimer`）——isolate 死则全部消失
- 后台：[background_service.dart](../../lib/src/features/auto_reply/data/background_service.dart) 用 `workmanager` 拉起独立后台 isolate

两套语义不同、状态不共享，且都不知道对方在做什么。

**（4）API key 明文落盘**

[ui_models_store_local_data_source.dart](../../lib/src/features/settings/data/local/ui_models_store_local_data_source.dart) 把 `apiKeys` 作为普通字符串数组写入设置存储。项目未引入 `flutter_secure_storage` 或 `EncryptedSharedPreferences`（已确认）。

## 第二部分：上游 DSH 实际提供了什么（这改变了设计）

读完官方 `docs/subsystems/` 后，最重要的发现是：**AIcove 2.0 方案里准备手写的一大半基础设施，上游已经有了成熟的能力 seam。**

### 2.1 会话持久化：崩溃安全是内置的

来自 `docs/subsystems/persistence.zh.md`：

- `SessionEvent` 是**仅追加日志**，即真相源。每条事件带单调递增 `seq` + `time`
- 事件分两类：`surface`（生成 LLM 消息，进派生历史）与 `log-only`（可持久化可回放，不进历史）
- **flush 检查点**：`session/event` 是同步通知，持久化插件复制到逐会话控制器，不阻塞生产方；固定批处理窗口成批落盘
- **崩溃恢复保留被中断的轮次**（原文重点）：

> 后端重新加载一个在轮次中途崩溃的日志时，会发现一个已打开的 `turn/start` 却没有 `turn/end`。它**不会**截断日志……后端改为用一个合成的 `turn/end { reason: { kind: 'interrupted' } }` 关闭这个遗留轮次。

- 后端可插拔：`dsh-session-persistence-jsonl`（带 checksum 的 Zstandard frame，崩溃安全原子写入）、SQLite 等
- 提供 watermark 读模型原语：「read models that resume from a watermark（例如只折叠 checkpoint 之后尾部的持久化投影缓存）」

**对照现状**：我们是「内存里攒着，结束才落盘」；DSH 是「每个事件追加落盘，崩了自动配平」。这是数量级的差距，且不用自己写。

### 2.2 会话分叉与恢复：一等公民

来自 `persistence.zh.md` 的 `SessionHeader` / `SessionCreateOptions`：

- `parentSession` —— fork 的谱系来源
- `seedLength` —— 种子边界，让 resume 和 replay 区分父历史与子工作
- `session/end-seed` 事件 —— 标记 seed 结束，之前的事件来自 resume / fork / replay
- 回放/fork：`ctx.sessions.create(id, { seed: seedEvents })`
- 恢复为活跃 agent：`ctx.agents.resume({ resumeSessionId })`

> AIcove 方案 §9.3 手工设计的 `seededThroughMessageId` + `seedHash` seed 机制，和 DSH 原生 seed 语义高度重合。**应改为直接用上游的。**

### 2.3 客户端协议：已有现成的

来自 `docs/api-gateway.zh.md`：

| 组件 | 提供什么 |
|---|---|
| `@deepseek-ai/dsh-client-connection` | RPC carrier、请求关联、**信任边界**、**取消**、响应 envelope、`/api` HTTP bridge |
| `dsh-host-apiproxy` | 历史尾页 + `session/projection` 推送帧 |

调用形态：`connection.rpc.call('/api', '<namespace>/<method>', { args }, signal)`，HTTP 对应 `POST /api/<namespace>/<method>`。

> AIcove 方案 §7 设计的 `bridge.handshake` / `run.start` / `session.event` / 版本协商 / 取消 / replay，**大部分是在重造 `dsh-client-connection`**。

### 2.4 会话投影：也已有

来自 `docs/subsystems/session-projection.zh.md`：

> 领域 host 插件经由它向客户端载体供给按会话的日志派生状态的当前全量值……注册表只订阅一次 `session/event`，并把每个已提交事件折叠进每个单元；领域不持有任何订阅，**客户端也从不折叠领域事件——它们收到的是成品值**。

> AIcove 方案 §9.2 的 `dsh_event_projection_receipts` + 手写投影层，应先评估能否直接注册一个投影单元。

### 2.5 压缩可替换（修正上轮结论）

来自 `docs/subsystems/compaction.zh.md`：

- `ctx.compaction` 是 **abstract seam**，`CompactionEngine` 暴露 `compactIfNeeded` / `compactNow` / `compactRegion`
- `dsh-compaction-basic` 只是默认实现，「拥有阈值、保留尾部策略、溢出上限与失败处理」
- 压缩全过程有锁：`compaction/start` → 摘要 → `compaction/summary` + `user/message` 替换 → `compaction/end`。崩溃表现为可检测的遗留锁，不会假装完成

> **陪伴向记忆策略可以自己实现**。这条推翻了上轮「产品命脉外包」的判断。

### 2.6 调度是 session-local（这条限制很重要）

来自 `docs/subsystems/schedule.zh.md`：

> `session-local` 表示原 Session 必须处于 live 状态：**不存在外部通知渠道或 cold Session scheduler**。

还有：

> 如果一个 Session 在多个目标到期期间处于 cold 或 busy 状态，一条 Every 记录只会贡献其中最新的一次到期触发。

> **DSH 不会替你唤醒手机。** 「什么时候醒」必须由 Android 侧负责，这印证了原方案 §13 的分工是对的——但现在有官方文档背书了。

### 2.7 其他有用的 seam

- `ctx.jobs` —— 长时间运行任务运行时（JobRegistry 抽象 seam），运行时拥有身份/访问权限/生命周期状态
- `ctx.tokenMeter` —— 估算与回放，压缩阈值靠它
- `ctx.toolResultPruner` —— 工具结果剪枝（可选）
- `agent-preset` —— 每个 session 记录 `agent-preset/selected`，resume/fork 时重建同一组合

## 第三部分：后台不掐断——重新设计

### 3.1 核心原则（一句话）

> **把「谁持有正在进行的对话」从 Flutter 挪到 Node，Kotlin 持有 Node，Flutter 降级为可随时死掉的订阅者。**

Agent 关键路径上不得出现 Flutter。这是硬约束，不是优化项。

### 3.2 进程与所有权

```
Android 应用进程
├─ Kotlin HarnessService（前台服务，唯一进程主人）
│   ├─ 持有 Node/DSH 子进程（ProcessBuilder，App UID）
│   ├─ 持有 Unix domain socket，代理 capability 请求
│   ├─ 持有产品数据库（Room/SQLite）
│   └─ 持有通知投递与 TTS 排队
│
├─ Node / DSH 子进程（App UID）
│   ├─ Agent loop，SSE 直连模型 provider
│   ├─ SessionPersistence → 事件 append-only 落盘
│   ├─ 自定义 CompactionEngine（陪伴向保留策略）
│   └─ Aicove capability 插件 → 经 socket 回调 Kotlin
│
└─ Flutter UI（可随时销毁、随时回来）
    └─ 只订阅投影 + 从 watermark 补齐，不持有任何真相
```

### 3.3 三层生存性

| 死掉的东西 | 后果 | 恢复方式 |
|---|---|---|
| **Flutter 引擎** | **零影响**。Node 继续跑完这一轮，事件继续落盘，通知照发 | 用户回来时从 `lastSeq` 补齐投影 |
| **Node 进程** | 只丢未 flush 的尾巴（一个批处理窗口） | Kotlin 重启，DSH 自动补 `turn/end{interrupted}`，已落盘半句保留，UI 显示「刚才说到一半」 |
| **整个进程** | 同上 | 前台服务 + `START_STICKY` 拉回；开机由 `BootCompletedReceiver` 恢复 |

对比现状（掐断 = 全丢），这是根本性改善，而且**主要靠上游已有能力，不是自己造**。

### 3.4 四个必须落实的具体改动

#### 改动一：前台服务类型换成 `specialUse`

```xml
<service
    android:name=".HarnessService"
    android:foregroundServiceType="specialUse"
    android:stopWithTask="false"
    android:exported="false">
    <property
        android:name="android.app.PROPERTY_SPECIAL_USE_FGS_SUBTYPE"
        android:value="on_device_agent_runtime" />
</service>
```

理由：`dataSync` 在 Android 15 有 6h/24h 上限。`specialUse` 的用途说明只在 Play 审核时才被审查——**既然走 GitHub 分发，这里没有约束**。这是当前分发决策带来的第一个实际红利。

#### 改动二：生命周期分三档，不做 24 小时常驻

| 档位 | 触发条件 | Node | 前台服务 |
|---|---|---|---|
| 冷 | 无未完成轮次、无临近 schedule | 不在 | 不在 |
| 温 | 有未闭合 turn，或 schedule 30 分钟内到期 | 在 | 在 |
| 热 | 聊天页在前台 | 在 | 跟随 |

关键设计：**「有未完成的 turn」必须从 DSH session 日志读**（存在 `turn/start` 无匹配 `turn/end`），不能靠内存标志位。这样进程被杀后重启也能正确判断要不要恢复。上游的 `SessionPersistence.inspect(id)` 正好提供这个——它构造不可变逻辑 Session、在内存中配平中断轮次、但不写入恢复内容。

#### 改动三：唤醒职责切分

```
AlarmManager.setExactAndAllowWhileIdle   ← 精确提醒（现在权限白申请了，终于用上）
WorkManager                              ← 宽松兜底、网络恢复重试
        ↓
Kotlin HarnessService 拉起 Node
        ↓
ctx.agents.resume({ resumeSessionId })
        ↓
DSH schedule 到期 → 作为普通 follow-up 轮次回到 live session
        ↓
事件落盘 → Kotlin 读投影 → 发通知
```

分工铁律：
- **Android 只回答「什么时候允许醒」**，不复制任何 Agent 决策
- **DSH 拥有「醒了该做什么」**（schedule 记录、提醒内容、agent 判断）

注意上游的补偿语义：多个目标到期期间 session 处于 cold，一条 Every 记录只贡献最新一次触发，不会枚举补跑错过的间隔。这个行为要在产品层向用户解释清楚（「离线太久只会收到最近一条」）。

#### 改动四：数据归属重划（最大改动）

| 数据 | 归属 | 存储 |
|---|---|---|
| Agent 执行历史、模型可见上下文 | **Node / DSH** | SessionEvent 日志（JSONL + zstd，或自实现 SQLite 后端） |
| 联系人、投递状态、已读、附件索引 | **Kotlin** | Room / SQLite |
| UI 渲染态、草稿、滚动位置 | Flutter | 内存 + 轻量本地 |

**Drift 必须让位**。理由是硬的：后台投递必须在 Flutter 死掉时完成，而 Drift 活在 Flutter isolate 里。

> **推论（重建才有的选项）**：既然 Agent 层归 Node、数据层归 Kotlin，Flutter 只剩渲染。
> 那 UI 换 Compose 可以省掉一层 MethodChannel、一个引擎实例、一次跨语言序列化，并让数据层天然归 Kotlin。
> 代价是失去桌面/iOS 的 UI 复用（但原方案 §16 本就把 iOS 列为暂缓、桌面另做 Host）。
> **这个评估必须在动工前做一次，之后不会再有机会。**

### 3.5 顺带解决的问题

- API key：搬进 Android Keystore 加密存储，Node 子进程只通过环境变量拿运行期引用；不再明文落 JSON
- 双套主动关怀：`workmanager` 后台 isolate 整条删除，统一走 Kotlin 唤醒
- Dart `Timer` 调度：删除，改由 DSH schedule + AlarmManager 承担

## 第五部分：修订后的推进顺序

### Phase -1：动工前必答（纯决策，不写代码）

1. **UI 栈定型**：Flutter 保留 vs 换 Compose。见 §3.4 推论
2. **会话格式风险应对**：格式 v0 不保证兼容，导出格式与降级只读方案先定
3. **bundle 组成裁剪**：确定要不要 `git`（GPL-2.0）、用 toybox 换 bash（0BSD）、`pnpm` 是否随包

### Phase 0：一次性抛弃型 Spike（不写产品代码）

**先钉死放弃线，再开跑**：

| 指标 | 建议放弃线 |
|---|---|
| Runtime bundle 体积 | > 250 MB |
| 冷启动到可对话 | > 8 秒 |
| Node 常驻 RSS | > 400 MB |
| 连续 patch 数 | 单次 DSH 升级 > 15 处 |

**必测清单**（在上一版基础上补齐）：

- [ ] 真机启动官方 DSH，完成一次真实模型回合
- [ ] `ctx.sessions.create(id, { seed })` 分叉验证
- [ ] 杀进程 → 重启 → 验证 `turn/end{interrupted}` 补齐、半句保留
- [ ] `specialUse` 前台服务在 Android 14/15 真机长跑 24h
- [ ] Direct Boot：重启后未解锁时 `filesDir` 可用性
- [ ] Node DNS（`dns.lookup` vs `dns.resolve`）与 CA 信任行为
- [ ] Doze 下 AlarmManager 唤醒 + 长任务实际存活时长
