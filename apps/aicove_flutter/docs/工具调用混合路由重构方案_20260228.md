# 工具调用混合路由重构方案（2026-02-28）

> 适用范围：`apps/aicove_flutter/lib/src/features/chat/`、`apps/aicove_flutter/lib/src/features/plugins/image/`、`apps/aicove_flutter/lib/src/core/api/`
>
> 目标：把“体验优先”和“结果准确优先”拆成两条可维护路径，减少图片等待体感。

---

## 1. 先说结论（给后续维护者）

我们采用 **混合路由**：

1. `fast`：工具先启动，聊天随后继续（体验优先）
2. `stable`：等工具真实结果再继续聊天（准确性优先）

这不是“两套完全独立系统”，而是同一条发送链路里的两种策略分支。

---

## 2. 当前痛点（为什么要改）

用户体感差的根因不是“模型多思考一次”，而是“图片工具启动太晚”。

旧体验像这样：

1. 模型先输出一段聊天文本
2. 文本输出完才触发 `draw_image`
3. 图片生成再等 5~15 秒

结果：用户看起来像“先聊完了，才开始干活”。

---

## 3. 为什么“只改提示词”不够

很多人会建议：在 system prompt 里写“先 tool_calls 再 content”。

这只能提高概率，不能保证。

原因：

1. 官方 Function Calling 协议里，`content` 和 `tool_calls` 同属 assistant message
2. 字段顺序不等于执行顺序
3. 不同模型/网关在流式增量里的拆分行为不稳定

所以：**提示词可辅助，但不能作为顺序保证机制**。

---

## 4. 两条路径怎么定义

### 4.1 Fast（体验优先）

适用：`draw_image` 这类“聊天文本不依赖最终图片结果”的工具。

策略：

1. 第一轮先拿到工具调用参数并立即触发工具
2. 工具快速返回 `accepted + job_id`（后台继续跑）
3. 不等待图片完成，马上进入下一轮输出聊天内容
4. 图片完成后异步回填会话

一句话：`先开工，再说话，图随后到`。

### 4.2 Stable（准确性优先）

适用：搜索、查库、计算、结构化查询等“文本依赖工具返回值”的工具。

策略：

1. 工具执行完成
2. 把真实结果喂回模型
3. 模型基于结果生成最终回复

一句话：`拿到结果，再说话`。

---

## 5. 时序对比（简化）

### 5.1 Fast（目标）

```text
用户消息
  -> 模型第1轮（决策工具）
  -> draw_image 接单（accepted + job_id）
  -> 模型第2轮（流式聊天文本）
  -> 后台图片完成并回填
```

### 5.2 Stable

```text
用户消息
  -> 模型第1轮（决策工具）
  -> 工具完整执行（等待结果）
  -> 模型第2轮（基于结果生成文本）
```

## 7. 协议选择策略（官方协议 vs 自定义流式 JSON）

### 7.1 官方协议（推荐主链路）

优点：

1. 稳定，跨模型兼容更好
2. 工具成功/失败语义清晰
3. 日志、回归测试、故障定位更容易

缺点：

1. 典型是两轮
2. 多一次请求往返

### 7.2 自定义流式 JSON（可作为实验分支）

优点：

1. 可能把“工具触发”和“聊天文本输出”放在同一流里并发
2. 极限情况下更快

缺点：

1. 需要残缺 JSON 状态机解析，复杂度高
2. 模型格式漂移风险高
3. 容易出现线上难复现问题

建议：只对 `draw_image` 做可开关实验，不直接替换主链路。

## 8. 分阶段落地计划

### 阶段 A（先做，主线）

1. 明确 `fast/stable` 工具路由规则（按工具类型，不只按会话模式）
2. `draw_image` 在 `fast` 下返回 `accepted + job_id`
3. `chat_send_api_runner` 在 `fast` 工具接单后继续下一轮聊天
4. UI 处理流式重置，避免前置文案污染

### 阶段 B（可选实验）

1. 为 `draw_image` 增加“自定义流式 JSON 协议”开关
2. 仅在白名单模型上开启
3. 失败自动回退官方协议

## 9. 监控与日志补齐建议

为避免“改完体感变差却不知道卡在哪”，建议新增这些指标：

1. `tool_first_call_latency_ms`：用户发送到工具接单耗时
2. `image_job_total_latency_ms`：接单到图片完成耗时
3. `round2_first_token_latency_ms`：工具接单后第二轮首 token 耗时
4. `last_model_text`：最近一次聚合后的模型文本（调试用途）

日志建议带上：

1. `sessionId`
2. `turnId`
3. `round`
4. `toolName`
5. `job_id`

## 10. 测试用例（先复现再修复）

### 10.1 Fast 路径

1. 工具返回 `accepted + job_id` 时，必须继续下一轮聊天
2. 第二轮聊天不等待图片完成
3. 图片完成后异步回填会话消息

### 10.2 Stable 路径

1. 工具未完成时不允许进入下一轮文本
2. 工具失败时错误链路可见且可回退

### 10.3 监控

1. 流式碎片最终能聚合为完整字符串
2. 调试页可以看到最近模型字符串（若启用）

## 11. 基础操作检查（排障时别漏）

遇到“看起来没生效”时，先检查这 6 项：

1. `flutter pub get` 是否完成
2. 是否用当前分支重新编译安装（非旧包）
3. `imageGenerationEnabled` 是否开启
4. 图片 provider / model / API key 是否配置完整
5. 当前会话是否真的处于 `fast` 模式
6. 网络是否能访问目标图片服务（如 NovelAI）

## 13. 当前实现补充（2026-03-13）

为避免后续排查时把“设计目标”和“当前代码行为”混在一起，这里补一条现状说明：

1. `stable` 仍然是标准两阶段：工具执行完成后，再把结果回写给模型组织最终回复。
2. `fast` 不再是“永远只跑一轮模型”。
3. 对 `draw_image`：
   - 如果工具返回 `accepted + job_id` 这类异步接单结果，会补第二轮正文；
   - 如果图片已经同步产出，通常不再补第二轮。
4. 对非 `draw_image` 工具（如搜索、查询、查日程）：
   - 即使会话设置处于 `fast`，也会自动回落到 `stable` 路由；
   - 会按普通工具回合执行，不再吃生图专用的异步快路径，也不再被强行截成 2 轮。
5. 如果同一轮同时出现 `draw_image` 和非生图工具：
   - 整轮也会回落到 `stable`；
   - `draw_image` 不会注入 `_aicove_async`，避免混合轮次继续走高风险快路径。

一句话：

`stable` = 结果优先，完整回合。
`fast` = 体验优先，但仅限纯生图轮次；非生图或混合工具会自动回落 `stable`。
