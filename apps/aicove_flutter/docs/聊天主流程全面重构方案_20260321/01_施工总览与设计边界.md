# 施工总览与设计边界

## 目标

本轮重构不是“追求完美架构”，而是解决当前聊天主流程里最影响迭代效率的 4 个结构问题：

1. 主发送链没有唯一骨架。
2. 状态管理没有唯一真相源。
3. 页面和业务边界严重串层。
4. 历史过渡代码没有被及时清退。

---

## 当前问题地图

### 1. 发送主链分散

当前至少有以下几层都在参与“发消息”：

- `lib/src/features/chat/application/chat_send_use_case.dart`
- `lib/src/features/chat/services/chat_send_service.dart`
- `lib/src/features/chat/services/chat_send_backend_service.dart`
- `lib/src/features/chat/services/chat_send_api_runner.dart`
- `lib/src/features/chat/services/chat_send_trace_payload_builder.dart`
- `lib/src/features/chat/presentation/chat_actions.dart`
- `lib/src/features/chat/presentation/chat_actions_action_ops.dart`

问题不在“层数多”，而在职责切分并不稳定：

- 有的层负责参数整形
- 有的层负责模型选择
- 有的层负责回调状态
- 有的层只做转发
- 有的层同时掌握业务和 API 细节

结果就是：`send / retry / regenerate / proactive` 表面都叫“发送”，实际却不是同一条执行骨架。

### 2. `ChatActions` 仍是共享上帝类

虽然拆成了多个 `part` 文件，但它们共用同一组内部状态、私有方法和副作用入口。常见问题包括：

- 一个局部改动需要理解整个对象上下文
- 发送、重试、消息删除、流式占位、会话编辑都挤在同一类里
- 很多能力不能独立测试，只能依赖庞大对象图跑集成

### 3. 流式临时消息存在双通路

当前“临时占位消息”至少有两套思路同时存在：

- Provider 路径：`conversation_timeline_providers.dart`
- HistoryStore 路径：`chat_actions_stream_placeholder.dart`

两套路径长期并存会导致：

- 维护者不知道哪套是真正在线路径
- UI/Provider/Actions 可能各自读自己的状态
- 后续修复临时气泡闪烁、重复、交接空窗时容易修错位置

### 4. Provider 组织方式不是按职责，而是按历史阶段

当前 Provider 主要分散在：

- `chat_providers.dart`
- `providers2.dart`
- `conversation_providers.dart`
- `chat_layer_providers.dart`
- `conversation_timeline_providers.dart`

这 5 个文件不是按“谁是真相源、谁是派生、谁是命令入口”来组织的，而更像随项目演进堆出来的结果。

### 5. 页面文件承担业务层职责

典型现象：

- `chat_page.dart` 自己判断模型是否支持视觉能力
- `chat_page.dart` 自己拼引用消息协议文本
- `chat_message_list.dart` 同时掌握分页、贴底、占位、视窗、动作、渲染

这意味着 UI 修改成本会随着业务复杂度一起上涨。

## 目标架构口径

本轮建议把聊天主流程收敛为 5 层，但不是机械分层，而是按“责任是否稳定”来收：

### 1. UI 编排层

职责：

- 页面路由和交互编排
- 展示状态订阅
- 把用户操作转成明确命令

不负责：

- 发送协议拼装
- 模型能力兜底
- 请求参数归一化
- 临时消息生命周期判断

### 2. 应用层

职责：

- 接收统一命令
- 组织一次聊天 turn 的完整执行
- 协调状态回调、持久化与失败恢复

它应该成为聊天主链的“唯一骨架”。

### 3. 领域状态/策略层

职责：

- 会话当前状态
- 临时消息交付状态
- 模型选择策略
- 发送变体归一化规则

这里不直接碰 UI，也不直接碰 HTTP。

### 4. 基础设施层

职责：

- 持久化
- Provider Adapter
- API 请求执行
- 插件/工具接入

基础设施层可以复杂，但不能反向决定业务边界。

### 5. API 传输层

职责：

- 地址解析
- 请求组装
- 流式/非流式协议传输
- 原始响应解析

这里不应知道“这是普通发送还是重生成”。

---

## 本轮不做的事

为了避免越改越大，本轮明确不做以下事项：

1. 不顺手重写整套聊天数据库结构。
2. 不引入新状态管理框架。
3. 不重做插件系统协议。
4. 不先为了“更漂亮”而大规模重命名所有文件。
5. 不把所有巨型文件一次性炸成十几个新类后再慢慢拼。

原则是：先建立稳定主骨架，再做必要抽离。

## 关键设计决策

### 决策 1：发送主流程先收口，再考虑是否 rename

当前已有 `ChatSendUseCase`，本轮建议优先把它收成唯一公开主入口。是否在后续 rename 成 `ChatTurnUseCase`，放到第二阶段评估，不在第一批就大范围改名。

### 决策 2：流式占位必须只有一条写路径

无论最终落到 Provider、HistoryStore 还是两者组合，对外都必须只有一个“交付协调者”。

### 决策 3：Provider 先按角色分类，再谈文件数量

不是简单把 5 个 Provider 文件合并成 1 个或拆成 8 个，而是先划清：

- 真相源
- 派生选择器
- 命令入口
- 临时过渡兼容

### 决策 4：页面瘦身必须配合能力下沉

如果只把 `chat_page.dart` 拆成几个 widget，但能力判断、引用协议拼装仍留在 UI，本质问题不会解决。

## 分阶段落地建议

### 阶段 A：收骨架

- 先统一发送命令和执行骨架
- 先让 `AgentApi` 回到“传输层”职责
- 不急着做命名与 dead code 清理

### 阶段 B：收状态

- 收 `ChatActions`
- 收流式交付状态机
- 收 Provider 真相源

### 阶段 C：收页面

- 把页面从业务细节中解放出来
- 补针对性测试

### 阶段 D：清历史包袱

- 删除确认无调用的旧类/旧方法/旧文件
- 修正命名与目录组织
- 更新文档与施工记录

---

## 每阶段交付物

### 阶段 A 交付物

- 统一发送命令模型
- 统一执行骨架
- `AgentApi` 公共逻辑收敛

### 阶段 B 交付物

- `ChatActions` 拆责完成
- 临时消息交付真相源唯一化
- Provider 文件边界清晰

### 阶段 C 交付物

- `chat_page.dart` 只保留编排职责
- `chat_message_list.dart` 只保留列表/视窗职责

### 阶段 D 交付物

- dead code 清理
- 命名统一
- 文档、测试、回滚方案补齐
