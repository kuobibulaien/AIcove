# 发送主链路收口方案

## 本文目标

把聊天发送统一成“一条主骨架 + 多种命令变体”，避免 `send / retry / regenerate / proactive` 各自维护自己的发送逻辑。

---

## 当前症状

当前发送链路主要涉及这些文件：

- `lib/src/features/chat/application/chat_send_use_case.dart`
- `lib/src/features/chat/application/chat_ports.dart`
- `lib/src/features/chat/infrastructure/chat_port_adapters.dart`
- `lib/src/features/chat/services/chat_send_service.dart`
- `lib/src/features/chat/services/chat_send_backend_service.dart`
- `lib/src/features/chat/services/chat_send_api_runner.dart`
- `lib/src/features/chat/services/chat_send_trace_payload_builder.dart`
- `lib/src/features/chat/presentation/chat_actions.dart`
- `lib/src/features/chat/presentation/chat_actions_action_ops.dart`

现状问题：

1. 多个入口都能决定“这次发送怎么配模型、怎么拼参数、怎么回调状态”。
2. `chat_send_service.dart` 与 `chat_send_backend_service.dart` 有明显转发/套壳关系，边界不清。
3. `ChatSendUseCase` 中已有主骨架雏形，但没有成为真正唯一的发送入口。
4. retry / regenerate 对默认模型解析的处理方式和普通发送并不一致。
5. tracing 逻辑和请求装配逻辑耦合较深，不利于后续继续调整。

---

## 目标口径

### 统一原则

1. 对外只有一个发送主入口。
2. 所有发送动作先归一化成统一命令，再进入同一执行骨架。
3. 模型选择、工具注入、上下文装配都在主骨架内集中执行。
4. `ApiRunner` 只负责调用和流式响应驱动，不负责业务分支。
5. trace payload 只作为旁路输出，不再反向污染主发送流程。

### 建议保留的主入口

第一阶段建议继续保留 `ChatSendUseCase` 作为唯一公开入口，避免一开始就 rename 带来全局 churn。

可以在 use case 内部引入统一命令模型，例如：

- `normalSend`
- `retryTurn`
- `regenerateAssistant`
- `proactiveSend`

是否真的新增类型名，可以在实施时根据现有类型复用情况决定；关键是统一骨架，而不是执着于新建类名。

---

## 目标职责分层

### `ChatSendUseCase`

只做：

- 接收统一发送命令
- 协调 turn 生命周期
- 调用请求准备、API 执行、响应落地
- 对外暴露稳定回调

不做：

- 直接拼底层 HTTP 细节
- 承担纯转发适配壳

### 请求准备层

建议把“准备请求”的职责收成一组稳定能力：

- 模型决策
- 消息上下文组装
- 工具/插件注入
- trace 所需上下文采样

这里可以沿用现有 service 文件，但职责必须收清，避免重复准备。

### `ChatSendApiRunner`

只做：

- 调 Agent API
- 处理流式事件
- 输出标准化响应事件

不做：

- 决定发送变体
- 决定业务状态切换

### 响应落地层

建议显式收一个“响应落地/状态应用”职责，统一：

- assistant 消息落地
- tool 结果交付
- 错误回滚
- 状态切换

如果现有逻辑已能自然吸收到 use case 内，就不必强行新增文件；关键是把职责从 `ChatActions` 和 API runner 身上拿下来。

---

## 推荐重构步骤

### Step 1：先定义“统一发送命令”的最小口径

先把 4 类入口梳理成统一字段集：

- 会话标识
- 联系人/角色标识
- 用户输入或触发来源
- 本次 turn 类型
- 模型选择输入
- 是否带引用
- 是否允许工具
- 是否需要占位/流式

不要一开始就为每个场景造一堆子类，优先用一个最小 command 结构跑通。

### Step 2：让所有入口都只负责构造命令

把这些入口统一改成“只构造命令，不各自执行业务流程”：

- `ChatActions.send()`
- `ChatActions.retry()`
- `_regenerateInternal()`
- `sendProactiveTrigger()`

所有真正的执行都沉到 `ChatSendUseCase`。

### Step 3：合并重复的后端转发层

重点审视：

- `chat_send_service.dart`
- `chat_send_backend_service.dart`

如果其中一层仅承担“把参数再传给下一层”的工作，就应该被吸收。保留两层的前提只能是：

- 一层负责业务 orchestration
- 一层负责纯后端交互

否则就删壳。

### Step 4：统一模型选择和缺省规则

把普通发送、重试、重生成、主动触发对模型默认值的处理收口到一处。避免出现：

- 普通发送跟随联系人/会话配置
- retry / regenerate 却直接回落到某个全局默认模型

### Step 5：trace 旁路化

`chat_send_trace_payload_builder.dart` 继续保留也可以，但要保证它：

- 只消费已准备好的上下文
- 不决定发送链路分支
- 不成为请求装配的事实依赖

这些留给其他窗口，减少冲突。

## 与其他子任务的接口约定

### 给 `ChatActions` 窗口的约定

`ChatActions` 只需要知道：

- 如何构造统一发送命令
- 如何订阅稳定状态回调
- 失败时能拿到什么标准化错误/恢复信息

它不该再关心发送骨架内部如何执行。

### 给 Provider 窗口的约定

Provider 只关心发送状态的公开输出，不要再反向驱动发送内部细节。

### 给 UI 窗口的约定

UI 只调用 `ChatActions` 或其他明确命令入口，不直接触达发送 service。

---

## 验收标准

满足以下条件才算收口成功：

1. `send / retry / regenerate / proactive` 最终都进入同一 use case 主骨架。
2. 默认模型解析只剩一处权威实现。
3. `chat_send_service.dart` 和 `chat_send_backend_service.dart` 中不再存在明显重复转发壳。
4. `ChatSendApiRunner` 不再承担业务分支判定。
5. trace 输出仍可用，但去掉了对主逻辑的反向耦合。

---

## 风险点

1. 重构过程中最容易把“主动触发发送”和“普通用户发送”混成一套字段，导致上下文污染。
2. retry / regenerate 可能依赖历史消息裁剪逻辑，迁移时要先确认旧行为。
3. 如果一次性把太多回调签名改掉，会与 `ChatActions`、Provider、UI 三边同时冲突。

建议策略：

- 先保留兼容签名，内部收口
- 再做第二步清理旧接口
