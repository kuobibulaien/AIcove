# UI 页面与消息列表瘦身

## 本文目标

把聊天 UI 从“页面兼业务层”收回到“页面编排 + 展示组件”职责，并为后续持续迭代留下稳定落点。

---

## 当前症状

重点文件：

- `lib/src/ui/features/chat/pages/chat_page.dart`
- `lib/src/ui/features/chat/widgets/chat_message_list.dart`

当前主要问题：

1. `chat_page.dart` 体量过大，同时承担路由、输入、发送前拼装、能力判断、引用协议、页面回调。
2. `chat_message_list.dart` 既负责渲染，又负责分页、贴底、滚动状态、流式交接、动作回调，导致修改风险极高。
3. 页面层自己补业务兜底，使 Provider 和应用层本该处理的事情继续泄漏到 UI。

---

## 目标口径

### `chat_page.dart`

应负责：

- 页面路由参数承接
- 订阅页面需要的视图状态
- 组装 UI 控件
- 把用户动作转发给 `ChatActions` 或稳定命令入口

不应负责：

- 视觉模型能力判断
- 引用协议字符串拼装
- 会话状态多源 fallback
- 发送参数业务归一化

### `chat_message_list.dart`

应负责：

- 消息列表渲染
- 视窗控制
- 分页交互
- 与列表渲染直接相关的局部表现逻辑

不应负责：

- 自己定义临时消息生产规则
- 自己兜底状态来源
- 自己承担过多业务动作分支

---

## 建议拆分重点

### 1. 页面输入准备逻辑下沉

像以下逻辑应离开页面：

- 是否允许带图发送
- 当前模型/联系人是否支持视觉
- 引用消息如何转换为发送协议
- 发送命令字段如何归一化

页面只需要拿到已经整理好的“发送命令输入”。

### 2. 页面状态读取统一化

`chat_page.dart` 不再自己做：

- 当前会话 snapshot/db 双路径兜底
- 临时消息来源二选一
- 页面层私有重复派生

所有这些都应由 Provider 层提供稳定出口。

### 3. 消息列表只消费统一时间线视图模型

消息列表理想输入应该是：

- 一份稳定的时间线视图模型
- 一组明确动作回调
- 一组视窗配置

而不是让列表内部再去拼“临时消息 + 正式消息 + 交接状态 + 页面操作”。

### 4. 大文件拆分优先按“职责块”，不是按长度均分

对于 `chat_message_list.dart`，建议优先把以下能力拆出去：

- item 渲染族
- 视窗控制器协作
- 仅与分页相关的逻辑
- 仅与气泡动作菜单相关的逻辑

但列表主文件仍保留“列表编排层”角色，不要拆成毫无上下文的碎片。

---

## 推荐施工步骤

### Step 1：先收页面对业务层的越界逻辑

优先把这些逻辑从页面下沉：

- 发送前业务判断
- 引用协议构造
- 模型能力兼容判断

这样即便还没拆 widget，页面已经先轻一截。

### Step 2：统一页面读取出口

把页面所有关键状态读取切到稳定 Provider/视图模型，不再出现页面自己兜底第二数据源的情况。

### Step 3：拆消息列表内部职责块

建议按“可独立测试的职责块”拆：

- 渲染
- 视窗
- 分页
- 动作菜单

不要单纯为了压行数去切很多无语义的小部件。

### Step 4：回头压缩 `chat_page.dart` 公开体积

只有前 3 步做完后，再回头看页面是否还需要继续拆文件。否则很容易把业务逻辑只是从一个 UI 文件搬到另一个 UI 文件。

---

## 可再拆成两个窗口的子范围

如果你想继续分给两个窗口，可以这样拆：

### UI-A：页面编排窗口

负责：

- `chat_page.dart`
- 与页面输入、顶部栏、底部操作条直接相关的 widget

### UI-B：消息列表窗口

负责：

- `chat_message_list.dart`
- 与列表 item、分页、视窗控制相关的 widget

两个窗口尽量不要同时写同一个文件。

---

## 建议写文件范围

推荐由 UI 窗口负责：

- `apps/aicove_flutter/lib/src/ui/features/chat/pages/chat_page.dart`
- `apps/aicove_flutter/lib/src/ui/features/chat/widgets/chat_message_list.dart`
- `apps/aicove_flutter/lib/src/ui/features/chat/` 下与聊天页面强耦合的子 widget

是否继续扩散到 `features/chat/` 内部应用层文件，不由 UI 窗口主导。

---

## 与其他窗口的接口约定

### 给 Provider 窗口

UI 只接受稳定 Provider，不自行做 fallback。

### 给 Actions/发送窗口

UI 只传命令输入，不再依赖发送 service 的内部细节。

### 给清理窗口

UI 窗口确认页面不再引用旧 helper/旧兼容函数后，清理窗口再删除。

---

## 验收标准

1. `chat_page.dart` 不再承担模型能力判断、引用协议拼装、状态多源 fallback。
2. `chat_message_list.dart` 只处理列表/视窗/渲染职责。
3. UI 对外只依赖稳定 Provider 和动作入口。
4. 页面修改不再需要同时理解发送链内部细节。

---

## 高风险点

1. 页面越界逻辑下沉时，最容易出现“功能没坏，但交互细节变了”的回归。
2. 列表拆分时，最容易破坏自动跟随、分页加载、流式交接这类细腻行为。
3. 如果 UI 在其他窗口接口没稳定前就先拆，返工概率会很高。

建议：

- 先等发送/Provider 边界稳定
- 再推进 UI 瘦身
