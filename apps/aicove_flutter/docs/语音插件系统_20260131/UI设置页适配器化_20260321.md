# TTS 设置页适配器化记录（2026-03-21）

## 背景

`lib/src/ui/features/plugins/widgets/tts_settings_form.dart` 之前同时承担了这些职责：

- 解析当前渠道和模型
- 判断阿里云 / 硅基流动的分支逻辑
- 直接拉取远端音色
- 直接删除远端音色
- 维护自定义音色编辑弹窗

这导致设置页一旦接新厂商，就需要继续往 UI 里塞厂商判断，文件很快膨胀成“大杂烩”。

## 本次拆分

### 1. `tts_provider_context.dart`

位置：`lib/src/features/plugins/tts/tts_provider_context.dart`

职责：

- 从 `TtsConfig + AppSettings` 解析当前选中的 TTS 渠道
- 统一给 UI 提供：
  - 当前 `ProviderAuth`
  - 当前 `TtsVoiceProvider`
  - `apiKey`
  - `requestFormat`
  - `TtsCapabilities`

这样设置页不再自己判断“这是不是阿里云 / 硅基流动”。

### 2. `tts_voice_catalog_service.dart`

位置：`lib/src/features/plugins/tts/tts_voice_catalog_service.dart`

职责：

- 统一收口远端音色的：
  - `listVoices`
  - `createVoice`
  - `deleteVoice`
  - `queryVoiceStatus`

UI 只关心“我要列音色 / 删音色 / 创建音色”，不再直接依赖某个厂商的 service。

### 3. `tts_settings_form.dart`

主表单只保留：

- TTS 模型选择
- 语音频率
- 通用设置
- 组合音色区块

音色相关重逻辑已经拆出主文件。

### 4. `tts_voice_preset_section.dart`

职责：

- 展示当前音色列表
- 根据 `TtsCapabilities` 渲染提示
- 触发“获取音色 / 自定义音色 / 查看详情 / 删除本地音色”

### 5. `tts_voice_catalog_sheet.dart`

职责：

- 通过 `TtsVoiceCatalogService.listVoices()` 获取远端音色
- 动态展示“预置音色 / 已创建音色”
- 通过 `TtsVoiceCatalogService.deleteVoice()` 删除远端音色

### 6. `tts_voice_preset_editor_sheet.dart`

职责：

- 编辑本地音色素材
- 根据 `TtsCapabilities` 动态显示：
  - 本地文件上传
  - URL 输入
  - 参考文本必填 / 选填
  - 审核 / 过期提示
- 在渠道适配器可用时，通过 `TtsVoiceCatalogService.createVoice()` 直接创建远端音色

## 当前收益

### 设置页不再硬编码厂商判断

之前：

- UI 里直接写阿里云 / 硅基流动分支
- 远端删除直接调厂商 service
- 获取音色时还要手工区分不同返回格式

现在：

- UI 统一吃 `TtsProviderContext`
- 远端音色操作统一走 `TtsVoiceCatalogService`
- 厂商能力通过 `TtsCapabilities` 驱动显示

### 新接入厂商的改动范围缩小

现在新接一个厂商，设置页这层原则上只需要：

1. 实现新的 `TtsVoiceProvider`
2. 在 `TtsProviderFactory` 注册
3. 让渠道 `requestFormat` 能被识别

不需要再去主设置页里继续塞厂商 if-else。

## 仍然保留的边界

这次只处理了“设置页 + 音色管理”链路，没有继续改 `tts_service.dart` 的语音合成分发。

也就是说：

- 音色的列出 / 创建 / 删除已经适配器化
- 真正的语音合成请求构建仍然在 `tts_service.dart`

## 后续建议

### 1. 继续收缩 `voice_manager_service.dart`

当前设置页已经不再依赖它，但旧链路还没完全退场。

### 2. 给 `VoicePreset` 补厂商无关的元数据结构

现在 `VoicePreset` 里仍保留 `aliyun*` / `siliconFlow*` 字段，MiniMax 还在用临时 extension 存 `voiceId`，后面可以继续抽象成统一 metadata。

### 3. 第二阶段再处理 `tts_service.dart`

如果后面要把“语音合成”也彻底 adapter 化，可以再做一轮：

- 请求体构建下沉到各厂商适配器
- `TtsService` 只保留门面和调度职责
