# 连续打断转场方案调研

日期：2026-09-14。状态：调研与候选建议，尚未采用；不替代现行[全端布局规范](../../界面布局说明.md)或 ADR0033。

## 结论

有可行的动画机制，但本轮没有找到可以直接替换现有路由、且已证明同时满足连续打断与手机性能要求的成品。

优先进入页面原型验证的候选是 **Motor**：交给库维护弹簧和目标切换时的速度衔接，项目维护统一的导航接入。**Flutter 官方 SpringSimulation** 是零新增依赖的对照方案；若 Motor 在真实路由接入上没有明显减少维护工作，应优先保留官方原语方案。两者均未证明比当前 Cupertino 在手机上更快。

这与“换回自写曲线”不同之处在于物理算法由 SDK 或库负责，但项目仍必须承担页面生命周期和手势接入。不能把这一成本隐藏为“只需换一个动画”。

## 需求与判断口径

连续打断包括：进入途中返回、返回途中重新进入、连续退两层、手势取消后立刻再次操作。新操作必须立即成为目标，衔接当前可见位置和速度；不允许通过禁点、排队等待旧动画完成来掩盖问题。页面身份、表单草稿和实际导航栈也必须正确。

保留速度意味着反向操作后可能先有很短的减速再反向，这是物理连续性；它不应变成“仍然等待旧返回走完”。弹簧也不等于明显弹跳，可使用临界阻尼或无明显回弹的预设。

必须分别验证三层：数值是否连续、整个页面栈是否正确跟随、手机是否在帧预算内完成绘制。第一层通过不能代替后两层。

## 候选比较

版本来自调查当天 pub.dev API；源码检查与实验固定到表中版本，不把在线文档的较新 Flutter 版本当成本项目版本。

| 方案 | 本轮证据 | 维护与接入成本 | 判断 |
|---|---|---|---|
| Motor 1.1.0 | 60 次连续改目标，位置和速度连续，最终正确收敛 | 自动保存当前速度；无原生插件，依赖 Flutter、equatable、meta；没有现成 Navigator 页面栈适配 | 优先做真实路由原型 |
| Flutter 3.44.6 SpringSimulation | 相同实验通过，与其他两种引擎在相同弹簧参数下结果相同 | 无新增依赖；切目标时自行传入当前位置和速度，处理正反向状态与导航生命周期 | 零依赖对照候选 |
| flutter_physics 0.2.3 | 相同实验通过 | 仅依赖 Flutter；提供 PhysicsController，但仍需导航适配；当前处于 0.2.x | 备选，不同时引入两个引擎 |
| swipeable_page_route 0.4.8 | 返回中重进的底层轨迹与原版 Cupertino 完全一致 | 主要扩展滑动手势，默认仍用 CupertinoPageTransition；转场中禁止开始新滑动 | 不作为本问题的替代方案 |
| SwiftUIKit 0.2.1 的 SwiftPageRoute | 返回中重进时，底层仍继续向旧返回终点移动 | 继承 CupertinoRouteTransitionMixin，另有 auto_route、屏幕圆角等依赖 | 本轮场景未解决问题，不选 |
| 官方 animations 3.0.0 / PageTransitionSwitcher | 源码说明快速切换会同时保留多个退出子树；未做本轮运行实验 | 不是导航栈；已退出中的同 key 页面重进也可能生成新子树，需要另做页面身份和退出清理 | 适合另行评估视觉切换，不能直接替代当前导航 |

Motor 的发布版日期为 2025-12-02，flutter_physics 为 2026-09-12，SwiftUIKit 为 2026-08-06，swipeable_page_route 为 2026-01-02，animations 为 2026-08-19。发布日期不等于质量或维护保证，最终以固定版本实测为准。

### 手机系统返回的另一条路径

Android Predictive Back 支持返回手势过程中预览下层并取消，值得单独评估系统返回接入；它不是任意 push/pop 连续中断的完整保证，也不直接覆盖 Mac 的相同行为。本轮只查文档，未进行该路径的设备验证，不把它列为已通过候选。[Flutter 官方接入文档](https://docs.flutter.dev/platform-integration/android/predictive-back)

## 实验结果

实验位于仓库根 `.codex-temp/transition-research/probe/`，是独立 Flutter 工程；未修改 AIcove 的 pubspec 或 lockfile。SDK 使用项目 tool/flutterw，对应 Flutter 3.44.6。

### 动画引擎的连续改目标

统一弹簧参数：mass=1、stiffness=400、damping=40。目标在 0 和 1 之间切换 60 次，间隔轮流为 12、29、46、63ms；每次立即检查位置和速度衔接，最后等待收敛。

| 引擎 | 最大位置跳变量 | 最大速度跳变量 | 测试页面 build 次数 |
|---|---:|---:|---:|
| 官方 SpringSimulation | 5.55e-17 | 1.78e-15 | 1 |
| Motor | 5.55e-17 | 1.78e-15 | 1 |
| flutter_physics | 5.55e-17 | 1.78e-15 | 1 |

误差为浮点量级，三者通过设定断言。页面使用 AnimatedBuilder 的固定 child 和 Transform.translate；结果说明这种接法不必每帧重建页面，不是对真实设置页的 build 次数或帧率测量。

这里使用无固定时长的真实弹簧模拟。给 flutter_physics 指定固定 duration 或只把 Spring 当作 Curve 使用，不能直接沿用本次保速结论。

### 成品路由的返回途中重进

360×780 逻辑尺寸，先完整进入详情，再返回 160ms，立即 push 新详情。观察底层页面横坐标；负值表示向左移，0 表示回到原位。

| 路由 | 重进前底层 x | 重进 16ms 后 | 重进 160ms 后 | 此时新详情 x |
|---|---:|---:|---:|---:|
| 原版 Cupertino | -29.831 | -24.374 | -4.086 | 75.221 |
| swipeable_page_route | -29.831 | -24.374 | -4.086 | 75.221 |
| SwiftUIKit | -21.489 | -16.640 | -6.268 | 42.887 |

新详情已经向内进入时，底层却仍朝 0 完成旧返回。这说明这两个成品没有解决本轮检查的底层跟随问题。SwiftUIKit 对照关闭圆角裁剪并设 minScale=1，以隔离平移动作；未检验它全部转场或手势功能。

日志显示“6 tests passed”只表示三个引擎断言通过、三个路由轨迹采集和最终清理完成，不表示三个路由符合连续打断要求。

证据：`probe/test/candidates_test.dart`、`probe/tests.log`、`probe/pubspec.lock`。复跑方式是在 probe 目录运行项目绝对路径的 tool/flutterw test test/candidates_test.dart --reporter expanded。

## 为什么换一个弹簧库还不够

Motor 源码的 MotionController.animateTo 在停止当前 ticker 前保存位置和速度；官方 SpringSimulation 也可接收当前位置、目标与初速度。但 Navigator 的退出完成、重进后下层页面选择跟随哪个动画，是另一套状态管理。

当前问题涉及次级动画接力；不能只把前景曲线改为弹簧、继续依赖未处理的旧 secondaryAnimation。候选原型需要让同一页面的可见运动状态承接新的导航目标，并正确处理多层退出、路由销毁和取消。只用动画锁等旧退出结束不符合本次要求。

官方 AnimationController.animateWith 的动画状态保持 forward，返回需要正确使用 animateBackWith 或适配状态；直接将独立控制器实验复制成 PageRoute 会漏掉这个问题。[官方 API](https://api.flutter.dev/flutter/animation/AnimationController/animateWith.html)

## 性能判断与下一步验证

代码结构上，单轴弹簧加页面平移不需要整页布局动画，也不要求新增模糊、透明度或缩放层。它具有保持低开销的条件，但没有测量证据证明 Motor 比官方弹簧更快。固定 child 也不意味着所有像素不重绘，页面材质、阴影和业务初始化仍可能产生绘制成本。[Flutter 性能建议](https://docs.flutter.dev/perf/best-practices)

下一步只验证一个共用导航原型，以 Motor 与官方原语对照；在确认路线前不全量替换业务页面。后续验收至少包含：

1. 真实设置→聊天插件→长期记忆，以及设置→模型→供应商链路；覆盖二级、三级、连续退两层和立即重入。
2. 进入后 80/180/300/380ms 返回、返回途中重进、连续点击与手势取消；保留页面身份、草稿和 PopScope 语义，不禁点或排队掩盖问题。
3. 在手机 Profile 构建测量 UI/raster 帧耗时、P95/P99 与超帧预算比例，按实测刷新率确定预算；与相同页面、相同材质、相同输入序列的当前版比较。
4. 检查结束后 route/overlay/监听器数量恢复，重复操作不积累退出页面；同时回归宽屏同级直接切换与跨宽度状态保留。

调研阶段没有将候选接入 AIcove，没有重装应用，也没有完成候选方案的手机帧率或整页手势验收。后续组件库演示另记如下。调研确认了引擎连续性与两个成品的具体局限，尚不能承诺整页效果已解决。

## 组件库交互演示（2026-09-14）

按用户要求，在设置→调试→组件库顶部增加 Motor、官方弹簧、flutter_physics 三个按钮。各自使用实际库控制器，参数保持本报告中的 mass=1、stiffness=400、damping=40；普通轨迹接近属于预期，不通过人为换参数制造差异。

演示使用同一页面和固定 child 的平移；底部“返回／重新进入”按钮始终可点，页面可横向拖动，支持拖动取消和系统返回，系统减少动画时直接到目标位置。它使用组件库专用的透明零时长路由承载；实际页面位移由所选引擎完成，退出完成前保持该路由挂载以允许重进，取消的旧退出不会移除新目标页面。此接法演示一个页面的运动与打断，不模拟完整业务多层栈或 Cupertino 的底层视差。

实现：lib/src/ui/features/debug/pages/spring_transition_demo.dart。新增依赖固定 Motor 1.1.0 与 flutter_physics 0.2.3，仅用于组件库。业务路由仍遵循现行规范，正式选型未定。
