# 聊天 TTS 多模态拆分记录（2026-03-20）

## 背景

`lib/src/features/chat/services/chat_tts_handler.dart` 之前同时承担了这些职责：

- 多模态片段规则规划
- 流式后补插槽计算
- TTS 占位创建与原位补齐
- 慢图占位、生成、交接与失败回挂
- 最终写库编排

这会让流式链路和多模态执行细节耦合过深，后续只要改动 `<tts>` 或 `<image>` 其中一条链路，就很容易误伤另一条。

## 本次拆分

### 1. `chat_multimodal_delivery_planner.dart`

只负责把 `replyText + pluginEvents` 规划成执行计划，不碰数据库、不发起 TTS、不发起生图。

当前输出两类计划：

- `planSequentialSteps()`：给非流式混排使用
- `planPostStreamSupplements()`：给流式收尾后的后补阶段使用

### 2. `chat_pending_tts_resolver.dart`

只负责 TTS 占位消息：

- 创建 `AudioBlock(pending)` 占位
- 调用 `TtsPlayerManager` 生成音频
- 成功时原位更新为 `AudioBlock(success)`
- 失败时回退为文本消息

### 3. `chat_deferred_image_delivery.dart`

只负责慢图链路：

- 挂出尾部“生成中...”占位
- 调用图片插件生成 inline image
- 等待正式消息稳定交接后移除临时占位
- 失败时把隐藏图片上下文挂回最近文本锚点

### 4. `chat_tts_handler.dart`

保留为门面与编排层：

- 判断当前是普通交付还是流式后补
- 调用规划器拿到执行计划
- 按计划串起文本、TTS 占位、慢图任务
- 统一维护写库串行队列

## 现在的交付规则

对于类似：

`文本a。<tts>语音段</tts>文本b。<image>slow landscape</image>文本c。`

当前规则是：

1. 先发 `文本a。`
2. 立刻发 TTS 占位
3. 继续发 `文本b。`
4. 如果 image 还没好，不阻塞，继续发 `文本c。`
5. 尾部保留一个正常“生成中...”气泡等待图片
6. 图片完成后原位让位给最终图片消息

## 排查入口

- 文本 / TTS / image 的顺序不对：先看 `chat_multimodal_delivery_planner.dart`
- TTS 占位没有原位更新：看 `chat_pending_tts_resolver.dart`
- 慢图占位不消失、图片突然插错位置：看 `chat_deferred_image_delivery.dart`
- 流式 finalize 后补链路接错：看 `chat_tts_handler.dart`

## 2026-03-21 补充：移除“消息整理中”阶段

### 现象

- 多模态回复已经按顺序自然落位；
- 但在 API 返回、`buildAssistantMessages()` 开始前，发送链路还会额外切一次 `ChatStatus.processingResponse`；
- 前端标题会短暂显示“消息整理中...”，和慢图 / TTS 的正常补位叠在一起，造成一次明显闪烁。

### 根因

- `chat_send_use_case.dart`
  - `_executeTurn()` 之前会在真正进入多模态交付前调用 `onProcessingResponse()`；
  - 这一步来自旧的“后处理”心智，但当前消息已经改成在 `deliverResult()` 中直接顺序发送；
  - 因此它不再承担实际工作，只会多制造一次状态切换。

### 调整

- 保留 `thinking / toolCalling / generatingVoice / generatingImage` 等真实阶段；
- 移除运行时的 `processingResponse` 切换，不再向前端广播“消息整理中...”；
- 多模态仍按既有 planner 与 handler 直接交付：
  - 文本先发；
  - TTS 先占位再原位补齐；
  - 慢图尾部挂正常“生成中...”气泡，生成完成后自然接管。
