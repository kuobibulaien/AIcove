# 聊天主流程 + API层 + 插件层全面重构方案

> 创建日期：2026-03-22
> 状态：设计中
> 定位：总方案入口

---

## 概述

这份方案不是上一版“聊天主流程全面重构方案”的覆盖版，而是它的上位总方案。

原因很简单：

1. 本轮问题已经不再只是 `features/chat/` 内部失控，而是聊天主流程、`core/api/`、`features/plugins/` 三层相互缠绕。
2. 如果继续只从聊天层动刀，`agent_api.dart`、TTS 路由、生图适配器旁路这些结构问题还会反向把聊天层拖回去。
3. 用户后续明确要做多厂商接入，因此必须把“聊天供应商 / 生图供应商 / TTS 供应商”放进同一套架构口径里重新定义。

本方案的目标不是一次性大换血，而是先建立一套可长期演进的施工蓝图，让后续多窗口并行施工时不再“各写各的”。

---

## 本轮总目标

1. 让聊天发送从多入口、多骨架，收敛成一条稳定主链。
2. 让 `core/api/` 从“大门面 + support 旁路”变成真正分层的执行体系。
3. 让聊天、生图、TTS 三套适配器从各自为政，收敛成统一的供应商接入模型。
4. 让 TTS 和 image 插件从“插件里兼任半个 API 层”回到编排职责。
5. 让 `memory / sticker / time_awareness / trigger` 这些插件补上统一模板，减少样板分叉。
6. 让迁移有清晰阶段、清晰回滚点、清晰并行边界。

## 总成功标准

如果这轮总方案真正落地，团队应该能得到下面这些结构性收益：

1. 查“发一条消息到底怎么走”时，只需要沿一条主链往下读。
2. 查“某个 provider 为什么被选中”时，有统一的 provider metadata / capabilities / adapter registry 可以看。
3. 新增聊天、生图、TTS 厂商时，接入步骤稳定可预测，而不是每次重新摸索。
4. TTS 和 image 插件不再各自暗藏一套厂商路由和半套 API 执行链。
5. 旧 support、旧 dead code、旧注释大块不再长期悬空。
6. 并行施工时，每个窗口都知道自己能动哪些文件、不能动哪些文件。
