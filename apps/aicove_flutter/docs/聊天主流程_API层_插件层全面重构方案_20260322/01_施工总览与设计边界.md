# 施工总览与设计边界

## 这轮到底在解决什么

当前问题不是“有几个大文件”，而是三条主轴同时失稳：

1. 聊天主流程没有唯一骨架。
2. API 层没有真正稳定的执行边界。
3. 插件层已经演变成多套半抽象运行时，尤其是 TTS 和生图。

这三个问题互相放大：

- 聊天层为了兼容现状，不断往 `ChatActions`、`ChatSendBackendService`、`ChatSendApiRunner` 里塞兜底。
- API 层因为没有统一 transport / runtime / adapter 边界，只能在 `agent_api.dart` 和 support 文件里继续堆分支。
- 插件层因为拿不到稳定的供应商抽象，只能自己判断 provider、自己拼请求、自己兜兼容。

所以这轮不是三个独立重构，而是一轮“聊天主链 + API 运行时 + 插件接入模型”联合治理。

---

## 统一设计原则

### 1. 先冻结契约，再迁移实现

不要一边改调用口，一边改内部职责，一边删旧代码。先把对外契约、阶段边界、兼容壳定义清楚，再逐步搬实现。

### 2. 先收唯一真相源，再谈文件数量

目标不是把巨型文件机械拆碎，而是明确：

- 哪一层是唯一入口
- 哪一层是真相源
- 哪一层只是派生
- 哪一层只是兼容壳

### 3. 新旧链路可以并存，但必须有主次

迁移期间允许新旧实现共存，但必须满足：

- 主链已明确
- 新链是未来目标
- 旧链只是过渡
- 删除时机已写进计划

### 4. 统一供应商接入模型必须跨聊天、生图、TTS 三域

不能只给聊天做 adapter，给生图做一半 adapter，给 TTS 只做音色 CRUD。否则多厂商扩展永远无法稳定。

### 5. 页面层只做编排，不做协议

UI 层可以决定用户体验，但不应再负责模型能力判断、请求参数整形、厂商语义兜底。

## 本轮目标架构口径

建议把本轮相关代码统一理解为 5 层：

### 1. UI 编排层

职责：

- 页面展示
- 用户交互
- 轻量编排
- 调用应用层命令

不负责：

- 请求协议拼装
- provider 能力兜底
- transport 细节
- 插件厂商判断

### 2. 应用层

职责：

- 接收一次聊天 turn 或一次插件任务的统一命令
- 组织完整执行流程
- 协调交付状态与落库

### 3. 领域策略层

职责：

- provider 选择策略
- 插件能力判定
- 发送命令归一化
- 流式交付状态机
- 音色/图片参数的领域规则

### 4. 基础设施层

职责：

- adapter registry
- provider metadata
- 持久化
- 配置解析
- 日志诊断

### 5. 传输执行层

职责：

- 构建 HTTP / WS 请求
- 发送请求
- 处理 stream / direct 响应
- 转换异常
- 提供统一执行结果

### 本轮明确不做

1. 不重做数据库真相源与 schema。
2. 不改后端接口协议。
3. 不引入新状态管理框架。
4. 不先做全局 rename 再慢慢回填职责。
5. 不为了“统一抽象”而把所有小插件强行写成一模一样。

## 统一命名与职责口径

后续文档里统一使用以下口径：

- `Facade`
  - 对外稳定入口，只聚合，不承载大段执行细节。
- `Runtime`
  - 真正执行一类任务的运行时模块，例如 chat stream runtime。
- `Transport`
  - 发送请求、处理超时、读取流、转换异常的层。
- `Adapter`
  - 面向某个供应商，完整覆盖请求构建、响应解析、能力声明、必要的 transport policy。
- `Provider Metadata`
  - 供应商基础信息、鉴权方式、请求格式、显示名、默认模型、能力等静态声明。
- `Coordinator`
  - 协调多个状态源的交付器，例如流式占位与正式消息交接。
- `Compatibility Shell`
  - 旧接口兼容壳，只转发，不继续扩张功能。

## 关键结构判断

### 判断 1：`agent_api.dart` 必须回归 Facade

只要 `agent_api.dart` 还同时承担上下文解析、日志、payload、直连、流式、生图和旧接口兼容，它就仍然是上帝类。

### 判断 2：聊天主流程必须有唯一执行骨架

`send / retry / sendWithImage / proactive / regenerate` 可以有多种入口，但不能有多条执行骨架。

### 判断 3：TTS 要拆成“合成运行时”和“音色目录”

当前 TTS 最大的问题之一是把“音色管理”和“语音合成”糊成了一套。后续必须拆成两个稳定抽象。

### 判断 4：image 插件必须停止兼任半个 API 层

`ImagePlugin` 应该只做插件编排、参数准备、结果回灌，不应该继续自己承担 provider/model 解析和执行细节。

### 判断 5：其他插件主要做标准化，不做业务重写

`memory / sticker / time_awareness / trigger` 本轮重点是统一模板和边界，而不是重写业务逻辑。

## 这轮文档的使用方式

本目录是为后续施工服务的，不是单纯的讨论稿。

每一卷都尽量给出：

- 当前问题
- 目标口径
- 建议模块划分
- 迁移顺序
- 写文件边界
- 验收标准

这样后面无论是单窗口施工还是多子代理并行，都能直接拿某一卷开工。
