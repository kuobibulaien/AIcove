# 其他插件联动与边界清理

## 这一卷的定位

本卷不追求把 `memory / sticker / time_awareness / trigger` 重写一遍，而是解决另外一个长期问题：

这些插件虽然都挂在统一插件体系下，但内部配置、提示词、事件输出和服务初始化方式仍然各写各的。

本卷目标是把它们收成“统一模板 + 保留业务差异”的形态。

---

## 统一模板目标

建议把插件至少分成三类：

### 1. Prompt 型插件

例如：

- `time_awareness`
- `sticker`

主要职责：

- 注入 system prompt
- 做轻量响应文本处理

### 2. Tool 型插件

例如：

- `trigger`

主要职责：

- 暴露工具
- 处理工具结果

### 3. Service 型插件

例如：

- `memory`

主要职责：

- 对接外部服务
- 提供数据能力
- 按插件协议给聊天主链输送能力

---

## 统一约定

建议所有插件都显式遵守下面这些约定：

1. 配置对象必须具备 `fromJson / toJson / copyWith`
2. 插件 `enabled` 语义一致
3. `getSystemPrompt()` 只负责 prompt，不偷偷做请求
4. `processResponse()` 只负责文本与事件，不偷偷改配置
5. 工具定义统一通过 `AITool`
6. 插件事件命名统一且 payload 结构可追踪

---

## 具体联动方向

### `memory`

方向：

- 把服务初始化和插件协议边界分清
- 避免“插件对象本体直接承担太多服务细节”

### `sticker`

方向：

- 统一 prompt 注入口径
- 统一响应文本清洗和事件输出格式

### `time_awareness`

方向：

- 统一 prompt 生成
- 避免配置和运行时逻辑杂糅

### `trigger`

方向：

- 工具定义和运行时处理分开
- 避免和主动关怀系统的后续重构边界冲突

---

## 命名与目录治理

本轮建议同步做这些清理：

1. 统一插件配置对象命名
2. 统一 provider / service / runtime 的后缀语义
3. 删除确认无调用的旧注释大块与过渡文件
4. 避免同一概念在 config、plugin、service 各起一个不同名字

---

## Dead Code 清理原则

### 可以删

- 已确认无调用
- 已有稳定替代链路
- 测试已覆盖替代路径

### 不能急删

- 运行期仍可能通过旧入口触达
- 还承担数据兼容
- 还未完成新旧切换验证

原则：

删除 dead code 必须跟着迁移阶段走，不能先凭感觉大扫除。

---

## 验收标准

1. 周边插件对外协议一致性提高。
2. 插件配置对象的风格统一。
3. prompt 型 / tool 型 / service 型插件边界更清楚。
4. 注释掉的大块旧实现与确认无调用的旧文件开始进入清理计划，而不是永久悬空。
