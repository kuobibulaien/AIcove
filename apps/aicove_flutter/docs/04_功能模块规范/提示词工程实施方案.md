# 提示词工程实施方案

> 更新日期：2026-04-16
> 依赖阅读：[提示词装配链路.md](提示词装配链路.md)

---

## 1. 目标

这份文档不再描述“现状是什么”，而是回答三件事：

1. 当前提示词工程里哪些问题最值得先修
2. 应该按什么顺序收口，避免越改越乱
3. 每一批改动大概落在哪些文件、要怎么验收

---

## 2. 收口原则

后续不管按几批落地，都建议先统一三条原则：

1. 单一真入口原则：
   - 聊天主链路的 prompt 装配只能认 `ChatSendBackendService`
2. UI 只暴露真实生效配置：
   - 配置页里能改的字段，要么真的进运行时，要么明确标记“当前不生效”
3. 文本规则与运行时路由分离：
   - “提示词文案写什么”和“消息/工具/adapter 如何路由”是两件事，不要混在同一个配置项里

---

## 3. 问题分级

### P1：页面可编辑，但运行时大概率不生效

#### P1-1 TTS `systemPromptTemplate` 与主链路脱节

现状：

- 配置页可以编辑 `ttsConfig.systemPromptTemplate`
- 调试页会展示它
- 但 `TtsPlugin.buildTagSemanticsPrompt()` 当前直接返回硬编码拼接文本，未读取该模板

风险：

- 用户/开发者误以为“改了就生效”
- 调试页与真实线上行为不一致
- 后续排障成本高

相关文件：

- `lib/src/features/plugins/tts/tts_plugin.dart`
- `lib/src/features/plugins/tts/tts_config.dart`
- `lib/src/features/plugins/plugin_providers.dart`
- `lib/src/ui/features/debug/pages/tool_prompts_page.dart`

建议决策：

- 二选一，不要继续维持中间态
- 方案 A：让运行时真正读取 `systemPromptTemplate`
- 方案 B：如果当前设计只需要固定标签语义，就撤掉该编辑项，避免 UI 制造假入口

#### P1-2 Trigger `logicSystemPrompt` 与主聊天链路脱节

现状：

- 配置页可以编辑 `logicSystemPrompt`
- 插件本身 `getSystemPrompt()` 直接返回 `null`
- 主聊天链路已接入 `trigger` 的提醒工具收集，但仍不注入额外 system prompt

风险：

- 配置项仍可能误导
- 新人容易误以为 `logicSystemPrompt` 会直接进入主聊天 prompt

相关文件：

- `lib/src/features/plugins/trigger/trigger_plugin.dart`
- `lib/src/features/plugins/trigger/trigger_config.dart`
- `lib/src/features/chat/services/chat_send_backend_service.dart`
- `lib/src/ui/features/debug/pages/tool_prompts_page.dart`

建议决策：

- 如果 Trigger 继续只通过工具接入，就在 UI 与文档里明确标注“提醒工具已进入主聊天链路，但 `logicSystemPrompt` 仅保留兼容回看”
- 如果后续希望它再承担 prompt 注入职责，再单独补齐 `getSystemPrompt()`、测试与 trace，不要让旧编辑项继续假装生效

### P2：结构清晰度不足，容易把维护带偏

#### P2-1 Time Awareness 模板配置未真正进入主链路

现状：

- 存在 `currentTimePromptTemplate`
- 但主链路实际走 `buildSystemReminderPayload()` 拼句子
- `buildSystemReminderFieldGuide()` 当前返回空字符串

风险：

- 页面改动与运行时效果不一致
- “时间提示规则”落在代码里，不便复用和观测

建议决策：

- 统一成“模板驱动”或“固定代码驱动”其中一种
- 不建议继续保留“配置字段存在，但主链路不用”的状态

#### P2-2 两套装配器并存

现状：

- `chat_request_builder.dart` 仍保留完整 prompt 装配逻辑
- 当前真实主入口已经是 `chat_send_backend_service.dart`

风险：

- 新改动写进旧装配器，实际线上不生效
- 代码评审和排障时认知分裂

建议决策：

- 先把旧装配器打上显式废弃标记
- 再逐步清点剩余引用，避免一上来直接删文件导致测试或工具页失血

#### P2-3 system prompt 极端膨胀时，可能只剩 system

现状：

- `truncateMessagesToFit()` 在 `chatBudget <= 0` 时直接返回 `systemMessages`

风险：

- 模型拿不到本轮用户消息
- 会表现成“规则很多，但像没听见用户在说什么”

建议决策：

- 把“最后一条真实用户消息必须保留”升级成硬约束，而不是尽量保留

#### P2-4 调试页不是最终 prompt 真相源

现状：

- `ToolPromptsPage` 更像片段视图
- 真实最终 prompt 还会叠加 runtime 信息、role 绑定、adapter 改写、截断结果

风险：

- 调试页看着正常，线上请求却不同
- 排障要多跳一步才能看到真实请求

建议决策：

- 调试页继续保留，但文案要明确它是“片段视图”
- 真相源应该收敛到 trace 面板或单独的最终请求预览能力

### P3：长期维护风险

#### P3-1 `personaPrompt` 一字段多职责

现状：

- 同时承载人设、绘图附加规则、工具预设绑定、画师预设绑定

风险：

- 数据观察困难
- 单项迁移或清洗时更容易误伤

## 4. 建议的收口顺序

### 第一批：先定唯一真入口

目标：

- 明确 `ChatSendBackendService` 是聊天主链路唯一装配器
- 旧装配器只保留过渡职责，或明确标记废弃

建议动作：

1. 在 `chat_request_builder.dart` 顶部加废弃说明
2. 全局搜索所有引用，确认是否仍有测试/工具页依赖
3. 如果仅剩历史残留，迁完后删除

预期收益：

- 后续所有 prompt 相关改动只落一处
- 减少维护者误判
- 给后续快照测试提供稳定装配面

### 第二批：清理死配置与假入口

目标：

- 保证“页面可编辑”的配置，要么真实生效，要么明确标注当前不生效

优先顺序：

1. TTS
2. Trigger
3. Time Awareness

建议动作：

- TTS：
  - 让 `buildTagSemanticsPrompt()` 走配置模板，或移除该编辑项
- Trigger：
  - 如果当前设计就是不参与聊天主链路，则把调试页文案改成“当前不注入聊天主 prompt，仅用于主动触发体系”
  - 如果计划接入，则补上清晰入口，不再保持半连接状态
- Time Awareness：
  - 决定是彻底模板化，还是删除 `currentTimePromptTemplate`

阶段产物：

- UI 不再展示误导性字段，或者字段和运行时已经打通
- 文档库、调试页、运行时代码三者口径一致

### 第三批：补运行时护栏

目标：

- 避免 system prompt 膨胀后吞掉用户输入

建议动作：

1. 在截断前保证“最后一条真实用户消息必须保留”
2. 给 system prompt 长度建立 warning 阈值
3. 在 trace 里明确记录：
   - 截断前消息数
   - 截断后消息数
   - 是否保留最新用户消息

阶段产物：

- 即使 system prompt 爆长，主链路仍能拿到用户当前输入
- 排障时能一眼看出“问题是超预算”还是“问题是装配错位”

### 第四批：补观测与快照测试

目标：

- 让“最终真实发送的 prompt”可以被稳定验证

建议动作：

1. 对 OpenAI / Claude / Gemini 各保留一份请求快照测试
2. 覆盖以下断言：
   - system prompt 内容
   - reminder 位置
   - tool schema 是否正确
   - 截断是否保留最新用户消息
   - trigger 是否未进入聊天主链路

阶段产物：

- 改提示词装配逻辑时，可以通过快照和断言快速发现回归
- Provider 适配层的格式差异不再靠人工目测兜底

### 第五批：长期数据模型整理

目标：

- 逐步拆掉 `personaPrompt` 混合字段的多职责设计

建议动作：

1. 先保留 `PersonaPromptCodec` 兼容旧数据
2. 新增结构化字段承接：
   - user prompt
   - custom drawing prompt
   - drawing tool preset name
   - drawing artist preset name
3. 迁移完成后再考虑移除混合编码

## 6. 最小实施批次建议

如果希望减少一次性爆炸，建议按下面的最小批次切：

### Batch A：认入口

- 给旧装配器加废弃说明
- 文档明确 `ChatSendBackendService` 为唯一真入口
- 补一份主链路快照测试骨架

### Batch B：清假入口

- 处理 TTS / Trigger / Time Awareness 三个“可编辑但未必生效”的配置
- 同步修正 `ToolPromptsPage` 文案和入口说明

### Batch C：补护栏

- 截断逻辑强制保留最新用户消息
- trace 新增“是否保留最新用户消息”等关键字段

### Batch D：做长期迁移准备

- 梳理 `personaPrompt` 的拆分目标字段
- 先建兼容层，再谈数据迁移

## 7. 验收标准

### A. 功能一致性

1. 调试页里能编辑的 prompt，真实请求里能看到对应变化
2. 标记为“不进入主聊天 prompt”的配置，在 UI 文案与实现上都保持一致
3. OpenAI / Claude / Gemini 三路请求结构都能稳定产出

### B. 护栏

1. 即使 system prompt 过大，也必须保留最新用户消息
2. 截断后 reminder 仍在正确位置
3. trigger 工具不误入聊天主模型

### C. 可观测性

1. trace 能看到 system 各段来源
2. trace 能看到最终 system prompt
3. trace 能看到截断前后差异

### D. 维护性

1. 仓库里只存在一个主聊天装配真入口
2. 配置页与运行时行为不再打架
3. 新人通过文档库能快速定位主链路和旁路链路

---

## 8. 验证策略

建议至少覆盖三层验证：

### 自动化测试

1. Provider 请求快照：
   - OpenAI / Claude / Gemini 各保留一份
2. 主链路装配断言：
   - system prompt 顺序
   - reminder 插入位置
   - trigger 不进入主聊天链路
3. 截断护栏断言：
   - 超预算时仍保留最新用户消息

### 手动排障回归

1. 打开调试页确认可编辑项和真实运行时一致
2. 打开 trace 面板确认最终 system prompt、messages 角色和截断结果
3. 验证视觉回退、`<tts>`、`<image>`、`<system-reminder>` 三类标签行为没有串线

### 文档一致性检查

1. `docs/README.md` 有入口
2. 现状文档和实施文档口径一致
3. UI 文案与文档不互相打架

## 9. 推荐实施节奏

### Phase 1：一周内可做

- 明确唯一真入口
- 清理或标注 TTS / Trigger / Time Awareness 假入口
- 补最关键的提示词快照测试

### Phase 2：随后推进

- 给截断逻辑补“保留最新用户消息”的硬约束
- 提升 trace 的最终 prompt 可视化

### Phase 3：中长期

- 结构化拆分 `personaPrompt`
- 收敛各插件配置模型

---

## 10. 实施前的注意事项

1. 不要一边保留旧装配器，一边继续往旧装配器加新逻辑
2. 不要让 UI 继续暴露“可编辑但不生效”的 prompt 字段
3. 对于 Trigger 这种明确走旁路体系的能力，要在文案和代码边界上都写清楚，不要继续维持半接入状态
4. 涉及提示词字段删改时，先核对调试页、设置页、trace 面板是否都有对应调整，避免只改运行时不改观测面

---

## 11. 和现状文档的配合方式

建议后续使用方式：

1. 先看 [提示词装配链路.md](提示词装配链路.md)，确认“当前真相”
2. 再看本文件，决定“先修哪一批”
3. 真正动手时，把每一批改动拆成独立任务，避免一次性大爆炸
