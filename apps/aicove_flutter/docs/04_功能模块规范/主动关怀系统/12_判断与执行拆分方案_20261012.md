## 1. 目标

1. **拆开「判断」和「执行」**：所有判断都交给决策模型（jev 这一类，只回答选择题和是非题）；只有「要发给用户的那句话」由聊天模型写。
2. **后台并回主链路**：不再有第二套请求拼装。用户收到的每一条主动消息，都由主聊天链路（人设、预设、插件说明、摘要齐全）生成。
3. **没配决策模型也能用**：退回用聊天模型做判断，并跳过审稿这类可选步骤。
4. **提示词全部重写**：删掉旧的三条，新写的读起来要像人话。
5. **流程变成固定流水线**：由代码按顺序编排，不再有「Agent 自己调工具，工具里再套一个模型」的循环。
6. **主动回复不只是发消息**：角色可以从一份「主动动作」工具列表里选择怎么联系用户。第一批动作是发消息和打电话（见 §4.8）。打电话在主动回复设置里单独开关，默认关闭；开了就说明用户欢迎被打扰，由聊天模型结合人设自由决定打不打，护栏只留最低限度。这是「判断都归决策模型」原则的唯一例外。

不在本次范围内：
- 改变触发时机的总体策略（例如静默 5 分钟后开始分析、后台分析的冷却时间）。
- 夜间免打扰规则本身，沿用现有的 `quietHours`。
- 云同步。
- 界面重做。设置页只做最小改动。

## 2. 决策模型是什么、能做什么

jev（TypeSafe 的判断模型）的接口不是聊天接口，而是「给一段事实，问几道题」：

- **请求**：`state`（一段事实文本）＋ `questions`。题目有三种：
  - `noul`：是非题；
  - `choice`：单选题，每个选项附一句说明；
  - `score`：有序档位。
- **回答**：每道题一个答案，加上置信度。
- **接入方式**：
  - TypeSafe 直连：`POST https://api.typesafe.ai/v1/systemone`
  - OpenRouter：`POST https://openrouter.ai/api/alpha/decisions`（alpha 接口，路径可能变）

  两者请求体一样，都用 Bearer key。
- **能力边界**：不能写字，不能输出任意数字。所以「几分钟后发」要改成「选一个时间段」，再由代码换算成具体时间；「旁白」这种需要写出来的内容，在新流程里取消（见 §4.3）。

依据：本机 `jev-use` 0.7.1 源码中的 `src/backends/native.ts`、`typesafe.ts`、`openrouter.ts`。

## 3. 新流程总览

```text
用户发消息 ──► ① 清场计时（代码）
                     │ 5 分钟没人说话
                     ▼
               ② 门卫（代码）── 不满足 ──► 结束
                     │
                     ▼
               ③ 判断（决策模型；无则聊天模型）：要不要、哪一种、什么时候
                     │ stay_silent / 置信度低 ──► 结束
                     ▼
               ④ 定时间（代码：时间段 → 具体时刻，套夜间规则）
                     │
                     ▼
               ⑤ 预生成（聊天模型，主链路，按「发送时刻」装配；开了打电话时可调用 call_user）
                     │
                     ▼
               ⑥ 审稿（决策模型；无则跳过）── 不过 ──► 重写 1 次 ── 仍不过 ──► 结束
                     │
                     ▼
               ⑦ 入库（代码：再确认用户没插话，存闹钟＋缓存＋指纹）
                     │ 到点
                     ▼
               ⑧ 执行动作（代码）：发消息，或者来电响铃
                    ├─ 指纹有效 → 前台、后台都直接用缓存
                    └─ 指纹失效 → 前台：回到③重新判断；后台：不发，留给前台
```

每一步都有明确的输入和输出，没有回头的箭头（⑥ 的重写是代码控制的固定一次）。这样它就是一条真正的 DAG，可以直接对上 Agent 运行时第二批的固定阶段管线。

## 4. 各步骤细节

### 4.1 ① 清场计时、② 门卫

逻辑不变，仍在 `analyzer_scheduler.dart`。

### 4.2 ③ 判断

新增应用层端口 `ProactiveDecisionPort`，有两个适配器：

| 适配器 | 何时使用 | 怎么问 |
|---|---|---|
| `JevDecisionAdapter` | 「判断模型」选的是决策模型类供应商 | 一次请求，批量问完全部题目 |
| `ChatModelDecisionAdapter` | 没配决策模型，或「判断模型」选的是普通聊天模型 | 一次聊天请求：不带工具，温度 0.2，要求只回一行 JSON |

两个适配器共用**同一份题目定义**（`ProactiveDecisionQuestions`）。jev 版把它转成 `questions`，聊天模型版把它渲染进提示词。题目的措辞因此只有一处。

本次要问的题：

| 题号 | 类型 | 问什么 | 选项 |
|---|---|---|---|
| `kind` | choice | 现在该怎么做 | `stay_silent` / `continue_chat` / `check_in` / `new_topic` |
| `timing` | choice | 如果要找，什么时候合适 | `in_minutes` / `in_half_hour` / `in_hours` / `later_today` / `next_morning` / `next_noon` / `next_evening` |
| `reminder_requested` | noul | 用户有没有明确让角色过一会儿提醒他 | 是 / 否 |
| `night_ok` | noul | 用户有没有说深夜也可以找他，或者约好的事本来就在深夜 | 是 / 否 |
| `already_covered` | noul | 已定好的提醒里，有没有一条和这次目的相同 | 是 / 否。只在已有提醒时才问 |

代码怎么用这些答案：

- `kind` 为 `stay_silent`，或 `already_covered` 为是：结束。
- **低置信度一律按沉默处理**：`kind` 置信度低于阈值，或 jev 返回 `escalate`，都结束。阈值沿用 jev-use：单选题报告置信度低于 0.5、是非题确定度（2·|P(是)−0.5|）低于 0.4 算拿不准；只有 `kind` 拿不准时才按沉默处理。理由是少打扰一次没关系，打扰错了用户会烦。
- **优先级不再问模型**：`reminder_requested` 为是时取 `high`；否则按类型取默认值（`continue_chat` / `check_in` → `medium`，`new_topic` → `low`）。
- `night_ok` 对应现有字段 `allowNight`。

### 4.3 ④ 定时间（代码）

各时间段的取值，以及哪些类型可以用：

| 时间段 | 换算 | 允许的类型 |
|---|---|---|
| `in_minutes` | 3～8 分钟 | continue_chat |
| `in_half_hour` | 25～40 分钟 | check_in |
| `in_hours` | 1～2 小时 | check_in |
| `later_today` | 3～6 小时 | check_in、new_topic |
| `next_morning` | 下一个 07:30～09:30 | check_in、new_topic |
| `next_noon` | 下一个 11:30～13:00 | new_topic |
| `next_evening` | 下一个 18:00～20:00 | new_topic |

规则说明：

- 范围内取随机值，避免每次都在整点发。
- 如果选的时间段不在该类型允许的范围内，就改用该类型的默认时间段：continue_chat → `in_minutes`，check_in → `in_hours`，new_topic → `next_morning`。
- 落在免打扰时段、并且 `allowNight` 为否时，顺延到免打扰结束后。顺延沿用现有逻辑。

**取消旁白**。旧流程让管家写一段 `background_narration`，再塞给聊天模型。新流程里，聊天模型本来就能看到完整的聊天记录，用户说过「去开会」它自己看得到。只要代码告诉它「现在是几点、隔了多久、这次大概是哪种开口」就够了（见 §6.4 提示词）。这样少了一次写作，也少了一个出错点。

### 4.4 ⑤ 预生成

- 仍走 `chatSendService.prepareApiConfig` 加 `executeApiCall`：不带工具，只跑 1 轮。
- 修一个现有问题：主链路里的时间感知插件用 `DateTime.now()` 作为当前时间（`chat_send_backend_service.dart` 约第 449 行）。所以预生成时，模型看到的「现在」是预生成那一刻，不是将来发送的那一刻。新增参数 `requestTimeOverride`，预生成时传入发送时刻。
- 提醒内容由代码按模板 `auto_reply.reach_out.reminder` 渲染，作为最后一条 user 消息里的 `<system-reminder>` 放进去。放置方式和现在一样。

### 4.5 ⑥ 审稿

把候选回复、发送时刻和最近聊天放进 state，一次问三道是非题：

| 题号 | 问什么 |
|---|---|
| `pushy` | 有没有在质问、催促或者怪用户不回消息 |
| `time_mismatch` | 提到的时间（早上、晚上、刚才、昨天）和发送时刻对不上 |
| `out_of_character` | 读起来不像角色本人在聊天，比如提到系统、提醒、说明，或者像客服 |

三题都答「否」才算通过。不通过时重新预生成 1 次；还不通过就放弃这次主动消息，只记日志。没有决策模型时整步跳过，也就是方案里说的「可以跳过的步骤」。

### 4.6 ⑦ 入库

- 保留现有检查：用户在这期间发了新消息，本次作废。
- 新增**缓存指纹**，和闹钟、缓存一起存：
  - 会话最后一条消息的 id；
  - 角色人设、绑定预设、聊天模型三者的版本摘要。

### 4.7 ⑧ 发送

**缓存是否有效，改为看指纹，不再看是否超过 60 分钟。** 用户一发新消息，闹钟就会被清掉，所以只要指纹没变，缓存就是按当前上下文写的。另外加一条：实际发送时刻比计划晚超过 2 小时（例如手机休眠、WorkManager 延迟），也算失效，因为话里提到的时间可能已经不对了。

| 场景 | 指纹有效 | 指纹失效 |
|---|---|---|
| 前台 | 发缓存，按正常回复做插件后处理和分段 | 回到③重新判断：情况可能变了，不一定还该发 |
| 后台（WorkManager） | 发缓存，写数据库并弹通知（和现在一样） | **不发**，把闹钟标为「待前台处理」。App 回到前台后，如果离计划时间不到 6 小时，走前台的失效流程；超过就丢弃 |

删除内容：
- `background_service.dart` 里的 `_fetchAiReply`、`buildBackgroundLiveGenerationSystemPrompt` 和那条独立的请求拼装；
- 提示词节点 `auto_reply.background.objective`。

### 4.8 主动动作（工具列表）

主动回复的结果不再固定为「发一条消息」，而是由一份**主动动作注册表**决定还能做什么。每个动作是一条定义：

| 字段 | 作用 |
|---|---|
| `id` | 例如 `send_message`、`call_user` |
| 可用条件 | 由代码判断，例如设置开关、插件是否开启、平台是否支持 |
| 工具声明 | ⑤ 预生成时交给聊天模型的工具名、说明和参数 |
| 底线护栏 | 无论模型怎么选都要守的规则，违反就降级 |
| 执行器 | ⑧ 到点后具体做什么 |

`send_message` 是默认动作，不需要工具：模型直接写出来的正文就是消息。以后加新动作（发一张图、发语音条），加一条定义即可，流水线不用改。

**打不打电话由聊天模型结合人设决定（用户 2026-10-12 裁决）**

「允许主动打电话」默认关闭。用户主动打开它，就说明愿意被打扰，所以这时要给角色更大的自由：

- **谁来决定**：不放进决策模型的选择题，而是在 ⑤ 预生成时把 `call_user` 作为真正的工具交给聊天模型。聊天模型走主链路，带着完整的人设和预设：古灵精怪的角色可能动不动就打过来，文静的角色可能很少打，这正是想要的效果。模型调用 `call_user(opening_line)` 就是打电话，参数是接通后的第一句话；不调用工具、直接写正文，就是发消息。
- **只有这一个工具**：预生成时其他工具仍然全部关闭，只暴露 `call_user`，而且只在开关打开、可用条件满足时才暴露。工具调用只是被记录下来，不会立即执行，到点后才由 ⑧ 执行。
- **决策模型也知道用户欢迎打扰**：开关打开时，§6.2 的事实里多两行：一是「用户开启了允许角色主动打电话，欢迎被主动联系」，二是一段截短的人设（300 字以内）。这样「要不要主动联系」本身也会更积极，而且符合角色的性格。
- **开关关闭时**：工具不出现，事实里也没有这两行，行为和 §4.2～§4.7 完全一样。

**两个动作的规则：**

| 动作 | 可用条件 | 底线护栏 | 执行 |
|---|---|---|---|
| `send_message` | 始终可用 | 无 | 和现在一样：发消息、分段、后台通知 |
| `call_user` | 「允许主动打电话」已打开（**默认关**）；该角色的语音插件开着，音色预设支持流式合成（目前只有 Fish）；有可用的识别来源；平台支持（见下表） | 只留三条：① 免打扰时段内不响铃，除非 `night_ok` 为是；② 同一时间只能有一通来电；③ 连续 2 通没接，暂停主动来电，直到用户下次回消息 | 来电响铃，见下文 |

和上一版相比，删掉了「每天最多 1 通」「不用于 continue_chat」「没接冷却 24 小时」三条，打电话的频率交给人设来决定。

保留下来的三条是用户自己设的免打扰时段、技术上的互斥，以及防止没人接时一直打。护栏否决时，把开场白当作消息正文发出去，不放弃这次主动联系。

**来电怎么响：**

| App 状态 | 表现 |
|---|---|
| 前台 | 弹出全屏来电页（复用通话页的样式，按钮换成接听和拒绝），响铃 30 秒 |
| 后台或已被杀（Android） | WorkManager 到点后发一条高优先级来电通知，带「接听」「拒绝」按钮。点接听打开 App，直接进入通话 |
| Mac | App 在运行时同前台；没在运行就收不到，和现在的主动消息一样 |
| iOS | 没有服务器推送，App 被杀后到不了点。本批不支持主动来电，选项不出现 |

Android 的全屏来电界面（锁屏上直接弹出）需要「全屏通知」权限，Android 14 起要用户在系统设置里手动授予。本批先只做普通的高优先级通知，不申请这个权限。

**接通以后：**
- 走现有语音通话流程（`activeVoiceCallProvider`），只加一点：**角色先开口**。接通后立刻把预生成好的开场白送去合成并播放，这一句作为通话的第一轮写进逐句记录。之后就和普通通话一样。
- 开场白有没有过期，按 §4.7 的指纹判断。过期了就不打这通电话：前台回到③重新判断，后台按「待前台处理」走。

**没接、拒绝、超时：**
- 在聊天里留一条「未接来电」的通话气泡。复用 `CallRecordBlock`，时长为 0，标记为未接，不写 `call_sessions`。
- 模型之后看到的文字是「`[未接的语音通话]`」，角色能知道自己打过电话、对方没接。
- 不自动补发消息，避免一次打扰变成两次。

**设置项：** 主动回复设置页新增「允许主动打电话」开关，默认关闭，下方说明「打开后，角色会按自己的性格决定要不要给你打电话，可能会比较频繁；免打扰时段不会响铃」。语音插件没开，或者音色不支持时，开关置灰，并显示原因。

## 5. 设置与数据

- **「判断模型」沿用现有设置项** `analyzerProvider` / `analyzerModel`，存储字段不变，只扩展含义：
  - 选的是决策模型类供应商，走 jev；
  - 选的是普通聊天模型，走聊天模型判断；
  - 不选，用默认聊天模型。
- **供应商新增一种协议「决策模型」**，可选 TypeSafe 直连或 OpenRouter decisions，填 key 和模型名（默认 `jev-latest`）。这种供应商不会出现在聊天模型的选择列表里。
- **删除「自定义分析提示词」**（`autoReplySettings.analyzerPrompt`）。新流程没有能整段替换的分析提示词。已经存过的自定义内容保留在设置数据里但不再读取，界面上去掉这个入口。
- **缓存指纹的存储**：需要给闹钟加字段。触发器目前存在 `auto_reply_trigger_storage`，实施时先确认是 JSON 存储还是数据库表；如果是数据库表，就需要一次 schema 迁移，开工前会单独说明影响和回滚。
- **隐私**：用了决策模型，最近 10 条聊天会发给所选的决策模型服务商。这和选用聊天模型服务商性质相同，设置页要写一句提示。

### 6.2 新增 `auto_reply.decision.state`：交给判断的「事实」

jev 和聊天模型判断共用这份事实。

```text
下面是用户和 AI 角色「{assistant_name}」的聊天。用户有一阵子没说话了，要决定角色要不要主动找他。

现在是 {now}，{weekday}，{day_period}。
用户最后一次说话是 {last_user_ago}前。
这之后角色已经主动发过 {unreplied_count} 条，用户还没回。
角色上一次主动找用户：{last_proactive_ago}。

已经定好、还没发的提醒：
{trigger_list}

最近的聊天：
{transcript}
```

- `transcript` 每行一条，格式为「`[10-12 21:03] 用户：……`」或「`[10-12 21:04] {assistant_name}：……`」，取最近 10 条。
- 默认不放人设：判断「要不要说话」主要看聊天内容。只有「允许主动打电话」打开时，才追加以下两段（见 §4.8）：

```text
用户开启了「允许角色主动打电话」，欢迎角色主动找他。
角色的性格：{persona_brief}
```

### 6.3 判断题目 `auto_reply.decision.questions`

这里的措辞就是 jev 的 `instructions` / `criteria`，也是聊天模型兜底时的选项说明。

**kind：角色现在该怎么做？**
- `stay_silent`：先不打扰。用户说了晚安、明显在忙、想自己待着，或者话已经聊完、没有自然的由头，或者角色已经主动找过、对方还没回。
- `continue_chat`：话说到一半停住了，用户可能只是走开一下，过几分钟接着聊很自然。
- `check_in`：用户说过要去做一件事（洗澡、吃饭、开会、出门、睡觉），等这件事差不多结束了，问问怎么样。
- `new_topic`：这轮已经自然聊完，隔一段时间再找个新话头打招呼。

**timing：如果要找用户，什么时候合适？**
- `in_minutes`：几分钟后
- `in_half_hour`：半小时左右
- `in_hours`：一两个小时后
- `later_today`：今天晚些时候
- `next_morning`：下一个早上，对方醒了以后
- `next_noon`：下一个中午
- `next_evening`：下一个傍晚

**reminder_requested**：用户有没有明确让角色过一会儿提醒他、叫他？

**night_ok**：用户有没有说深夜也可以找他，或者约好的事本来就在深夜？

**already_covered**：已经定好的提醒里，有没有一条想做的事和这次一样？

**审稿题**（⑥ 用，state 里会多出「发送时间」和「准备发的话」）：
- `pushy`：这条消息是不是在质问、催促，或者怪用户不回消息？
- `time_mismatch`：消息里提到的时间（早上、晚上、刚才、昨天之类）和发送时间对不上吗？
- `out_of_character`：这条消息读起来不像角色本人在聊天吗？比如提到了系统、提醒、说明，或者口气像客服。

### 6.4 新增 `auto_reply.decision.chat_fallback`：没有决策模型时给聊天模型

```text
你在帮一个聊天应用拿主意：用户有一阵子没说话了，AI 角色「{assistant_name}」要不要主动找他、什么时候找。你只做判断，不用写要发的话。

{state}

回答下面几个问题：

{questions}

拿不准就选 stay_silent。少打扰一次没关系，打扰错了用户会烦。

只回一行 JSON，别的什么都不要写：
{"kind": "...", "timing": "...", "reminder_requested": false, "night_ok": false, "already_covered": false}
```

`{questions}` 由 §6.3 的题目定义自动渲染，不另写一份。解析失败按沉默处理。

### 6.5 新增 `auto_reply.reach_out.reminder`：预生成时给聊天模型的提醒

```text
（这条不是用户发的。）
用户有一阵子没说话了。现在是 {fire_time}，离用户最后一条消息过去了 {gap}。你想主动给对方发条消息{kind_hint}。
就像你自己突然想起对方那样，自然地开口。对方没回可能只是在忙，别追问为什么不回，也别解释你为什么现在发消息，更不要提到这条说明。
```

`kind_hint` 由代码按类型填：
- continue_chat →「，接着刚才没聊完的说」
- check_in →「，问问对方之前说要去做的事怎么样了」
- new_topic →「，聊点新的，或者就是打个招呼」

### 6.6 新增 `auto_reply.tool.call_user`：打电话工具的说明

只在开关打开时，随 §6.5 的提醒一起交给聊天模型。在 §6.5 末尾追加一句：

```text
如果按你的性格，这会儿更想直接打个电话给对方，就用 call_user 打过去；不想打就照常写消息。
```

工具声明：

```text
名称：call_user
说明：直接给对方打电话。对方接起来以后，你说的第一句话就是 opening_line。想听对方声音、有话想当面说、或者就是想闹一闹对方的时候都可以打，按你自己的性格来。
参数 opening_line：接通后你说的第一句话。是在打电话，要像说话一样：短一点，口语一点，不要用表情、括号里的动作和任何标签。别解释为什么打来。
```

审稿时，打电话也要过 `out_of_character` 这道题；另外加一道 `not_spoken`：这句话是不是不像人在电话里会说出口的（太长、像书面语、带了动作描写）？

### 6.7 改写 `system_reminder.semantics`（全局共用）

```text
<{tag_name}> 里是应用附上的背景说明，不是对方说的话。心里有数就好，别照着念，也别提到它。
```

## 10. 需要用户拍板

1. ~~**后台失效时怎么办**~~：已被 Agent 运行时第二批 2f 取代（后台用无界面容器跑主链路，相当于下面的备选 B），见 §11。以下保留原文

   A 的代价：手机长时间不打开 App、并且上下文又变了的少数情况下，这条主动消息会延后到打开 App 时处理，或者直接丢弃。
2. **低置信度怎么处理**
   - 推荐：按沉默处理。
   - 备选：转交聊天模型再判一次。代价是多一次请求、多花钱。
3. ~~打电话由谁来决定~~：用户已裁决（2026-10-12）。开关打开时交给聊天模型结合人设决定，护栏只留三条底线，见 §4.8。

### 开工前的现场（2026-10-13）

Agent 运行时第二批（分支 `claude/jovial-goldberg-cb6b4a`，还没合进 main）的 2f 已经把前台、后台的主动回复收拢到同一个 `ProactiveReplyGenerator`。后台在 WorkManager 里起无界面的 Provider 容器，跑完整的主链路装配，并有租约认领和送达后标记；手机实测还没做。

### B1（2026-10-13）

| 方案条目 | 实际做法 |

| 判断端口与两个适配器 | `auto_reply/domain/proactive_decision.dart`：端口 `ProactiveDecisionPort`，题目定义 `ProactiveDecisionQuestions`。题目措辞只写在这里，jev 请求和聊天模型兜底共用。适配器是 `jev_decision_adapter.dart`（按地址选 `/v1/systemone` 或 `/api/alpha/decisions`）和 `chat_model_decision_adapter.dart`（后台 Agent 跑 1 轮、不带工具，解析一行 JSON；解析失败按沉默） |

| ⑦ 入库 | 写完再核对一次「用户这期间有没有说话」，说过就不建触发器 |

**与方案的差异：**
- **缓存有效性**：没有做指纹。AI 触发器的 `preparedAt` 改记为计划发送时刻，因为文案是按那一刻写的。沿用「60 分钟内算新鲜」，含义就变成了实际发送比计划晚超过 60 分钟才现场重写。上下文变化已经由「用户一说话就清掉触发器」保证。人设或预设被改动的情况暂不处理，到 B2 再看是否需要指纹。
- **题目措辞放在 Dart 常量里**，不放进 `prompt_defaults.json`。因为题目带选项结构，提示词库只存纯文本模板。

验证：`test/features/auto_reply/proactive_decision_test.dart` 覆盖了沉默判定、时间段越界与默认值、窗口翻到第二天、免打扰顺延、优先级、jev 请求格式与解析（低置信度、缺答案、HTTP 失败）、兜底 JSON 解析、事实与提醒的渲染，以及审稿重写和放弃。`headless_proactive_reply_test.dart` 增加了一条测试：传入 `requestTime` 就不读时钟。真实模型请求、jev 真实调用、实机都还没验证。

## 12. 收缩：暂不接入决策模型（2026-10-14）

**用户裁决**：决策模型的用途目前只有这一个功能，为它单独引入供应商类型、设置界面和一条从未用真实 key 跑通的请求路径，复杂度不划算。先留好接口，等决策模型有更多用途再接。

**保留**（与模型无关的部分）：
- 判断端口 `ProactiveDecisionPort` 与题目定义 `ProactiveDecisionQuestions`，以后接决策模型只需新增一个适配器。
- 一次批量回答选择题、代码换算时间、按发送时刻预生成、新提示词。
- 「判断模型」设置：选的聊天模型（可换便宜的小模型）通过 `ChatModelDecisionAdapter` 回答，只回一行 JSON，解析失败按沉默。

**删除**：
- `jev_decision_adapter.dart` 与供应商 `decision` 能力分支。
- `ProactiveAnswer` 的置信度字段，以及 `kind` 拿不准时按沉默的规则。现在只有缺答案或答案非法时按沉默。
- ⑥ 审稿：三道审稿题、`ContextAnalyzer.review`、`writeReviewedProactiveReply`、重写循环。⑤ 写完直接进 ⑦。§6.6 打电话审稿也随之取消。
- B3 整批，以及 §8 的对照实验。
- 真实模型测试只保留 DeepSeek 兜底那一半。

**以后接回**：新增一个适配器实现端口，在 `_defaultDecisionPort` 里按供应商能力选择。审稿如果需要，在端口上重新加，题目可从本文 §6.3 恢复。

| 接听 | `IncomingCallNotifier.accept` → `activeVoiceCallProvider.start(openingLine:)`，`ScriptedOpeningReplyGenerator` 让第一句直接说开场白，之后交回模型。App 跳到该角色聊天并打开通话页 |
| 没接、拒绝 | 账本记为 `missed`，由 `ProactiveCallSettler` 统一结算：`VoiceCallArchiver.archiveMissed` 以角色名义写一条 `CallRecordBlock.missed`（模型看到 `[未接的语音通话]`，时间取接听截止），不补发消息。结算在 App 启动、回前台、每次来电结局后运行，并在下一个截止时刻自醒（出错 15 秒后再试）；回前台时仍在响的后台来电直接在 App 里接着响 |
| 后台（Android） | WorkManager 到点：开关开着、没暂停时，先在账本占位（接听截止 1 分钟），占不到就当消息发；再认领送达并确认、发「角色来电」通知（`接听`／`拒绝` 按钮，响 30 秒），触发器记为已发。「拒绝」不打开 App，在通知回调 isolate 里直接把账本记为未接；点通知或「接听」在截止前直接接通，过了截止记未接。清单注册了插件的 `ActionBroadcastReceiver` |

**与方案的差异：**
- **提示词调过一轮**：初版提醒和工具说明里有「想闹一闹对方的时候都可以打」，真实请求里文静人设也每次都打。改为「电话比消息更打扰人，只有按性格真会直接打过去才打」，工具说明点明「爱打电话的常打，文静的多半只发消息」。改后 DeepSeek Flash 三轮：古灵精怪人设 3/3 打电话，文静人设 3/3 发消息（`proactive_call_real_model_test.dart`）。
- **开场白新鲜度**沿用 B1 的「计划时刻起 60 分钟」，没做指纹。
- **后台不检查音色与识别**：后台没有 Riverpod 容器，判断时已经查过；接通时不可用会在通话页显示原因。
- **铃声**：没有内置铃声文件，只有震动（手机）和系统提示音（桌面）。
- **电话也占主动回复额度**：响铃算一次送达，和消息共用每日上限与最小间隔。
- **后台看不到 App 内通话**：WorkManager isolate 只能看账本，用户正在 App 里打语音通话时，后台仍可能弹来电通知（App 在前台时由前台分发处理，此情形只在 App 被挂起而通话未挂断时出现）。
