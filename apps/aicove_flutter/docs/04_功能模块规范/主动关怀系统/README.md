## 概述

本文档描述「主动关怀」功能的完整重构方案，将现有的 XML 标签解析方式升级为原生工具调用（Function Calling），并实现完善的预生成、作废、触发机制。

### 什么是主动关怀？

想象你的 AI 女友能像真人一样：
- 早上主动发”早安”
- 你说去开会，2小时后她问”会开完了吗？”
- 深夜发”想你了”

这就是主动关怀——让 AI 在合适的时机主动联系用户，而不是只会被动回复。

截至当前代码：

- **AI 管家仍是 JSON**：`lib/src/features/auto_reply/data/context_analyzer.dart` 强约束 JSON 解析（待后续统一为 tool calling）
- **触发器持久化是 SharedPreferences**：`lib/src/features/auto_reply/data/auto_reply_trigger_storage.dart`（后续可迁移到 SQLite）
- **Tool Calling 基础设施已存在**：`AITool/ToolParameter` + `AgentApiClient.sendMessageRich(... tools: ...)` + provider adapters + `ChatSendService`
- **执行权认领表已就位**：Schema v14 `auto_reply_trigger_claims` 表，前后台原子互斥

### 口径确认（本次重构的”唯一标准”）

> 这部分是为了让”施工的 AI/同学”不跑偏：只要按这 4 条做，就不会方向错。

1. **工具调用升级为“两回合（可递归多回合）”**：先让模型提出 tool_calls → 系统执行工具 → 把 tool 结果回填到 messages → 再请求模型生成“人话回复”。  
2. **新增 `list_reminders` / `search_reminders` 工具**：并允许 `delete_reminder` 用 `query` 删除（因为用户通常不知道提醒 ID）。  
3. **触发时机统一走 `AnalyzerScheduler`**：只用 `5分钟无消息` / `切后台（10秒防抖 + 冷却期）` 触发 AI 管家分析；收敛 `ChatActions._scheduleContextAnalysis()` 的 2 秒直触发。  
4. **作废判断用“最后一条用户消息 id/时间”**：不再用“消息总数”判断，避免 AI 自己回复/系统消息导致误伤。

## 核心设计要点

### 1. 双轨制：对话 AI + AI 管家

```
┌─────────────────────────────────────────────────────────────┐
│                        双轨制架构                            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   用户明确要求"设提醒"                                        │
│          │                                                  │
│          ▼                                                  │
│   ┌─────────────┐     原生工具调用                           │
│   │  对话 AI    │ ──────────────► create_reminder           │
│   │ (角色扮演)  │                                           │
│   └─────────────┘                                           │
│                                                             │
│   ─────────────────────────────────────────────────────     │
│                                                             │
│   对话自然结束（切后台/5分钟无消息）                           │
│          │                                                  │
│          ▼                                                  │
│   ┌─────────────┐     原生工具调用                           │
│   │  AI 管家    │ ──────────────► schedule_proactive        │
│   │ (独立上下文) │                                           │
│   └─────────────┘                                           │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 2. 预生成 + 延迟发送

```
创建触发器 ──► 保存上下文快照 ──► 预生成内容 ──► 等待 ──► 检查作废 ──► 发送
                    │                              │
                    │                              ▼
                    │                        用户发了新消息？
                    │                         ├─ high: 继续发
                    │                         ├─ medium: 作废
                    │                         └─ low: 作废
                    │
                    └── 记录“创建时最后一条用户消息 id/时间”，用于判断是否有新消息
```

### 3. 触发器优先级

| 优先级 | 场景 | 作废条件 |
|--------|------|---------|
| **high** | 用户明确设的闹钟/提醒 | 不作废，到时间必发 |
| **medium** | AI 管家自动创建的关怀 | 用户发了新消息就作废 |
| **low** | "想你了"之类的情感消息 | 用户发消息 或 正在聊天就作废 |

## 快速理解

用一个完整场景串联：

> **场景：用户说"我去睡了"**
>
> 1. 用户发送"我去睡了，晚安~"
> 2. AI 回复"晚安，好梦 ❤️"
> 3. 用户切到后台
> 4. 系统检测到对话结束，调用 **AI 管家**
> 5. AI 管家分析对话，决定创建一个"早安"触发器
> 6. AI 管家调用 `schedule_proactive` 工具：
>    ```json
>    {
>      "title": "早安问候",
>      "delay_minutes": 480,
>      "priority": "medium",
>      "prompt": "现在是早上，用户昨晚说去睡觉了，请温柔地说早安"
>    }
>    ```
> 7. 系统创建触发器，**保存创建时最后一条用户消息 id/时间**
> 8. 系统用独立 session 调用 AI，**预生成内容**："早安呀~昨晚睡得好吗？"
> 9. 8小时后，触发时间到
> 10. 系统检查：当前“最后一条用户消息”还是当时那一条吗？
>     - 如果是 → 发送预生成的"早安呀~"
>     - 如果不是 → 用户已经发过新消息了，这个触发器作废
