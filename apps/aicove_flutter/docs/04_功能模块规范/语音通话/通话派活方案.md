# 通话派活：实施方案（ADR0090）

- 状态：待审，未施工（2026-10-17）
- 决定见 [ADR0090](../../../../../docs/项目记忆/决策记录/0090-通话Agent可派活并进入等待.md)；派活工具、回执和转告的既有机制见 [ADR0088](../../../../../docs/项目记忆/决策记录/0088-聊天模型委派杂活Agent.md) 与 [杂活 Agent 实施方案](../../02_前后端分离与架构规范/Agent工作区与杂活Agent实施方案.md) W2。

## 1. 现状与缺口

| 部件 | 现在 | 要改什么 |
|---|---|---|
| 通话插件 | `kVoiceCallContextPluginIds` 只有 `memory`、`time_awareness`（`api_runner_call_reply_generator.dart`） | 加入 `delegate_task`，仍受 `delegateTaskEnabled` 和 `supportsToolCalling` 控制 |
| 通话请求 | `prepareVoiceCallBaseConfig` 里 `clearTools: true`；`streamReply` 里 `availableTools: const []`、`maxRounds: 1` | 只保留 `delegate_task` 一个工具；仍是单轮请求，工具由通话会话自己执行 |
| 生成端口 | `CallReplyGeneratorPort.streamReply` 只吐台词增量 `Stream<String>` | 改为吐事件：台词增量、工具调用（流结束时给出） |
| 通话会话 | `VoiceCallSession` 只有音频阶段 `VoiceCallPhase`，轮次来源只有用户说话 | 加「等待中的任务」集合和回执输入队列；轮次边界检查队列 |
| 回执转告 | `TaskAgentService.deliver` 认领后调用注入的 `relay(conversationId, receipt)`，写人设文字消息 | 通话进行中，`relay` 交给 `ActiveVoiceCall`；挂断时没进入生成的退回文字转告 |
| 通话记录 | `CallRecordBlock` 存 `callId`／`durationMs`／`summary`／`turns`／`missed` | 加 `tasks` 字段；`content` 追加代码写的任务状态行 |
| 负责设备 | 用户发消息时 `ProactiveOwnership.claim` | 接通时也 `claim` |

## 2. 改动点

### 2.1 生成：台词和工具调用一起出

- `CallReplyGeneratorPort.streamReply` 改为返回 `Stream<CallReplyEvent>`：`CallReplyText(delta)` 和 `CallReplyToolCall(id, name, arguments)`。台词照旧边到边切句；工具调用在流结束时随最终结果给出。
- `ApiRunnerCallReplyGenerator` 传入 `delegate_task` 的工具定义，`maxRounds: 1` 不变（运行器不执行工具，只把调用交回来）。
- 请求历史由通话会话持有：每次工具调用以「助手工具调用＋工具结果」一对接在对应的助手轮次后面。只放在内存里，用来拼下一轮请求，不进逐句记录。
- `buildVoiceCallMessages` 的通话约束提醒加入派活规则（ADR0090 第 1 条），并接收等待中任务的列表（第 3 条）。

### 2.2 通话会话：等待与输入队列

- `VoiceCallSession` 新增：
  - `pendingTasks`：任务 ID → 任务说明摘要、开始时间。`start` 成功时加入，收到终态回执时移出，`needs_input` 时保留并标「等你回答」。
  - `_receiptQueue`：等待进入生成的回执。
  - `offerReceipt(receipt) → Future<bool>`：回执入队；包含它的那一轮开始生成时完成为 `true`；通话在那之前结束时完成为 `false`。
- 轮次边界：`_startReply` 之前、`_checkTurnEnd` 判定角色说完之后、`_commitUserTurn` 时，都检查队列：
  - 用户这一轮提交时队列非空：回执事件排在用户这句之前，一起进入这次生成；
  - 角色说完、用户没在说话（没有未提交的识别片段）且队列非空：立即用回执事件开一轮；
  - 其他时候（正在说、正在想、用户正在说）不动，等下一个边界。
- 回复里带工具调用时，台词照常播放；流结束后执行工具：
  - 有台词：执行完就结束，不补轮；
  - 没台词，或工具结果是失败：立即补一轮。
- 通话阶段 `VoiceCallPhase` 不新增值，等待是独立的状态；`ActiveVoiceCall` 把 `pendingTasks` 暴露给界面和小窗镜像。

### 2.3 转告路由

- 在注入 `TaskAgentService.relay` 的地方（`task_agent_providers.dart`）包一层：该会话有进行中的 `ActiveVoiceCall` 时，调用 `offerReceipt` 并返回它的结果；返回 `false`（挂断前没进生成）时，接着走原来的文字转告，返回文字转告的结果。认领（`claimDelivery`）和完成（`completeDelivery`）仍由 `deliver` 负责，不另起一套去重。
- 接通时调用 `ProactiveOwnership.claim(conversationId)`，保证 `ownsConversation` 为真。
- 通话期间 `TaskAgentSupervisor` 的周期扫描照常运行；扫到待转告的回执同样会路由进通话。

### 2.4 通话记录与模型可见文字

- `CallRecordBlock` 加 `tasks`：每项 `{taskId, instruction（截断）, startedAfterTurn, receipts: [{receiptId, status, relayedAfterTurn}], atHangup: relayed | running | fallback}`。`startedAfterTurn`／`relayedAfterTurn` 是在 `turns` 里的位置，记录页据此在逐句记录里插一行灰字事件。
- `content` 在摘要之后追加一行任务状态，例如：
  - `电话里派出的任务：查明天的天气（已在电话里告诉用户结果）`
  - `电话里派出的任务：订周六的位子（挂断时还没完成，结果会另行转告）`
  - 通话前派出、通话中转告的任务也列出。
- `VoiceCallSummarizer` 的输入 `turns` 之外加 `tasks`，提示词加一句「电话里派出的任务和结果按 tasks 写，不要猜状态」。
- 旧客户端：`CallRecordBlock.fromJson` 不读 `tasks`，`turns` 结构不变，所以不报错；它看到的 `content` 也含状态行。

### 2.5 界面

- 通话页和悬浮窗：有等待中的任务时，在状态行下方显示一枚小标签「在办 1 件事」，点开是任务列表（复用「后台任务」页的条目组件，只读）。
- 桌面小窗镜像：`pendingTasks` 随状态一起推送。
- 通话记录页：在 `tasks` 指定的位置插入灰字事件行（「派出：查明天的天气」「结果：已完成」）。

## 3. 测试

全部离线可测，`VoiceCallSession` 只依赖端口。

1. 生成器：模拟供应商流先吐台词再吐工具调用，事件顺序正确；只有工具调用时补一轮。
2. 会话：回执分别在静默、用户说话中、角色说话中到达，生成次数和输入内容符合 ADR0090 第 4 条；两条回执合成一轮。
3. 挂断：队列里的回执 `offerReceipt` 完成为 `false`，文字转告恰好一次；已进入生成的回执不再文字转告。
4. 记录：`tasks` 序列化往返；没有 `tasks` 的旧 JSON 能读；`content` 状态行按三种 `atHangup` 正确生成。
5. 请求：通话最终请求只有 `delegate_task` 一个工具；模型不支持工具调用时请求与现在完全相同。
6. 真实模型：DeepSeek Flash 走一遍「电话里让角色查东西 → 先回话 → 任务完成 → 角色主动说结果」，记首字延迟与现在的差值。

## 4. 分批

一批完成：2.1～2.4 是一条链路，拆开无法单独验收；2.5 界面跟在同一批里做，附源码渲染预览。不涉及数据库迁移（`tasks` 在块 JSON 里）。

## 5. 留给用户否决的实现选择

- 通话前在文字聊天里派出的任务，结果在通话中到达时也在电话里说（ADR0090 第 4 条）。另一种做法是只转告这通电话派出的任务，其他照旧走文字。
- 包含回执的那一轮一开始生成就算转告完成，被打断也不重说。
- 等待期间不自动说「还在查」。
