# MVU 变量与表格记忆兼容方案（第四版，B1 已实施）

> 状态：2026-10-09 第一版经用户同意第 6 节三项决定；同日按 Codex 四轮审查定稿为第四版，决策见 [ADR0071](../../../../../docs/项目记忆/决策记录/0071-MVU变量与表格记忆按消息快照.md)。**B1 已实施（离线验证通过，真实模型请求与实机未验）**；B2、B3 未开工。
> 目标：吸收酒馆生态里「MVU 变量」和「记忆增强表格（填表）」的数据能力，用来辅助维持记忆与上下文。**不实现酒馆助手（JS-Slash-Runner）运行时，不渲染卡片自带的 HTML 状态栏，不执行卡片脚本或 EJS。**

## 1. 调研结论

| 项目 | 是什么 | 许可 | 结论 |

| JS-Slash-Runner（酒馆助手）4.11.3 | 在酒馆网页里用同源 iframe 执行卡片 JS，暴露约 150 个接口 | PolyForm NonCommercial | 深度依赖酒馆内部（约 198 个源文件中 85 个直接引用酒馆模块）、运行时从 CDN 拉 Vue/jQuery，脚本可读密钥和聊天记录。**不移植**，只把类型声明当作「卡片在用哪些接口」的参考 |

### 1.1 MVU 的工作方式

1. **初始化**（上游 `src/function/initvar/variable_init.ts`）：
   - 世界书里名字含 `[InitVar]`（不区分大小写）的条目是一段 JSON/YAML，条目关闭也照样读取，内容先展开宏，可包在代码围栏里；多个条目依次深合并。叶子常写成 `[值, 说明]`。
   - 开场白里的 `<initvar>…</initvar>` 块是**替换**：以该块内容为角色初始状态，忽略角色世界书的 `[InitVar]`（其他世界书的 InitVar 再合并上来）。
   - 开场白里的 `<UpdateVariable>` 是**增量**：在初始化结果上执行一次。
   - 初始化检查发生在加载聊天、发送与生成开始时，已初始化过的世界书记在 `initialized_lorebooks`，不会重复初始化。
2. **给模型看**：卡片世界书用 `{{get_message_variable::stat_data}}`（或 `{{format_message_variable::…}}` 的 YAML 版）把当前变量塞进提示词，并要求模型在回复末尾输出更新块。宏取的是「最近一条有变量的消息」，以 `$` 开头的键被去掉，字符串原样、其余 JSON 序列化。
3. **模型输出**：
   ```text
   <UpdateVariable>
   _.set('理.好感度', 33, 35);//愉快的讨论
   _.add('理.好感度', 2);
   _.insert('物品', '钥匙');
   _.remove('物品', '钥匙');
   </UpdateVariable>
   ```
   也接受 `<JSONPatch>` 里的 JSON Patch 数组（`replace` / `delta` / `add` / `insert` / `remove`；`move` 只在翻译层出现，执行器未实现）。`<think>` 等思考区内的命令不执行。命令按原文位置排序执行。
4. **存储**：每条 AI 消息（每个 swipe）各存一份「回复完这条后的变量」`{stat_data, schema, initialized_lorebooks}`。
5. **结构规则**（`$meta`）：`strictSet`、`template`、`extensible`、`required` 等会改变实际写入结果，不只是校验。
6. **展示与进阶**：HTML 状态栏读 `display_data`；可选「额外模型解析」；大量卡片用 EJS 模板做分段好感度。这些本期都不做。

### 1.2 填表的工作方式

1. **模板**：默认 6 张表（时空、角色特征、角色与用户社交、任务约定、重要事件、重要物品），每张表有列名和「何时插入／更新／删除」的说明。
2. **注入**：默认 system 身份插到深度 1，内容为表格说明＋当前表格（宏 `{{tableData}}` 等）。
3. **模型输出**：
   ```text
   <tableEdit>
   <!--
   insertRow(4, {"0":"理", "1":"第一次一起主持礼拜", "2":"03-15", "3":"教堂", "4":"紧张"})
   updateRow(0, 0, {"1":"10:00"})
   deleteRow(3, 2)
   -->
   </tableEdit>
   ```
   执行顺序（上游 `index.js` `sortActions`）：先全部更新，再插入，再删除；**删除按行号从大到小**，避免删一行后行号前移删错。`updateRow` 的行号越界时改为插入。
4. **存储**：上游 `hash_sheets` 存的是单元格引用，要配合聊天元数据里的表格历史才能还原，不是自包含快照。我们内部不照搬，自己存完整的表定义和行值。

## 2. 与现有架构的关系

- **原文仍是唯一真相**：状态 = 冻结的初始化基线 + 沿当前消息链重放原文里的更新块。逐条快照只是缓存，可以从「基线＋原文」重新算出。
- **基线不是缓存**：基线来自当时的世界书和开场白，世界书以后会被改，所以基线要冻结保存，不能每次重算。
- **当前消息链**：目前没有分支树（ADR0068 只定了方向，未实施），重新生成和编辑提交会软删除后续消息。所以本期的「消息链」口径见 3.1。等 ADR0068 落地，链改为「当前分支路径」，状态读取接口本来就收一条明确的消息路径，不用改算法。
- **请求副本**：历史消息里的更新块只在请求副本中去掉，原文保留（ADR0017）。**只清理历史消息内容，不动预设和世界书提示词**，因为卡片的规则说明本身就带着 `<UpdateVariable>` 示例。
- **显示**：更新块标签在 `content_tags` 注册表登记为隐藏（ADR0044），解析与隐藏用同一份标签别名清单。卡片里输出 HTML 的状态栏正则继续不执行（ADR0046）。解析只读持久化的原始回复（`rawReplyText`），不读显示文本、`processedText` 或分段气泡（ADR0052）。
- **与长期记忆（ADR0038）的分工**：两者并存、互不写入（已确认）。

  | | MVU 变量／表格 | 记忆库 |
  |---|---|---|
  | 内容 | 当前状态（好感、地点、时间、物品、近期事件） | 跨话题沉淀的事实与经历 |
  | 更新者 | 聊天模型每轮顺带输出 | 压缩后由记忆 Agent 整理 |
  | 生命周期 | 跟随消息链 | 跟随角色 |

- **现有 `setvar/getvar` 不动**：它们是按会话＋预设存的字符串变量（`SillyTavernVariableStore`），与 MVU 状态是两套东西，互不覆盖。

## 3. 设计

### 3.1 状态底座（MVU 与表格共用存取与校验，执行器各自实现）

**分层**（DEVELOPMENT.md 跨层约定）：

| 层 | 名称 | 职责 |
|---|---|---|
| Port | `ConversationStatePort` | `read(conversationId, kind, {anchorMessageId})` 返回某消息处的状态视图（数据＋状态＋诊断）；`refresh(conversationId)` 把链尾算到最新 |
| Adapter | `SqliteConversationStateAdapter` | 读链、读写 `message_states`、事务与并发控制 |
| 纯领域 | `MvuEngine`、`TableEngine` | `apply(前态, 原文) → (后态, 状态, 诊断)`，无 IO，可单测 |

宏装配、聊天提交后的刷新、状态面板都只经 Port。

**表 `message_states`**（数据库 20 → 21，本期只存本机、不同步，已确认）：

| 字段 | 说明 |
|---|---|
| `conversation_id` + `anchor_id` + `kind` | 联合主键。`kind` 为 `mvu` / `table`。`anchor_id` 是消息 id，或固定值 `__init__` 表示初始化基线 |
| `prev_anchor_id` | 计算这份状态时用的前一份状态的锚点（基线行为空） |
| `raw_hash` | 计算时这条消息原始回复的指纹（基线行为来源指纹） |
| `engine_version` | 执行器版本，升级后旧缓存自动失效 |
| `status` | 消息行：`applied` / `partial` / `no_ops` / `parse_error`；基线行：`ready` / `init_failed` |
| `data_json` | 计算后的完整状态（MVU：`stat_data` 与单独的 `config`；表格：表定义与行值） |
| `diagnostics_json` | 跳过的命令及原因、不支持的特性 |
| `sources_json` | 仅基线行：用到的世界书条目名与内容指纹、开场白指纹、表格模板 |
| `updated_at` | |

`conversation_id` 外键到会话表；另建 `(conversation_id, kind)` 索引。

**消息链口径**：复用 `MessageRepository` 现有的稳定会话查询（`deleted_at IS NULL`、`replaced_by IS NULL`，按 `created_at, rowid` 升序），再筛出 `role = assistant` 且 `status = sent` 的消息。等 ADR0068 落地改为当前分支路径。

**读取与重算（在一个数据库事务内完成）**：

1. 同一会话加进程内互斥锁，再开事务；在事务里读链、基线和缓存，保证三者来自同一份数据。
2. 取基线行，在事务内按三种情况处理：
   - 不存在：按 3.2 / 3.3 初始化后插入。并发首次初始化时先写入的保留（只约束这一种情况）。
   - 为 `init_failed` 且来源指纹已变化：重试初始化，条件更新这一行。
   - 开场白指纹与基线记录不同：重新初始化并替换基线，同一事务内令全部消息缓存失效、整链重算。
3. 沿链从头遍历。某条消息的缓存有效，当且仅当：行存在、`prev_anchor_id` 等于链上前一份状态的锚点、`raw_hash` 等于当前原文指纹、`engine_version` 等于当前版本。
4. 遇到第一条无效的，从前一份有效状态开始往后用纯函数重算，在同一事务里写回到链尾。

不做事务外计算再回写，避免拿旧链覆盖新链。代价是事务期间同一数据库执行器上的其他查询要等待（Drift 持锁到事务结束），重放计算也在主 isolate 上执行；**是否足够快不预设结论，列为 B1 性能验收项**（见第 4 节）。约束：
- `refresh` 在原文落库事务提交之后执行，不并入原文事务。
- 每轮请求只读一次状态，宏展开复用这份快照。
- 状态刷新失败只记诊断，不能把已落库的聊天报成发送失败；独立连接的锁冲突沿用 `database.dart` 现有的有界重试。

效果：
- 删除、恢复、重新生成、编辑提交都会改变链或原文，后续缓存自动失效重算。
- 同一输入重复处理得到同一结果，`_.add`、`insertRow` 不会累加两次。
- 写快照时机因崩溃漏掉，下次读取时补上。

**写入时机**：AI 回复落库（`appendAssistantRawMessage`）后调用 `refresh`。只处理 `sent` 消息；`sending` / `failed`、流式预览不处理。

**单条消息的失败语义**（与上游一致，逐条跳过而不是整条回滚）：
- 无法解析的更新块（如 JSON Patch 不是合法 JSON）只贡献零条命令，不撤销其他块的更新。
- 非法命令跳过并记诊断，其余命令照常执行。
- 状态：有成功也有跳过＝`partial`，保存成功命令执行后的结果；只有失败、没有任何成功命令＝`parse_error`，`data_json` 等于前态；没有更新块＝`no_ops`。
- 测试覆盖「有效 → 非法 → 有效」三条命令，以及跨多个块的「有效 `add +1` 块 → 坏 JSON Patch 块 → 有效 `add +2` 块」累计 +3。

**清理**：软删除的消息保留状态行（恢复时还能用；不在链上的行不会被读到）。物理删除分三种：
- `MessageRepository.purgeExpired()`：同一事务里只删被清除消息对应的缓存行，**保留会话基线**。
- `MessageRepository.deleteByConversation()`：视为会话状态重置，连同 `__init__` 基线删除该会话全部状态行。
- 会话物理删除：外键 `ON DELETE CASCADE` 清除全部状态行。

**旧会话首次启用**：从数据库完整原文链重放，不用压缩后的上下文窗口。开场白缺失时只用世界书初始化，并写诊断。

**换设备**：状态不同步，其他设备首次读取时用它当时的世界书和开场白初始化，诊断注明「本机初始化，来源可能与原设备不同」。不承诺换设备后一致。

**请求期间固定**：一次请求开始时取定 owner、消息锚点、状态和预设里的 MVU 开关，宏展开、条目跳过、注入都用这一份。回复落库后的刷新（`refresh`）重新读取当前预设与开关：它只是补算缓存，状态始终可由基线＋原文重放得到，下一次发送也会重新校验，所以生成途中切换开关不会留下错误状态（10-09 修订）。

### 3.2 MVU 执行器（`kind = mvu`）

**初始化**：
1. 读当前角色绑定世界书中名字含 `[initvar]`（不区分大小写）的条目，**包括已关闭的条目**；不读不属于该角色的世界书。去掉条目内容外层的 `<initvar>` 包装和代码围栏，展开已支持的宏，按 JSON → YAML 顺序解析，依次深合并。
2. 开场白原文里有 `<initvar>` 块：用块内容替换第 1 步结果。
3. **提取并清理元数据**（与上游 `generateSchema` + `cleanUpMetadata` 一致）：`$meta` 中的 `strictSet` 等配置存入 `config`；从 `stat_data` 中删除 `$meta` 键、数组里的 `$__META_EXTENSIBLE__$` 标记，以及同时含 `$meta` 且 `$arrayMeta === true` 的数组元数据元素（与上游 `schema.ts` 条件一致）。此后执行用的 `stat_data` 是干净的，数组下标与模型看到的一致。
4. 记录来源指纹到 `sources_json`，状态 `ready`，冻结。
5. 开场白里的 `<UpdateVariable>` 不放进基线，作为链上第一条消息正常执行，只执行一次。
6. 任何一步内容含 EJS（`<%`）或无法解析：基线记为 `init_failed`，诊断写明是哪个条目；本会话 MVU 不生效，不执行脚本，不假装成功。用户修好条目后（来源指纹变化）下次读取自动重试。

**开场白变化**：开场白消息 id 固定，若其原文指纹与基线记录不同（例如换了开场白），按 3.1 第 2 步替换基线并整链重算，诊断注明。中途给角色新增世界书不会自动补初始化（基线冻结）；手动「重新初始化」入口本期不做。

**解析语义（B1 测试表）**：

| 项 | 规则 |
|---|---|
| 标签 | 解析 `<UpdateVariable>`、`<VariableUpdate>`、`<JSONPatch>`、`<json_patch>`，大小写不敏感，在统一标签扫描入口内实现。上游还接受的 `<update>` 太通用，不支持 |
| 结构化负载边界 | JSON Patch 负载按 JSON 字符串规则扫描，字符串值里出现的 `</JSONPatch>` 不算结束标签；在统一扫描入口补这项能力，不另写正则 |
| 思考区 | `<think>`、`<thinking>`、`<reasoning>`、`<analysis>`、`<analyze>` 内的命令不执行；未闭合的思考区到文末都忽略（与上游一致） |
| 伪命令 | 字符串字面量里的 `_.set(`、JSON Patch 值里像脚本的字符串都是数据，不执行 |
| 顺序 | 脚本命令与 JSON Patch 混用时按原文位置排序 |
| `set` 路径 | 三参数时旧值只是提示，不作比较条件；路径不存在不自动建路径（诊断跳过）；空路径 `''` 替换整个 `stat_data` |
| `set` 与 `[值, 说明]` | 仅当未开 `strictSet`，且目标是长度为 2 的数组、第二项是字符串、**第一项不是数组**时，只改第 0 项并保留说明；此时若旧值是数字且新值 `!== null` 则转数字。其余情况整体替换（旧值是数字、新值是字符串时转数字） |
| `insert`/`assign` 两参数 | 目标是数组：把第二参数作为**一个元素**追加，不展开；目标是对象：深合并 |
| `insert`/`assign` 三参数 | 目标是数组：按 JS `splice` 语义在下标处插入（负数从末尾倒数，如 `-1` 插在末项之前；超长下标追加到末尾）；目标是对象：第二参数是**字面量键**（不再解释成路径），已有键会被覆盖 |
| `remove`/`unset`/`delete` 一参数 | 删除该路径；删数组元素时数组收缩，不留空洞 |
| `remove` 两参数 | 数组：数字＝下标，其他＝删**第一个**深相等的元素；对象：数字按 `Object.keys` 顺序选键，字符串按键名删 |
| `add` | 只支持数值加减；目标是带 `Z` 或明确时区偏移的 ISO 日期字符串、且增量为数字时，按毫秒偏移并以 UTC ISO 字符串存回（上游接受范围更宽，本期取此子集，保证重放与系统时区无关）；不带时区的日期、布尔值和其他类型不修改并诊断 |
| `move` | 上游执行器未实现（只在 JSON Patch 翻译层出现），本期不支持，诊断跳过 |
| JSON Pointer | 支持 `~0`、`~1` 转义和数组末尾 `-` |
| 值字面量 | 带引号＝字符串；JSON/JSON5 字面量照常解析；不带引号的纯数字四则运算（`+ - * / % ()`）求值；其余表达式（`math.*` 等）不执行，命令跳过并诊断。不执行任意 JS |

**`$meta` 兼容矩阵**：

| 特性 | 本期 |
|---|---|
| `strictSet` | 支持（影响赋值语义） |
| `template` / `concatTemplateArray` / `strictTemplate` | 不支持；检测到时诊断「此卡使用 MVU 模板，插入的新条目不会自动补全字段」 |
| `extensible` / `required` 等结构约束 | 不校验，比上游宽松；检测到时诊断 |

**宏**：在 `SillyTavernMacroEvaluator` 中新增，经 Port 取请求固定的状态：
- `{{get_message_variable::路径}}`：从 `stat_data` 所在的消息状态按路径读取，去 `$` 键；字符串原样，其余 JSON。路径不存在返回空并诊断。
- `{{format_message_variable::路径}}`：同上，输出 YAML。
- `chat` / `character` / `preset` / `global` 作用域的同名宏不支持，原样保留并诊断；不与现有 `setvar/getvar` 混用。

**MVU 专属条目识别**：世界书条目或预设提示词内容含 `get_message_variable` / `format_message_variable` 宏，或含 MVU 更新标签（输出协议示例），即视为 MVU 专属；`[InitVar]` 条目本身永不注入。

**开关**（2026-10-09 修订）：MVU 是酒馆生态的扩展，归在「酒馆相关」之下，不是独立聊天插件。每套酒馆预设的世界书页有「MVU 变量」开关（存 `compatibilityData.mvu`，缺省开），并显示找到的 `[InitVar]` 条目数；角色插件列表不再出现 MVU。会话用上某套预设（角色绑定或默认预设）且该预设没关 MVU 时才可能生效，实际生效还需有 `[InitVar]` 条目或开场白带 MVU 标签。

| | 开启 | 关闭 |
|---|---|---|
| 初始化、事后解析 | 执行 | 不执行 |
| MVU 专属条目 | 正常注入，宏展开，协议示例保留 | **跳过整个条目**，不发送状态，也不发送更新协议 |
| 历史消息里的更新块 | 请求副本中去掉、气泡隐藏 | **例外：照样去掉、照样隐藏**（ADR0017：插件关闭后屏蔽对应标签，原文保留） |

重新开启：状态 = 基线＋重放全部原文，结果确定。

**EJS**：本期不实现（已确认）。世界书条目与预设提示词装配时检测 `<%…%>`，**跳过整个条目**并给出具体条目名的诊断（ADR0010）。

### 3.3 表格执行器（`kind = table`）

- 同 MVU，表格记忆也归在「酒馆相关」之下：开关放在酒馆预设里（2026-10-09 修订，原写「角色插件列表新增」作废），与记忆库并存。关闭时不注入、不解析；历史 `<tableEdit>` 照样在请求副本中去掉、气泡隐藏（同上例外）。
- 内部表定义：每张表有稳定 id、名称、列（稳定 id＋名称）、插入／更新／删除说明；状态 = 表定义＋各表行值，完全自包含。
- 模板：内置一套默认模板（我们自写说明）。导入外部模板**只在拿到真实导出文件并写成测试夹具后**才支持，B2 没拿到就不做导入。
- **模板随基线冻结**：会话启用时把当时的模板冻结进基线。之后修改模板只影响新会话，已有会话不变，因此历史 `tableIndex/colIndex` 永远按冻结的表序和列序解释，可重放。已有会话换模板留给以后的「重新初始化」。
- 注入：默认 system 深度 1，内容为表格说明＋当前表格；`{{tableData}}` 宏给自带写法的预设。
- 执行：解析 `<tableEdit>` 中的 `insertRow` / `updateRow` / `deleteRow`；顺序为更新 → 插入 → 删除，同表删除按行号降序；`updateRow` 越界改插入；不存在的表、列或行号诊断跳过。

### 3.4 界面（最小化）

- 聊天页菜单加「状态」，打开原生底部面板：MVU 显示可折叠的变量树，表格显示原生表格，底部列出诊断。宽窄屏共用（ADR0019）。
- **本期只读**。手动修改留到后续单独交付。

8. 性能（记录数值，不预设结论）：在 500 条与 2000 条消息的会话上测缓存全命中读取、首次整链重放、中间消息失效后重放的耗时，以及重放期间另一会话查询的等待时间。超出可接受范围（测后与用户确认阈值）再考虑增量校验等优化，本期不预先做。
