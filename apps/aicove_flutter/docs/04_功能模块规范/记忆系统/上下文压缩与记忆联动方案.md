# 上下文压缩与联系人记忆联动

更新：2026-09-13。**手动新话题与发送前/工具循环自动压缩及记忆增量补写均已实现，运行端验收范围见项目需求日志。**

用户目标：修改角色卡后，**内容继承、格式重置**。旧话题不是被删除，而是不再作为原始回复示例进入新话题；重要内容通过一段摘要立即接上。

## 1. 使用入口

1. 聊天右上角 →「压缩并开启新话题」。正在生成的目标角色不能压缩。
2. 点击「整理内容」，读取该角色当前话题的数据库 raw 消息；长文本分块整理。此时不改上下文，也不写记忆。
3. 检查并可编辑「新话题内容摘要」。默认保留事实、经历、约定，排除旧角色卡、格式要求和回复样例。
4. 该角色允许且启用 MD 记忆时，可选择「同时归档到该角色记忆」。请检查敏感内容；确认前可以取消。
5. 点击「保存并开启」。同一按钮内另有「撤销上次压缩」和「补写待归档记忆」。

使用已配置的总结模型；未配置时用默认聊天模型（默认聊天模型列表第一项，否则 defaultModelName），不是强制使用当前联系人的临时模型。需要至少 8192 tokens 的模型上下文配置，不依赖 Embedding。整理会产生模型调用费用；本地保存不代表整理材料不发送给所选模型服务。

## 2. 手动与自动的区别

| 项目 | 手动：已实现 | 自动：发送前已实现 |
| --- | --- | --- |
| 意图 | 新的一段，摆脱旧格式影响 | 当前话题没结束，只是上下文快满 |
| 摘要 | 纯内容：事实、经历、约定，不强制追旧任务 | 工作摘要：当前讨论、约束、决策与未完成事项 |
| 新请求 | 最新角色卡/预设＋有效角色记忆＋内容摘要＋新话题消息 | 另外保留最近完整轮次，用于继续当前对话 |
| 旧原文 | 不带旧话题消息尾巴 | 保留近期完整轮次，压缩更早部分 |
| 界面 | 显示新话题分隔线，原聊天可上翻 | 不开新话题、不插主题分隔线 |

内容摘要不是系统权限或回复样例。旧剧情必须与用户现实事实区分，历史设定不得覆盖最新角色卡。普通发送与酒馆预设装配路径都已接入摘要。后台主动关怀/分析器没有在本批新增摘要装配权限；不宣称全部 Agent 链路已统一接入。

连续手动压缩会传入上一内容摘要与本段增量 raw 消息，而不是只总结最后几条。摘要始终有界，不无限堆叠。模型某一分块返回空事实列表时保留已有摘要，避免“没有新增内容”意外清掉旧内容。

## 3. 存储契约

```text
TopicCompactionButton / Dialog
  → TopicCompactionPort（应用层）
    → TopicHandoffStorePort → SqliteTopicHandoffStore
    → TopicSummaryPort → BackgroundTopicSummaryAdapter → BackgroundAgentService
    → ContactMemoryPort → 该角色的 MEMORY.md
```

SQLite v15 → v16 只新增 `topic_handoffs` 表与 owner/boundary 索引，**不删除/转换原聊天、旧记忆或角色卡**。该表由专用 Adapter 的参数化 SQL 访问；不改变 Drift 已有实体或生成文件。

| 数据 | 保存位置 / 用途 |
| --- | --- |
| 原始消息 | 既有 DB raw messages，仍是聊天语义真相源 |
| 内容摘要 | `topic_handoffs.summary`，是可追溯的派生交接材料，不是新的聊天正文 |
| 来源与版本 | `source_ids`、`source_digest`、owner、当前/上一次边界；摘要文本也参与记录 ID 计算，修改内容不会覆盖不同版本 |
| 活动边界 | 既有 `conversations.contextStartMessageId`，与摘要记录在同一数据库事务中更新 |
| 归档状态 | `off` / `pending`（旧摘要归档）/ `pending_updates`（新增量）/ `archived` / `cancelled`，与交接记录一起可靠保存 |

来源摘要绑定实际 raw 消息的 ID、角色、正文、时间、状态与 blocks；记录/资料修改后不继续注入过期摘要。保存前重新比较完整快照，期间新消息、编辑、删除角色或另一次压缩会使旧草稿提交失败。角色卡变化不影响原消息版本；提交只更新边界，不回写整张旧角色卡。

用户重放摘要覆盖范围内的旧消息时，不注入这份后来才生成的交接摘要。该保护不等同于回滚长期记忆；已归档的联系人记忆仍按自己的权限和读取规则工作。

## 4. 记忆增量

同次整理返回结构化摘要及独立记忆建议。摘要用于继续对话，记忆建议只提取有来源的稳定事实或重要经历；先对照旧记忆做语义去重、更正自动记录，最终还做版本和文字去重校验。手写正文、手写往事与人工改过的自动记录不覆盖。手动预览编辑后，仅保留正文仍出现在编辑后摘要的建议。

增量先与摘要在同一事务写入compaction_memory_jobs，再由CompactionMemoryService更新MD；写失败留下待办，后续发送/压缩/补写入口重试。文件appliedCompactions标记避免文件成功、DB标记失败后重复写；手动撤销取消未完成作业。旧pending归档仍按原方式补写，不混成新增量。

自动常驻事实编码为memoryKind=core的事件，与手写常驻正文合计约2000tokens；超出的内容保持可检索。所有来源ID、版本及runtime原文引用保存在SQLite，MD保留可读正文和生成版本元数据。权限须同时满足全局记忆、角色许可、角色存活和MD开启；不自动开启MD，不写旧向量库。

## 5. 失败、取消与撤销

| 情况 | 行为 |
| --- | --- |
| 模型失败、JSON 不合规、取消预览 | 不移动边界、不写 MD。取消后不启动后续分块；已发出的那次请求可能继续结束并产生费用，其迟到结果不会提交 |
| 摘要/边界数据库写入失败 | 同一事务回滚，原话题保持不变 |
| MD 版本冲突、文件失败或授权关闭 | 内容交接仍已保存，提示记忆待补写；重新打开同一按钮可补写，每批最多 32 项，重启后仍保留 |
| 来源消息已变化 | 不注入/补写旧摘要；整理入口提示先撤销后重做，不把旧事实悄悄当新事实 |
| 最新角色卡、摘要与工具挤满预算 | 拒绝发送残缺请求，提示换大上下文模型或撤销后整理更短摘要，不静默丢掉当前问题 |

撤销恢复上一次上下文边界，保留期间的新消息；取消该次尚未完成的记忆补写。**已写入 MD 的内容不自动撤回**，避免覆盖用户后来编辑的笔记。若文件已写成功但 DB 状态尚未标记，也不删除该文件内容。

撤销不把数据库降级回 v15。回滚应用代码时仍应保留 v16 建表支持，不保证旧二进制可直接打开较新 schema。

从 MD 移除往事不会同时清除会话内容摘要和原聊天。完整“忘记”/墓碑防复活、物理清理及新增备份同步协议不在本批；不得据此宣称已实现全局遗忘。

## 6. 规模与实际限制

1. 摘要改为背景、偏好、进展、待办、细节五栏；最多约8192 tokens且不超过32768 UTF-16字符，取消固定600字目标；手动保存前可人工修改。摘要有损，不承诺保留全部细节或百分之百遵循新格式。
2. 本批整理 raw 的文本正文；非文本空消息仅标记未识别，不额外识图/转写音频，不把附件的未知内容编成事实。
3. 按所选总结模型的上下文配置动态整理：预留窗口的 10% 作为估算余量，再预留窗口的 1/8（最少 2048、最多 8192 tokens）供响应/推理，扣除提示词、上一摘要与 JSON 封装后用于 raw 输入。能装下时一次整理；超过预算才分批滚动合并，不设 32 批上限。整条消息优先，单条超预算才按 Unicode 字符分割并保留来源与偏移，所有尾部均进入后续批次。
4. 手动点击、请求达到安全预算或服务器报告超限时整理；不新增定时扫历史或每N句自动入库。
5. 新表/MD 未增加独立云端同步或 JSON 导出协议。卸载或清除应用数据可能丢失仅本地保存的交接和记忆，不能把旧记忆备份范围冒充新 MD 已备份。

## 8. 自动压缩（2026-09-13）

默认窗口272000是容量，安全触发线为有效窗口80%（默认217600），若模型/预设容量减输出预留更小则进一步收紧。预算包含系统、预设、工具schema和历史；近期原文预算16%（默认43520），按完整轮次/闭合工具步骤保留。原文、手动边界和聊天UI记录保持；raw编辑使派生摘要失效，旧轮次重放不倒灌未来摘要。

ChatSendApiRunner每次模型调用前检查；单一用户轮次中也能整理闭合工具步骤。服务器明确超限才执行一次恢复，成功工具不重跑。压力下大于8192 Unicode字符的工具正文保留4096头/1024尾，非文本及调用元信息保留，先持久化原文并提供绑定角色的context_read（id、message、offset、query）分页检索。当前输入与未闭合工具组受保护，无法缩小则明确报错。

自动历史摘要仍存topic_handoffs(memory_state=automatic)；运行时快照存runtime_context_records，记忆待办存compaction_memory_jobs。摘要及记忆增量同事务，文件失败可重试；详情、参考来源及回滚见[ADR0027](../../../../../docs/项目记忆/决策记录/0027-压缩与持久记忆联动.md)。本地测试不替代真实模型语义质量与多模态分词验收。

## 9. 长上下文修复（2026-09-06）

旧实现虽然读取模型窗口，却只检查至少 8K，随后固定 2400 tokens/32 批，在模型调用前拒绝长历史。现按第 6 节的实际预算整理，200K/1M 配置不再被旧上限拦截；模型/渠道配置仍须与实际服务能力相符，不按模型名称一律假设 1M。

- 后台运行壳新增可选的单次响应上限，沿既有 ProviderChatRequestOptions 传入 OpenAI/Claude/Gemini adapter；其他后台任务不传时保持原行为。
- 每次合并后的摘要（含 JSON 转义）重新计入预算；连续整理始终携带前批摘要。空事实结果仍保留已有摘要。
- 仅在模型请求明确报告上下文超限时，减半未处理材料的批次预算重试，最多额外 4 次；鉴权、网络、超时或摘要格式错误不触发拆分重试。所有批次完成并经用户确认之前，仍不提交边界和记忆。
- 请求超时沿用应用的模型调用超时设置，取消压缩独有的 90 秒硬限制。取消后不发后续请求，已在途请求仍可能完成；迟到结果不提交。
- 本次借鉴 Pi 的窗口预算、响应预留和增量摘要机制（[官方说明](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/docs/compaction.md)），保持本入口“内容继承、格式重置、确认后开启新话题”的契约；当时自动压缩/保留近期原文属于第二批，现状见第8节。
- 回滚可仅撤回本次摘要适配器、后台运行壳可选输出参数与 provider 超时传递，不修改数据库或已保存摘要。

### 2026-09-06：模型 JSON 包装兼容

真实 Gemini 请求返回 HTTP 200 和有效 facts JSON，但包在 Markdown 代码框内，旧 normalize 直接 jsonDecode 导致界面仅报整理失败。现允许整段响应外层为 json/JSON 或无语言标记代码框，再按原有 facts 字段/条数/长度严格验证；不从夹杂额外指令的响应中抽取 JSON。两项新回归先复现失败，再修复；压缩与窄宽屏 UI 共 39 项通过，静态检查无问题。另一次 Claude 整理的第二批返回服务端 HTTP 502，与解析兼容是两类失败。

随后真实 Opus 请求再次返回 HTTP 200，但事实文本内的双引号未转义，造成 JSON 语法错误。现对以 JSON 对象或代码框起始的语法错误结果，最多增加一次仅携带该摘要的格式修复请求，不重发 raw 历史；保留同一模型、无工具、输出预算、取消守卫与原有事实结构/长度校验。自由说明/拒绝文字不送修，字段或事实类型错误仍直接拒绝。两项新增回归先复现失败再修复，压缩及窄宽屏 UI 合计 41 项通过；格式修复不是无损语义保证，最终摘要仍可编辑。

真实保存继续暴露块反序列化创建时间漂移：MessageBlock 每次读取会创建新的 createdAt，而来源摘要此前包含 b.toJson() 全字段，导致未编辑历史也触发版本冲突。来源校验现保留消息原始时间、块身份/顺序/状态/内容，只排除块的派生 createdAt/updatedAt；不修改数据库或关闭真实编辑校验。真实 SQLite＋正式 raw loader 回归先复现不同 revision，修后验证重复读取、提交、重新读取活动摘要成功，实际修改块正文仍拒绝过期提交。压缩/UI共42项通过，三文件静态无问题。旧摘要不批量重写；旧摘要若已因派生时间失效，仍按现有撤销后重新整理流程处理。
