# 测试验收与回滚

## 测试策略总览

这轮重构的风险不在“能不能编译”，而在：

- 行为是否漂移
- provider 是否选错
- 流式是否退化
- 插件是否悄悄失效

所以测试要分四层：

1. 契约测试
2. 集成测试
3. UI / 交付回归
4. 运行验证

---

## 契约测试

### 聊天主链

要覆盖：

- 普通发送
- retry
- 带图发送
- proactive / regenerate
- 失败清理
- 流式占位到正式消息交接

### API 层

要覆盖：

- direct 请求
- stream 请求
- image 请求
- headers / timeout / 错误映射
- diagnostics 字段完整性

### provider / adapter

要覆盖：

- provider 解析
- alias 命中
- capability 命中
- fallback 行为
- 未知 provider 的明确失败

### TTS

要覆盖：

- provider resolve
- requestFormat 统一命中
- 合成成功与失败
- 音色创建 / 删除 / 状态查询

### 生图

要覆盖：

- `draw_image` 工具链
- `<image>` 快速链
- NovelAI
- OpenAI-compatible

---

## 集成测试

建议重点保住以下集成场景：

1. 聊天发送 -> API -> 流式 -> 落库 -> UI 展示
2. 工具调用 -> 生图 -> 文件落盘 -> 消息回灌
3. TTS 标签 -> 合成 -> 播放队列 -> 回收
4. provider 切换后同一路径仍保持行为正确

---

## UI 与交付回归

### 聊天 UI

要重点回归：

- 阅读态滚动
- 流式增量
- 占位消息
- 正式消息交接
- 页面切换和会话切换

### TTS UI

要重点回归：

- provider 切换
- model 切换
- 音色列表刷新
- 音色创建与删除

### image UI

要重点回归：

- 工具入口
- 快速出图入口
- 默认参数覆盖
- 失败提示

---

## 运行验证

后续真正进入代码施工后，每一批改动都要做：

1. `flutter test` 跑对应测试集
2. `flutter run --no-resident` 真机或已连接设备验证

尤其是：

- 聊天主链改动
- API transport 改动
- TTS 运行时改动
- image 插件执行链改动

不能只跑静态分析就交付。

---

## 回滚策略

### 原则

- 旧入口先保留为兼容壳
- 新链路先通过测试和 smoke 再切主
- 删除旧代码必须在新链稳定之后

### 触发回滚的信号

1. 流式响应大面积退化为整段返回
2. provider 命中错误导致请求打到错误厂商
3. TTS 合成成功率明显下降
4. image 出图成功率明显下降
5. UI 交付出现重复消息、空窗、闪断

### 回滚方式

- 先切回旧兼容入口
- 保留诊断日志
- 定位失败阶段
- 不跨阶段混合回滚

---

## 阶段验收标准

### Phase 1-2 验收

- 聊天主链唯一入口可用
- API transport 收口后行为不漂移

### Phase 3 验收

- 新 registry 能正确选择 provider
- fallback 行为明确且可观测

### Phase 4 验收

- TTS 新旧厂商都能正常合成
- 音色目录操作正常

### Phase 5 验收

- 工具链与快速链都能稳定出图
- NovelAI 不再依赖 support 旁路

### Phase 6 验收

- dead code 删除后无回归
- 配置兼容仍成立
