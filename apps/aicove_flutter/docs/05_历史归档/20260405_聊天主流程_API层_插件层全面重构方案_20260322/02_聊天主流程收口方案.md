# 聊天主流程收口方案

## 目标

这一卷负责解决一个根问题：

“从用户点击发送，到最终消息交付到时间线，中间到底应该只有哪一条主链？”

当前聊天链路的问题不只是文件多，而是：

- 发送入口多
- 命令模型不统一
- 状态更新散落
- 交付时序存在重复模板
- 页面还掺着业务参数整形

本卷目标是把这些分散动作收敛成统一执行骨架。

---

## 当前问题归纳

### 1. 发送变体太多，但没有统一命令模型

现状里至少存在这些变体：

- 普通发送
- 带图发送
- 带文件发送
- retry
- proactive trigger
- regenerate

它们表面都叫“发送”，但内部处理流程并不统一，导致：

- trace 行为不一致
- failover 不一致
- 临时消息清理方式不一致
- 结果交付方式容易继续漂移

### 2. `ChatActions` 仍在掌握太多流程控制

`ChatActions` 当前仍然同时参与：

- 发送入口
- 流式占位
- 结果落地
- 失败清理
- 会话状态切换

它应该逐步退出“主执行骨架”，转为 UI/页面层可调用的命令入口壳。

### 3. `UseCase / Service / Runner` 边界不稳

当前常见问题：

- `UseCase` 负责一部分参数准备
- `Service` 有时只是转发，有时又掺工具逻辑
- `Runner` 同时管 transport、tool loop、文本清洗、最终文案策略

结果是分层存在，但稳定性不够。

---

## 目标主链

建议收敛为下面这条稳定主链：

1. UI 层产生 `ChatTurnCommand`
2. `ChatTurnUseCase` 作为唯一应用层入口
3. `ChatTurnNormalizer` 把不同发送变体归一化
4. `ChatTurnExecutor` 执行一次完整聊天 turn
5. `ChatDeliveryCoordinator` 协调流式占位、正式消息、失败清理
6. `ChatHistoryStore` 作为落库与时间线真相源

---

## 建议模块口径

### 1. `ChatTurnCommand`

统一描述一次发送动作，至少包含：

- 发送类型
- 用户输入文本
- 图片/文件引用
- 目标会话
- provider/model 选择结果
- 是否 retry / regenerate / proactive
- trace / telemetry 基础上下文

原则：

- 页面层只负责装命令，不直接拼 API 请求。
- 所有发送变体先变成命令，再进入执行骨架。

### 2. `ChatTurnUseCase`

定位：

- 唯一公开主入口
- 只组织流程，不沉淀太多供应商细节

职责：

- 接收命令
- 调用 normalizer
- 调用 executor
- 把结果回交 UI/调用方

### 3. `ChatTurnNormalizer`

职责：

- 收集一次发送所需的统一上下文
- 归一化附件、引用、插件能力、模型能力
- 产出标准的执行参数

它负责的是“准备一次执行”，而不是“执行 API 请求”。

### 4. `ChatTurnExecutor`

职责：

- 驱动请求发送
- 协调插件、工具调用和交付
- 持有本次 turn 的运行态

它不直接负责 UI，也不直接承担所有 transport 细节。

### 5. `ChatDeliveryCoordinator`

职责：

- 建立流式占位
- 接收流式增量
- 协调正式消息交接
- 处理失败回退

要求：

- 只能有一条写路径
- UI 与 Provider 不再各自维护一套临时消息状态

---

## 页面层瘦身目标

### `chat_page.dart`

重构后应只负责：

- 页面生命周期
- 路由参数
- 页面编排
- 用户交互触发

应下沉出去的能力：

- 模型能力判断
- 引用消息协议拼装
- 发送参数兜底
- Trace 驱动标题生成的业务策略

### `chat_message_list.dart`

重构后应只负责：

- 展示
- 滚动控制
- 视窗状态
- 局部交互

不再直接参与：

- 消息交付状态机
- 临时消息生命周期判断
- 历史分页和流式落库的业务协调

---

## 推荐迁移步骤

### 第一步：冻结统一命令模型

- 先定义 `ChatTurnCommand`
- 明确每种发送入口如何映射到命令
- 暂时不改具体执行逻辑

### 第二步：建立新 UseCase 主入口

- 新主入口只做编排
- 旧入口转发到新主入口
- 不立刻删除旧方法

### 第三步：抽出交付协调器

- 先从 `ChatActions` 和 `Runner` 中抽流式占位与交接逻辑
- 建立单一协调器

### 第四步：清理页面业务职责

- 先让页面改走新命令
- 再把模型能力判断、引用拼装等策略全部下沉

### 第五步：清理旧动作模板

- 把重复 trace、failover、失败清理模板收掉
- 删除确认不再需要的过渡入口

---

## 写文件边界建议

### 可并行但不能抢同一文件

- 窗口 A：`features/chat/application/`、发送命令与 use case
- 窗口 B：`features/chat/services/`、执行器与交付协调
- 窗口 C：`ui/features/chat/`、页面与消息列表瘦身
- 窗口 D：`test/`、聊天链路测试补强

### 不建议并行的部分

- `ChatActions` 拆责
- 流式占位真相源切换
- 页面层改新命令入口

这些部分依赖关系强，应该分阶段串行推进。

---

## 完成标准

1. 所有发送入口最终都走同一条主执行骨架。
2. `ChatActions` 不再掌握完整执行链。
3. 流式占位与正式消息交付只有一条主写路径。
4. 页面不再判断 provider/model 协议细节。
5. 以后继续加发送变体时，只需要补命令归一化，而不是复制整套流程。
