## 一分钟版

- 和"记住东西"有关的功能，现在一共有**五块**：
  1. **旧记忆库**：系统自动把聊天剪成卡片、按"像不像"检索（向量四层 L1～L4，外加日记）。**没单独设置过的角色，默认还在用它。**
  2. **角色记忆本**：每个角色一份 `MEMORY.md`，分"常驻笔记"和"往事"两部分。要在角色里手动打开才会启用。
  3. **手动压缩**：聊天页右上角"压缩并开启新话题"，相当于翻篇。
  4. **自动压缩**：发送前发现快装不下了，把比较早的对话写成摘要，然后接着聊。
  5. **运行时压缩**：模型在一次回复里反复调用工具、内容暴涨时，当场裁剪或者摘要，只影响这一次请求。
- 第 1、2 块管"过很久还记不记得"；第 3、4、5 块管"这一次还装不装得下"。09-13 起两边连起来了：压缩的时候，顺手给角色记忆本提几条"记忆增量"。
- 觉得散，是因为确实散：两套记忆同时存在，还挤在同一个插件里；三种压缩用三个服务，分在两个模块里互相引用；总结模型的设置放在"长期记忆"插件里；"摘要"这个词指好几样东西；另外还有几段已经没人调用的旧代码。第 7 节逐条列出来。
- **眼下最要紧的一件事**：09-13 新加的两张表没有升数据库版本，老设备上自动压缩和工具结果裁剪会报 `no such table`。修复已经写好，也随 09-22 的发布装到手机上了，但本地 `main` 上还是未提交状态，需求日志没补结果，也没人回头复验。见第 8 节第 1 条。

## 1. 先把几个词说清楚

| 词 | 人话解释 |
|---|---|
| 原文（raw 消息） | 数据库 `messages` 表里的每条聊天原件。它是唯一的真相：压缩和记忆都只是从它整理出来的"笔记"，原文不会因为压缩被删掉。 |
| 上下文窗口 | 模型一次最多能读多长的内容，单位是 token，可以粗略理解成"字数"。默认 272k。 |
| 摘要 / 压缩 | 把一段旧对话写成一份短笔记。发给模型时用笔记代替原文，给新内容腾出位置。 |
| 工具调用 | 模型写到一半说"帮我查一下"，App 去执行，再把结果交回给模型接着写。一次回复里可能来回好几轮。 |
| owner（所属角色） | 这条数据属于哪个联系人。代码里全程明确传这个值，不跟着"当前打开的是哪个页面"走，这样不会串到别的角色。 |
| 总结模型 | 专门用来写摘要、提炼记忆的模型，不是和你聊天的那个模型。 |

## 2. 打个比方，把五块放在一起看

| 功能 | 打个比方 | 存在哪 | 什么时候起作用 |
|---|---|---|---|
| 聊天原文 | 录音原带，永远不剪 | SQLite `messages` / `message_blocks` | 一直在 |
| 旧记忆库 | 自动剪报柜：隔天把聊天剪成小卡片，分进四个抽屉；你发消息时，挑最像的几张给模型看 | SQLite `memories` 等几张表 | 每次发消息都检索；隔天自动整理 |
| 角色记忆本 | 每个角色一本笔记本：封面贴着便利贴（常驻笔记，每次都看），抽屉里放往事档案（先看目录，要用再翻） | `contact_memories/<角色ID哈希>/MEMORY.md` | 每轮都带上便利贴和最近 5 条目录；模型需要时再用工具去翻 |
| 手动压缩 | 翻篇：把上一章写成读书笔记，新的一章只带笔记、不带原文，所以旧文风不会带过来 | `topic_handoffs` 加上会话的"新话题边界" | 你点按钮的时候 |
| 自动压缩 | 桌上快堆满了，把最早的几摞写成一页便签，最近几轮原样留着 | `topic_handoffs`（标记为 automatic） | 发送前估算超过触发线 |
| 运行时压缩 | 干活时工具吐出一大堆东西：只留头尾，原件放进储物柜；或者把前面做完的步骤写成便签 | 原件存 `runtime_context_records`，便签不留 | 工具循环里，每次请求模型之前 |
| 记忆待写队列 | 待办小票：先记下"要往笔记本里写什么"，写失败了下次补上 | `compaction_memory_jobs` | 每次压缩之后、每次发送之前 |

## 3. 按下发送之后，到底发生了什么

入口在 `ChatSendBackendService.prepareApiConfig`，发请求在 `ChatSendApiRunner`。按顺序是这样：

```text
你按发送
│
├─ ① 读原文：从数据库取出当前话题（新话题边界之后）的全部原文
├─ ② 补账：上次没写进记忆本的增量，先补写一遍
├─ ③ 找笔记
│    · 自动压缩便签：有的话，便签已经概括过的那些旧消息，就不再原样发送
│    · 手动压缩读书笔记：只有"当前边界正好是那次压缩"时才带上；
│      你重发、重新生成更早的消息时不带，免得把"后来才写的笔记"塞回过去
├─ ④ 拼系统提示：角色卡 → 读书笔记 + 自动便签 → 各插件的提示
│    └─ "长期记忆"插件在这一步放内容：
│       记忆本模式放"常驻笔记 + 最近 5 条往事目录"；旧库模式放检索到的卡片
├─ ⑤ 拼工具：插件提供的工具（记忆本模式下有 memory_search / memory_read），
│    另外只要模型支持工具，就固定再加一个 context_read
├─ ⑥ 量长度（本地估算）
│    · 没超过触发线 → 直接发
│    · 超了 → 先把超过 8192 字的工具结果剪成"开头 4096 字 + 结尾 1024 字"，原件存档
│    · 还是超 →
│        还没被便签概括的用户发言有 2 条或更多：走【自动压缩】，写一张新便签后回到 ① 重来
│            （每次发送最多压两次，第二次只保留最后一轮；还不行就报错，不发）
│        只剩最后 1 条：走【运行时压缩】，只改这一次请求
└─ ⑦ 发给模型（工具循环）
     · 每一轮请求模型之前再量一次，超线就当场做运行时压缩
     · 服务器明确回"太长了"：强制压缩后，只重试这一次模型调用；已经执行过的工具不会重跑
```

几个数字（出处是 `context_window_policy.dart`）：

- **有效窗口** = 你设置的窗口（默认 272k）和当前模型、预设容量之间，取小的那个。
- **触发线** = 有效窗口的 80%，和"窗口减去输出预留"比较，取小的。输出预留取角色绑定预设的"最大输出 tokens"，没设才用 2048。默认是 217,600。
- **近期原文预算** = 有效窗口的 16%，默认 43,520。自动压缩时，会尽量原样保留这么多最近的对话。
- 长度都是本地估算的，和各家模型的真实计数会有出入，图片的估值出入更大。

## 4. 记忆：两套同时存在

### 4.1 一个角色用的是哪一套？

由两道开关决定：

1. **这个角色允许"长期记忆"插件吗？** 入口是：编辑角色 → 插件列表 → 记忆。不允许的话，两套都不用。全局开关从 09-15 起已经取消，现在恒为开启（ADR0035）。
2. **这个角色的记忆本打开了吗？** 入口是：插件列表"记忆"下面的"角色记忆文档" → "使用独立 MD 记忆"。这个开关其实存在 `MEMORY.md` 的文件头里。
   - 打开了：用记忆本，旧库对这个角色完全停用，既不读也不写。
   - 没打开，或者还没有这个文件：用旧库。**这是默认状态。**

### 4.2 旧记忆库现在还在做什么

- **读**：每次发消息，拿最近 2 条消息加上你这句话（最多 200 字）去检索，最多取 5 张卡片。配了 Embedding 的话按"向量 70% + 关键词 30%"打分；没配就只用关键词。再加上 L1"用户攻略"，一起拼进系统提示。"嗯""好的"这类寒暄短句，会直接沿用上一次的检索结果。
- **写**：现在只剩"隔天整理"这一个入口还在工作。你每发一条消息，系统会顺便检查 24 小时以前还没整理过的消息，交给总结模型拆成一条条事实，按类别放进 L2/L3/L4。L3 的事实会同时写进"日记"；反复出现（大约 3 次）的特点会升级成 L1。
- **这三个旧入口已经没人调用了**：
  - pre-flush：原来靠"历史条数裁剪"触发，09-13 删掉条数设置后就断了。
  - 旧的"开新话题前先整理"（`startNewTopic`）：右上角按钮换成压缩之后，现在只剩测试在调用它。
  - `onSessionEnd`：是个空函数。
- **依赖**：写入必须同时配好 Embedding 模型和总结模型；读取在没有 Embedding 时，可以退回到只用关键词检索。
- **回收站**：数据管理页里的"记忆回收站"，管的就是旧库。
- **日记只写不看**：日记页现在没有任何入口（09-15 聊天菜单去掉了"日记"），但旧库还在往里写，云同步也还在同步它。

### 4.3 角色记忆本是怎么工作的

文件的结构是：文件头（格式版本、属于哪个角色、是否启用）→ 常驻笔记 → 一条条往事（标题、日期、正文；自动生成的往事还带着来源标记）。

- **每轮自动带给模型**：
  - 常驻笔记：你写的正文，加上自动提炼的"常驻事实"，合计大约 2000 tokens 封顶，超出的部分留在往事里；
  - 最近 5 条往事的"日期 | 编号 | 标题"。
- **往事正文不会自动带上**。模型需要时自己调工具：先用 `memory_search` 按关键词或日期查目录（每页 8 条），再用 `memory_read` 按编号读正文（每次 1200 字，可以翻页）。这里的关键词是按字面匹配，不是按意思检索。
- **模型不支持工具时**：只能看到常驻笔记和目录，提示里会明确告诉模型"读不了往事正文"。
- **安全措施**：
  - 工具参数里不能指定别的角色或文件路径，属于哪个角色在组装请求时就定死了。
  - 文件格式损坏、或者文件头写的角色对不上时，会直接拒绝读取，不会当成空文件覆盖掉。
  - 写入前会核对文件版本，发现被别人改过就不覆盖。
- **限制**：单个文件最大 8 MiB；往事正文不超过 2 万字，标题不超过 120 字；你手写的常驻笔记超过约 2000 tokens 就存不进去。
- **同步**：`MEMORY.md` 已经随云同步 v3 一起同步了（模块文档里"未接同步"的说法已经过时）。

### 4.4 谁会往记忆本里写东西

| 写入来源 | 写什么 | 条件 |
|---|---|---|
| 你手动编辑 | 任何内容 | — |
| 手动压缩时勾选"同时归档" | 这次整理时顺手提炼出的几条记忆（带来源） | 该角色开了记忆本 |
| 自动压缩 | 同上 | 该角色开了记忆本（不用勾选） |
| 运行时压缩 | 同上 | 同上 |

三种压缩共用同一个写入服务（`CompactionMemoryService`），规则是：

- 模型只能**提建议**：要么新增一条，要么更正一条"之前自动生成、而且你没改过"的记录。你手写的内容、你改过的自动记录，一律不碰。
- 每条建议都要有来源（引用原消息的编号）。和已有内容逐字重复的，直接跳过。
- 建议先和摘要一起存进数据库的待写队列，然后再写文件。写文件失败不影响聊天，等下次发送、下次压缩或者你点"补写"时再重试。
- 自动提炼的"常驻事实"，其实是一种特殊的往事（`memoryKind=core`），算在 2000 tokens 的常驻额度里。

有一点要注意：勾选"同时归档"之后写进去的，是**提炼出的几条记忆，不是整段摘要**。09-05 最早的版本是把整段摘要当成一条"话题归档"往事写进去；09-13 之后，新的压缩都改成按条写增量。整段写入的老做法，现在只剩下给当时没补写完的旧记录用。

## 5. 压缩：三条路

| | 手动压缩（翻篇） | 自动压缩（腾地方） | 运行时压缩（边干边收拾） |
|---|---|---|---|
| 谁来触发 | 你点右上角按钮；先预览，可以改摘要，确认后才生效 | 发送前超过触发线，而且还有 2 条或更多没被概括的用户发言 | 发送前超线但只剩最后一轮；工具循环里某一轮超线；服务器报"太长" |
| 整理什么 | 当前话题里用户和助手的文字（附件只标"未识别"） | 除最近几轮以外的旧对话，包括工具调用和结果 | 这次请求里比较早的、已经完整结束的步骤 |
| 摘要口径 | 只继承事实、经历、约定；不带旧原文和旧格式，按最新角色卡说话 | 保留目标、进度、待办和工具结果，方便接着聊 | 同自动压缩 |
| 界面上的变化 | 出现新话题分隔线；可以撤销 | 没有 | 没有 |
| 存在哪 | `topic_handoffs`，同时移动会话的新话题边界 | `topic_handoffs`（标记为 automatic），不动边界 | 原件存进 `runtime_context_records` 供 `context_read` 翻看；下次发送还是从原文重新组装 |
| 记忆增量 | 勾选归档才写 | 开了记忆本就写 | 开了记忆本就写 |
| 失败时 | 原话题不变 | 这次消息发不出去，会提示错误，原文不受影响 | 同左 |
| 代码里的 Agent 定义 | `local.topic_content_handoff` | `local.automatic_context` | 沿用自动压缩的定义 |

三条路**共用**的部分：

- **同一个总结适配器**（`BackgroundTopicSummaryAdapter`）：按总结模型的窗口决定一次整理多少，装不下就分批、滚动合并；模型返回的 JSON 格式坏了，会请模型修一次；服务器报超长就把批次减半重试，最多重试 4 次。
- **同一个总结模型**：在"长期记忆"插件设置里选；没选的话，用默认聊天模型列表里的第一个。总结模型的窗口至少要有 8192。
- **同一套"防过期"校验**：摘要会记下它概括了哪些原消息，以及这些消息的"指纹"。原消息被编辑或删除后，旧摘要自动作废，改回用原文。
- **同一个记忆待写队列和写入服务**。

两个容易误会的地方：

- **手动压缩预览时，只要改了摘要的文字，这次的记忆建议基本会被全部丢掉。** 代码要求每条记忆的正文必须逐字出现在改过的摘要里；但记忆和摘要是模型分开写的，很少会逐字一致。这是 ADR0027 有意采用的保守设计，只是实际效果可能和你预想的不一样。
- **手动压缩之后，自动压缩会从新话题重新开始**，不会接着用上一个话题的自动便签。上一个话题的内容，由手动压缩那份读书笔记带过来。

## 6. 数据和设置都在哪

### 6.1 数据

| 存放位置 | 归哪块 | 里面是什么 | 云同步 |
|---|---|---|---|
| `messages` / `message_blocks` | 聊天 | 原文（唯一真相） | 同步 |
| `conversations.context_start_message_id` | 聊天 | 新话题边界 | 同步 |
| `topic_handoffs` | 压缩 | 手动读书笔记、自动便签、归档状态 | 同步 |
| `compaction_memory_jobs` | 压缩 → 记忆 | 待写进记忆本的增量 | **不同步** |
| `runtime_context_records` | 运行时压缩 | 被裁剪之前的整份请求原文 | **不同步** |
| `contact_memories/…/MEMORY.md` | 新记忆 | 常驻笔记 + 往事 | 同步 |
| `memories`、`memory_fts`、`memory_tombstones`、`summarization_records`，以及 `messages.summarized` 字段 | 旧记忆 | 卡片、全文索引、删除墓碑、"已整理"记录 | 同步（全文索引除外） |
| `diaries` | 旧记忆 | 日记 | 同步 |

三张压缩相关的表，代码里只有写入和改状态，没有按时间清理。表上设了外键级联，只有角色记录被真正删除（不是软删除）时，才会连带删除。这三张表都是手写 SQL，不走 Drift 的表定义，建表语句都在 `database.dart` 的 `_ensureTopicHandoffs` 里。

### 6.2 设置入口

| 想改什么 | 去哪改 | 实际存在哪 |
|---|---|---|
| 总结模型 | 设置 → 插件 → 长期记忆；（09-19 新增，未提交）设置 → 模型 → 默认模型设置 → 自动压缩 | 长期记忆插件的配置 |
| 上下文窗口（默认 272k） | 默认模型设置页里的"上下文窗口"；（同上，未提交）自动压缩页 | 全局设置 `contextWindowTokens` |
| Embedding 模型（只有旧库用） | 长期记忆插件页 | 长期记忆插件的配置 |
| 某个角色用不用记忆 | 编辑角色 → 插件列表 → 记忆 | 角色的 `enabledPlugins` |
| 某个角色用记忆本还是旧库 | 编辑角色 → 记忆 → 角色记忆文档 → "使用独立 MD 记忆" | `MEMORY.md` 的文件头 |
| 手动压缩 / 撤销 / 补写待归档的记忆 | 聊天页右上角图标 | — |
| 旧库回收站 | 数据管理 → 记忆回收站 | `memories` 表 |

## 7. 为什么感觉"散"：具体散在哪里

1. **两套记忆挤在一个插件里。** `MemoryPlugin`（约 620 行）既是记忆本的入口，又背着旧库的全套服务：检索、隔天整理、画像、合并、容量淘汰、日记。每次组装请求，都要先读一遍这个角色的 `MEMORY.md`、看文件头里的开关，才知道该走哪一套。
2. **三种压缩用三个服务，分在两个模块里互相引用。** 压缩和记忆本这两块加起来有 11 个接口、9 个实现类（不算测试），分散在 `features/chat` 的 domain / application / data / providers 和 `features/memory` 的 domain / application / data 里。chat 这边的压缩要调用 memory 的写入服务；memory 这边的待写队列又反过来要用 chat 的"来源指纹"函数和消息模型；运行时存储放在 chat 里，却直接调用 memory 里的入队函数。两个模块已经拆不开了。
3. **设置放错了地方。** 总结模型是压缩最核心的配置，却存在"长期记忆"插件的配置里；上下文窗口则在全局设置里。09-19 的改动又新加了一个"自动压缩"设置页，结果总结模型和窗口各有两个入口。
4. **一个字段干两件事。** `topic_handoffs.memory_state` 既表示手动压缩的归档状态（off / pending / pending_updates / archived / cancelled），又用 `automatic` 这个值表示"这是一张自动便签"。
5. **"摘要"一词多义。** 手动的读书笔记、自动的便签、运行时的步骤摘要（不留存）在代码里都叫 summary；旧库还另有一套"已整理"记录（`summarization_records`）。看代码和日志时很容易对不上。
6. **三张新表挤在一个建表函数里。** 函数名 `_ensureTopicHandoffs` 只提到了其中一张表。09-13 往里追加另外两张表时没有升数据库版本，就是这样漏掉的（见第 8 节第 1 条）。
7. **开关一层叠一层。** 角色插件允许 + 记忆本开关 + 压缩时的"同时归档"勾选；以前还有一个全局开关（现在恒为开启）。界面上的文字还停留在旧说法上（见第 8 节第 7 条）。
8. **遗留代码和没有入口的页面。** 第 4.2 节提到的 pre-flush、`startNewTopic`、`onSessionEnd` 都已经没人调用；日记页没有入口，但日记还在写、还在同步。另外，`记忆存储与召回方案.md` 和 `记忆重要性计算.md` 是 2026-02 旧向量库的设计稿，现在还和现行文档放在同一个目录里。

## 8. 已知问题（都在代码里核实过）

按严重程度排序：

1. **老设备缺两张表，自动压缩和工具结果裁剪会失败**（最要紧）
   - 原因：09-05 手动压缩上线时，数据库升到了 v16，当时只建了 `topic_handoffs`。09-13 做自动压缩时，往同一个建表函数里又加了 `compaction_memory_jobs` 和 `runtime_context_records`，但版本号还是 16。已经是 v16 的设备（比如 09-05 以后一直在用的手机）升级时不会再跑建表，于是这两张表根本不存在。新装的设备不受影响。
   - 表现：开了记忆本的角色，自动压缩会在总结模型跑完（费用已经产生）之后存不进去，这次发送失败；不管有没有开记忆本，只要需要裁剪超长工具结果，或者要做运行时压缩，也会失败。
   - 现状：修复已经写好——版本升到 17，从 16 升上来时补建这两张表，还配了 5 个迁移测试，测试注释写明复现的就是"手机上的 no such table"。同一批改动还改了总结模型的引用方式（以前只传模型名，不带渠道），并新增了"自动压缩"设置页。这批改动已经进了 09-22 那次发布的快照提交 `f037e67f2`（`codex/release-snapshot` 分支，也就是 GitHub 公开仓库的 main），并随那次安装装到了手机上。**但是本地 `main` 上它还是未提交的改动，需求日志 09-19 那条的结果还是"待补"，也没有记录复验过"new"会话的自动压缩有没有恢复。** 你 09-19 说的"大部分模型压缩失败、对话中断"，很可能主要就是这个原因，但这一点还没被复验证实。
2. **旧库没配 Embedding 时会"假整理"。** 隔天整理发现没有 Embedding，就直接返回、也不报错，外层随后把这些消息标记成"已整理"。结果是什么都没记住，而且以后就算配上 Embedding，也不会回头补这些消息。（`memory_service.dart` 的 `summarizeAndStore` 和 `_ingestUnit`）
3. **旧库的"重新丰富"只是套模板。** 被检索命中的 L4 卡片，在下次整理时会被替换成一段模板文字（"【重新丰富】事件：旧内容 聊天经过：这批被整理消息里的前 3 条原文 → 当前状态：基于最近对话重新确认"），并且升级成 L2。整个过程不调用模型，拼进去的那 3 条聊天也不一定和这条记忆有关。
4. **三张压缩表只写不清。** 运行时压缩每触发一次，会往 `runtime_context_records` 写 2～4 行，每一行都带着整份请求原文；`topic_handoffs` 里的自动便签、待写队列里已完成的记录也都不删。工具用得多的长会话里，数据库会一直变大。
5. **运行时压缩提炼的记忆，来源对不上原消息。** 这条路径交给总结模型的是请求里的片段，片段编号是临时起的 `runtime_…`，所以记忆里记下的"来源"和数据库里的原消息编号对不上（整批对应的原消息范围倒是另外存了）。
6. **记忆本文件头里的"已应用压缩"列表只增不减。** 每写入一次压缩结果，就追加一个编号。不影响功能，但文件头会越来越长。
7. **文案和文档过时。** 改起来都很小，但会误导人，也会误导 agent：
   - 角色记忆页写着"当前为手动维护版，尚不自动整理聊天"，但现在压缩会自动写增量；"记忆存本机"也不对，MD 已经随云同步上传；还写着"仍需启用全局……长期记忆插件"，但全局开关 09-15 已经取消了（`contact_memory_page.dart` 第 237、240 行）。
   - 长期记忆插件页只说"在压缩确认时归档"，没提自动压缩也会写记忆。
   - [联系人Markdown记忆.md](联系人Markdown记忆.md) 说 MD 没有云同步、"自动部分留第二批"，这两点都已经过时。
   - [上下文压缩与记忆联动方案.md](上下文压缩与记忆联动方案.md) 第 6 节说新表和 MD 都没有云同步。实际上 `topic_handoffs` 和 MD 已经同步了，另外两张表确实没有同步。
   - [聊天请求上下文真相源与组装规范.md](../../02_前后端分离与架构规范/聊天请求上下文真相源与组装规范.md) 手动压缩一节末尾说"自动压缩也尚未接入"，但 09-13 就已经接入了。

## 9. 如果要收拢（建议，未实施）

顺序是：先止血，再定方向，最后整理。

1. **先止血**：核对 09-19 那批改动（v17 补表、总结模型引用、设置页），提交到本地 `main`；在手机"new"会话上复验自动压缩；补上需求日志的结果。
2. **决定旧库的去留**（这件事需要你拍板，定了之后不好回头）
   - 推荐做法：**冻结旧库，默认改用记忆本。** 旧库只读，停掉隔天整理和日记；新角色，以及从没用过旧库的角色，默认打开记忆本；对用过旧库的角色，提供一次"导入到记忆本"（L1 转成常驻笔记，L2/L3 转成往事，你确认之后再写入）。
   - 理由：两套记忆同时存在是"散"的最大来源。记忆本已经接上了压缩联动和云同步；旧库的写入依赖 Embedding，还有第 8 节第 2、3 条的问题。
   - 代价：会失去向量那种"按意思"的检索（记忆本目前只能按字面匹配）；导入是有损转换；旧库数据还要再保留一段时间，方便回退。如果以后往事多到按字面检索不够用，就单独给记忆本加索引，不回到四层结构。
3. **设置归位**：把"总结模型 + 上下文窗口"从长期记忆插件里挪出来，放到一个"上下文与压缩"设置里，只保留一个入口。长期记忆插件页只管记忆本身；Embedding 跟着旧库冻结一起下线。
4. **压缩收成一个入口**：对外只保留一个"上下文管理"接口，内部分三种策略（翻篇 / 腾地方 / 现场收拾）；存储合并成一个 Store，把 `memory_state` 的两层意思拆开；三张表的建表语句各自独立，并配上迁移测试。
5. **打扫**：删掉没人调用的旧入口；日记页要么恢复入口，要么跟旧库一起停写；旧设计稿移到 `05_历史归档/`；修正第 8 节第 7 条列的文案和文档；给 `runtime_context_records` 加上保留期清理。
