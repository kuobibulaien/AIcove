# 10 主动回复流程重排与会话状态方案

> 创建日期：2026-04-16
> 适用范围：`lib/src/features/auto_reply/` 主动回复链路
> 目标：把“会话状态机 + 触发器 + 预生成 + 发送后阶梯”收敛成一条当前项目可落地的单一流程

---

## 1. 背景

当前主动回复实现已经具备以下基础能力：

- `AnalyzerScheduler`：用户发消息后，延迟 5 分钟触发一次分析
- `ContextAnalyzer`：使用后台 Agent 读取近期消息并生成触发器建议
- `AutoReplyTriggerController`：管理触发器创建、轮询、作废与发送结果回写
- `BackgroundService`：在 App 不活跃时通过 WorkManager 兜底执行
- `ChatActions.sendProactiveTrigger()`：真正把主动消息送进聊天链路

但现有链路仍存在几个核心缺口：

1. 会话级“主动回复状态”没有独立持久化，只剩触发器状态。
2. “用户没回复几次、当前是不是沉默期、是否已经休眠”没有可靠落点。
3. `cachedContent` 虽然已经进入模型与发送链路，但没有形成统一的“预生成约定”。
4. 后台 Agent 的提示词容易越界到“指挥 chat 模型怎么说”，不利于保持通用性。

本文档给出一版基于现有架构的收敛方案。

---

## 2. 设计原则

### 2.1 会话状态与触发器状态分层

- 会话状态负责描述“当前聊天窗口处在什么阶段”。
- 触发器状态负责描述“某一条计划发送中的消息处在什么生命周期”。
- 不再让“触发器列表是否为空”承担会话状态判断。

### 2.2 用户新消息是最高优先级

用户任何新消息都应立即：

- 清除当前会话所有 AI 自动触发器
- 重置未回复计数
- 退出 `silent` / `dormant`
- 重新进入 5 分钟静默观察

### 2.3 每个会话同一时间最多保留 1 个 AI 自动触发器

- 手动提醒不受这个限制
- AI 自动关怀触发器始终采用“替换式更新”
- analyzer 的职责是“决定当前唯一应该存在的自动触发器”

### 2.4 后台 Agent 只描述客观状态，不指挥聊天人格

后台 Agent 生成的 `system_reminder` 应采用“旁白式、客观式、状态描述式”表达，例如：

- “距离用户上一条消息已过去 6 分钟，刚才话题像是停在半句。”
- “用户明确表示去洗澡，当前已过去约 40 分钟。”
- “这轮对话已经自然收束，当前更适合下次再开启新话题。”

不建议写成：

- “你现在要撒娇一点”
- “你要装委屈”
- “你必须哄他”

chat 模型应该根据上下文和 `system_reminder` 自己组织最终表达。

### 2.5 `cachedContent` 来自 chat 模型预生成

`cachedContent` 不是 analyzer 直接写出来的文案。

标准流程应为：

1. analyzer 输出客观的 `system_reminder`
2. 系统取“当前上下文快照 + system_reminder”
3. 调用 chat 模型预生成一条可直接发送的消息
4. 把该结果写入 `cachedContent`

也就是说：

- analyzer 决定“何时发、为什么发、当前客观状态是什么”
- chat 模型决定“具体怎么说”

## 3. 会话状态模型

建议新增 `conversation_proactive_state`，按 `conversationId` 持久化。

### 3.1 字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `conversationId` | `String` | 会话 ID |
| `mode` | `active \| silent \| dormant` | 当前会话主动回复模式 |
| `unrepliedCount` | `int` | 连续主动发送后用户未回复次数，建议范围 `0~3` |
| `lastUserMessageId` | `String?` | 最近一条用户消息 ID |
| `lastUserAt` | `DateTime?` | 最近一条用户消息时间 |
| `lastProactiveAt` | `DateTime?` | 最近一次主动发送成功时间 |
| `silenceUntil` | `DateTime?` | 沉默期截止时间 |
| `pendingAutoTriggerId` | `String?` | 当前待触发的 AI 自动关怀触发器 ID |

### 3.2 模式含义

#### `active`

- 默认活跃态
- 允许进入“5 分钟无消息 -> analyzer 分析”
- 当前没有沉默限制

#### `silent`

- 暂时不主动打扰
- 到 `silenceUntil` 后只唤醒一次 analyzer
- 唤醒后若仍无用户新消息，再决定是否创建新的自动触发器

#### `dormant`

- 达到默认最后一次主动尝试后停止自动主动消息
- 只有用户再次发消息时才会重置为 `active`

---

## 4. AI 自动触发器分类

AI 自动关怀触发器只保留以下 4 类业务语义：

| kind | 场景 | 建议延迟 |
|---|---|---|
| `continue_chat` | 对话明显没结束，用户像是暂时停住了 | `1~3` 分钟 |
| `check_in` | 用户明确说去洗澡、吃饭、出门、办事，存在回来再聊的语义 | `20~60` 分钟 |
| `new_topic` | 对话自然结束，适合隔一段时间重新开启 | `8~24` 小时 |
| `stay_silent` | 当前不应主动联系 | 不创建触发器，仅更新会话状态 |

说明：

- `stay_silent` 不是触发器实体，而是 analyzer 的“无触发器决策”。
- 手动提醒仍继续使用现有 `high priority + fixed/delay` 体系，不混入这套会话状态机。

---

## 5. 主流程

### 5.1 用户发来新消息

系统立即执行：

1. 清除当前会话所有 AI 自动触发器
2. 更新会话状态：
   - `mode = active`
   - `unrepliedCount = 0`
   - `lastUserMessageId = 当前用户消息 id`
   - `lastUserAt = 当前时间`
   - `silenceUntil = null`
   - `pendingAutoTriggerId = null`
3. 启动当前会话的 5 分钟静默观察计时

### 5.2 5 分钟内用户又发消息

- 取消上一次 5 分钟计时
- 重新开始 5 分钟静默观察
- 不创建任何自动触发器

### 5.3 满 5 分钟仍无用户新消息

只有在以下条件同时满足时才调用 analyzer：

- `mode == active`
- 当前会话没有待触发 AI 自动关怀触发器
- 不在 `silent` / `dormant`
- 没有命中 quiet hours / daily limit / min interval 的硬门禁

analyzer 只允许返回两类结果：

1. `session_patch`
2. `trigger_ops`

其中 `trigger_ops` 最终只能留下 0 或 1 个 AI 自动触发器。

---

## 6. analyzer 输出协议

建议统一成以下结构：

```json
{
  "session_patch": {
    "mode": "silent",
    "silence_minutes": 480,
    "reason": "user_may_be_busy"
  },
  "trigger_ops": [
    {
      "op": "replace",
      "kind": "new_topic",
      "title": "明早轻开话题",
      "delay_minutes": 480,
      "system_reminder": "距离上一轮对话已经过去一晚，这轮对话昨晚自然结束，当前更适合轻松开启一个新话题。",
      "allow_night": false,
      "priority": "medium"
    }
  ]
}
```

### 6.1 `session_patch`

只负责会话状态，不直接包含聊天文案。

建议字段：

- `mode`
- `silence_minutes`
- `reason`

### 6.2 `trigger_ops`

只负责触发器操作，不直接写最终发送文本。

建议字段：

- `op`
- `kind`
- `title`
- `delay_minutes`
- `system_reminder`
- `allow_night`
- `priority`

### 6.3 背景 Agent 的提示词边界

后台 Agent 应明确收到以下约束：

1. 你输出的是“会话状态补丁”和“触发器操作”
2. 你描述的是客观状态，不负责编写最终发给用户的消息
3. 你不要指挥 chat 模型扮演口吻、情绪、动作
4. 你不能因为“用户没回”就默认推断其生气、出事、需要被哄

---

## 7. `cachedContent` 预生成机制

### 7.1 基本规则

`cachedContent` 必须由 chat 模型预生成。

### 7.2 输入构成

预生成时的输入应由两部分组成：

1. 当前上下文快照 `contextSnapshot`
2. `system_reminder`

推荐做法：

- 以 `contextSnapshot` 作为历史消息
- 通过现有 `SystemReminderService` 把 `system_reminder` 以 system-reminder 形式注入上下文
- 不给 `userText`
- 让 chat 模型直接生成一条可发送的主动消息

### 7.3 预生成产物

预生成完成后回写：

- `cachedContent`
- `preparedAt`
- `status = prepared`

若预生成失败：

- 保留触发器
- 回退为 `pending`
- 到真正触发时再走即时生成

### 7.4 责任边界

- analyzer 负责：判断时机、输出客观提醒
- chat 模型负责：根据提醒与上下文生成最终说法
- 发送链路负责：优先发 `cachedContent`，失败时回退即时生成

---

## 8. 触发器到点前二次校验

触发器到点前必须重新检查以下条件：

1. 当前最后一条用户消息是否仍等于创建触发器时记录的 `contextLastUserMessageId`
2. 当前会话是否正在聊天界面
3. 当前是否命中 quiet hours
4. 当前会话是否已进入 `silent` / `dormant`
5. 当前会话是否已经有更新的自动触发器替代它

校验结论：

- 若用户已发新消息：作废
- 若当前正停留在聊天页且优先级较低：作废
- 若已被更新触发器替代：作废
- 若不允许夜间发送且命中 quiet hours：延后或作废

---

## 9. 发送成功后的阶梯流转

触发器发送成功后，不再立刻进入下一轮 5 分钟轮询，而是进入未回复阶梯。

### 9.1 `unrepliedCount = 1`

- `mode = silent`
- `silenceUntil = now + 8~12h`
- 不再追问“为什么不回”

### 9.2 `unrepliedCount = 2`

- 继续 `silent`
- `silenceUntil = now + 24h`
- 到点后仅唤醒一次 analyzer

### 9.3 `unrepliedCount >= 3`

- `mode = dormant`
- 停止自动主动回复
- 直到用户再次发消息才重置

---

## 10. 沉默期结束后的流程

到达 `silenceUntil` 时：

1. 若用户期间发过消息：本轮流程已被重置，不做任何事
2. 若用户没有发新消息：仅执行一次 analyzer

沉默唤醒时，analyzer 应受更严格限制：

- 优先 `new_topic`
- 允许非常轻的 `check_in`
- 不默认输出“怎么不回消息”
- 不默认输出“是不是出事了”
- 只有最近上下文中有明确情绪线索时，才允许温和关心一次

---

## 11. 建议删除的旧推断

以下旧逻辑建议直接删除或降级：

### 11.1 “触发器列表为空 = 没创建过 / 已失效”

不可靠。

原因：

- 已触发 / 已过期触发器会被清理
- 空列表不能推断历史状态

### 11.2 “用户没回复 = 用户出事了 / 生气了 / 要哄”

风险太高。

原因：

- 项目场景是心理陪伴，误判成本高
- 没回复不应直接推导成强情绪事件

### 11.3 “为什么不回复”

默认不应进入文案模板。

更推荐：

- 轻推当前话题
- 轻分享一个新话题
- 使用中性、低压的开场

## 12. 对现有实现的改造映射

### 12.1 新增

- `conversation_proactive_state.dart`
- `conversation_proactive_state_storage.dart`
- 统一的会话级调度协调器（负责 5 分钟、沉默到期、启动恢复）

### 12.2 改造

- `analyzer_scheduler.dart`
  - 从“只看 activeConversation 的单定时器”
  - 改为“按 conversationId 调度”

- `context_analyzer.dart`
  - 输出从“完整触发器列表 JSON”
  - 改为“session_patch + trigger_ops”
  - `system_reminder` 改为客观描述

- `auto_reply_trigger_controller.dart`
  - 增加 AI 自动触发器唯一性维护
  - 接入 `pendingAutoTriggerId`
  - 增加与会话状态联动

- `chat_actions.dart` / `chat_actions_action_ops.dart`
  - 用户新消息时重置会话主动状态
  - 主动发送成功后回写未回复阶梯

- `background_service.dart`
  - 后台发送时优先读取 `cachedContent`
  - 与前台采用同一套触发器语义

### 12.3 保留

- 手动提醒链路
- quiet hours / daily limit / min interval
- WorkManager 兜底执行

## 13. 一句话流程图

```text
用户发消息
  -> 重置当前会话主动状态
  -> 开始 5 分钟静默观察
  -> 满 5 分钟仍无新消息
  -> analyzer 输出 session_patch + trigger_ops
  -> 创建或替换唯一 AI 自动触发器
  -> 用当前上下文 + system_reminder 调 chat 模型预生成 cachedContent
  -> 到点前做二次校验
  -> 发送成功后按 unrepliedCount 进入 silent / dormant
  -> silenceUntil 到期只唤醒一次 analyzer
```

## 15. 结论

这次流程重排的核心不是“再加更多判断”，而是先把主动回复收敛成 3 条清晰边界：

1. 会话状态单独管理
2. 触发器只负责一次具体计划发送
3. 预生成内容由 chat 模型基于“当前上下文 + system_reminder”生成

只要这三层边界明确，主动回复链路才能稳定、可解释、可继续扩展。

### 16.1 Android 端补充说明

在 Android 14 及以上系统中，主动回复开启后会立即尝试拉起通知栏前台守护服务。若未在 Manifest 中声明 `foregroundServiceType`，服务可能在启动瞬间抛出前台服务类型异常，表现为“设置页一开启就闪退”。

第一轮实现后已补充：

1. `PersistentGuardService` 的 `foregroundServiceType="dataSync"` 声明。
2. `FOREGROUND_SERVICE_DATA_SYNC` 权限。
3. 服务启动失败时的原生兜底，避免直接拖垮整个应用进程。
