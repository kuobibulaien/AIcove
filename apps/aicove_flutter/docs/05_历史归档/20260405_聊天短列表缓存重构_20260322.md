# 聊天短列表缓存重构（2026-03-22）

> 2026-04-02 说明：
> 本文记录的“JSON 持久短列表”方案已退出主链路。当前运行实现已经切回“数据库 raw message + 前端投影 + 内存时间线缓存”，不再落盘 `window.json`，不再后台 `warmupConversations(...)`，也不再因消息分段策略触发 `rebuildAllFromDb()`。

## 目标

- 聊天页进入时不再依赖数据库现组装的“最近 20 条”窗口。
- 改为每个会话持久保存“最近若干条原始消息”的完整短列表，默认种子为最近 20 条。
- 图片、语音等多媒体在短列表层直接落到本地文件，进入聊天页时可直接读取。
- 点击联系人时不再临时预热消息列表；改为应用启动后后台准备各会话短列表。
- 单个会话短列表目录超过 50MB 时，才把该会话回收为最近 20 条。

## 核心实现

### 1. 新增 `ConversationTimelineCache`

路径：

- `lib/src/features/chat/services/conversation_short_window_store.dart`

职责：

- 维护每个会话的短列表 JSON 文件。
- 首次读取时，若本地已有缓存则直接恢复；否则从数据库取最近消息生成。
- 当可见消息数增加时，从数据库向前分页补齐，并把扩展结果继续持久化。
- 对图片、语音、文件、表情等本地资源做“自有目录收编”，避免进入聊天页时再做一次媒体解析。
- 只统计当前会话短列表目录大小；超过 50MB 时，仅压缩当前会话回最近 20 条。

存储位置：

- `getApplicationDocumentsDirectory()/conversation_short_windows/<conversationId-base64>/window.json`
- `getApplicationDocumentsDirectory()/conversation_short_windows/<conversationId-base64>/media/*`

### 2. 时间线 Provider 切换为短列表

路径：

- `lib/src/features/chat/conversation_timeline_providers.dart`

变化：

- `conversationMessageWindowProvider` 现在直接监听 `ConversationTimelineCache.watchWindow(...)`。
- 首屏和分页都按“原始消息条数”工作，默认 20 条，每次上翻再加 20 条。

### 3. 历史写入链路同步短列表

路径：

- `lib/src/features/chat/services/chat_history_store.dart`
- `lib/src/features/chat/conversation_providers.dart`

变化：

- 用户消息、助手消息、消息状态更新、消息编辑后，都会同步更新短列表。
- 删除/截断/替换消息后，短列表会按当前已加载深度从数据库重建。
- 清空会话和删除会话时，会一并删除短列表目录。

### 4. 页面进入链路减负

路径：

- `lib/src/ui/features/chat/pages/chat_page.dart`
- `lib/src/features/chat/presentation/widgets/contacts_list_content.dart`
- `lib/src/app.dart`

变化：

- 移除聊天页进入时的 0.4s 延迟壳启用路径，聊天页直接读短列表。
- 联系人列表只保留头像预热，不再点击时现读消息预热。
- App 启动后后台为所有会话准备短列表，不再预热最近会话的 30 条消息和消息图片。

## 2026-03-22 补充：流式占位退回 transient，短列表继续只存原始消息

### 背景

- 之前的流式占位链路会把 `MessageFormatConfig` 带进 `_StreamPlaceholderDelivery`；
- 当开启“界面分段”时，流式阶段会先把一条助手正文拆成多条 `Message`，再直接写入数据库和短列表；
- 结果就是“界面分段”这个本应属于 UI 的策略，污染到了正式历史和短列表持久层。

### 本次修正

- `_StreamPlaceholderDelivery` 不再写 `chatHistoryStore`，改为只更新 `conversationTransientTimelineProvider`。
- 流式收尾时，先清空 transient 占位，再走正式 `deliverSegmentedMessages()` 落库。
- 对于纯文本回复，正式历史和短列表现在只保留一条原始 assistant 消息；界面是否分段，统一交给 `ChatMessageList` 渲染层决定。
- 对于 TTS / 图片 / 表情包这类多模态顺序消息，仍按数据层真实语序落库；这部分不属于 UI 分段。

### 影响

- 新生成的消息不再被“界面分段策略”写死到数据库或短列表。
- 修改分段设置后，前端展示会按最新规则重算，不再和短列表持久化结果互相打架。
- 旧数据库里已经被拆成多条历史消息的记录，本次没有自动合并；后续若要修复，需要单独做历史数据迁移规则。

## 2026-03-22 补充：分段策略变更联动短列表全量重建

### 背景

- 用户反馈：后端已经回到“只存原始消息”，但前端本地短列表仍可能保留历史的前端快照内容；
- 当消息分段策略变更时，聊天页分段规则会更新，但短列表若不主动刷新，仍可能继续喂给 UI 旧消息窗口，导致“策略已改、展示不跟随”。

### 本次修正

- 在 `MessageFormatConfig` 增加统一签名函数 `buildMessageFormatProjectionSignature(...)`，用于判定分段策略是否真的变化。
- `AppSettingsNotifier.updateMessageFormatConfig(...)` 在策略签名变化后，会调用 `ConversationTimelineCache.rebuildAllFromDb()`。
- `ConversationTimelineCache.rebuildAllFromDb()` 会收集所有已知会话（内存 + 持久化 + 会话表），逐个按数据库原始消息重建短列表快照。

### 结果

- 后端存储仍保持原始消息；
- 前端展示分段和本地短列表会在策略修改后一起刷新，避免“界面策略”和“短列表持久化”继续冲突。

## 2026-03-23 补充：聊天页恢复首屏快照直出

### 背景

- 短列表与 `ChatMessageList` 的持久首屏快照能力都已存在；
- 但聊天页入口层一度把 `allowPersistentViewportBoot` 固定成 `false`；
- 结果是消息和语音条虽然已经持久化，进入会话时列表仍要先等异步时间线恢复，体感上像“还得再加载一下”。

### 本次修正

- 在 `lib/src/ui/features/chat/pages/chat_page.dart` 增加统一判断：
  - 普通进入会话时启用持久首屏快照直出；
  - 延迟壳阶段或当前无有效会话 ID 时，继续禁用该能力。
- 这样聊天页在数据库时间线尚未恢复完成前，可以先直接使用 `ChatMessageList` 已落盘的首屏快照。

### 结果

- 已持久化的最近消息窗口可以更早显示出来；
- 语音条作为正式消息仍来自短列表持久层；
- 若仍感到语音控件自身有一次小加载，那属于播放器控件重新建树后的音频源恢复，不是消息未持久化。

## 2026-03-23 补充：短列表成为唯一前台时间线，历史分页改为向前补页

### 背景

- 用户反馈：发送图片前后，尤其是最后一段流式文本收尾并衔接图片占位时，聊天视窗会被往上抬；
- 根因不是单纯的自动滚动，而是前台列表在“transient 流式占位”和“正式短列表消息”之间发生了交接切换；
- 旧链路里，流式结束后会先清掉临时占位，再由正式消息和后续图片占位重新进入列表，尾部高度在短时间内多次变化。

### 本次修正

- 聊天页前台显示统一只读 `ConversationTimelineCache`，不再把 `conversationTransientTimelineProvider` 直接喂给 `ChatMessageList`；
- `_StreamPlaceholderDelivery` 在流式阶段直接把占位消息写进短列表，并在收尾时通过 `replaceMessages(...)` 原位替换成最终文本锚点消息；
- 正式 assistant 文本先落数据库，但不立即回写短列表，由短列表原位替换负责承接 UI；
- 后续图片、TTS 等补充消息继续复用 `appendAfterStreamText` 机制，直接接在这批已提交的文本锚点后面；
- 用户上滑加载历史时，不再整窗重建“最近 N 条”，而是调用 `loadOlderMessages(...)` 从数据库向前补一页，并把结果前插到当前短列表快照。

### 结果

- 聊天页首屏和发送过程都只使用同一套持久短列表，减少“草稿层”和“正式层”切换造成的跳动；
- 流式文本收尾到图片占位接入之间，不再出现先清空尾部再重新插入的空窗；
- 数据库退回后台存储职责，只有用户主动上滑查看更多历史时，才参与当前前台列表扩展。

## 2026-03-23 补充：数据库正式回退为原始 assistant，前端投影由短列表独立维护

### 背景

- 用户明确要求把“数据库原始消息”和“前端消息列表”彻底拆开；
- 之前虽然短列表已经独立，但 assistant 的前端投影片段、TTS/图片后补消息仍可能继续写入 `messages` 表；
- 结果是上下文拼装看到的不是 AI 原始回复，而是已经被前端改写过的版本。

### 本次修正

- `messages` 表新增 `raw_payload`，assistant 正式入库时只写一条原始消息：
  - `content / blocks` 保留原始 reply、tool calls、tool results；
  - `raw_payload` 保存前端恢复投影所需的投影快照与插件元数据；
- 新增 `message_projection_mappings` 表，记录 `raw_message_id -> projected_message_id`；
- `ConversationTimelineCache` 从数据库读取原始消息后，统一经前端投影服务恢复成前端消息列表；
- `ChatSendService / ChatHistoryStore / ChatTtsHandler` 改为：
  - 正式历史只追加原始 assistant；
  - 前端补充消息（流式收尾、TTS 占位/完成、图片后补）只更新短列表，并回写所属原始 assistant 的投影快照；
- 上下文拼装链改为读取数据库原始消息，不再复用前端投影文本。

### 结果

- AI 上下文重新使用原始 assistant 回复，不再被 `<image>` / 分段 / 后补消息污染；
- 前端继续拥有独立的 20 条短窗缓存和分段策略控制权；
- 历史分页和短列表重建都能从原始 assistant + 投影快照恢复出一致的前端消息列表。

## 2026-03-23 补充：前端行为继续向短列表单点收口

### 本次补口

- `ChatDeferredImageDelivery.resolvePlaceholderBaseTime(...)` 改为读取 `ConversationTimelineCache.loadAllMessages(...)`；
  - 语义：图片占位时间排序只服从当前前台短列表，而不是数据库全历史投影；
  - 目的：避免前端补充消息尚未正式入库时，占位时间基准回退到旧历史。
- `ChatPageQueries.conversationHasImageMessages(...)` 改为读取短列表；
  - 语义：这是前端发送前判断，代表“当前前台时间线里是否存在图片”，不再代表数据库全历史事实。
- 移除 `ChatHistoryStore.watchWindow(...)` 这条数据库直投影窗口入口；
  - 聊天页正式时间线统一只走 `ConversationTimelineCache.watchWindow(...)`。
- 删除流式阶段的瞬时 timeline provider 写入依赖；
  - 流式占位仍可更新短列表，但不再保留第二条“正式列表候选源”。

### 边界结论

- 短列表是前端唯一正式时间线；
- 数据库是原始消息事实层；
- 前端查询如果描述的是“当前看到的聊天页状态”，都应优先基于短列表；
- 后端上下文、检索、原始历史统计则继续基于数据库 raw message。

## 2026-03-26 补充：短列表预算回收改为按单会话触发

### 背景

- 用户反馈：历史分页扩展后的短列表会很快又只剩 20 条；
- 排查发现预算回收曾按 `conversation_short_windows` 根目录总量触发；
- 这会导致某个会话只要新增一条消息，其他会话的媒体体积也可能把它连带压回 20 条。

### 本次修正

- 预算判断改为只看“当前会话自己的短列表目录”；
- 只有该会话目录超过 50MB 时，才把它回收到最近 20 条；
- 已分页加载的历史和后续新消息，在未触发本会话 50MB 阈值前都会继续保留。

### 数据口径补充

- 用户/原始多模态消息的图片块继续保存在 `message_blocks`；
- 助手后补图片/语音这类前端补充语义，2026-04-02 起改为分别回写 `messages.raw_payload.pluginContents` / `toolAudioResults`；
- 对慢图、流式后补等需要保留最终落位的场景，再额外回写 `raw_payload.supplementInsertOps`，用于表达“插在第几个文本段后 / 是否强制追加到尾部”；
- `raw_payload.projectedMessages` 仅保留旧数据兼容读取，短列表从数据库重建时需要兼容 `message_blocks`、补充语义字段、插入位点语义和旧 `projectedMessages` 四类来源。

## 2026-03-26 补充：用户图文混合消息只在前端短窗路径拆分

### 背景

- `loadAllMessages()` 在 action / retry / regenerate / 上下文拼装链路里继续承担 raw 历史语义；
- 但聊天页短列表需要把“用户文字 + 图片”这种混合消息拆成两条前端展示消息，保证尾消息和预览顺序符合 UI 预期；
- 若把这类拆分直接推广到 persisted history，会把 raw user 消息污染成 `__proj_*` 形态。

### 本次修正

- 保持 `ChatHistoryStore.loadAllMessages(...)` 的 persisted history 语义不变：
  - user/raw 图文混合消息在历史事实层仍保持原始单条消息；
- 新增前端专用投影路径：
  - 只有短列表写入、前端 best-effort 读取、按消息 id 恢复前端消息时，才对用户图文混合消息做拆分；
  - 这样短列表和从数据库重建的前端窗口仍会显示为 `文字 -> 图片` 两条，而 action 层继续读取 raw 历史。
  - 前台消息列表正式只消费 `conversationMessagesProvider / conversationHasMoreProvider`。
- `ConversationTimelineCache.watchWindow(...) / loadAllMessages(...)` 改为只读内存或磁盘短列表；
  - 若本地短列表尚未准备好，前台先返回空窗口，不再在读取路径里直接查数据库。
- `ConversationTimelineCache.warmupConversations(...)` 改为只把已有短列表从磁盘预热到内存；
  - 启动阶段不再因为“预热消息列表”而去数据库补建短列表。
- 数据库读取收口为显式链路：
  - `reloadConversationFromRawStore(...) / rebuildAllFromDb()`：后台重建或格式迁移；
  - `loadOlderMessages(...)`：用户主动上滑加载历史分页。

### 结果

- 前台消息列表只认一份持久化真源：`conversation_short_windows/<conversationId>/window.json`；
- 旧的消息列表持久快照和新的短列表不再重复保存同一批前端消息；
- 聊天页、前端动作链、列表渲染都不会再因为“短列表缺失”而在读路径里悄悄回退数据库。

## 2026-03-27 补充：进界面先恢复 20 条本地短列表，首帧后再补齐本地短列表

### 背景

- 用户反馈：第一次上滑扩展后，短列表文件里已经写入更多历史消息；
- 重新进入同一会话时，不应该一上来就把整份本地短列表全部抬到前台；
- 但也不能回退到“每次上滑都直接查数据库历史页”，否则体感上仍像短列表没有真正存住。

### 根因

- 前一版修正把“已持久化的扩展短列表”在重进会话时整份恢复到前台；
- 这样虽然解决了“短列表被裁回 20 条”的问题，但首帧会直接抬起整份本地窗口；
- 用户最新要求是把“进界面首帧”和“补齐本地短列表”拆成两段处理。

### 本次修正

- `ConversationTimelineCache.watchWindow(...)` 恢复按 `limit` 读取本地短列表尾部窗口；
- 聊天页进入会话时，首帧通过 `visibleCount` 的默认初始值维持 20 条；
- `visibleCount` 改为随聊天页监听生命周期自动回收，不再在页面生命周期里手动 reset；
- 首帧后再读取本地短列表总数，把 `visibleCount` 提升到当前会话已持久化的本地短列表长度；
- 用户主动上滑时，如果本地短列表还有未展示部分，先扩展到本地短列表总量；只有本地短列表已经补齐后，才继续查数据库历史页。

### 回归

- 新增测试：
  - `重进会话时应先恢复短列表尾部 20 条，并保留本地扩展段总数`
  - `已有扩展短列表时，时间线应先恢复 20 条，再按本地短列表总量补齐`
  - `聊天页进入阶段补齐本地短列表时，应把可见数提升到本地短列表总量`
  - `聊天页上滑分页时，应先消费本地扩展段，再继续查数据库历史页`

## 2026-03-24 补充：followLatest 的底部语义要对齐到输入框上沿

## 2026-03-24 补充：前置 TTS 占位不能抢在正文锚点前单独落窗

  - 如果回复片段一开始就是 `<tts>...</tts>`；
  - 旧逻辑会先把 pending 音频气泡写进短窗；
  - 等后面的可见正文到达后，再把正文锚点补到这条音频前面。

  - 蓝色尾消息先被 pending 音频顶一下；
  - 正文出来时再被补顶一次；
  - 重新生成场景尤其明显，因为本轮本来就只盯着输入框上沿附近。

- `_StreamPlaceholderDelivery._buildTimelineDescriptors(...)` 对“前置 TTS”改成延迟挂占位：
  - 在本轮 assistant 还没有任何可见正文锚点前，先缓存 pending 音频描述；
  - 一旦正文锚点出现，再把这些 pending 音频按顺序挂到正文后面；
  - 如果整轮最终只有 TTS、没有正文，收尾阶段仍会把 pending 音频正常落窗。
- 这样短窗里的可见顺序就重新收敛成：
  - 正文锚点优先；
  - 语音占位随后；
  - 收尾继续沿用同一批前端消息做原位补齐，不再发生“音频先抢跑、正文后回插”。

## 2026-03-25 补充：raw 历史、短窗投影与持久快照窗口重新收口

### 背景

- 聊天链路这几天同时在处理三套语义：
  - action 层做 `retry / edit / regenerate` 时需要拿 **raw 历史消息**；
  - 短窗列表显示和流式占位需要拿 **前端本地投影消息**；
  - 持久快照恢复只需要最近固定轮数，而不是跟 live timeline 共用首屏 20 轮。
- 旧实现把这些语义混在了同一个 `loadAllMessages()` / `projectMessages()` 上：
  - action 层会误吃到短窗投影态，导致图文 user 消息被拆成 `__proj_*`；
  - 流式纯文本分段会被直接写进 raw assistant payload，正式历史被 UI 分段污染；
  - 同一个空会话 id 重新进入时，短窗缓存还可能把旧消息复活回来；
  - 持久快照测试期望最近 5 轮，但调用链默认仍走 20 轮。

### 本次修正

- `ChatHistoryStoreAdapter.loadAllMessages(...)` 改回 raw 语义：
  - action 层统一从 `ChatHistoryPort` 拿 raw 历史；
  - 前端短窗继续单独走 `loadFrontendMessages(...)`。
- `ChatActionsActionOps` 的 canonical 消息解析改成：
  - 先用当前 history port 里的 raw 历史定位；
  - 只有必要时才回退到 `chatHistoryStoreProvider` 按 `sourceMessageId` 找原始消息。
- `ChatHistoryStore` 的持久历史投影改成“assistant 可重建、user 默认直通”：
  - user/raw 图文消息不再在稳定历史里自动拆成多条；
  - assistant 如果 payload 里只剩纯文本流式分段，会在读取时重新收口成正式正文消息；

- 对短窗缓存补了“空会话首条消息前先清旧窗”：
  - 只要数据库里该会话还没有消息，就先把短窗残留清掉；
  - 避免同一个 conversation id 在测试或重建后把旧首屏缓存带回来。
- 流式占位层补了两条稳定性约束：
  - 增加写回失效序号，防止 `removePlaceholders()` 后旧 flush 再把占位写回短窗；
  - “生成中...” 占位阈值收紧到约 0.45s，抵消调度抖动后仍满足“约 0.5s 出占位”的交互要求。
- `ChatTtsHandler` 的非流式混排路径把 TTS 实际转换启动挪到函数尾部：
  - 先把 pending 语音条、后续文本和慢图占位全部落窗；
  - 再统一异步启动 TTS，避免 `deliverSegmentedMessages()` 返回时 pending 已经被过快回填成 success。
- `resolvePersistentSnapshotWindow(...)` 的默认轮数拆成独立常量：
