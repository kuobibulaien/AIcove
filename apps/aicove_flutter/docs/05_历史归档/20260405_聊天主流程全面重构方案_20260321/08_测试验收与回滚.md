# 测试验收与回滚

## 本文目标

为聊天主流程重构提供统一的测试口径、阶段验收标准和失败回滚策略，避免多个窗口各改各的，最后没人能确定“到底稳不稳”。

---

## 验收原则

### 1. 先保行为，再谈结构

这轮重构首先要保证主流程行为不倒退：

- 能正常发送
- 能正常重试
- 能正常重生成
- 流式展示正常
- 失败时能恢复
- 页面列表不出现明显交接闪烁或状态缺失

### 2. 每个窗口都要给出“本窗口验证结果”

不要只留下“已改完”。至少需要说明：

- 改了哪些文件
- 跑了哪些测试/命令
- 哪些风险点还没验证

### 3. 最终以整链路验收为准

单窗口自测通过，不代表整条链路就一定没问题。

---

## 分层测试建议

### 发送主链

至少覆盖：

- 普通发送
- retry
- regenerate
- proactive trigger 发送
- 模型默认值解析
- 工具调用场景
- API 失败回退

### 流式交付

至少覆盖：

- 创建占位
- 流式增量刷新
- 最终落库交接
- 失败时回滚
- 工具调用中间态

### Provider/状态层

至少覆盖：

- 当前会话真相源输出
- timeline 输出
- 页面不再依赖双路径 fallback
- 旧 Provider 下线后的等价行为

### UI 层

至少覆盖：

- 页面发送入口
- 引用消息发送
- 历史分页
- 自动跟随/脱离跟随
- 回到底部/新消息提示

### API 层

至少覆盖：

- stream/direct 共用装配不破坏现有请求
- endpoint/provider 解析一致
- 旧兼容入口仍可正常转发或已被正确下线

---

## 建议命令

### 基础静态检查

```powershell
flutter analyze
```

如变更范围较大，至少对聊天主链相关文件跑定向 analyze。

### 单元/组件测试

按各窗口影响面选择现有测试，并补必要回归用例。

### 真机主流程验证

根据项目约定，代码改动完成后需要执行：

```powershell
flutter run --no-resident
```

重点人工验证：

1. 新开会话发送
2. 老会话发送
3. retry / regenerate
4. 流式输出
5. 引用发送
6. 页面切换后返回

---

## 推荐验收清单

### 窗口级验收

每个窗口提交时应附：

- 修改文件清单
- 验证命令
- 风险说明

### 主题级验收

每个专题文档完成后，应由总控窗口确认：

- 是否满足该文档里的验收标准
- 是否影响其他窗口边界

### 总体验收

最终合并前，统一确认：

1. 发送四大入口全部可用
2. 临时消息/流式交接正常
3. 页面不再自己兜底第二数据源
4. `AgentApi` 调用无回归
5. dead code 清理未误删在线路径

---

## 回滚策略

### 1. 按批次回滚，不整锅回滚

建议回滚粒度按专题进行：

- 发送链一批
- Actions/Provider 一批
- UI 一批
- API 一批
- 清理一批

### 2. 每个批次保留可独立恢复点

避免把 5 个窗口的修改混成一个不可拆的大补丁。

### 3. 删除类改动必须在最后批次

dead code 清理尽量后置，这样一旦回滚前面结构变更，不会因为旧文件已删而难以恢复。

---

## 风险升级条件

出现以下任一情况，应暂停继续推进并重新收敛：

1. 任一窗口改动导致主发送链无法跑通。
2. 流式占位与正式消息交接出现重复/丢失/闪烁明显回归。
3. Provider 重组后页面出现持续性空白或状态不更新。
4. API 层改动影响所有模型渠道。

这时应优先回到“上一稳定批次”，而不是继续叠修补。
