# 聊天主流程全面重构方案

> 创建日期：2026-03-21
> 状态：设计中

---

## 概述

本文档给出聊天主流程的一次系统性重构计划，目标不是“把大文件切碎”这么简单，而是把当前聊天链路里最容易继续失控的几条主线彻底收口：

- 发送主链路只有一条骨架，`send / retry / regenerate / proactive` 不再各走各路
- `ChatActions` 不再继续承担上帝类职责
- 流式占位与时间线临时消息只有一套真相源
- Provider 体系从“历史堆叠”改成“按真相源和派生关系”组织
- `chat_page.dart`、`chat_message_list.dart` 从“半页面半业务层”收回到展示与编排职责
- `AgentApi` 与请求装配逻辑完成边界清理
- 确认无调用的旧实现、重复实现、过渡文件集中清退

这套方案专门按“可多窗口并行施工”来写。每一份子文档都尽量给出：

- 当前问题
- 目标口径
- 建议拆分
- 施工步骤
- 写文件边界
- 验收标准

这样你可以把不同文档直接丢给不同窗口，让它们按自己的写入范围推进。

---

## 为什么要单独做这轮重构

本次审计暴露的核心不是单点 bug，而是结构性问题：

1. 聊天发送主流程没有唯一骨架，入口分散但彼此又共享状态，导致一处变更要同时改多条链路。
2. `ChatActions` 虽然被拆成了多个 `part` 文件，但仍是一个共享巨型状态对象，阅读成本和变更风险都很高。
3. 流式占位消息存在“旧 Provider 路径”和“新 HistoryStore 路径”并存，维护者很难判断哪条才是真实生效链路。
4. Provider 文件分布在 5 个文件里，但边界并不按职责划分，而是按历史阶段叠出来的。
5. UI 层承担了模型能力判断、引用拼装、发送参数整形等业务职责，页面越来越难改。
6. API 层中直发、流式、请求归一化、地址解析等逻辑有重复实现；老接口仍残留在公共类中。

如果不先做一轮结构重整，后续继续叠功能只会让聊天链路越来越“各写各的”。

---

## 本轮重构的统一口径

1. 聊天发送对外只保留一个主入口。
2. 所有发送变体都先归一化成统一命令，再进入同一执行骨架。
3. 临时消息、流式占位、最终落库三者必须由同一套交付状态机协调。
4. 页面文件只做编排和交互，不拼业务协议、不兜底数据源。
5. Provider 先区分“真相源 Provider”和“派生/选择器 Provider”，再谈拆文件。
6. `AgentApi` 只承担网络协议和传输细节，不保留业务分叉。
7. 废弃代码清理必须以“确认无调用 + 替代链路已稳定”为前提，不做一边迁移一边误删。

## 成功标准

如果这轮重构完成后，团队应该能明显感受到以下变化：

1. 想查“发一条消息到底怎么走”时，只需沿一条主链看下去，而不是在 `actions / service / provider / api` 之间来回跳。
2. 想修“流式占位和正式消息交接”时，只需看一个交付状态机，而不是猜旧 Provider 和新存储谁在生效。
3. 想调整聊天页面交互时，不需要先理解一堆业务协议拼装逻辑。
4. 想继续加功能时，新增逻辑能落到稳定边界里，而不是被迫继续塞进巨型文件。
