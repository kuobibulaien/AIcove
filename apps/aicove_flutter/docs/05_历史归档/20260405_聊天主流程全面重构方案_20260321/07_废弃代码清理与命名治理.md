# 废弃代码清理与命名治理

## 本文目标

在主链、状态、UI、API 基本收口后，集中完成 dead code 清理、重复实现收敛与命名统一，避免旧包袱继续误导后续开发者。

---

## 清理必须遵守的前提

1. 先完成替代链路。
2. 再确认读写调用都已迁走。
3. 最后才删除旧实现。

不能边迁移边凭感觉删文件。

---

## 第一批重点清理对象

### 1. 过渡命名

典型对象：

- `providers2.dart`

目标：

- 停止新增引用
- 迁移完现有 import
- 删除过渡文件

### 2. 重复实现

审计中已发现明显重复的方向：

- 请求装配/候选配置逻辑
- assistant message build result 类定义
- assistant delivery result 类定义
- 旧 `ChatRequestBuilder` 与现有配置装配职责重叠
- 旧 `ChatResponseHandler` / `ChatMessageBuilder` 与现有消息构建职责重叠

这些不一定一次性全删，但必须建立唯一权威实现。

### 3. 疑似已废弃 API/Provider/Helper

包括但不限于：

- 已无调用的旧 API 方法
- 已无 writer 的流式/临时消息 Provider
- 页面不再引用的旧 helper

### 4. 命名不统一

典型表现：

- 同一概念同时叫 conversation / contact / role
- 同一类动作在不同文件里有不同叫法
- UI 文案和内部状态名混用中英文习惯

---

## 命名治理原则

### 1. 概念先统一，再批量改名

先定义：

- conversation：会话实体
- contact：联系人/角色入口
- timeline：时间线消息视图
- turn：一次发送-响应交互
- placeholder：临时占位消息

没有概念表，批量改名只会越来越乱。

### 2. 文件命名要表达职责，不表达历史

避免继续出现：

- `providers2.dart`
- `xxx_new.dart`
- `xxx_temp.dart`

### 3. 状态/动作命名分开

例如：

- 状态用 `current / active / resolved / derived`
- 动作用 `load / send / retry / apply / delete / sync`

不要让一个名字既像状态又像动作。

---

## 推荐施工步骤

### Step 1：建立清理台账

先列清：

- 文件
- 符号
- 当前是否还有调用
- 替代实现是什么
- 删除前依赖哪个窗口确认

### Step 2：先删无争议 dead code

如：

- 明确无 import / 无调用的方法
- 已完成迁移的兼容 barrel 文件

### Step 3：再收重复实现

对于重复类型定义，优先决定唯一保留点，再逐步把引用迁过去，最后删除副本。

### Step 4：最后做命名统一

命名统一尽量放在功能稳定后做，减少和功能性重构交叉冲突。

---

## 建议写文件范围

这个窗口不宜一开始就开工，建议放在后半程，由“清理窗口/收尾窗口”执行。

它可能涉及的范围会比较广，包括但不限于：

- `apps/aicove_flutter/lib/src/features/chat/`
- `apps/aicove_flutter/lib/src/ui/features/chat/`
- `apps/aicove_flutter/lib/src/core/api/`

因此应避免与其他功能窗口并行修改同一文件。

---

## 验收标准

1. 过渡命名文件被清空或下线。
2. 重复实现只保留一份权威定义。
3. 已确认无调用的旧方法/旧 Provider/旧 helper 被删除。
4. 核心概念命名一致，阅读成本明显下降。

---

## 高风险点

1. 清理窗口最容易误删“看似没用、实则反射/动态调用”的代码。
2. 命名统一若过早启动，会和功能性重构撞在一起。
3. 一次性清太多文件，review 难度会急剧上升。

建议：

- 分批删除
- 每批都附调用证据和替代链路说明
