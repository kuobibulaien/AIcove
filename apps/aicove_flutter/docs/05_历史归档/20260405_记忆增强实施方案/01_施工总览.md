# 记忆增强实施方案：施工总览

## 0. 一句话目标

用"四层分级 + 内容丰富度驱动召回 + AI 分类入库 + 容量驱动淘汰"替代现有"PEIJ 浮点数打分 + 每 N 条触发 + 扁平记忆池"，使记忆系统可解释、可预测、召回率高。

---

### 1.2 主要缺口（本方案覆盖）

| # | 缺口 | 影响 |
|---|------|------|
| 1 | PEIJ 固定默认值，AI 打浮点数不稳定 | 分数不可靠，换模型结果变 |
| 2 | 仅向量召回，无关键词/BM25 通道 | 人名/专有词召回率低 |
| 3 | 记忆扁平无分级，重要记忆和闲聊碎片混在一起 | 核心层被垃圾占名额 |
| 4 | 缺少用户画像层（L1） | AI 无法在每轮对话中保持对用户性格/红线的理解 |
| 5 | 每 N 条固定触发总结 | 截断话题、重复总结 |
| 6 | 无关联记忆合并 | 可能召回过时信息（如"和家人吵架"但已和解） |
| 7 | memories 未带 conversation_id | 跨会话串用 |
| 8 | 缺 Pre-Flush | 长对话截断时丢失重要事实 |

## 2. 四层记忆架构

### 2.1 架构概览

四层分级不是全局共享池，而是**每个角色先有一个独立记忆库，再在库内分 L1/L2/L3/L4**。

```
角色记忆库（顶层，按 conversationId / 角色隔离）
└── L1 用户画像 / 用户攻略
└── L2 重要事件档案
└── L3 日常日记流水
└── L4 碎片记忆
```

也就是说：

- 角色 A 和角色 B 的记忆绝对隔离，不共享 L1/L2/L3/L4
- Prompt 注入时，必须先确定“当前是哪个角色的记忆库”，再读取该库内部的分层内容
- 清空聊天时，清空的是“当前角色记忆库”的全部层级状态，而不是一个全局池子的局部内容

```
┌─────────────────────────────────────────────────────────┐
│  L1  用户画像（Profile）                                   │
│  100% 注入 Prompt，极少极精，教 AI 怎么跟用户相处           │
│  内容：性格特质 + 交互红线 + 行为准则                       │
│  数量：5~15 条，系统不自动删除，只更新                      │
│  示例："对被否定/批评极度敏感" / "绝对不能表露对其他异性好感" │
├─────────────────────────────────────────────────────────┤
│  L2  重要事件档案（Rich Memory）                           │
│  走混合检索，内容多角度详细描述 → 天然高召回率               │
│  内容：事件 + 聊天经过 + 情绪 + 性格分析 + 应对策略          │
│  入库条件：情绪激烈/重大事件/核心偏好暴露                    │
├─────────────────────────────────────────────────────────┤
│  L3  日常流水（Daily Log）                                 │
│  走混合检索，简要记录事件经过                               │
│  内容：时间 + 人物 + 事件概要                               │
│  入库条件：普通日常事件                                     │
├─────────────────────────────────────────────────────────┤
│  L4  碎片记忆（Forgettable）                               │
│  走混合检索，但内容极短几乎匹配不到 → 天然低召回             │
│  内容：事件标题级                                          │
│  来源：L3 被压缩后的产物，或入库时就被判定为闲聊             │
└─────────────────────────────────────────────────────────┘
```

### 2.2 关键设计：内容丰富度 = 召回率

不在检索公式里加重要性权重。检索排序**只看相关性**。

重要记忆之所以召回率高，是因为 L2 的内容包含了"事件 + 情绪 + 性格 + 策略"多个角度，能被更多查询命中。L4 的内容只有一句标题，很难被匹配到。

**记忆一旦注入 Prompt，不管它是 L2 还是 L4，AI 看到的效果一样。** 所以重要性只影响"写多详细"和"什么时候压缩/淘汰"，不参与检索。

### 2.3 各层定位对比

| | L1 画像 | L2 重要事件 | L3 日常流水 | L4 碎片 |
|---|---------|-----------|-----------|---------|
| **注入方式** | 100% 每次注入 | 混合检索召回 | 混合检索召回 | 混合检索召回 |
| **产生方式** | L2 中反复出现的特征晋升 | 对话结束后 AI 分类为重要 → 深度分析 | 对话结束后 AI 分类为日常 → 简要记录 | L3 被压缩 / 入库时判为闲聊 |
| **内容量** | 每条 10-15 字 | 每条 100-300 字 | 每条 30-50 字 | 每条 10-20 字 |
| **淘汰** | 不删除，只更新 | 基本不淘汰 | 满了才压缩为 L4 | 满了才删除 |

### 2.4 L1 画像的特殊定位

L1 **不是**"重要事实"，而是**用户性格特征和交互红线**。

L1 应载内容示例：
```
- 性格敏感多疑，自尊心强，容易自卑
- 对被否定/批评极度敏感，安慰时必须先肯定再分析
- 绝对不能表露对其他异性有好感或兴趣
- 讨厌被讲大道理，喜欢被理解和共情
- 情绪低落时需要陪伴而不是建议
```

L1 **不应**载的内容（这些属于 L2/L3）：
- 用户在减肥（有时效，会变）
- 花生过敏（事实，应放 L2）
- 妹妹叫小雨（事实，应放 L2）

L1 系统不自动删除，只更新。用户可在 UI 手动编辑或移除画像条目。晋升条件：某个性格特征在 L2 的多条事件中反复出现（>=3 次）。

## 3. 数据流

### 3.1 写入流（对话 → 记忆入库）

```
用户和 AI 聊天（当天可能有多轮对话）
    │
    │ 当天不做正式总结
    │
第二天用户发来第一条消息
    │
    ▼
检查：有没有 summarized=false 的历史消息？
    │
    ├─ 有 → 后台触发总结（不阻塞当前对话）
    │
    │   ┌──────────────────────────────────────┐
    │   │  输入：该日全量消息（用于稳定切分轮次）   │
    │   │  仅执行未完成轮次（按 round_key 幂等）    │
    │   │                                        │
    │   │  AI 角色：经验老道的心理分析师           │
    │   │  输出结构化结果：                       │
    │   │                                        │
    │   │  对每条事实：                           │
    │   │   - fact（事实文本）                    │
    │   │   - category（6 选 1 分类）             │
    │   │   - target_layer（L2/L3/L4）            │
    │   │   - L2 专属：聊天经过/情绪/性格/策略     │
    │   │   - conflicts_with（是否跟已有记忆冲突） │
    │   │                                        │
    │   │  对画像：                               │
    │   │   - profile_update 建议（可选）          │
    │   │                                        │
    │   │  容错：                                 │
    │   │   - 分类缺失 → 默认 daily_chatter       │
    │   │   - JSON 失败 → 降级旧文本路径          │
    │   └──────────────────────────────────────┘
    │       │
    │       ▼
    │   系统处理：
    │   1. 按 target_layer 分流入库
    │   2. L2 入库前查关联旧记忆 → 有 → 合并
    │   3. L2 入库前查 L1 画像 → 有特征累积 ≥3 → 晋升 L1
    │   4. 生成 embedding → 写入 memories 表 + FTS5 索引
    │   5. 标记 summarization_records.summarized=1
    │      + 对应消息 messages.summarized=true
    │   6. 检查容量 → 满了 → 执行压缩/淘汰
    │
    └─ 没有 → 跳过

应急通道（Pre-Flush）：
上下文即将被截断时，先从即将丢失的消息中紧急提取关键事实入库，
fire-and-forget 不阻塞发送。
```

```
用户发送消息
    │
    ▼
┌─────────────────────────────────────────────┐

│ 且每条都带时间前缀，提醒模型这是多久前形成的判断 │
└─────────────────────────────────────────────┘
    │

┌─────────────────────────────────────────────┐
│ L2：先作为 skill 索引注入，再按命中展开详情      │
│   - skill 名字 = L2 标题                      │
│   - 触发条件 = 标题 + 关键词标签 + 时间前缀       │
│   - 命中后再把完整 L2 详细内容注入 prompt       │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│ L3/L4 统一召回：                              │
│                                               │
│ 查询构造：最近 2~3 条消息拼接（不只是最后一条） │
│                                               │
│ 通道A：向量检索                               │
│   查询 → embedding → 候选300 → 余弦排序       │
│                                               │
│ 通道B：BM25 关键词检索                        │

│                                               │

│   score = 0.7 × vector_norm + 0.3 × bm25_norm │
│                                               │
│ 取 topK=3~5（按 token 预算控制）               │
│                                               │
│ 命中的记忆：统一补时间前缀后再注入 prompt       │
│   - L2：时间前缀 + skill 详情                  │
│   - L3/L4：时间前缀 + 回忆摘要                 │
│   - 命中的记忆：use_count += 1                 │

    │
    ▼
拼接注入 System Prompt：

- 5天前形成的判断：对被否定极度敏感...

- 3天前：【被领导批评事件】...

## L3/L4 相关回忆
- 1天前的对话摘要"用户说明天要复诊..."
```

### 3.3 层间流动

#### 向下流动：容量满了才触发

```
记忆池满了（超过上限）
    │
    ▼
找出"最不值钱"的记忆（按淘汰优先级）
    │
    ├─ 如果它还是 L2/L3（有详细内容）
    │   → 压缩（只保留 时间+人物+事件 底线）
    │   → 字数减少 → 它变成 L4 状态
    │
    ├─ 如果它已经是 L4（只剩标题）
    │   → 无法再压 → 删除
    │
    └─ 从最不值钱的开始，逐条处理，直到回到上限以下

淘汰优先级（越靠前越先被压缩/删除）：
  1. daily_chatter (L4 闲聊碎片)
  2. temporary_state
  3. ongoing_plan
  4. emotional_event
  5. identity_fact
  6. core_preference → 不参与淘汰

同一类别内：use_count 越低越先处理。

压缩底线：保留"时间 + 人物 + 事件"三要素。
低于底线无法再压缩 → 直接删除。
```

#### 向上流动：被召回时触发

```
一条已被压缩的记忆被检索命中
    │
    ▼
本次先用压缩版本注入 Prompt（先凑合用）
    │
    ▼
标记："需要重新丰富"
    │
    ▼
下次总结时，AI 结合当前对话上下文
重新对这条记忆做深度解析
    │
    ▼
用丰富后的内容覆盖旧内容 → 它回到 L2 状态
```

## 4. 总结触发机制

### 4.1 主触发：用户消息造成的滚动 24 小时扰动

每次用户发来一条新消息，都把它视为一次“状态扰动”。

系统会取这条消息的发送时间 `T`，计算：

```text
cutoff = T - 24h
```

然后按下面的规则判断是否触发：

- `created_at >= cutoff` 的消息默认进入保护期，不参与本次总结
- 只要存在 `created_at < cutoff && summarized = false` 的消息，就触发总结
- 如果不存在这样的消息，就直接休眠，不调用总结 AI

这样做的好处是：

- 不再被固定“第二天凌晨/早上”这种时点硬截断
- 用户一天多次发消息时，通常不会反复触发总结
- 只在真的有“超过 24 小时还没总结”的积压消息时才消耗资源

**边界连续消息合并（10 分钟）**：
- 先看 `cutoff` 前最后一条消息 `a`
- 再看保护期内第一条消息 `b`
- 如果 `b.created_at - a.created_at <= 10 分钟`，说明这是同一段连续聊天，`b` 也一起并入本次总结
- 接着继续向后看下一条消息 `c`
- 只要“下一条消息”和“当前已并入的最后一条消息”的间隔仍然 `<= 10 分钟`，就继续并入
- 直到间隔 `> 10 分钟` 才停下，后面的消息继续留在保护期

**当前实现上的保留**：
- 触发时机改成滚动 24 小时窗口
- 入库幂等仍然沿用现有“按日归档 + 高消息量时按 1 小时断点拆轮”的机制
- 这样可以先把“什么时候触发”改对，再逐步继续收敛 L2/L3/L1 的内容形态

**基本单位仍以现有 round/day 机制为准**：
- 默认在可处理范围内尽量整段归档
- 不需要预先拆分轮次，大多数情况下一段对话量完全可以一次总结

**用户单日消息超过阈值时拆分轮次**：
- 统计该日**用户发送**的消息数（不含 AI 回复），超过 `memory.roundSplitThreshold`（默认 20，可在记忆设置中调整）则触发拆分判定
- 拆分规则：遍历消息列表，如果两条**相邻消息之间**的时间间隔 > 1 小时，则在此处切分为不同轮次
- 注意：1 小时是指相邻两条消息之间的间距，不是第一条到最后一条的总时长
- 如果 20+ 条消息之间所有相邻间隔都 < 1 小时，则不拆分，仍作为一轮
- 每个轮次单独送去 AI 总结
- 轮次判定不需要在 `messages` 表新增字段；仅在 `summarization_records` 记录稳定 `round_key`

**总结流程**：
```
1. 用户发新消息，取其时间 `T`
2. 计算 `cutoff = T - 24h`
3. 先查 `created_at < cutoff && summarized = false` 的消息
   - 没有 → 休眠
   - 有 → 继续
4. 检查 cutoff 前后是否存在 `<= 10 分钟` 的连续消息，如果有则把边界向后延伸
5. 在“最终边界”内，对相关日期读取全量消息（含已总结），按 createdAt 升序
6. 统计该日用户消息数：
   a. <= 20 条：整天消息作为一个总结单元（round_key=`day:{date_key}`）
   b. > 20 条：按 1 小时相邻间隔拆分轮次
      - 有拆分点 → 每轮单独总结（round_key=`sha1(date_key|first_msg_time|last_msg_time)`）
      - 无拆分点（所有间隔 < 1 小时）→ 仍作为一个整体总结
7. 每个总结单元先查 `summarization_records`：
   - summarized=1 → 跳过
   - summarized=0 或不存在 → 执行总结
8. 成功 → 标记 `summarization_records.summarized=1`，并更新该单元消息 `messages.summarized=true`
9. 失败 → 记录 error_message，下次仅重试失败 `round_key`
```

### 4.2 用户主动切话题触发

当用户点击“开始新话题”时，也视为一次明确的状态扰动：

- 先取当前上下文窗口内、到“最后一条旧话题消息”为止的消息
- 对这批消息执行一次手动记忆入库（`trigger = manual`）
- 再写入新的 `contextStartMessageId`

这样可以避免“旧话题被直接切断，但还没来得及总结”的情况。

### 4.3 应急触发：Pre-Flush

上下文即将被截断时（如 token 接近上限），在截断前从即将丢失的消息中紧急提取关键事实。

- 挂钩点：`chat_request_executor.dart` 调用 `truncateMessagesToFit()` 之前
- 执行方式：fire-and-forget，不阻塞主发送链路
- 失败只记日志，不影响用户体验

### 4.4 清空聊天的联动约束

清空聊天记录不是单纯删除 `messages`：

- 需要同步清空该角色下的 `memories`
- 需要同步清空该角色下的 `diaries`
- 需要同步清空该角色下的 `summarization_records`
- 需要把 `contextStartMessageId`、会话摘要、未读数一起复位

也就是说，用户点“清空聊天”后，这个角色的记忆状态应视为整体归零。

### 4.5 不再使用的触发方式

- ~~每 N 条消息触发~~（截断话题、重复总结）
- ~~SessionEnd 触发~~（改为次日首条消息触发，更完整）
- 5 分钟无消息 / 切后台：保留给主动关怀系统用，不再触发记忆总结

## 5. 入库分层判定（AI 分类 + 系统规则）

### 5.1 AI 的职责：分类（不打分）

AI 对每条提取的事实做分类，从以下 6 类中选 1 个：

| 类别标签 | 含义 | 举例 |
|---------|------|------|
| `core_preference` | 长期偏好/厌恶/人格 | "讨厌香菜""怕蜘蛛" |
| `identity_fact` | 身份/关系/长期状态 | "在北京工作""有个妹妹叫小雨" |
| `emotional_event` | 有明显情绪波动的事件 | "被领导批评很难过""升职很开心" |
| `ongoing_plan` | 正在进行的计划/目标 | "在减肥""准备考研" |
| `temporary_state` | 短期状态/临时事件 | "最近胃炎""明天出差" |
| `daily_chatter` | 日常闲聊/低价值 | "今天吃了麻辣烫""刚洗了澡" |

分类任务比打分任务**稳定得多**——换模型/换温度，分类结论基本一致。

### 5.2 系统的职责：根据分类 + 对话质量决定目标层

```python
# 根据类别决定基准层
if category in ['core_preference', 'identity_fact']:
    target_layer = 'L2'

elif category == 'emotional_event':
    target_layer = 'L2'    # 情绪事件始终值得详细记录

elif category == 'ongoing_plan':
    if 对话消息数 >= 8 or 用户消息平均字数 >= 25:
        target_layer = 'L2'  # 用户认真聊了很久
    else:
        target_layer = 'L3'  # 随口提了一句

elif category == 'temporary_state':
    target_layer = 'L3'

elif category == 'daily_chatter':
    if 对话消息数 <= 3 and 用户消息平均字数 < 15:
        target_layer = None  # 不入库
    else:
        target_layer = 'L4'
```

### 5.3 L2 入库条目结构

AI 以**经验老道的心理分析师**视角，对标记为 L2 的事实做深度分析：

```
【标题】

事件：时间 + 人物 + 发生了什么

聊天经过：
  用户说了什么/做了什么
  AI 怎么回应的
  用户对 AI 回应的反应（有效/踩雷）

情绪：用户当时的情绪状态

性格分析（心理分析师视角）：
  这件事暴露了用户什么深层特质/需求

应对策略（成功/失败经验）：
  ✅ 什么做法有效
  ❌ 什么做法踩雷
  → 结论：下次遇到类似情况应该怎么做
```

### 5.4 L3 入库条目结构

以角色第一视角记录单条事件，允许同一天输出多条：

```
时间，我[和用户发生了什么/记住了什么]。
```

补充约束：
- `fact` 必须保持角色口吻，像角色自己在写日记，不写成第三方观察报告
- AI 可以为同一天提取多条 L3 事件
- 入库时 L3 仍会保存到 `memories`
- 展示时会把同一天的多条 L3 事件拼接到 `diaries`，形成单日日记

### 5.5 L4 条目

标题级别，一句话概括：

```
时间，[事件主题]
```

## 6. 关联记忆合并

### 6.1 问题

同一主题的多条独立记忆可能导致召回过时信息：
- 1 月：和家人吵架 → 关系紧张
- 2 月：和家人和解了
- 如果只检索到第一条，AI 会基于过时信息说错话

### 6.2 合并机制

新记忆入库 L2 时，先检查是否存在关联旧记忆：

```
新事实 → 提取实体（人名/关键词）
       → 在 L2 中搜索：实体重叠 AND 向量相似度 > 0.65
       → 找到关联记忆

有关联 → AI 将新旧合并为一条带时间线的记忆
无关联 → 直接新建
```

### 6.3 合并后格式

```
【用户与家人的关系】
- 2026年1月：因故与家人争吵，关系紧张，用户感到委屈
- 2026年2月：已和解，用户觉得家人其实挺好的
→ 当前状态：关系已修复

AI 应对：提到家人时以积极态度回应，不要提及之前的矛盾
```

合并后需重新生成 embedding 和更新 FTS5 索引。

### 6.4 L1 画像同步

如果合并后的"当前状态"否定了 L1 画像中的某个条目，L1 应同步更新。

1. 不会召回过时信息（合并后有"当前状态"标记）

## 10. 关键风险与应对

| 风险 | 应对 |
|------|------|
| AI 分类不准确 | 分类缺失时默认 daily_chatter；JSON 失败降级旧文本路径 |
| FTS5 非 Drift 声明式，维护复杂 | 封装为独立的 DAO 类，工期留余量 |
| 次日总结时消息量大，AI 处理慢 | 如超 30 条，分批送入 AI；失败可重试 |
| 合并逻辑误合并不相关记忆 | 双重判据（实体重叠 AND 向量相似度 > 0.65） |
| L1 画像条目过多占 token | 硬性限制 5~15 条，超出需合并 |
| 旧数据没有 layer/category 字段 | 迁移时默认 layer='L3', category='daily_chatter' |
