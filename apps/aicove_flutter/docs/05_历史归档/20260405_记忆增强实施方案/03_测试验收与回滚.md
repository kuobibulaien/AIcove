# 记忆增强实施方案：测试验收与回滚

## 1. 测试目标

确保四层记忆架构在"召回率、分层准确性、数据完整性、性能、可回滚"五个维度达标。

---

## 2. 测试分层

### 2.1 单元测试（MUST）

新增测试文件：

| 文件 | 阶段 | 覆盖内容 |
|------|------|---------|
| `test/features/memory/category_classifier_test.dart` | P0 | AI 分类输出解析、字段级容错 |
| `test/features/memory/hybrid_search_test.dart` | P0 | 双通道检索、合并打分、归一化 |
| `test/features/memory/lexical_tokenizer_zh_test.dart` | P0 | 中文 2-gram、ASCII 整词、单字兜底 |
| `test/features/memory/layer_routing_test.dart` | P0 | 分层判定（category + 对话质量 → L2/L3/L4） |
| `test/features/memory/profile_service_test.dart` | P0 | L1 画像 CRUD、晋升判定 |
| `test/features/memory/daily_summarization_test.dart` | P0 | 次日触发、24h窗口归属、消息标记 |
| `test/features/memory/memory_merger_test.dart` | P1 | 实体匹配、向量相似度阈值、合并格式 |
| `test/features/memory/memory_compressor_test.dart` | P1 | 压缩规则、底线保留、淘汰优先级 |
| `test/features/memory/conversation_isolation_test.dart` | P0 | conversation_id 隔离 |
| `test/features/memory/preflush_hook_test.dart` | P1 | Pre-Flush 触发与非阻塞 |

关键用例：

**P0 - 分类与分层**：

1. AI 输出完整 JSON → 正确解析 category 和 target_layer
2. AI 输出 JSON 但缺少 category → 默认 `daily_chatter`，分到 L4
3. AI 输出非 JSON → 降级旧文本路径，默认 L3
4. category=`emotional_event` → 一定进 L2
5. category=`daily_chatter` + 对话 ≤ 3 条 → 不入库
6. category=`ongoing_plan` + 对话 ≥ 8 条 → 升级 L2
7. category=`core_preference` → persistenceP 映射为 1.0

**P0 - 混合检索**：

8. 人名"小雨"能通过 BM25 通道精确命中
9. 语义查询"心情不好"能通过向量通道命中"被批评很委屈"
10. 两通道都命中的记忆分数更高
11. L1 记忆不出现在检索结果中
12. 查询构造使用最近 2-3 条消息而非仅最后一条

**P0 - L1 画像**：

13. L1 记忆 100% 注入 Prompt
14. L1 不参与淘汰
15. L1 不参与混合检索（只固定注入）
16. L1 条目数超过 15 时有告警

**P0 - 次日总结**：

17. 用户第二天发消息 → 触发昨日总结
18. 总结成功 → 消息标记 `summarized=true`
19. 总结失败 → 消息标记不变，下次发消息时重试
20. 跨午夜的对话轮次按起始时间归属日期
21. 已总结的消息不会被再次总结
22. 分轮总结生成稳定 `round_key`，重试不依赖轮次序号
23. 某日多轮中“部分轮次成功 + 部分轮次失败”后，仅重做失败 `round_key`

**P0 - 隔离**：

24. 角色 A 的记忆不出现在角色 B 的检索结果中
25. 角色 A 的 L1 画像不注入角色 B 的 Prompt

**P1 - 合并**：

26. 实体重叠 + 向量相似度 > 0.65 → 触发合并
27. 合并后的记忆包含时间线和"→ 当前状态"标记
28. 合并后旧记忆被替换，不产生重复
29. 合并后 embedding 被重新生成

**P1 - 压缩/淘汰**：

30. 容量不满时不触发任何压缩/淘汰
31. 容量满时：L4 闲聊最先被删
32. L2 记忆先被压缩为 L4（保留三要素），不直接删除
33. core_preference 永不被淘汰
34. 压缩后的记忆 layer 字段更新为 'L4'

**P1 - 重新丰富**：

35. 被压缩的记忆被召回后 `needs_enrichment` 标记为 1
36. 下次总结时对标记的记忆执行重新丰富
37. 丰富后 layer 回到 'L2'，`needs_enrichment` 重置为 0

**P1 - Pre-Flush**：

38. Pre-Flush 仅在截断前触发
39. Pre-Flush 不阻塞主发送链路
40. Pre-Flush 失败不影响消息发送成功率

### 2.2 集成测试（MUST）

目标：打通完整链路。

建议场景：

1. **完整写入链路**：对话 → 次日触发 → AI 分类 → 分层入库 → 各层数据正确
2. **完整检索链路**：L1 注入 + 混合检索 → Prompt 格式正确
3. **层间流动**：入库为 L2 → 容量满了 → 压缩为 L4 → 被召回 → 重新丰富回 L2
4. **关联合并**：入库两条相关事实 → 自动合并为一条带时间线的记忆
5. **失败重试**：总结失败 → 消息标记不变 → 下次发消息时自动重试
6. **轮次级幂等**：同一天拆分为多轮，首轮成功次轮失败 → 重试时仅执行失败 `round_key`
7. **迁移兼容**：旧库数据（无 layer/category 字段）在新版本上正常运行

### 2.3 手动验收（MUST）

验收脚本：

| # | 场景 | 预期结果 |
|---|------|---------|
| 1 | 输入情绪激烈的对话（"被领导骂了好难过"），第二天发消息 | 记忆以 L2 格式入库，包含聊天经过/情绪/策略等维度 |
| 2 | 输入日常闲聊（"今天吃了什么"），第二天发消息 | 记忆以 L4（或不入库）形式处理 |
| 3 | 查询"小雨"（人名） | BM25 通道精确命中妹妹小雨相关记忆 |
| 4 | 多次表现出"对批评敏感"的特征 | L1 画像中出现"对被否定敏感"条目 |
| 5 | 1 月说"和家人吵架了"，2 月说"和家人和解了" | 两条记忆被合并，有"→ 当前状态：已和解"标记 |
| 6 | 切换到另一个角色 | 前角色的画像和记忆不出现 |
| 7 | 故意制造总结失败（网络断开） | 下次发消息时自动重试 |
| 8 | 连续长对话触发截断 | Pre-Flush 提取关键事实，不丢失 |
| 9 | 同一天被拆分为多轮，第一次仅部分轮次成功 | 第二次只重试失败轮，不产生重复记忆 |

## 3. 验收指标（上线门槛）

### 3.1 召回率指标

| 指标 | 目标 | 说明 |
|------|------|------|
| 专有名词查询 Recall@5 | 提升 ≥ 30% | BM25 通道贡献 |
| 情绪相关查询 Recall@5 | 提升 ≥ 20% | L2 多维度内容贡献 |
| L2 记忆在 topK 中的占比 | ≥ 60% | 内容丰富度驱动召回 |

### 3.2 分层准确性指标

| 指标 | 目标 | 说明 |
|------|------|------|
| 分类解析成功率 | ≥ 95% | 字段级容错后统计 |
| L2 入库率 | 10%~30% | 大多数应为 L3，L2 是少数重要事件 |
| L1 画像条目数 | 5~15 条/会话 | 太多说明晋升太宽松 |

### 3.3 性能指标

| 指标 | 目标 | 说明 |
|------|------|------|
| 混合检索 p95 延迟 | ≤ 150ms | 本地 800 条记忆 |
| Prompt 注入构建 p95 延迟 | ≤ 200ms | 含 L1 读取 + 检索 |
| 次日总结耗时 | ≤ 30s | 一天对话量 ≤ 100 条 |
| Pre-Flush 不阻塞发送 | 100% | 异步 fire-and-forget |

### 3.4 数据完整性指标

| 指标 | 目标 | 说明 |
|------|------|------|
| 跨会话误召回率 | 0% | conversation_id 隔离 |
| 数据迁移成功率 | 100% | 旧库→新库无崩溃 |
| 重复记忆率 | ≤ 5% | content_hash 去重 |
| 总结失败后消息标记正确率 | 100% | 失败不标记为已总结 |

### 3.5 分阶段门槛

| 阶段 | 必须达标指标 |
|------|------------|
| P0 | Recall@5、分类解析成功率、混合检索延迟、隔离误召回率 |
| P1 | 合并触发率、压缩/淘汰行为正确性、Pre-Flush 成功率、重复记忆率 |
| P2 | UI 可用性 |
| P3 | Embedding 缓存命中率 |

## 4. 发布与灰度

### 4.1 Feature Flag 启用顺序

```
第一批（P0 核心）：
  memory.enable_category_classification
  memory.enable_hybrid_search
  memory.enable_four_layer
  memory.enable_profile_layer
  memory.enable_next_day_trigger
  memory.enable_conversation_isolation

第二批（P1 质量）：
  memory.enable_memory_merge
  memory.enable_capacity_compress
  memory.enable_pre_flush

第三批（P3 优化）：
  memory.enable_embedding_cache
```

### 4.2 灰度节奏

1. 内部测试版先验证第一批 flags
2. 测试渠道观察 3 天稳定后启用第二批
3. 正式版小版本上线，保留开关可快速关闭
4. 确认稳定后下一小版本默认开启

### 4.3 止损条件

任一触发即关闭新开关：

1. 崩溃率异常上升
2. 混合检索延迟持续超 300ms
3. 跨会话记忆注入被复现
4. 总结失败率 > 20%
5. 用户反馈记忆内容明显错误

---

## 5. 回滚方案

### 5.1 逻辑回滚（首选）

1. 关闭对应 feature flag → 回退旧检索（纯向量）与旧写入流程
2. 保留新增字段（layer/category/content_hash），不做 destructive migration
3. 旧逻辑只读新字段，忽略不识别的值

### 5.2 数据回滚

原则：
1. 不执行删表/删字段回滚
2. 若 FTS5 有问题，仅停用 BM25 检索路径
3. L1 画像回滚：关闭画像注入，不删除画像数据

### 5.3 版本回滚预案

1. 迁移脚本前向兼容旧逻辑读取
2. 回退版本前先禁用新开关
3. 新增字段有默认值，旧版本可正常忽略
