## 1. 为什么先 Web 后 App

Agent 上下文系统还处于抽象收敛期，尤其包含：

- SillyTavern 预设导入
- `prompt_order` 分组选择
- 世界书 / Lorebook 绑定
- Regex / Extension Prompt 规则
- Token budget 预览
- Provider-specific message 渲染
- 组装 trace / warnings / safe preview

这些能力适合先在 Web 管理端做大屏调试，不适合一开始塞进移动端。

App 端现在要保持稳定：

- 不破坏现有聊天发送链路。
- 不重写 `ChatSendUseCase`。
- 不抢先做复杂资产库 UI。
- 不把尚未稳定的上下文 schema 写入本地数据库。
- 不把 SillyTavern 预设当成长 prompt 编辑器。

## 2. 正确架构口径

AIcove 做的是 **Agent 上下文管理系统**，不是提示词管理系统。

```text
AgentDefinition
  = ModelRef
  + ContextProfile
  + ContextRecipe
  + ContextAssemblyPermissions
  + ToolPolicy
  + OutputContract
  + PostProcessors / DeliveryChannel
```

所有 Agent 都有同一套定义面。区别不是“哪个 Agent 有上下文资产，哪个没有”，而是：

```text
不同 Agent = 不同装配权限 + 不同工具边界 + 不同输出契约 + 不同投递通道
```

权限口径：

| Agent | 权限口径 | App 端最终表现 |
|---|---|---|
| ChatAgent | `full_chat` | 联系人级聊天 Agent，可使用完整上下文资产 |
| ProactiveAgent | `proactive_specialized` | 主动关怀 Agent，只开放主动关怀需要的资产和输出 |
| AnalyzerAgent | `analyzer_specialized` | 后台分析 Agent，偏结构化判断和 trace |
| MemoryAgent | `memory_specialized` | 记忆总结 / 写入 Agent |
| RendererAgent | `renderer_specialized` | 输出事件执行 Agent，如 TTS / image / sticker |

联系人级 ChatAgent 第一阶段仍按：

```text
contactId == conversation.id
agentId = chat_agent:<contactId>
contextRecipeId = standard_chat_recipe:<contactId>
contextAssemblyScope = full_chat
```

## 5. Web 管理端成熟后的迁移目标

Web 端成熟后，App 端再按以下顺序迁移。

### Phase A：只读消费 Web 导出的 Agent Context Profile

目标：App 能读取 Web 导出的稳定配置，但不提供编辑。

输入来源：

```text
cloud_backend export / sync scope
  - agent.context_profiles
  - agent.assets
  - agent.bindings
```

App 端新增轻量模型：

```dart
class AgentContextProfileSnapshot {
  final String agentId;
  final String? contactId;
  final String? contextRecipeId;
  final String scope;
  final List<String> assemblyPermissions;
  final List<AgentAssetBindingSnapshot> bindings;
  final Map<String, Object?> metadata;
}

class AgentAssetBindingSnapshot {
  final String assetType;
  final String assetId;
  final bool enabled;
  final int priority;
  final Map<String, Object?> safeSummary;
}
```

要求：

- 只读解析。
- 解析失败不影响聊天。
- 缺失配置时回退当前本地 `Conversation.personaPrompt` / 插件配置。
- 不默认显示原文，只显示 safe summary。

### Phase B：联系人设置页只读展示 Agent 状态

目标：用户能在 App 里看到“该联系人正在使用 Web 管理端配置”。

入口位置：

```text
聊天设置页 -> Agent 上下文状态
```

页面只读展示：

```text
agentId
contextRecipeId
scope = full_chat
已绑定资产摘要
  - ST preset: 已绑定 / 未绑定
  - lorebook: n 个
  - regex: n 条
  - memory: 已启用 / 未启用
  - tool policy: 已绑定 / 默认
  - output contract: standard_chat
最后同步时间
```

不提供复杂编辑。

### Phase C：App 端轻量开关

Web schema 稳定后，App 可以提供少量轻编辑：

- 启用 / 禁用某个已绑定资产。
- 切换当前联系人使用哪个已存在 preset。
- 切换 tool policy / output contract。
- 查看 safe preview。

仍不建议在 App 端做：

- 大段 ST preset 编辑。
- 世界书全文编辑。
- Regex 复杂编辑。
- Prompt order 拖拽管理。
- Provider renderer 调试。

这些仍应留在 Web 管理端。

### Phase D：运行时接入稳定 profile

目标：聊天请求真正使用 Web 管理端导出的 profile。

迁移方式：

```text
Conversation / contactId
  ↓
查找 AgentContextProfileSnapshot(agentId = chat_agent:<contactId>)
  ↓
加载 bindings 和 assets safe/compiled data
  ↓
AgentContextAssembler 组装
  ↓
ProviderMessageRenderer 渲染
  ↓
ChatSendUseCase / ModelRunner
```

要求：

- 保留旧链路 fallback。
- 每次迁移只切一个联系人 / 一个测试 profile。
- trace 必须能看到使用了哪个 profile、哪些 assets、哪些 transforms。

## 8. App 端验收标准（未来迁移时）

当开始 App 迁移时，必须满足：

1. 没有 Web profile 时，聊天行为与现在完全一致。

   - asset binding summary
   - transform trace
   - budget trace
5. App 默认只展示 safe summary，不展示大段预设原文。
6. 不破坏 TTS / image / sticker / trigger 等现有插件投递。
