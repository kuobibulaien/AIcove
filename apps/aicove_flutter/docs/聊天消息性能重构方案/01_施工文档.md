# 聊天消息性能重构施工文档（预缓存 + 首屏限制 + 分页加载）

> 更新日期：2026-01-20
> 
> 目标：参考微信/Telegram体验，首屏只渲染最近消息并进行图片预缓存，滚动上拉分页加载历史消息，显著降低冷启动与进入聊天页的卡顿和闪烁。

---

## 1. 背景与问题

### 1.1 当前问题
1. 会话初始化时一次性加载每个会话最多 1000 条消息，并且逐条查询消息 blocks，导致启动和进入聊天页卡顿。
2. 图片消息直接 `Image.network` / `Image.file` 渲染，未进行预缓存，首次展示存在闪烁。
3. 进入聊天页时首帧 UI 需要等待大量 IO + 布局，造成明显卡顿。

### 1.2 目标体验
- 冷启动或进入聊天页时，首屏只渲染最近 30 条消息，立刻可见。
- 上滑时再加载更旧消息（分页），按需加载。
- 图片/表情/头像首屏预缓存，避免“空白后加载”的闪烁。

---

## 2. 范围与约束

- **消息首屏加载数**：30 条（已确认）。
- **允许新增依赖**：是（可使用 `cached_network_image`）。
- **不改变现有 UI 结构与交互**，仅调整数据流与加载策略。

---

## 3. 依赖策略

### 3.1 新增依赖
- `cached_network_image: ^3.3.1`
  - 用于网络图片磁盘缓存与重复利用。

### 3.2 预缓存 API
- 基础能力：Flutter 官方 `precacheImage`（把图片解码后放进 `ImageCache`）。
- 本项目实践：使用“分帧预热队列”把图片预热拆成很多小任务，避免把解码/IO 堵在“点击转场”这条关键路径上（见第 6 节 `ImagePreheatQueue`）。

## 4. 数据层改造

### 4.1 会话初始化仅加载最近 30 条消息
**文件**：`lib/src/features/chat/conversation_providers.dart`

**当前问题**：每个会话 `getByConversation(limit: 1000)`，且逐条查询 blocks。

**改造方式**：
- 将 `limit` 改为 30。
- 使用 `MessageBlockRepository.getByMessages` 批量查询 blocks。
- 通过 `messageId` 分组回填到 `Message`。

**伪代码**：
```dart
final dbMsgs = await msgRepo.getByConversation(dbConv.id, limit: 30);
final messageIds = dbMsgs.map((m) => m.id).toList();
final dbBlocks = await blockRepo.getByMessages(messageIds);
final blocksByMsgId = groupByMessageId(dbBlocks);
final messages = dbMsgs.reversed.map((dbMsg) {
  final blocks = blocksByMsgId[dbMsg.id] ?? [];
  return MessageConverter.fromDb(dbMsg, blocks: blocks.isEmpty ? null : blocks);
}).toList();
```

### 4.2 保持消息顺序
- `getByConversation` 默认 desc（新->旧），UI 需要旧->新，继续使用 `dbMsgs.reversed`。

## 5. UI 层改造（分页加载）

### 5.1 ChatMessageList 增加分页触发
**文件**：`lib/src/ui/features/chat/widgets/chat_message_list.dart`

**改造内容**：
- 添加 `ScrollController`。
- 当列表滑到顶部（reverse=true 时接近 `maxScrollExtent`）触发 `onLoadMore`。
- 增加防抖/加载中状态，避免多次重复触发。

**接口设计**：
```dart
final Future<void> Function()? onLoadMore;
final bool isLoadingMore;
```

### 5.2 ChatPage 实现 loadMoreMessages
**文件**：`lib/src/ui/features/chat/pages/chat_page.dart`

**改造内容**：
- 读取当前会话最旧消息时间 `oldestMessage.createdAt`。
- 调用 `messageRepository.getByConversation(limit: 30, beforeTime: oldestTime)`。
- 批量拉取 blocks，组装为 Message。
- 更新 `conversationsProvider.updateOne`，把更旧消息插到头部（时间更早）。

**伪代码**：
```dart
final oldest = conv.messages.first.createdAt;
final dbMsgs = await msgRepo.getByConversation(conv.id, limit: 30, beforeTime: oldest);
// 批量 blocks
final older = buildMessages(dbMsgs);
await ref.read(conversationsProvider.notifier).updateOne(
  conv.id,
  (c) => c.copyWith(messages: [...older, ...c.messages]),
);
```

## 6. 图片/表情/头像预缓存

### 6.1 预热总策略（三段式）
这次要同时满足两个体验目标：
- **动画要立刻开始**（不能点一下先顿一下）
- **图片不要闪**（不能先空白/占位，再突然切出来）

可以类比成“进场前热身 + 分批搬箱子”：
1. **列表可见时先热身（普通优先级）**：先把每个联系人的头像预热；再对列表前几个常用会话，少量预热一些会话内图片/表情。  
   **文件**：`lib/src/features/chat/presentation/widgets/contacts_list_content.dart`
2. **手指按下就加急（高优先级）**：`onTapDown` 立刻对“即将进入的会话”做高优先级预热，争取在转场过程中命中缓存。  
   **文件**：`lib/src/features/chat/presentation/widgets/character_list_item.dart`（透传 `onTapDown`）  
   **触发点**：`lib/src/features/chat/presentation/widgets/contacts_list_content.dart`
3. **进入聊天页后兜底（首帧后后台预热）**：如果前两步没赶上，聊天页首帧渲染完再慢慢补预热，避免抢动画帧。  
   **文件**：`lib/src/ui/features/chat/pages/chat_page.dart`
4. **App 启动/从后台恢复时预热（高优先级）**：提前预热“最近 3 个会话”的最后 10 条消息相关图片，让你即使刚重启 App 也不容易再闪。  
   **文件**：`lib/src/app.dart`

### 6.2 为什么不要在“点击那一刻”直接做重预热
把“点击联系人 → 页面转场”想成“按电梯按钮，电梯门要立刻开始关”：
- 如果你在按按钮那一刻还要**现场打包很多箱子**（同步循环/IO/解码），电梯门就会**等你打包完才动**，就会出现“点了先顿一下，动画才开始”。
- 正确做法是：箱子提前打包（列表可见时预热），临上电梯再把最重要的手提包拎上（onTapDown 高优先级），剩下的到电梯里再慢慢整理（聊天页首帧后兜底）。

### 6.3 ImagePreheatQueue（分帧预热队列）
**文件**：`lib/src/core/utils/image_preheat_queue.dart`

**它做了什么**：
- 把“图片预热”拆成队列任务，**每一帧只处理少量**，不跟动画抢时间。
- 支持 **高/普通优先级**，并且在用户点击时会尽快让高优先级任务先跑。
- 有 **去重**、**最大待处理数**、**单任务超时**，避免队列被慢任务卡死。

**核心用法**（不需要 await，丢给队列后台做）：
```dart
final queue = ref.read(imagePreheatQueueProvider);
queue.enqueueAllFromContext(context, providers); // 普通优先级
queue.enqueueAllFromContext(
  context,
  providers,
  priority: ImagePreheatPriority.high, // 高优先级（onTapDown / onTap）
);
```

### 6.4 图片来源对应的 ImageProvider
- `ImageBlock.url` → `CachedNetworkImageProvider` / `NetworkImage`
- `ImageBlock.localPath` → `FileImage`
- `ImageBlock.base64` → `MemoryImage`
- `EmojiBlock.path` → `NetworkImage` / `AssetImage` / `FileImage`

1. 冷启动进入聊天页，首屏只渲染 30 条以内，不卡顿不闪烁。

## 10. 风险与注意事项

- **分页加载顺序**：需确保 older messages 插入列表头部（时间更早）。
- **重复加载**：需要避免 beforeTime 相同导致重复（可记录 oldestTime）。
- **ImageCache 过大**：如需优化可设置 `PaintingBinding.instance.imageCache.maximumSizeBytes`。
- **网络图片失败**：仍需保留 errorBuilder 兜底。
- **预热过度**：列表预热要“少量、多次、分帧”；必要时调整 `ImagePreheatQueue` 的超时与队列上限。

## 12. 2026-03-18 补充：持久视口快照按“最近 5 轮问答”构建

### 12.1 背景

- 聊天页首进恢复使用的是“持久视口快照”。
- 之前快照直接截取最近 `5` 条数据库消息。
- 但 AI 一次回复可能被拆成多条文本 / 语音 / 图片消息，导致：
  - 单次回复里的多条多模态消息会重复占用快照额度；
  - 首屏恢复看到的不是“最近 5 轮问答”，而是“最近 5 条碎片消息”；
  - 恢复后历史分页的可见窗口数仍停留在 5，和快照实际覆盖范围不一致。

### 12.2 修复口径

- 持久视口快照改为按“最近 5 轮问答”收口：
  - 以用户消息作为轮次锚点；
  - 每轮后续连续的助手消息全部归入同一轮；
  - 助手被拆出来的语音 / 图片 / 文本消息不会再各自单独计数。
- 当当前内存窗口不足以覆盖最近 5 轮时，快照构建会继续向前补拉历史页，再落持久缓存。

### 12.3 与分页的协调

- 真实数据库时间线也改为按“轮次窗口”分页：
  - 初始窗口 `5` 轮；
  - 每次上滑继续追加 `5` 轮；
  - 不再按 `5` 条原始消息扩窗。
- 持久快照元数据改为写 `visibleTurnCount`；
- 它记录的是“当前页面已经展开到多少轮”，而不是“当前快照里有多少条消息”；
- 快照恢复后，需要把这个 `visibleTurnCount` 回传给上层分页状态；
- 这样发送消息触发重建、或从快照切回真实数据库时间线时，会继续按同一轮次窗口恢复，不会把上方已经读到的内容吞掉。
